<div class="parsedown-markdown"><h2 id="55048610_ast还原ob混淆">AST还原ob混淆</h2>
<h3 id="55048610_碎碎念">碎碎念</h3>
<p>上期说过要出一个AST还原分析，但是拖了好久，为啥呢？因为没劲，为啥会没劲呢？因为还原的意义不大，而且使用古法手工还原不仅费眼睛还慢还会错，扔给AI分析一下，马上就帮你还原好了。在这种时候坚持古法，基本上是吃力不讨好。<br />
而且这个还原没什么复杂的思维过程(不过也可能是我菜，不知道其中的巧思；如有，还望大佬评论区指点一二)，更多人的卡点是在于不会用语法。就比如看到表达式return 3+4，那肯定知道要还原成7，可是如何使用代码去还原，这个就不会了。再比如看到肯定不会执行的死代码，那肯定知道要删掉啊，可怎么用代码删除呢？不会了。我个人感觉大部分人是被语法卡住了。那么有必要学习语法吗？额，不好说，我个人认为这种直接交给AI就行了，没必要劳神苦思，我古法还原(小部分还是依靠AI)纯粹是过一下还原思路。<br />
再者就是AST没有一个固定的标准，还原到什么程度算成功？？？答案是无所谓，你觉得OK就行，懂了原理压根儿不用还原，在几个关键位置自己手动算一下就行了，其他的非关键点全是干扰，看都不用看；心大的，挑几个类型还原一下，看着输入了就进入下一阶段开始分析了；胆子小的/强迫症的，不行，必须严格按照流程，所有的混淆都要还原。。。只能说仁者智者，丰俭由君～</p>

<h3 id="55048610_字符串混淆">字符串混淆</h3>
<h4 id="55048610_缘起">缘起</h4>
<blockquote>
<p>这个字符串数组怎么来的？为什么出现这三者意味着字符串混淆？字符串混淆为了啥？</p>
</blockquote>
<p>举个例子，假设我们现在在逆向一个<code>login</code>接口，我们只知道接口中存在校验参数<code>X-Sign</code> ，我们按照一贯的套路，肯定是先使用搜索大法(搜索大法未必是最快的定位方式，这里包括之后都为演示需要)，看看能不能定位到<code>X-Sign</code>的生成逻辑</p>
<p>倘若JS文件中的代码如下o</p>
<pre><code class="language-jsx">function login(username, password) {
&nbsp; &nbsp; var token = generateToken(username, password);
&nbsp; &nbsp; fetch("https://api.xxx.com/login", {
&nbsp; &nbsp;&nbsp; &nbsp;&nbsp;&nbsp;method: "POST",
&nbsp; &nbsp;&nbsp; &nbsp;&nbsp;&nbsp;headers: {
&nbsp; &nbsp;&nbsp; &nbsp;&nbsp; &nbsp;&nbsp; &nbsp;"X-Sign": token
&nbsp; &nbsp;&nbsp; &nbsp;&nbsp;&nbsp;}
&nbsp; &nbsp; });
}
token = func(xxx)</code></pre>
<p>那么显然，<code>X-Sign</code>的值来自于<code>token</code>，下一步我只需要继续搜索<code>token</code>即可，逆向过程畅通无阻。</p>
<p>那么作为防护者，肯定是不希望我们这么轻松的逆向出生成逻辑，他就想&#129300;好嘛，你喜欢搜索是吧，好好好，那我就让你搜索不到，是的，就是这么朴实无华。</p>
<h4 id="55048610_字符串混淆诞生">字符串混淆诞生</h4>
<p>那么如何让搜索失效呢？不如把这个<code>X-Sign</code>使用base64编码的结果<code>WC1TaWdu</code>替换吧？嗯哼，好像可以诶，这样如果你直接搜索<code>X-Sign</code>啥也搜不出来，然后每次我自己执行的时候我就调用一下base64解码，我发送的时候还是正常请求。因此混淆后的代码就变成了</p>
<pre><code class="language-jsx">function login(username, password) {
&nbsp; &nbsp; var token = generateToken(username, password);
&nbsp; &nbsp; var headerName = atob("WC1TaWdu");
&nbsp; &nbsp; var requestOptions = {
&nbsp; &nbsp;&nbsp; &nbsp;&nbsp;&nbsp;method: "POST",
&nbsp; &nbsp;&nbsp; &nbsp;&nbsp;&nbsp;headers: {}
&nbsp; &nbsp; };
&nbsp; &nbsp; requestOptions.headers[headerName] = token;
&nbsp; &nbsp; fetch("https://api.xxx.com/login", requestOptions);
}</code></pre>
<p>上面是初级混淆，有经验的逆向者一眼看破，不就是调了个base64嘛，轻松还原，你能调我也能调，pass～</p>
<h4 id="55048610_解密函数诞生">解密函数诞生</h4>
<p>防守者：“靠，我应该如何继续升级呢？？？上次被破解是因为逆向者发现我调用了base64，完成了定位，我该如何让他发现不了我调用base64呢？</p>
<p>诶，不如我把base64这个<strong>解密函数</strong>抽离出来吧，我也别叫他atob了，我弄个十六进制的变量名就好了。让这个变量等于atob，但是叫做abto还是会被发现啊，我直接通过方括号属性访问器在<code>window</code>中取值就好了诶，方括号中可以是任意字符串，这里能做文章的地方就多了去了。我可以把<code>atob</code> 这四个字符通过转义字符的方式转换成对应的ASCII码值。所以混淆后的代码如下</p>
<pre><code class="language-jsx">var _0x4a7f = window['\x61\x74\x6f\x62'];

function login(username, password) {
&nbsp; &nbsp; var token = generateToken(username, password);

&nbsp; &nbsp; // Step 2: Use the aliased function instead of the original 'atob'
&nbsp; &nbsp; var headerName = _0x4a7f("WC1TaWdu");

&nbsp; &nbsp; var requestOptions = {
&nbsp; &nbsp;&nbsp; &nbsp;&nbsp;&nbsp;method: "POST",
&nbsp; &nbsp;&nbsp; &nbsp;&nbsp;&nbsp;headers: {}
&nbsp; &nbsp; };

&nbsp; &nbsp; // Step 3: Assign and send
&nbsp; &nbsp; requestOptions.headers[headerName] = token;
&nbsp; &nbsp; fetch("&lt;https://api.xxx.com/login&gt;", requestOptions);
}</code></pre>
<p>逆向者：嗯哼，有点意思，所有的类base64字符串之前都跟着一个<code>_0x4a7f</code> ，那么大概率这玩意儿就是解密函数，打点验证一下，嗯，没毛病，pass～</p>
<p>防守者：。。。靠，我该怎么办，解密函数这里已经穷尽变化了，再怎么变也变不出花来了，那么想要获得最终结果，需要输入&amp;解密函数，那么现在只能在输入上做文章了，逆向的视角每次看到JS中的base64字符串就知道这里要调用解密函数，实在是可恶，我要把JS中所有能用字符串代替的东西都抽离出来，放到一起，这样就算你看到了类base64字符串，你也不知道哪里调用了，而我把那些抽离出来的字符串存放在一个数组中，在调用的地方通过数组索引取到对应的字符串，然后再调用解密函数，这样不就完美了嘛？简单写一下就类似于<code>decrypt(string_array[index])</code></p>
<p>所以升级完整的代码如下</p>
<pre><code class="language-jsx">var _0x5a2e = ["WC1TaWdu", "POST", "&lt;https://api.xxx.com/login&gt;"];

var _0x4a7f = window['\x61\x74\x6f\x62']; // window['atob']

function login(username, password) {
&nbsp; &nbsp; var token = generateToken(username, password);

&nbsp; &nbsp; // _0x5a2e[0] is "WC1TaWdu"
&nbsp; &nbsp; var headerName = _0x4a7f(_0x5a2e[0]);

&nbsp; &nbsp; var requestOptions = {
&nbsp; &nbsp;&nbsp; &nbsp;&nbsp;&nbsp;method: _0x5a2e[1], 
&nbsp; &nbsp;&nbsp; &nbsp;&nbsp;&nbsp;headers: {}
&nbsp; &nbsp; };

&nbsp; &nbsp; requestOptions.headers[headerName] = token;

&nbsp; &nbsp; fetch(_0x5a2e[2], requestOptions); 
}</code></pre>
<h4 id="55048610_字符串数组&amp;自执行函数诞生">字符串数组&amp;自执行函数诞生</h4>
<p>但是到这儿也有个问题，就是逆向者只需要根据索引在数组中找到对应的字符串再调用解密函数即可，还是会被比较简单攻破，还有什么方法呢？？？既然薄弱点事因为索引和字符串对应，那么我们直接让索引和字符串不对应，这样逆向者根据索引取到的字符串不就是错误的吗，诶嘿，这样就能增加难度了</p>
<p>那么如何保证静态分析的时候索引对应错误字符串，但是执行的时候又正常呢？简单，我们可以在代码执行对开始的时候对数组进行初始化，将数组中错误的顺序还原成正确的顺序，然后在之后的计算中就能够正确运行了，概括一下就是</p>
<pre><code class="language-jsx">string_array=[]
string_array=sorted(string_array)
string=decrypt(string_array[index])</code></pre>
<p>为了继续恶心逆向者，我再把索引改成十六进制，这样一来看起来就让人亚历山大，说不定逆向者扫了一眼就觉得这玩意儿难的一批，直接开摆了，所有最终的代码如下</p>
<pre><code class="language-jsx">// Step 1: The Scrambled Array (被打乱顺序的字典，故意把 URL 放在了第一位)
var _0x5a2e = ["&lt;https://api.xxx.com/login&gt;", "WC1TaWdu", "POST"];

// Step 2: The Self-Invoking Restorer Function (自执行还原函数，sorted 逻辑)
(function(arr, shiftCount) {
&nbsp; &nbsp; // 当 shiftCount 大于 0 时，不断循环
&nbsp; &nbsp; while (shiftCount--) {
&nbsp; &nbsp;&nbsp; &nbsp;&nbsp;&nbsp;// 把数组开头的元素拿出来，塞到数组末尾去
&nbsp; &nbsp;&nbsp; &nbsp;&nbsp;&nbsp;arr.push(arr.shift());
&nbsp; &nbsp; }
})(_0x5a2e, 0x1); 
// 0x1 就是数字 1。执行一次后，第一个元素跑到最后，数组就变回了正确的 ["WC1TaWdu", "POST", "&lt;https://api.xxx.com/login&gt;"]

// Step 3: The aliased decrypt function
