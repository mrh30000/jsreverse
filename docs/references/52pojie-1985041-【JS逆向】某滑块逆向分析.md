## 逆向目标

* 网址：`aHR0cHM6Ly93d3cuY2hhbm1hbWEuY29tL3JlZ2lzdGVyLmh0bWw=`
* 目标：通过滑块接口，拿到成功响应

## 抓包分析

首先点击获取验证码，会发送一个请求，该接口没有加密参数，响应包含了`背景图、滑块图以及sessid（后续请求会用到）`。

![](https://attach.52pojie.cn/forum/202411/24/171743jpt5td3994s4uygx.png)

拖动滑块，会再发送一个请求，其中`collect和sign`是需要逆向的参数。

![](https://attach.52pojie.cn/forum/202411/24/171745hhgn3nzlllfnirrp.png)

如果请求失败，接口返回验证失败。

![](https://attach.52pojie.cn/forum/202411/24/171747gomwnasoo9meemwm.png)

如果请求成功，接口返回`ticket`。

![](https://attach.52pojie.cn/forum/202411/24/171749erxqn2he4tarypqq.png)

## 逆向分析

我们先从启动器入手，看到了`verify`字样，直接进去。

![](https://attach.52pojie.cn/forum/202411/24/171752jufv4fa6k282472d.png)

发现代码被混淆了。

![](https://attach.52pojie.cn/forum/202411/24/171754qh5s59fmymayufwm.png)

碰到混淆，老规矩，AST一把梭，当然，也可以硬刚，只是需要多耗点时间。

反混淆后的代码明显更加容易分析了。

![](https://attach.52pojie.cn/forum/202411/24/171756im2tafmozeyzezfm.png)

我们先把混淆的文件替换为本地的（具体的替换方法可以自行百度），替换成功后，随便滑动一次失败的。

还是从`verify`进去，下断，重新滑动一次，发现参数已经生成，在`_0x3d1ca1`中。

![](https://attach.52pojie.cn/forum/202411/24/171758kb36332f932fe7p2.png)

往前分析，发现`_0x3d1ca1`经过`_0x14c612(_0x481e7d)`生成，而`_0x481e7d`已经有`collect`，那`_0x14c612(_0x481e7d)`很可能就是生成`sign`的。

![](https://attach.52pojie.cn/forum/202411/24/171800n7x396of9fj1hgxh.png)

再往前分析，发现`_0x4b9595`经过`_0x2440f7({'position': _0x2c2063,'path': _0x1dc4f9});`生成，其中`_0x2c2063`是经过缺口距离计算得出，`_0x1dc4f9`是轨迹。

![](https://attach.52pojie.cn/forum/202411/24/171802b7a42uaaq44my7wz.png)

我们先搞清楚加密的逻辑，然后再分析`距离和轨迹`是怎么生成的。

直接在生成`collect`处下断点。

![](https://attach.52pojie.cn/forum/202411/24/171804jiugwwl3ozxjmmxi.png)

一直跟进去，就会跟到下图的地方，一眼AES，那`collect`的生成逻辑就是`将包含缺口距离和轨迹的对象进行序列化，然后进行AES加密`。

![](https://attach.52pojie.cn/forum/202411/24/171807ahaa01ewae7n007h.png)

接下来分析`sign`的生成逻辑。

先在`_0x3d1ca1 = _0x14c612(_0x481e7d)`下断，因为`_0x481e7d`现在还是没有`sign`值的，经过这之后就发包了，那`sign`很可能就是在里面生成的。

![](https://attach.52pojie.cn/forum/202411/24/171809m0c99ejs8er7umj6.png)

老样子，一直跟进去，就会到下图的地方，其实跟一遍就会挺清晰的，生成`sign`的逻辑就是`先往传入的对象添加一个时间戳，然后将该对象经过_0x40a595方法处理成字符串，然后对该字符串进行MD5就生成了sign`。

![](https://attach.52pojie.cn/forum/202411/24/171811gogfrttraob3tcox.png)

总的来说，反混淆后，`collect`和`sign`的逆向并不难。

---

下面继续分析`缺口距离和轨迹`是怎么生成的。

我们知道缺口和轨迹都是传参进来，那就一直往前跟栈，就会到下图的地方，其中`this["left"]`就是经缺口计算的，`this["rawList"]`就是轨迹。

![](https://attach.52pojie.cn/forum/202411/24/171813yrfgo2mm822vwrgr.png)

先搜索`this["left"]`，会搜到这个地方，`setLeft`关键字提示我们left应该就是在这被设置的。

![](https://attach.52pojie.cn/forum/202411/24/171815cpfooo02e766zoow.png)

那我们继续搜索`setLeft`，会搜到这个地方，如果你在这个地方下断，那么你一动滑块它就会断住，你就不清楚参数是怎么生成的。

![](https://attach.52pojie.cn/forum/202411/24/171817or3xnrhjlymxxbba.png)

所以我们先简单分析分析。

> 我们要的`left`是`_0x4a8918`
> 而`_0x4a8918`可能是`_0xd25440 / this["parentWidth"] * 0x64 + 0x0`，也可能是`0x64 * (0x1 - this["width"] / this["parentWidth"]`
> 如果是第一种情况，那`_0xd25440`由`_0x45279e["clientX"] - this["startX"]`生成

我更倾向于第一种情况，然后我们下一个日志断点`_0xd25440,_0x4a8918`。

![](https://attach.52pojie.cn/forum/202411/24/171819dh9c77nqn5cqd06c.png)

拖动一次滑块，然后查看日志输出，经比对，`_0xd25440`是真实的距离，`_0x4a8918`取的第一种情况。

![](https://attach.52pojie.cn/forum/202411/24/171821sd3ou3hpou24zu3r.png)

`left`搞定后，我们再看轨迹，前面在`setLeft`之后直接`setRawList`了，那我们直接搜索`setRawList`，就会到下图这个地方，经常搞滑块的朋友看一眼大概就知道怎么回事了。

`'x'`就是滑块移动的距离（只是这里经过`parseFloat(_0x220aec["toFixed"](0x2)) + this["width"] / this["parentWidth"] * 0x64 / 0x2`处理，其中`_0x220aec`就是`left`的值），`'y'`就是滑块垂直方向的距离，`'t'`就是时间。

![](https://attach.52pojie.cn/forum/202411/24/171824sq05axvuuu1iiyq5.png)

所有参数分析完毕，那我们直接模拟请求，缺口距离的识别可以用开源的模型，也可以走打码平台。轨迹可以自行构造，也可以用开源的模型。
