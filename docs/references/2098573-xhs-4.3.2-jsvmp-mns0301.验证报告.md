## 1. 已确认成立（可复用部分）

**方法论层（最有价值的部分，全部复现成功）**

1. "不靠 AST 解 ob，也能定位插桩点"：先用 `_0x341b` 大数组 + `push/shift` 旋转 + `_0x1769(i)=arr[i-0x0]` 判据锁定混淆家族，再用「解密函数的块级别名链」把 `apply` 反查成 `_0x????(0x32)`，最后由 `0x1f===opcode` 分支确认调用点。**这条链在本次验证里一步不差地在线上脚本上跑通**（`node _verify2098573/check.mjs` 第 1–8 项）。
2. "进 VM 前先初始化栈 → 栈与栈指针可反推"：实测 `_0x47fda0=[]`（操作数栈）、`_0x4cd76e=0x0`（栈顶指针）、`h[++p]=…` 37 处，与文中"`stack[stack_top_pointer] = stack[stack_top_pointer] operator value`"一致。
3. "VMP 只能动态插桩，静态读不出结构"：成立。`mns0301` 字面量不在任何下发脚本里（0 命中），只存在于运行时输出前缀，静态搜索会直接扑空。
4. "日志不稳定时 hook `rand`/`Date.now()`，并注意 `ts_i` 取用点位"：线上 `getdss()` 非单调、且与真实时钟偏移约 9 天，确实会让多次日志错位——该建议是**必需**而非可选。

## 2. 文中的瑕疵（阅读时须自行修正）

1. **`arr_44` 分段区间笔误（硬错）**：文中 `[0-3][4-7][8-15][15-23][24-27][28-31][32-35][35-43]` 字面求和 = **46**，索引 15、35 被重复计入；按 `arr_44 = 44 字节` 反推应为 `[16-23]`、`[36-43]`，修正后 4+4+8+8+4+4+4+8 = **44**，且每段长度 ∈ {4,8}（正好印证"或 4 或 8"）。
2. **"按照两个字节长度进行拆分"用词错**：示例 `[48][2D][CD][0E]` 是按 **2 个十六进制字符 = 1 字节** 拆分，不是"两个字节"。
3. **"小段序"应为"小端序"**（文中多处）。
4. **`uint32_to_LE_list(TIMESTAMP & 0xFFFFFFFF)` 是 Python 风格伪码，直接照抄进 JS 会错**：JS 的 `&` 先 ToInt32，低 32 位 ≥ 2^31 时结果为负（实测 `1788934758050 & 0xFFFFFFFF = -2066604382`），必须 `>>>0`。当前取样时刻恰好没踩雷（`1528362914`），所以"看起来对"。
5. **`arr_16` 一名两用**：一处是 `arr_16 = func(arr_24)`（chacha 类变换输出），另一处是 `arr_16 = arr_4 + arr_12`。文中"更聪明的做法是…形式为 `_0x???????[0x32]`"也用中括号表示函数调用（实际是 `_0x???????(0x32)`），照抄搜索式会漏。
6. **章节层级/顺序错乱**：`## arr_144生成方式分析` 下直接接 `## arr_20`（应为子节）；`final: arr_20 = arr_4 + arr_16` 落在 `arr_24` 小节末尾；`[8-23]` 那段 Python 式描述实际讲的是 `arr_24` 的字节布局，标题却写在 `arr_16 = func(arr_24)` 下。读者需按"名字=字节数"重排。
7. **留白项作者自认**：`arr_44` 的 `[24-27]` 段"不清晰来自哪里"；RC4 密钥来源、base64 表全貌均未给出 → 文章是"分析记录"，不是"可交付复现"。
