### 三、新坑 56（本轮最重要的修复）：已归档 ID 正则会**吃掉首位数字**

历轮（含 skill 的 `jsrev-scan.py`）用 `^[a-z0-9]*-?(\d{5,})-?.*\.md$` 提取已归档帖子 ID。
问题出在 `[a-z0-9]*` —— **它包含数字**，贪婪匹配会把文件名开头的数字一起吃掉：

| 文件名 | 错误结果 | 正确结果 |
| --- | --- | --- |
| `2080428-shortvideo-sig3-fingerprint-pure-algo.md` | `80428` | `2080428` |
| `2066191-websocket-reverse-rebuild-html.md` | `66191` | `2066191` |

⇒ **全部 51 个早期 `<id>-<slug>.md` 文件的 ID 提取都是错的**，已归档集合因此漏掉 **49 个 ID**；
后果是这些老帖会被重复抓取、重复归档（`52pojie-2080428-*.md` 与 `2080428-*.md` 并存）。

**本轮实测影响面**：256 条候选里 **32 条其实是已归档老帖**（`2082553` 某御验证码、`2123850` 某 q 音乐
jsvmp、`2106217` iv8、`2066191` WebSocket… 全是历轮已归档的「名帖」，所以命中表每轮都把它们捞回来）。

**修复**＝文中第一个长度 ≥5 的数字串即帖子 ID：

```python
m = re.search(r"(\d{5,})", f)     # ✅ 正确
# m = re.match(r"^[a-z0-9]*-?(\d{5,})-?.*\.md$", f)   # ❌ 会吃掉首位数字
```

⚠️ **同时修正历轮 README 的计数**：第二十轮 README 写的「唯一帖子 ID 852」正是这个错误正则的产物，
**实际当时是 827**；本轮修正后为 **854**（827 + 本轮 27）。此后各轮计数应以新正则为准。

5. **待办**：把本轮两处口径修正（`SERIES` 禁裸序数词；`钓鱼` / `脚本` / `小程序` 等歧义/过泛词不得单独进 WEBCTX）

### 三、本轮三条口径结论

#### 结论一（本轮最大收获）：**「系列帖」会因标题正则的 `\b` 语义被整系列静默漏掉**

《JavaScript AST其实很简单》五篇标题含 `AST`，历轮 `STRONG` 里写的正是 `\bast\b`。
但在 Python 的 `re` 里 **CJK 字符属于 `\w`**，所以 `AST其实` 中 `T` 与 `其` 之间**没有词边界**，
`\bast\b` 匹配失败 —— 与**坑 51（中英混排一律不加 `\b`）完全同族**，代价是整个 5 篇系列全漏。

同理「小白讲解」系列 11 篇里，只有标题恰好含 `sign|验证码|邮箱登录` 的 4 篇（02/03/06/09）进了归档，
含 `param|载荷|房产|signature|X-sign` 的 6 篇全部落空。

⇒ **教训**：① 中英混排的标题正则**一律不加 `\b`**；② **系列帖必须按「系列名」整体核对**（本轮做法：
对池内标题做「系列名子串」检索并**与已归档集合对比**，缺口一目了然）；③ 这类漏网**不会体现在任何审计表**里，
因为审计表都是「候选池内部」的，而这些帖**从未进过候选池**。

#### 结论二：黑名单（G 表）正文级体检**值得做成固定通道**，但产出率低（3381 → 3，0.09%）

3436 条噪声里 3381 条本地有正文。逐条跑正文度量后 RESCUE 31 条，人工复核**只收回 3 篇**（0.09%）。
但收回的 3 篇都是真阳性，且**都是标题级黑名单的必然误伤**：

| `2046628` 寻一个会 JS 堆栈的大佬… | 版块「悬赏问答区」+ 标题含「帮我解密」→ 判为求助帖 | 完整的 `session_key → login_name` 参数生成分析（请求报文 + 断点位置 + 运算链） |

产出率虽低（0.09%），但**成本近乎 0**（正文全在本地），可作为固定体检保留。

#### 3.1 第一版实现：直接失败（本轮最值钱的一课）

以 ~11 s/作者的节奏在同一标签页里连发**同步 XHR**（每位作者 = 1 次资料页 + 若干页主题列表），
**约 90~110 次请求后**站点返回 `/wzws-waf-cgi/`（网宿 WAF）挑战页，随后升级为
**`waf_slider_verify.html`（"请完成安全验证! IP:x.x.x.x 向右滑动填充拼图"）**；
**并且是 IP 级的** —— 同一时刻：

```bash
hubcli 52pojie Thread --page 1 --json      # → []       （策展榜第一页本应有 198 条）
hubcli 52pojie content --url 1288315       # → 只剩头部，正文为空壳（服务的是 WAF 页）
```

即 **浏览器侧的过频动作会把 RPC 通道一起封掉**，整轮抓取瘫痪（约 20 分钟后自行解除）。
⇒ 由此定下三条硬约束（已写成坑 97）：**① 浏览器侧动作必须排在所有 RPC 侧动作之后；
② ≥6 s/次 + 每 20 次导航一次首页刷新 WAF cookie；③ 一旦发现 WAF 立即整轮停止**。

#### 3.2 第二版实现：跑通（三个技术细节）

1. **`hubcli browser eval` 不 await Promise**：`(async()=>{…})()` 一律得到 `result = None`
   ⇒ 必须改用**同步 `XMLHttpRequest`**（`x.open(m, u, false); x.send()`），一次 eval 就能翻完某作者的全部页；
2. **Discuz 的 `?username=` 参数要 GBK 百分号编码**：`%CC%CE%D6%AE%D3%EA` = `涛之雨`；传 UTF-8 直接得到「提示信息」错误页。
   **与坑 27（搜索关键词要 GBK）完全同源** —— 且 **ASCII 用户名能过会误导你以为方案没问题**（`LaoBwait` 能过、`漁滒` 不能）；
3. **主题列表选择器用 `#ct .mn a[href*="thread-"]`**：站点顶栏也含 `thread-` 链接（`Windows破解入门` / `Android逆向入门` / 总版规），
   且每条主题会重复出现多次（标题 + 页码 `1/2/3…`）⇒ **按 ID 去重并取最长文本**。

**产出**：`110 位作者 → 2278 条主题 → 未归档未黑名单 800+ → 过标题门禁 149 候选 → 抓 40 篇正文 → 定稿 18 篇`。
命中率 ~45%（远高于互链的 ~21%），**是历轮所有通道里最高的一次**。
