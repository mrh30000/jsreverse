## 2. 文章代码的真实缺陷（复现中定位到）

1. **CFF 顺序依赖是硬约束，且失败是静默的**（高）。`handlerWhileSwitch` 用 `strPath.node.value.includes("|")` 找执行顺序；未先做字符串还原时，兄弟节点里的 `_0x315530(0x3b)['split']('|')` 先被命中，取到 seq `"|"`，`caseMap` 一个都匹配不上，`replaceWithMultiple([])` 把整个循环删掉。文章口头提示了顺序，但没提"顺序错了不报错、直接毁代码"。建议加守卫：要求 `sequenceArray.every(k => caseMap[k] !== undefined)` 且 `caseMap` 非空后再替换。
2. **`handlerDict2Func` 对"函数调用形态"的规则不普遍成立**（中）。`types.callExpression(path.node.arguments[0], args.slice(1))` 只在包装体是 `p0(p1,…)` 时是字面正确的；样本里 6/34 包装体是 `return 其它字典['key'](p0,…)`（其中 4 个首句还是 `var x=_0xc8b2` 声明）。这些点最终结果对，靠的是 `exit` 序遍历时先重写了内层转发调用（把 `return D2.f(...)` 塌缩成 `return p0(p1)` 或 `p0+p1`），即**顺序敏感的递归归约**，而非文章规则直接成立。若某转发点的 `arguments[0]` 不是 Identifier（字符串/数字），产物会变成 `''(...)`、`3(...)` 这类非法/错误调用；本样本 34/34 调用点 arg0 均为 Identifier，恰好没踩到。更稳的写法：取 `returnArgument.callee`，若为形参则用 `args[0]`，否则直接内联 `returnArgument.callee`，再按形参位置映射实参。
3. **只取 `value.body.body[0]?.argument`**（低）。包装函数体首句不是 `return` 时被 `continue` 静默跳过。样本中 4 个包装首句是 `var x = ...`（如 `'yxEcc'`、`'LWnlF'`），只是因为字符串还原阶段把 `var x=_0xc8b2` 删除后函数体塌缩成单条 `return`，才被后续处理到——真实还原顺序一旦改变就会漏。
4. **`handlerDict2Str` 直接 `path.node.object.name`**（低）。对象不是 Identifier 时 `undefined`，不会崩但会漏判；建议加 `types.isIdentifier` 守卫。
5. **文章没交代"ob 代码是 eval 字符串"这一前提**（中）。当前构建必须先从 `String.raw(templateObject_1)` 抽出源码再喂给 babel，否则 AST 里看到的是一个大字符串字面量而非可遍历的语句。文章截图像是直接对明文源码操作，属于构建形态差异。

## 6. 结论与取舍建议

1. **当作 ob 家族识别与 AST 还原方法论模板：可用**。字符串数组/旋转/别名链/字典/CFF 六要素判定、`getBinding().referencePaths` 替换、`path.key-1` 找序列节点，都在真实样本上一步不差跑通；`dictList` 五个名字可照抄。
2. **当作可直接运行的脚本：需补 3 个守卫**（见 §2 第 1–3 条），否则 CFF 依赖顺序、字典转发/首句非 return 的边界上会静默产出错误代码。
3. **要落地到当前线上构建**：先在 webpack 模块 `signV2Init` 里从 `String.raw` 载荷抽源码，再做 AST；文章的截图流程少了这一步。
4. 顺手项：本 md 的 `发布时间/查看回复`、34 个空围栏、CFF 块丢围栏、`var_0x28aafb`/`var_0x5f1d55`/`return_0x19443e` 关键字粘连可修；`<https://…>` 尖括号属作者原文，勿改。
