# 调用点定位实战手册：跟栈、断点与「扣哪一段」

> **来源**：`docs/references/52pojie-1985694` / `1998689` / `1999830` / `2010991` / `2017218` / `2033662`
> ——同一作者（Aircraftcomman5）的「某某站逆向 · 小白讲解」系列六篇（服务网 / 房产 / 载荷 / 矿集团 param /
> 猫投诉 signature / 车辆对比 X-sign）。
>
> **本文的定位**：`04-debug-env-playbook.md` 讲的是「hook / logpoint / 最小补环境 / 证据管理」的**工具层**；
> 本文只讲一件事 —— **在 DevTools 里靠跟栈 + 断点，把「加密究竟发生在哪一行」钉死**。
> 这一族文章的原文价值不在某个算法，而在**每一步的判据**与**操作序列**；本文把它压成可复用的清单。
>
> **一句话总纲**：所有判据都基于同一件事 —— **目标参数在某处的「有 / 无 / 明文 / 密文」发生了变化，
> 变化点就是生成点**。跟栈不是「往上翻到看见为止」，是「找出那个变化点在哪两层之间」。

## §0 五条判据（先记这五条，比记操作序列有用）

| # | 判据 | 结论 | 出处 |
| --- | --- | --- | --- |
| **J1** | 参数在**更上层还在**、再往上一层**就没了**（变量名通常一起变） | 生成 / 加密发生在这两层之间 —— **「消失点」比「出现点」更好用** | 1998689（sign 到某栈就消失）、2033662（`x-sign` 在某栈没了） |
| **J2** | 断在函数**头部**，参数**已经带着密文**进来 | 加密不在这里 ⇒ 继续向上跟栈 | 2017218、2033662 |
| **J3** | 断在头部**没有**该参数，而函数**尾部 `return` 出的对象里有** | 参数在本函数体内**逐步生成** ⇒ 单步调试 | 1999830 |
| **J4** | 函数**没有形参** | 它不接受传值 ⇒ 密文必然在本函数体内生成，或来自**模块作用域**变量 | 2017218（原文明确用了这条） |
| **J5** | 控制台里某变量是**明文**，而请求里是密文 | 该变量就是**加密的输入**，下一步找「谁消费它」 | 1985694（断在生成处，打印得明文，全选得密文） |

**J1 是六篇里复用次数最多的一条**。它的操作性版本是三段式：

```
在 send 断住
  → 上一层：参数在不在？（在 ⇒ 位置还对，继续 | 不在 ⇒ 走过头了，回退一层）
  → 逐层收窄，直到「上一层有、这一层没了」
  → 加密调用就在这一层与上一层之间的那个函数里
```

**配套的「一条」纪律**（1998689 原文）：**第一个栈断不下来也不用纠结**（异步 / 已被优化 / 非本帧），
`send` 上面的**第二、第三个栈**意义相同 —— 目标是**找到参数**，不是**必须命中第一个栈**。

## §1 起点：把断点挪到 `send`

统一开场（六篇一致）：

1. 开发者工具 → Network → **勾 `Preserve log`**（防跳转丢包）；
2. 触发一次目标请求（分页 / 刷新）→ 目标包 → **Initiator / 启动器** → 点第一个堆栈；
3. **把断点挪到 `send` 那一行**（或它上面一行），重新触发，让它断住。

**为什么先断 `send`**：它保证你站在「请求正要发出的那一瞬间」，此刻 `arguments` /
请求配置对象里的值都是**最终值** —— 后面所有「对拍」都以这一瞬间的值为基准（§3）。

## §2 三种「生成形态」与对应的下一步

跟栈时你只会遇到三种情况，分别对应三种操作：

### 形态 A · 参数由**另一个模块 / 函数**产出 ⇒ 继续向上

- 症状：J1 —— 上一层有、这一层没了，且**没有可疑的赋值语句**。
- 操作：继续向上；到了「上一层有、这一层没有」的那个函数里，找**可疑的赋值点**。

### 形态 B · 参数在**本函数体内逐步生成** ⇒ 单步调试

- 症状：J3 —— 头部没有、尾部 `return` 里有。
- 操作：**单步调试（Step over 为主）**，一路往下走到「值出现」的那一行。
  - 原文自述：单步调试「虽然能看清每一步，但枯燥、效率慢」—— 所以在**范围已经收窄到单个函数**之后才用。
  - 常见生成位置：`if` 判断条件里（1999830 的 `n.data.code` / `n.data.timestamp` 就在一个 `if` 里被赋值）、
    `return` 里的三元表达式（1998689 的 `e.token`）。
- **先定义后使用**：值出现之后，**往上找它的定义处**（`var x = ...` / `const x = ...`），
  而不是在原地猜 —— 六篇里每一次「找 `p` / `o` / `r` / `B` / `h`」都是这个动作。

### 形态 C · 参数来自**认证 / 会话数据** ⇒ 往回查来源接口

- 症状：J5 打印出来是明文；或值看着像 token / cookie 片段。
- 操作：看它是从 `cookie` / `localStorage` / 上一个响应里取的（§4）。

## §3 唯一验收动作：断点处的值与最终请求里的值**对拍**

这是六篇里最硬的一条纪律，**不做这一步等于没做完**：

> 在「疑似加密处」下断，把**返回值**取下来；放行整个请求；把**最终发出去的包**（Network 里那个请求）
> 的同名字段取下来；**两者逐字符对比**。一致 ⇒ 位置确认；不一致 ⇒ 位置错了或少了参数。

六篇里的三种实际用法：

| 场景 | 对拍对象 | 出处 |
| --- | --- | --- |
| 找密文生成点 | 断点处变量的值 vs 最终 `payload` 里的密文字段 | 1998689（`sign:p` 与函数返回值一致 ⇒ 确认 `p` 是密文）、2010991（`case4` 处的密文 vs 抓包） |
| 判参数是不是动态 | **连抓两次包**（或刷新前后各抓一次）比字段值 | 2017218（`rs` 刷新前后不同 ⇒ 是动态的，必须还原）、2033662、1998689 |
| 判「明文是否一致」 | 本地拿到的明文 vs 浏览器里断点处的明文 | 1985694（原文总结第 2 条：**明文不一致 ⇒ 密文必然不一致**） |

**「连抓两次」这条同时是参数三分类（固定 / 上次返回 / JS 计算）的最快落地法**：
刷新前后都一样的字段直接写死；会变的字段才需要还原（2017218 就是靠这个把「要扣的只剩 `r`」定下来的）。

## §4 会话与时间：三个「不还原就永远不对」的隐藏依赖

这三条都不是算法问题，是**链路问题**，六篇里反复出现：

### §4.1 响应下发的 Cookie **既是加密输入、又是请求头**

1998689 的实测链路（**本手册最值钱的一条工程结论**）：

```
包①  首次进入页面（清理 cookie 后）→ 响应 Set-Cookie
包⑤  目标数据包 → 必须带上包①响应的 Cookie
      否则：请求能发出去，但响应里「令牌为空」（服务端认不出会话）
      并且：sign 的加密输入里也含这个 Cookie 派生的 token
```

- **判据**：清空站点 cookie → 观察是否多出「你没关注过的包」→ 看目标包携带了哪一次的 `Set-Cookie`。
- **结论**：写采集脚本时**不能只复制最终请求**，必须按顺序走完「取会话 → 带会话发目标请求」两步。
  这与 `10-waf-clearance-cookie.md` 是**同一族问题**（先拿准入 cookie 再进站），只是这里下发的是会话 cookie 而非 WAF cookie。

### §4.2 时间戳必须**同源**

- sign 里用的时间戳与请求体里的时间戳**必须是同一个值**（1998689 原文总结：「荷载里面的时间戳也需要放到请求里，
  不然也会获取数据失败」）。
- 推论：不要把「算签名用的 `ts`」和「拼请求用的 `ts`」写成两次 `Date.now()` —— 跨毫秒就会不一致。

### §4.3 表单数据的**格式**必须与浏览器完全一致

- 1998689 原文总结第 2 条：**「sign 加密时要看清载荷的表单数据的格式，不然加密的密文也是不正确」**。
- 落地：断点处**把待签的原始串整段复制出来**（不要自己按理解重拼），再与本地生成的串逐字符 diff。
  子项差异（`a=1&b=2` vs `{"a":1,"b":2}`、是否 `encodeURIComponent`、`JSON.stringify` 是否带空格）
  见 `06-engineering-maintenance.md` §12.3 / §12.5。

## §5 多包链：`public` 密钥包 → 目标密文包

2010991 完整记录了一条**两条请求的加密链**（RSA 场景的通用形状）：

```
包①  POST /open/homepage/public      → 拿服务端下发的 RSA 公钥
包②  POST <业务接口>  param=<RSA 密文>  → 目标
```

- **判据（30 秒）**：同一次交互里**一次发出两个包**，包① 体积很小、载荷里只有一条**长密文或空**
  ⇒ 那是密钥包。
- **代码形态**（`case0` 分支）：`t = new d["a"]`（创建 RSA 实例）→ `A.sent = 4`（把状态交给后续 case）
  → `Q.a.post("/open/homepage/public")`（请求公钥）。
- **调试口径**：跟栈时第一次断住的往往就是包①（变量是空的）—— **跳过它**，第二次断住的才是目标包。
- **本地复现**：公钥先**写死**（源文做法），把整条链跑通之后再改成动态取。

## §6 扣代码：`缺什么补什么` 的四个实操要点

### §6.1 用报错驱动补全（不要一次求全）

标准循环：**在本地跑 → 看报错 → 回浏览器搜那个标识符 → 把它扣出来 → 再跑**。

- 1985694：`A 未定义` → 补 `A`；`a 未定义` → 补 `a`（注意大小写是**两个不同的东西**）。
- 2010991：`n 未定义`（密钥，先写死）→ `m 未定义`（`a` 里用到的函数）→ `B()` 是 MD5 → `t.encryptLong` 不是方法（§6.3）。
- 2017218：`429` → 本地搜 `429` → 定位到加载器尾部。
- **单模块扣取**时的环境缺失直接置空：1985694 报 `self 未定义`，原文口径就是「没有，直接置空」
  （因为不是多文件整体扣取）。⚠️ 这与 `web-js-env-patcher` 的「精确补环境」口径**不同** ——
  **只要结果的办法是置空，要复现/长期用的办法是补环境**，按交付目标选。

### §6.2 让加载器**自己报出缺哪个模块**

webpack 场景下不要人肉翻模块表：

```js
// 在加载器的取模块函数里加一行（2010991 的「第二步」）
console.log(e);          // e = 被请求的模块 id ⇒ 缺哪个一目了然
```

- 浏览器里 `r(215)`、`r.s = 429` 这类写法**等价**（`r(r.s = 429)` == `r(429)`）。
- 拿到的模块是**空对象** ⇒ 浏览器里它什么也没做 ⇒ 本地**直接删掉那行加载**。
- 拿到的模块属性是 `window` ⇒ 本地把 `r(38)` **替换成 `window`**。
- **只扣需要的模块**：把加载器自带的模块表清空、只放你要的那几个（2010991 明确说该站可以这么做）。

### §6.3 ★ 原型追加的方法必须在 `new` **之前**补

2010991 的 `t.encryptLong 不是方法` 是全系列**最隐蔽**的一个坑：

```text
// 浏览器里这个方法不在模块本体里，而是在模块被使用之后「挂到原型上」
d["a"].prototype.encryptLong = function (…) { … };
// 业务代码随后才： t = new d["a"](); t.setpubickey(r); t.encryptLong(明文)
```

- **判据**：模块扣全了、加载器也对了，但业务代码报「某方法不是函数」⇒ 去浏览器双击那个方法名，
  看它是不是挂在 `X.prototype` 下。
- **处置**：把这段原型赋值**插到 `new` 之前执行**。
  理由（原文口径，本库认同）：`new` 之后拿到的是**实例**，对实例再加原型成员对**已经创建的那个实例**没意义
  —— 而这段代码是在 `new` 之前生效的，本地必须复现同一时序。
- **迁移性**：任何「模块扣出来之后缺方法」的场景都先查这条 ——
  同型结论见 `web-reverse-hook/SKILL.md` 的组件注册表替换（**替换必须早于实例化**）。

### §6.4 三种「模块不完整」形态（不能直接选中跳转去扣）

2017218 第五节记录的三种情形，处置各不相同：

| 形态 | 症状 | 处置 |
| --- | --- | --- |
| **模块只给一半** | 直接选中 `r(215)` 跳进去内容少得可怜，另一半在里面加载别的模块拼出来 | **在 `o = r(215)` 那一行单步调试**，按浏览器实际加载顺序（先 216 再 215）扣 |
| 加载器**形参丢参** | 本地报「模块错误」但模块明明都在 | 见 §6.5 |
| 模块是**空对象 / `window`** | 见 §6.2 | 删掉 / 替换成 `window` |

> 2017218 的原文结论值得原样记住：**「浏览器加载的模块没错，而是跳转的位置会使我们扣取错误（少扣）」**
> —— 即 **「跳到定义处」这个动作本身会骗你**。凡是 webpack 模块，都以**单步调试观察到的加载序列**为准。

### §6.5 加载器头部的「形参 / `e = {}`」冲突（2017218 / 1999830 同型）

本地加载器报错、但模块全在时，**去加载器头部看这两行**：

```text
(function (e) {          // ← 步骤1：这是形参位
  // var e = {};         // ← 步骤2：如果这里又有一句 e = {}，会把传进来的模块表覆盖成空对象
  ...
})( modules );           // ← 尾部实参直达步骤1
```

- **两个错法**：① 步骤1 **没有形参** ⇒ 参数传不进来（报模块相关的错）；② 步骤2 有一句 `e = {}`
  且形参也叫 `e` ⇒ 参数进来了也会被**置空**。
- **处置（原文口径）**：给步骤1 **补一个形参 `e`**，并把步骤2 那句 `e = {}` **注释掉**。
- 原文自评「8.5 过于隐蔽，不仔细看很容易忽略」—— 记在这里，别再踩。

## §7 条件断点：多包共用同一加密函数时的定位器

2033662 的核心增量。**场景**：同一个 `axios` 拦截器 / 加密函数被页面里**几十个请求**共用，
普通断点每次请求都断，根本走不动。

**做法**：

1. 在可疑行右键 → *Add conditional breakpoint*；
2. 条件写**能唯一识别目标包**的表达式，最常用的是 URL：
   ```js
   e.url.includes('param/get_param_details')
   ```
   （`e` 是当前帧里那个请求配置对象；**先看一眼当前帧有哪些变量**再写条件，别照抄变量名。）
3. 刷新 → 只有目标包会断住 ⇒ 从这里开始跟栈。

**三条配套判据**：

| 现象 | 处置 |
| --- | --- |
| 进入**异步**之后断点不起作用 | 把条件断点**改到异步那一帧里面**（异步边界外的断点对回调无效） |
| 跟栈时不知道该看哪个变量 | 用 `e.data` / `e.url` 判断「目标包有没有经过这里」，以此决定继续往上还是换栈 |
| 不知道跟到哪停 | **跟到「看不见 `x-sign`」或「出现 `"x-sign": a(或某变量)」这种赋值形态」为止** |

**边界**：条件断点靠**当前帧的局部变量名**（`e`、`t`…），换一帧或换一个函数就得重写 ——
它不是可持久化的资产，只在「定位」阶段用。要持久化就落成 `web-reverse-hook` 的 hook / 预设。

## §8 静默陷阱表（本批新收）

| # | 陷阱 | 症状 | 处置 |
| --- | --- | --- | --- |
| 1 | 抄请求串时遇到 **HTML 实体** | 2017218 的待签串里出现 `&#182;`（= `¶`），2033662 的字段分隔符也一样 | **抄串先搜 `&#`**（与 B30 的「先搜 `×`（`&times;`）」同族：语料页把实体渲染过一遍）。还原时按**原文实体**填，别按你看到的字形猜 |
| 2 | 只复制**最终请求** | 见 §4.1，服务端认不出会话，响应字段为空 | 按顺序走「取会话 → 带会话请求」 |
| 3 | 时间戳算两次 | 签名对、请求错（或反之） | 同一个 `ts` 变量贯穿到底（§4.2） |
| 4 | 自己重拼待签串 | 密文长度可能都对，值就是不对 | 断点处**整段复制原始串**，逐字符 diff（§4.3） |
| 5 | `o()(x)` 看成两种东西 | 1999830 里 `e = o()(r + "9527" + r.substr(0,6))` | `o()` 只是**柯里化包装**，`o()(x)` 与 `o(x)` 等价（原文口径：「可以自己在控制台打印试试，一样的效果」）。但**只对确认是这种包装的成立**，不要推广到任意 `f()(x)` |
| 6 | 待签参数数组**先 sort 再 join** | 2017218：`o([c,h,d,l,this.tabType,f,this.pageNum].sort().join(""))` | 顺序不是「书写顺序」而是**字典序**；漏掉 `sort()` 会得到一个稳定的错值 |
| 7 | 参数写在 **URL** 而不是 body 里 | 2017218：`"?ts=" + c + "&rs=" + h + "&signature=" + r` | 断点处先确认**参数在哪**（URL / header / body），别默认在 body |
| 8 | 扣了 webpack 但「怎么改都不对」 | 2033662 原文自述扣不动 | 兜底路线：把那个小模块**改成自执行**（IVFE）直接跑；或按 `webpack-bundle-extraction` 的模块抠取流程走 |

## §8.5 换靶：一个入口搜不到时的四个替代动作（B36 补）

来源：`52pojie-1853120`（拼音命名）、`52pojie-1829398` / `52pojie-1829895`（响应解密点、双向加密）、
`52pojie-1805527`（自定义 header 名）。**四条都是「第一个靶子打不中时」的下一步，不是并列选择。**

**动作 ① · 换关键词（拼音 / 别名 / 库名）**
搜 `password` 只找到一半时，源文改搜 **`jiami`** 才断成功。
关键词候选表见 `12-login-and-account-params.md` §4.5「事实三」。

**动作 ② · 找「响应解密出口」，而不是「请求加密入口」**（双向加密题的固定打法）

| 步 | 动作 |
| --- | --- |
| 1 | 响应体是密文 ⇒ **搜 `decrypt`**（**不是**搜 `encrypt`） |
| 2 | 在**两处同时**下断：**搜索结果那一行** 与 **该函数的 `return`** |
| 3 | 在断点处**反复试表达式**，直到打印出可读文本（源文原话：「多次输出 `a.toString(h.a.enc.Utf8)` 测试以后，发现该位置就是解密结果」） |
| 4 | 确认后**直接扣这个函数**（源文自陈「懒得扣也能看出来是 aes，用 py 自己改写也可以，我比较懒，直接扣的」） |

★★ **`CryptoJS` 解密出口的机械指纹**：**`<wordArray>.toString(CryptoJS.enc.Utf8)`**。
压缩后常写成 **`a.toString(h.a.enc.Utf8)`**（`h.a` 即 `CryptoJS` 的别名）
⇒ **见到 `.toString(<某个>.enc.Utf8)` 就基本可断定这是「WordArray → 明文字符串」的出口**，
是「解密结果点」的第一候选（与 `16-ciphertext-structure-diagnostics.md` 的「内置编解码函数形态速查」同一族判据）。

**动作 ③ · 「第一次请求返回空」⇒ 先去比 header，别先去怀疑参数**

源文 `1829398` 的形态：接口**不带 `Portal-Sign` 就没有数据返回**，
而且是**翻页几次之后**才发现这个头是必需的。

> ⇒ **判据**：**「第一次请求返回空 / 没数据」时，第一步是比对「多次请求之间的 header 差异」**，
> 而不是回去改 query 参数。**头里的自定义名**（`Portal-Sign` 这类）通常既不叫 `sign` 也不叫 `token`，
> **搜「长得像签名的值」比搜「名字像签名的字段」更有效**。

确认手法与 §3 的「唯一验收动作」一致：断点处**直接调用 `f.getSign(e)` 并与抓包值对拍**。

**动作 ④ · 「加密就是 `toString()`」——请求加密与响应解密可能是同一个对象**

源文 `1829895`：**请求体加密方法就是 `t.toString()`**，**响应解密用的也是 `t`**。

> ⇒ **判据**：在 `send` 断点处看到的是密文时，**调用栈里最近的那个「参数是对象、返回值是字符串」的函数**
> 往往就是它。**不要默认请求加密与响应解密是两套算法** —— 一个 `.toString()` + 一个 `.parse()` 就够。
> 反向也成立：**只扣了加密那一半**时，先怀疑「解密那半用的是同一个对象」。

## §8.6 三法覆盖率与「带分隔符的精确搜索」（B41 补）

**来源** `52pojie-1160287`（2020-04，作者的定位法总结帖）。它给了一个**可引用的比例口径**：

> 「以上这三种方法，可以帮助我们快速定位到**百分之 60** 的加密参数的位置；
> 至于剩下的百分之 40，我们就需要使用到 **hook** 来定位了。」

三法与其适用边界（源文原话归纳）：

| 法 | 定位到哪一环 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **全局搜索** | 赋值/拼接处 | 位置准确 | 命中多、**容易搜不到**（名字不叫 `password`） |
| **DOM 事件** | **明文入口**（用户输入 → … → 加密函数） | 「定位的位置比较靠前」 | 只覆盖表单类交互 |
| **XHR 断点** | **发包函数** | 能**跟栈** | 只覆盖 `XHR`；**`js 发包` / `html 表单发包` / `xmlhttp` 抓不到** |

> ★★ **可迁移判据（本节唯一新增动作）**：**全局搜索要带分隔符做「精确化」**——
> 从 `password` 收敛到 **`password=`**、**`password =`**、**`password:`**、**`password :`**
> 「会过滤掉一些不必要的结果」（源文原话）。
> ★ 这与 §8.5 动作 ① 是**互补**的：动作 ① 解决「名字不叫这个」，本节解决「名字叫这个但命中太多」。
> ★ 三法**覆盖率只有约 60%** ⇒ **剩下 40% 必须上 hook**（本仓库的 hook 侧见
> `../../web-reverse-hook/SKILL.md`）—— **不要因为三法都试过就认为「这个站没有加密」。**

## §8.7 ★★ 「搜字段名直接命中」= 判定在 Java/宿主层，不必上 frida（B42 补）

**来源** `52pojie-1894045`（小红书 Android `x-b3-traceid` / `x-xray-traceid`）。

```text
① 抓包看到两个新 header：x-b3-traceid、x-xray-traceid
② jadx 里**直接搜这两个字段名** ⇒ 命中 ⇒ 双击进代码 ⇒ 逻辑是：
   判断 header 里的 x-xray-traceid 是否为空；为空则
   String.format("%016x%016x", long0, long1)
③ 本地复现这段格式化 ⇒ 与抓包值一致 ⇒ **完事，不需要 frida**
```

> ★★★ **判据（可迁移到任何"客户端生成的 header"）**：
> **搜字段名即命中 ⇒ 生成逻辑就在宿主层（Java / ObjC），而且往往是纯格式化/纯哈希** ⇒
> **成本是"读几行代码"级别**。反之：
> **搜字段名搜不到 ⇒ 才需要考虑 so / 动态注册 / 混淆**（走
> `../../android-app-reverse/SKILL.md` 的分流表）。
> ⇒ **先花 30 秒搜一次字段名，再决定用哪套工具**（省掉一整轮 frida 环境搭建）。
> ★ 本条与 §8.5 动作 ① 方向相反但互补：§8.5 解决"**搜名字搜不到**"（换靶），
> 本条解决"**搜名字搜到了之后**该怎么判成本"。
