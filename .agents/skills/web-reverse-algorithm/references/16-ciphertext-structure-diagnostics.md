# 密文形态诊断：只有一段密文时先读什么

> **本文的定位**：`01-decision-tree.md` 解决「这题属哪族」，`15-call-site-locating-playbook.md` 解决
> 「加密发生在哪一行」，本文解决**它的上一层问题**：**你手上还没有（或永远拿不到）JS，只有一段密文/编码产物时，
> 能从它身上读出哪些客观信息。**
>
> 适用时机：
> - 求助帖式任务（**别人只给你一段密文和一个 URL**，原文根本没解出来）；
> - 接口字段「看着像密文」，但断点打不到、搜索搜不到；
> - 你要在动手扣代码之前，先判断「这事值不值得做」。

---

## 0. 一句话

**密文的形态会泄露明文的结构。** 长度、字符集、公共子串这三类信息**都不需要密钥**，
而且它们给出的结论是**可判定的**（不是猜）——先读形态，再决定要不要去追算法。

| 你有的信息 | 能推出的结论 | 推到什么程度就该停 |
| --- | --- | --- |
| 密制长度 | 块大小 / 明文长度区间 / 是否做过填充 | 到「16 字节块 + PKCS7」级别 |
| 字符集 | 编码链（hex / base64 / base64url / `%uXXXX` / 纯数字） | 到「先按哪个解码器解」级别 |
| **多个密文的公共子串** | **明文的公共子串位置**（ECB / CBC 两种机理） | 到「明文哪两段相同」级别 |
| 以上都不成立 | **说明有随机化**（IV / 盐 / nonce / 时间戳参与） | 到「别指望复现，去要 oracle」级别 |

> **反面纪律**：形态诊断**只能给出结构结论，不能给出明文**。凡是形态上「看不出来」的，
> 说「看不出来」；不要把一个结构观察包装成算法结论 —— 四之末的案例就是一个**没有结论**的求助帖。

## 1. 长度判据

| 观察 | 结论 | 注意 |
| --- | --- | --- |
| 密文长度是 16 的整数倍，且**刚好**等于明文长度 | 无填充（`NoPadding` / CTR / OFB） | CTR/OFB 的密文长度 = 明文长度，**不要因为它对齐就以为是 CBC 无填充** |
| 长度 = `ceil((明文+1)/16)*16` | PKCS7（最小区块） | 明文恰好 16 倍数时会**多整整一块**（全 `0x10`）⇒ 长度比预期多 16 是**正常**的 |
| 长度是 8 的整数倍而**不是** 16 的倍数 | DES / 3DES（块 8） | 先把「块大小」定下来，再谈模式 |
| 长度 ≈ 明文长度的 4/3 | base64 包裹 | 见 §2 |
| 长度 = 明文长度的 2 倍 | hex 包裹 | 同上 |

> 这条判据的**唯一用途**是**反向定块大小**。一旦块大小与你假设的模式不符，
> 立刻回头改假设 —— 而不是去调 padding 的实现。

## 2. 字符集判据（先选对解码器）

| 形态 | 编码 | 先试 | 坑 |
| --- | --- | --- | --- |
| `[0-9a-f]` 偶数长 | hex | `bytes.fromhex` | 大小写混用不报错；**长度是 32 的 hex 也可能不是 MD5**（见 §4） |
| `[A-Za-z0-9+/]`，尾部 `=` 或 `==` | 标准 base64 | `base64.b64decode` | 缺 `=` 补齐会 `binascii.Error`，先补再解 |
| `[A-Za-z0-9-_]`（含 `-` / `_`） | base64url | `s.replace('-','+').replace('_','/')` 后再解 | **不替换直接解会抛 `binascii.Error`**（反而好排查） |
| `%XX%XX…` | `encodeURIComponent` | `decodeURIComponent` | —— |
| `%uXXXX%uXXXX…` | **`escape()` 专属** | `unescape()` | ⚠️ **`decodeURIComponent` 解不了**（它不是百分号编码的合法形式），会原样返回或抛错 |
| 一串十进制数字 | 可能是 `charCode` 拼接或大整数 | 先试 `String.fromCharCode(...)` 分段 | 数字串也可能是**签名的一部分**，别默认它是编码 |
| 全是可打印字符但不是上面任何一类 | **自定义字符表**（魔改 base64 / 位移表） | 去 JS 里取表，**别猜标准表** | 见 `../../ast-deobfuscation/references/invisible-unicode.md` 的同型问题 |

**内置编解码函数的形态指纹**（来源 `52pojie-1820070`，一张速查表的价值在于**能从产物形状反查用了哪个函数**）：

| 函数 | 产物形态 | 复原 |
| --- | --- | --- |
| `escape("始識")` | `%u59CB%u8B58` | `unescape` |
| `encodeURI` | `%E5%A7%8B%E8%AD%98` | `decodeURI` |
| `btoa` | 标准 base64 | `atob` / `base64.b64decode` |
| `String.fromCharCode(101,118,97,108)` | `eval` | 反查：数字数组 ⇒ 逐个 `chr` |
| `CryptoJS.enc.Base64.stringify(CryptoJS.enc.Utf8.parse(t))` | 标准 base64，但**UTF-8 先编码** | 注意：`Base64.parse` 后必须 `toString(Utf8)`，否则拿到 `WordArray` |

> **判据（一句话）**：**先按形态选解码器，再按结果判断对不对。**
> 选错了**不会报错**，只会给你一段乱码 —— 所以「解出来是乱码」永远先怀疑**选错解码器**，
> 而不是怀疑算法。

## 3. ★ 公共子串判据（本文最有价值的一节）

当你**手上有同一目标的多个密文**（不同请求 / 不同账号 / 只改了一个字段）时，
**比对密文的公共子串**能直接告诉你**明文哪两段相同** —— 这一步不需要密钥。

| 机理 | 观察 | 推出 |
| --- | --- | --- |
| **ECB** | 两个密文在**同一偏移**出现相同的 16 字节块 | 对应明文块**完全相同** ⇒ **ECB**（也说明可以块重排，见下） |
| **CBC，IV 相同** | 两个密文**从第 0 字节起**有共同前缀 | 对应明文**前缀相同**且 **IV 相同**；公共前缀长度会被「第一个不同的 16 字节块」截断（CBC 会把这个差异扩散到**后面所有块**） |
| **CBC，IV 不同** | 两个密文**只有尾部**有公共子串 | 对应的**明文尾部相同**（差异都在前面）；且**尾部对齐**说明 padding 长度相同、明文字节长度一致 |
| 完全无公共子串 | 有明显随机化：IV / 盐 / nonce / 时间戳进了明文 | **别复现**，去拿 oracle（`14-browser-rpc-bridge.md`） |

**为什么尾部公共子串特别有用**：CBC 是**前向扩散**的（改一块只影响这一块之后），
所以「两个密文共享尾部」是**明文尾部相同**的充分证据，而且能把「哪一段是变动部分」切得干干净净。

> **★ 反向用法（比正向更硬）**：**公共段的长度如果不是块大小的整数倍，就反证了「整块加密」这个假设。**
> 实测（`52pojie-2046628` 的两个样本，本文实跑复核）：两个密文 base64 解码后**都是 40 字节**，
> 公共尾部 **12 个 base64 字符 = 8 字节**，公共前缀 **0 字节**。
> - 40 字节**不是 16 的整数倍** ⇒ **不是** 16 字节块的 AES-CBC（也不用再试 `PKCS7`）；
> - 40 = 5×8，且公共尾部恰好 **8 字节 = 1 个 8 字节块** ⇒ 与 **8 字节块加密（DES/3DES）**
>   或**「多段拼接 + 尾部有固定段」**两种读法都相容，**单凭长度无法二选一**。
>
> 这条的价值在于：**它把一个「看着像 AES」的字段直接排除了**，
> 省掉的是「用 AES 试一百遍然后怀疑 key」的时间。
> ⚠️ 该案例源文**没有给出明文**，因此上面只是**形态结论**，**不是**关于算法的结论。

> **注意**：CBC 的公共前缀只在前缀正好按 16 字节对齐、且**逐块**相同时才成立 ——
> 若差异出现在某块中间，**该块及之后全部不同**。所以「公共前缀长度」是**下取整到 16** 的量。

**操作姿势**（三段，都可机械做）：

```bash
# ① 先把两个密文的字符集归一到「原始字节」（hex / base64 / 原样三种形态都支持）
# 注意：位置参数写在 `python -` 后面，heredoc 只负责脚本本体
python - "<密文A>" "<密文B>" <<'PY'
import base64, binascii, sys
def raw(s):
    s = s.strip()
    if s.endswith('=') or (s and all(c.isalnum() or c in '+/-_' for c in s) and len(s) % 4 == 0):
        return base64.b64decode(s.replace('-', '+').replace('_', '/'))
    if len(s) % 2 == 0 and all(c in '0123456789abcdefABCDEF' for c in s):
        return binascii.unhexlify(s)
    return s.encode('utf-8')

a = raw(sys.argv[1]); b = raw(sys.argv[2])
n = min(len(a), len(b))
# ② 公共前缀（按 16 取整，因为 CBC 只按块扩散）
p = 0
while p < n and a[p] == b[p]:
    p += 1
# ③ 公共后缀
q = 0
while q < n - p and a[n-1-q] == b[n-1-q]:
    q += 1
print(f'len a={len(a)} b={len(b)} | common prefix={p} (blocks={p//16}) | common suffix={q} (blocks={q//16})')
PY -- ciphertext_a ciphertext_b
```

> 上例用 `python - <<'PY'` 从 stdin 读脚本、密文当位置参数传。密文里含 `$` / `!` 时**务必加引号**。

**从这条判据还能往前走一步（ECB 的条件下）**：块相同的两块明文相同 ⇒ 可以
**块重排**（把某个块搬到别处）而密文仍然「合法」；以及**块字典攻击**
（对「只有有限取值集」的字段逐个建立「密文块 → 明文」表）。这条不在本文展开，
归到「模式判错」的处置里：**一旦确认是 ECB，先问「这个字段的取值是不是可枚举的」**。

## 4. 别把「形态像」当成「就是它」

| 陷阱 | 说明 |
| --- | --- |
| 32 位 hex ⇒ 一定是 MD5 | 也可能是 **MD5 的变体**（加盐 / 双次 / 截断 / 拼接时间戳后再 hash），或**16 字节 AES 密文的 hex** |
| 末尾 `==` ⇒ 一定是 AES | 也可能是**纯 base64 的 JSON**（实测有站点直接 base64 传 JSON）⇒ **先用 base64 试一把**，能解出可读 JSON 就是纯 base64 |
| 解出来「部分可读」⇒ 快成了 | 可能是**用错了 IV**（CBC 的 IV 只影响第一块）⇒ 前 16 字节乱、后面全对是**典型 IV 错误**，不是算法错误 |
| 解出来是合法 UTF-8 ⇒ 明文对了 | **必须用业务可识别的判据**：能 `json.loads` / 字段名对得上 / 与浏览器控制台逐字节一致 |

## 5. ★ 没有结论时怎么登记（求助帖式任务的纪律）

`52pojie-2046628` 是一篇**悬赏求助帖**：提问者把发现全列了（`session_id` 来自
`uc-gateway.ykt.eduyun.cn/v1.1/sessions` 的响应、`login_name` / `password` / `zhitong_password`
三个字段的密文样本），**但帖子里没有解答、也没有最终方案**。
这类输入的正确处置是：**只登记可判定的结构观察，一条结论都不许往外推**。

该帖里**可以升格为方法**的只有两条（都不依赖它的最终答案）：

1. **跨请求参数依赖**：`session_id` 由**第 1 个接口**下发（响应里同时给 `session_id` / `session_key`），
   随后作为**第 2 个请求**（登录）的字段参与加密 ⇒ 属于「参数溯源三分类」里的**「上一次响应返回的」**。
   判据：**同一个值在两次请求里重复出现 ⇒ 先找它的来处，别把它当纯算输入**。
2. **密文结构观察（本文实跑复核，非源文结论）**：该帖给出的两个密文样本
   （`DsNK3t8OwQzw9OxWx8S3ZEwgqm4MWF5veO3agNYZqBl0LUmwP9Y5MQ==` 与
   `ytFWWexA2kRKwkQ+MLcJVWYgsLKaHk2FGB46W9PcYQh0LUmwP9Y5MQ==`）
   **base64 解码后都是 40 字节，公共尾部 12 个 base64 字符 = 8 字节，公共前缀 0 字节**
   （复核命令见 §3 的脚本）。
   ⇒ 按 §3，公共尾部 ⇒ 「明文尾部相同」；而 **40 不是 16 的整数倍** ⇒
   **可以直接排除「16 字节块的 AES-CBC」**（详见 §3 的「★ 反向用法」）。
   ⚠️ **本文只登记这些可复现的形态结论，不登记任何关于明文内容或算法的结论**
   （源文没有给出明文，也没有验证）。要升级成结论，必须补一次
   「构造两个已知明文尾部、用候选 key/IV 逐字节对拍密文尾部」的实测。

> ```

> 可判定结论：<由形态直接推出的结构结论>

> ```
