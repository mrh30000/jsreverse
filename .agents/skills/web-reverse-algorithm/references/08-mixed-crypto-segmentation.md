# 混合加密分段还原（黑盒推结构 → 分工定位 → 变体对照）

本文件是 `02-algorithm-families.md` §二「混合加密题」的展开。适用于**一个参数里塞了两段以上密码学**的场景
（典型：`前段密文 + 后段被加密的密钥`）。目标是让「没读过一行混淆代码」也能先把结构定下来，
再把工作量摊到可并行验证的小块上。

---

## 一、先量体征：不读代码就能推出骨架

把同一个参数在**多次不同请求**里拉出来做三条观察，通常 5 分钟就能猜出结构：

1. **字符集与编码层**：全是小写 hex？标准 base64？base64url（只有 `-` `_` 无 `+` `/` 无 `=`）？
   含 `()`、`,`、`.` 等非标字符 ⇒ 站点**自定义 base64 变体**（见 §四）或者纯自定义字符表编码。
2. **长度是否可变**：每次都不一样 ⇒ 明文里含行为/时间数据；长度恒定 ⇒ 明文是固定字段或定长结构。
3. **长度是否有规律**：前段总是 16 字节的整数倍（hex 编码后是 32 的整数倍），
   末尾**固定多出一截** ⇒ 末尾那截是独立算法（几乎必然是密钥包装）。

**长度 → 算法反查表**（hex 口径，1 字节 = 2 字符）：

| 尾部长度（hex） | 字节 | 结论 |
| --- | --- | --- |
| 256 | 128 | **RSA-1024** 密文 |
| 512 | 256 | RSA-2048 密文 |
| 128 | 64 | RSA-512 或 EC 签名 |
| 64 | 32 | 摘要（MD5/SHA-256 中段）而不是非对称密文 |
| 无固定尾段 | — | 大概率不是「密文 + 密钥密文」结构 |

> 实例（极验 v4 `w`）：长度每次变、全是小写 hex、末尾恒定 256 hex ⇒
> 第一假设就是 `w = hex(分组加密(明文)) + hex(RSA-1024(分组加密的 key))`。
> 前段是 16 字节倍数 ⇒ 分组加密块大小 16B（AES / SM4），极验这个量级基本就是 AES。

**这套「黑盒先定骨架、再进 JS 取证」的顺序很重要**：它把「读混淆代码」从开放式搜索变成了
「验证一个已有假设」，后面的每一处断点都有明确目的。

## 二、三段定位法（按性价比排序）

### 2.1 常量特征优先于关键字

混淆器可以改函数名、改字符串，但**很难改算法常量**。先把这些当指纹搜：

| 特征 | 命中含义 |
| --- | --- |
| `65537` | RSA `publicExponent`，非对称加密在附近 |
| `setPublic` / `setPublicKey` | RSA 公钥装载点（`N` / `E` 就在入参里） |
| `7274496` / `9483264` / `19220` / `235` | **极验自有 base64 变体**的四个位掩码（见 §四） |
| `ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789()` | 极验自有 base64 码表（尾两字符被 `()` 替换） |
| `maxPoints` / `percentPrecision` | 轨迹采集器的配置（**明文**，比解字符串表快得多） |

### 2.2 关键字：`w` / `encrypt` / `IV` / `padding` / `mode`

- 混淆后 `w` 本身通常还在（赋值给请求参数的对象字面量键名会保留），搜 `"\u0077"`（搜 `"w:"` 也可）。
- 极验 v4 直接搜 `process_token` 能落到 `w` 的组装点，比搜 `w` 更少误命中。
- `encrypt` 在**商业库调用**里常保留原名（CryptoJS 的属性名不被混淆）。
  做法：给每个 `encrypt` 命中处加一行 `console.log(arguments)`，跑一次，看哪几个有输出，
  再在第一个输出处**去上一个调用栈** —— 这比逐个下断点快一个数量级。

### 2.3 关键字全被清掉时的兜底：调用栈 + Proxy 陷阱

- **调用栈法**：从最终 `fetch/XHR.send` 回栈，找形如 `var n = {}; ... n.w = t[...]` 的组装点。
- **Proxy 陷阱法**（属性名被完全隐藏时最有效）：在对象定义之后立刻包一层 Proxy，
  在**设置目标属性**时 `debugger`：

  ```js
  o = new Proxy(o, {
    set(t, k, v) { if (k === "<要抓的字段名>") debugger; t[k] = v; return true; }
  });
  ```

  执行流会停在写入点，回栈即可拿到写入它的函数。
  实例：`h9s9` 这个字段在全文中搜不到赋值处（名字是运行时拼出来的），
  用 Proxy 拦一次就定位到了 `gct.js` 里的 `StJC` 函数。

## 三、逐段定界：给每一段贴上四元组标签

分段之后**必须**为对称段凑齐四元组，缺一项都会「解密失败但不报错」：

```text
对称段 = algorithm + mode + padding + key + iv
非对称段 = algorithm + keySize + padding + (N, e)
编码层  = 字符表 + 是否补位 + 大小写
```

取证顺序：**先固定 key/iv/明文在本地跑一遍，与浏览器产出的密文逐字节 diff**。
一致 ⇒ 标准实现，直接引库，不必扣代码；不一致 ⇒ 才去扣代码看是不是魔改。

| 项 | 常见坑 | 判据 |
| --- | --- | --- |
| `iv` | 混淆代码里 `"0000000000000000"` 是 **16 个 ASCII 字符 `'0'`（0x30）**，不是 16 个 `\x00` | 用 `\x00`×16 解出来的明文是乱码，用 `'0'`×16 正常 |
| `padding` | PKCS7 / 字符 `'0'` 手工补位 / nopadding 三种都见过 | 密文比明文多出**整整一个块** ⇒ PKCS7；多出的块是 `0x10`×16 ⇒ 直接确认 PKCS7 |
| `mode` | CFB / CTR 与 CBC **在解出明文长度上就不同**（无填充），但短明文容易看错 | 看 `Encryptor.processBlock` 形态；或改一位密文看错误是否扩散到整块 |
| `key` 来源 | 「时间戳派生」是最常见的**误判**（见 §五） | 同一会话多次请求：key 变 ⇒ 随机；不变 ⇒ 会话级复用 |

> **铁律**：`iv` 一定要按「混淆代码里的字符串字面量**原样**当字节用」，
> 不要按「语义上应该是零向量」去推。极验 v4 的 `w` 在这里卡过大量人。

## 四、变体对照表：同一骨架的四种落地

「AES 装货 + RSA 装钥匙」这个骨架在国产风控里高度同构，差别只在**编码层**和**key 生命周期**：

| 实现 | 前段算法 | 前段编码 | key 生成 | IV | padding | 后段 |
| --- | --- | --- | --- | --- | --- | --- |
| 极验 v3（2020 无感路线） | AES-128-CBC | **自有 base64 变体**（码表尾 `+/` → `()`，不足位补 `.`） | `(65536*(1+Math.random())\|0).toString(16).substring(1)` × 4 拼接（16 位 hex） | `"0000000000000000"` | 见 §五 歧义说明 | RSA-1024 / PKCS1v15 |
| 极验 v3（2024 fullpage / click 路线） | AES-128-CBC | 同上自有变体 | 同上，**同一会话内复用同一把** | 同上 | `CryptoJS.pad.Pkcs7` | RSA-1024 / PKCS1v15，**长度必须恰好 256 hex 否则重试** |
| 极验 v4（`gcaptcha4.js`） | AES-128-CBC | **`ArrayToHex` 小写 hex**（不是 base64） | 同上，**同一轮 AES 段与 RSA 段共用同一把** | 同上 | `CryptoJS.pad.Pkcs7` | RSA-1024 / PKCS1v15（`e = 65537`） |
| 通用「自定义 base64」家族（如 `+→- /→_ =→.` 双向对称的变体） | 任意分组 | 站点自有码表，**加密与解密方向必须对称改码表** | 随机或时间派生 | 常见 `'0'×16` | 逐站确认 | 常见 RSA / 或纯编码不收口 |

**极验自有 base64 的实现要点**（把 `7274496 / 9483264 / 19220 / 235` 四个掩码当成「位选择器」）：

```js
// 每 3 字节 → 24 位 → 4 个 6 位组 → 查码表；码表长度 64，越界返回 "."
var t = "ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789()";
```

它**不是**标准 base64 的等价实现（掩码不是 `0xfc0000 / 0x3f000 / 0xfc0 / 0x3f`），
所以不要用标准 base64 去解，也不要用标准 base64 去生成。**要原样扣这段表驱动逻辑**，
或按掩码逐位复刻。剩余 1 / 2 字节的尾部各补一个 / 两个 `.`（不是 `=`）。

## 五、两个必须写进报告的**歧义/版本差异**点

逆向结论一旦被当成「厂商常量」写死，换版本就会静默失效。以下两条必须以「版本 + 取证日期」标注：

1. **AES key 的生成方式**：2020 年的公开分析里写着「用时间戳生成 AES 密钥」，
   但同系列的**补遗**给出的实际代码是 4 段随机 hex 拼接：
   ```js
   function create_key() { return (65536 * (1 + Math.random()) | 0).toString(16).substring(1); }
   function get_aes_key() { return wr() + wr() + wr() + wr(); }
   ```
   ⇒ 结论按**后者**（随机）写，并注明「早期文章的时间戳说法是作者当时的推测，已被其本人补遗否证」。
   **同一个文件里只会生成一次**，所以同轮多个 `w` 共用同一把 key —— 这是最容易踩的坑
   （完整的共享值清单见本文 §六「会话级复用清单」）。
2. **padding**：站点侧（CryptoJS）2024 实测是 `pad.Pkcs7`；
   2020 年文章给的是**作者自己写的 Python 复现**（`text + '0' * add`），
   那属于复现脚本的实现选择，**不能反推站点 padding 语义**。
   判定唯一可靠办法：固定 key / iv / 明文，本地跑，与浏览器密文逐字节 diff。

## 六、会话级复用清单（提交前自检）

同轮内被多个密文段共享、**必须保持一致**的值：

- AES key（极验 v3 三个 `w` 共用；v4 前段与后段共用）；
- 随机的盐（v4 `pow_msg` 的 16 位 salt **与 AES key 不是同一个值**，别复用）；
- `challenge`：v3 第 5 步会返回**新 challenge**（比初版多 2 位尾巴），
  后续 `userresponse` / `rp` / 业务提交用的都是**这个新的**；
- 轨迹明文（v4 `td` 的参数）与它的签名（v4 `td_sign`）必须同源；
- 随机串一旦被 4 段拼接生成，**不要在多处重新随机**。

## 七、PoW 段（工作量证明）的归约

遇到 `pow_msg` / `pow_sign` 这类字段，结构固定为「模板串 + 随机盐 + 摘要」：

```text
pow_msg  = version | bits | hashfunc | datetime | app_id | session_id || salt(16 hex)
pow_sign = HASH(pow_msg)                      # 前缀 bits 个二进制位必须全 0
```

- 末尾的 `||` 是**空段**，不是笔误；
- `bits` 必须从响应里读（同一站点实测见过 8 和 10），写死必然偶发失败；
- 判定用**整数比较** `int(pow_sign, 16) < 2 ** (256 - bits)`，
  **不要数十六进制前缀零的个数**（bits 不是 4 的倍数时会数错，如 10）；
- 成本：bits=8 平均约 256 次、bits=10 约 1024 次摘要，毫秒级；
- 盐与同一轮其他随机值**必须各自独立**。

### 7.1 ★★ 第二种模板：hashcash 原教旨（`52pojie-1843070`）

极验那种「`pow_msg` + `pow_sign` 两字段」是**一种**落地。Apple 登录链上是**另一种**：

```text
X-APPLE-HC = {version}:{bits}:{date}:{challenge}:{ext}:{counter}
             version = 1（固定）
             bits    = 难度，页面可取，源文实测 10–12
             date    = 时间戳（源文样例形如 20230929145813，14 位）
             challenge = 页面上取的 32 位 hex（16 字节）
             ext     = 额外数据，可空 ⇒ 出现连续的 `::`
             counter = 从 0 开始递增，**直到 sha1(整串) 的二进制前 bits 位全为 0**
```

**提交物是「整串 + counter」，不是摘要** —— 服务端自己重算 SHA-1 并检查前导零。
⇒ ★★ **判据：看到「提交的值里带一个自增整数」+「服务端能自己复算」⇒ 就是这一族。**

**★ 两种「难度口径」不要混用（本节最重要的增量）**：

| 口径 | 判据写法 | 出处 |
| --- | --- | --- |
| **hex 语义**（极验） | 前导零 **hex 位** `bits//4` 个 + 第 `bits//4` 位 ≤ 7/3/1 | `../../web-verify-patcher/references/geetest-protocol-matrix.md` §8.1 |
| **bit 语义**（hashcash） | 二进制**前 `bits` 位全为 0** | 本条 |

> ★ **本批复算的硬结论**：hashcash 的两个源文样例（`bits=11` 与 `bits=12`）
> 的 SHA-1 **前导零分别是 109 位与 108 位**，远超 `bits`
> ⇒ **「前 bits 位为 0」是下界，不是精确值**；`bits=11` 时 108 位的解同样合法。
> ⇒ **不能用「前导零个数 == bits」当验收标准。**

### 7.2 ★★★ 本族的验收例外：PoW 类参数**不可逐字节复现**

**本批实测**（脚本 `b37-verify-numbers.py` §1，**Node/Python/真机 WebCrypto 三侧一致**）：

| 事实 | 实测值 |
| --- | --- |
| `bits=11` 的**最小** `counter` | **4824** ← 与源文给的完全一致 |
| `bits=12` 的**最小** `counter` | **5126** ← 与源文给的完全一致 |
| `counter` 取 `0` | **不合法**（前 11 位 = `11101111010`） |

⇒ ★★ **结论（比「解不唯一」更准确）**：
- **`counter` 是「从 0 顺序试出来的第一个解」**，源文给的正是**最小解** ⇒
  **给定同一组 `(version, bits, date, challenge)`，`counter` 是唯一确定的、可复算的**；
- ⇒ **但 `date`（时间戳）与 `challenge` 每次都变** ⇒ 整串变 ⇒ `counter` 变
  ⇒ **抓包里的那个 `counter` 仍然复现不了**；
- ⇒ **本库的验收纪律（`../../reverse-knowledge/references/platform-signature-patterns.md` §十二
  「只能与抓包真值逐字节相同」）在这一族有一个明确的例外**：
  **验收标准是「服务端接受」+「本地独立校验前 `bits` 位为 0」+「结构/字段与抓包一致」**，
  而不是「`counter` 与抓包值相同」。写报告时必须显式说明这一点，否则会被误判为「没还原对」。

> ⚠️ **边界**：源文未说明服务端是否校验 `counter` 的**唯一性/单调性**（防重放）。
> 若某站点会记录已用过的 `counter`，「永远取最小解」就可能被拒 —— **本库不裁决，实测为准**。
>
> ⚠️⚠️ **本批自曝的方法论缺陷（已修，务必记住）**：
> 初版判定用了 `bin(...)[2:].zfill(256)` —— **对 160 位的 SHA-1 会人为补 96 个前导 `0`**，
> 于是 `[:bits]` **恒为 0**，断言退化成**恒真**，一度得出「counter=0 也合法」的**错误结论**。
> ⇒ ★★ **规则：凡是「前导零 / 位长」类断言，位长必须从摘要长度推导
> （`zfill(len(digest) * 8)`），绝不能写死。**
> 这处假绿是**真机 WebCrypto 复算**抓出来的（Python 与 Node 两侧都没发现）。

## 八、密钥包装的另外四种形态（先认形态，再谈算法）

§一~§四讲的是「**前段密文 + 后段被加密的密钥**」这一种骨架。
实测里还有四种同样高频、但**判据完全不同**的形态。**先认形态，能省掉一整轮读代码。**

### 8.1 形态一：自描述密文（长度字段 + 尾部密钥）

**现象**：参数是一条长 base64/hex 串，**末尾多出一截「不像密文」的短串**；
解密函数里出现 `slice(0, -n)`、`substring(len - n)`、`parseInt(decode(v))` 这类写法。

```text
请求侧（实测）：
  k       = 7~9 位随机小写字母+数字
  payload = AES_CBC(JSON, key=md5(k)[16:32], iv=md5(k)[0:16]) + reverse(k) + str(len(k))
  另有字段 v = base64(十进制长度)          # 长度字段本身也单独编码

响应侧（更绕，双层）：
  ciphertext = url.slice(0, -n)            # n = parseInt(b64decode(v))
  realKey    = 尾部 n 位 → 用响应里的 key 字段解 → reverse → b64decode → JSON → 各元素 reverse → 用 '_' 拼
  plaintext  = 用 realKey 解 ciphertext
```

**判据与处置**：

- 量出「末尾多出多少字符」，再判断它是**密钥**、是**长度**、还是**两者都有**。
- 尾部内容**先 reverse 再 base64 decode** 是常见顺序，别按直觉直接解。
- **验收**：解出来必须是合法 JSON / 可读 URL。**「解出乱码但不报错」是这一形态的头号坑**
  （`md5(k)` 切两半时 key/iv 取反就会这样）。

### 8.2 形态二：响应自带密钥（同一次响应里给密文 + key + iv）

**现象**：一次响应里同时有密文字段与 `aes_key` / `aes_iv` / `key` / `iv` 之类字段。

```text
请求侧（独立一条）：
  key参数 = base64(AES_CBC(时间戳 + url, key=utf8(MD5HEX(时间戳+url)), iv=utf8("<站点固定>"), padding=Zeros))
响应侧：
  直接拿响应里的 aes_key / aes_iv 解 url / html —— 不需要逆任何算法
```

**判据**：「同一次响应里既有密文、又有 16 字符的 key」⇒ **停止寻找派生式**。

**坑**：

- padding 常是 **Zeros 而不是 PKCS7**（对端口径 `PaddingMode.Zeros`），用 PKCS7 会静默多出/少掉字节；
- 32 个 ASCII 字符的 MD5 十六进制串经常被**当 32 字节 key 直接用**（不是再摘要一次）。

### 8.3 形态三：算法按「时间戳奇偶 / 随机位」切换

**现象**：同一份 JS 里**成对出现**两条加密路径（AES 与 DES、CBC 与 ECB、两种口令），
调用点有一个共同的分支条件：

```js
return n % 2 == 0 ? this.AESEncrypt(e, t) : this.DESEncrypt(e, t);   // n === this.time
```

**判据**：加密与解密两处**都**带同一个分支条件，且条件变量来自**请求参数**（时间戳 / 随机数 / 会话位）。

**处置（最省力）**：**把那个分支变量写死**成自己实现得更好的那一路
（把 `tm` 固定为偶数即可锁定 AES），不必两套都实现。
**代价**：写死后提交的请求与站点不同源，若服务端对 `tm` 有单调性或时效校验，需同步放宽；
判据是**服务端仍返回正常结果**。

**坑**：只实现了一路、又没固定分支 ⇒ **在另一半请求上解出乱码但不报错**（典型的静默失败）。

### 8.4 ★★ 形态四：**密钥先「派生」、再被「插入」密文**（`52pojie-2005163`，so 层）

前三种形态都还承认「key 是一个独立的量」。这一种更绕：**提交出去的密文里自带 key 的原材料**。

源文（某程 so 层 `ctrip_enc`）的六段链：

```text
① random_key = 时间派生的随机 key（**不是最终 key**）
② encrypt_one(random_key, IV_A) → 真实 AES key
   └─ 内部：对 random_key 做 S-box 替换 → 行移位(4 字节组循环左移 1/2/3/4) → 列移位
      → 再对 IV_A 做一轮 S-box 替换；只跑 2 轮
③ AES-CBC(明文, 真实 key, IV_B) → 密文
④ encrypt_two：把 random_key 的每个字节，按 i = (i + Σ) % (n + len) + 1
   算出的位置插进密文、并把后续字节右移 ⇒ 输出长度 = len(key) + len(密文)
```

**★ 判据（三个层次，从便宜到贵）**：

1. **长度层（零成本）**：输出长度 = `ivlen + input_len`，
   而 `input_len` 已被 PKCS7 对齐到 16 的倍数 ⇒ **输出长度不是块对齐的整数倍**
   ⇒ **先怀疑尾部藏了什么东西**（本形态的第一判据）。
2. **常量层**：`aes_setkey_enc(CTX, X, 0x80)` ⇒ **`X` 就是真实 key**、
   **`0x80` = 128 位 = AES-128**。`ida` 里 `xmmword_*` 的 `DCB` 列表**恰好 16 字节** ⇒ IV/密钥候选。
3. **部件层**：把 S-box 的 256 项**逐字节对比** —— 若与标准 AES 一致，说明
   **是「标准部件复用当 KDF」，不是魔改 AES**。源文原话：「从头到尾，一个个对比过了，没毛病，一个字没动」。

**★ 填充的 C 语言等价形态（同源文，可直接照抄判据）**：

```text
if ((len & 0xF) != 0) padded = (len + 16) & 0xFFFFFFF0; else padded = len + 16;
if ((len & 0xF) != 0) padval = 16 - (len & 0xF);          else padval = 16;
memset(&buf[len], padval, padval);
```

> ★★ `(len + 16) & ~0xF` 与 `16 - (len & 0xF)` **同时出现** ⇒ **就是 PKCS7，没魔改**。
> ⚠️ **注意 `len` 恰为 16 倍数时补 16 而不是 0**（两个 `else` 分支就是为它写的）；
> 抄漏 `else` 会让「明文长度恰好是块整数倍」的请求**整体少一个块**（静默失败）。

**★ 解密顺序必须反着来**：先从密文**抽出** `random_key` → 用 `encrypt_one` + IV_A 算回真实 key
→ 再用 IV_B 做 AES-CBC 解密。

> ★★★ **手法层（本形态最值钱的一条，与 `../../wsam-reverse/` 的差分法同源）**：
> 源文没有读汇编去理解 `row_rotation` / `column_rotation`，而是
> **在 `unidbg` 里对同一个缓冲区「调用前打一次、调用后打一次」，用前后字节的对应关系反推语义**：
>
> ```text
> row_rotation 前：D4 3F 8B 24 | 1A 5E 7E 9D | 24 14 7E C6 | 49 7F DB 9E
> row_rotation 后：3F 8B 24 D4 | 7E 9D 1A 5E | C6 24 14 7E | 49 7F DB 9E
> ⇒ 四组分别循环左移 1 / 2 / 3 / 4 位（第 4 组移 4 = 不动）= 标准 AES 行移位
> ```
>
> ⇒ **判据：凡是遇到「名字像变换、代码一大坨」的函数，先做一次前后差分，
> 再决定要不要读代码。** 一份前后值往往就能把语义定死；读汇编既慢又容易读错。

> ⚠️ **边界**：源文的 `column_rotation` **只给了前后值、没给公式**，
> 本文件照实转述、**不代写公式**。上表里的 IV 常量（`xmmword_112C4`）是源文给出的完整 16 字节：
> `69 D2 55 B8 32 9E AC D4 0C 2A 9C 8B 68 75 87 05`。

### 8.5 形态速查（含本批新增）

| 现象 | 形态 | 第一个动作 |
| --- | --- | --- |
| 末尾多出一截短串 | 自描述密文（§8.1） | 量末尾长度；试 `reverse → b64decode` |
| 响应里同时有密文与 key/iv | 响应自带密钥（§8.2） | 直接解，别再找派生式 |
| 同文件里有成对的两套加解密 | 分支切换（§8.3） | 找共同条件变量，把它写死 |
| **密文长度 = 明文长度 + 16，非块对齐整数倍** | **密钥插进密文（§8.4）** | 先量长度差，再找插入循环 |
| 提交串里带**自增整数** | **PoW / hashcash（§7.1）** | 先确认难度口径是 hex 还是 bit |
| 前段密文 + 定长后段（256/512 hex） | §四 的「AES + RSA」 | 按 §一 的长度反查表走 |
| 密文长度 ≈ 明文长度 + 16（key 长度），且**不是块对齐的整数倍** | **密钥「插进」密文里**（本批新收，`52pojie-2005163`） | 先量长度差；找「把 key 逐字节插入并右移后续字节」的那段循环 |
| 提交串里带一个**自增整数** | **PoW / hashcash** | 走 §7.1，先确认难度口径是 hex 还是 bit |
