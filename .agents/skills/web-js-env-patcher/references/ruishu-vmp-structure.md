本文件记录**经第二来源交叉验证**的瑞数 VM 结构常量，用于把「只能靠断点跟栈 + 正则动态匹配」升级为「可确定性重算」。

取证、代际判据与环境矩阵见 `ruishu-botgate.md`；多趟 Cookie 见 `multi-pass-cookie-generation.md`。

## 1. `$_ts` 的完整结构

```js
{
  nsd: <数字>,        // 种子：决定变量名数组的置换结果
  cd:  "<字符串>",     // 内容串（长度随站点/版本变化，实测样例 2050）
  jf:  <布尔>,         // 格式校验标志（格式化检测 + 反码检测的结果）
  cp:  [ cp0, cp1, cp2, /*3,4,5*/ , cp6 ],  // 参数数组
  aebi: [],
  scj:  [],
}
```

| 字段 | 含义 | 来源 |
|---|---|---|
| `nsd` | 变量名置换种子 | 互证（文章提到 `nsd` 参与参数名生成；实现用它做 Fisher-Yates 种子） |
| `cd` | 内容串，先转数组再分段异或 | 互证（1988393 描述 cd→数组→前两位切分；实现 `example/codes/$_ts.json` 实测 `cd` 长度 2050） |
| `jf` | **格式校验结果**。代码被重新格式化后该标志变化 → 后续校验失败 | 实现单源；与文章「代码格式化后无法正常运行」互证 |
| `cp[0]` | 基础参数数组（按 96 一组切分使用） | 实现单源 |
| `cp[1]` | **变量名数组**（由 `nsd` 置换生成，见 §2） | 互证（1988393 称 `cp[1]`/`cp[3]` 与 `nsd` 相关；实现明确 `cp[1] = arraySwap(grenKeys(keynameNum), nsd)`） |
| `cp[2]` | 字符表与位运算位移参数（`alphabet`、`basestr` 等） | 实现单源（实现从 `cp2` 取字符表；文章未直接描述 `cp2`，勿当互证结论） |
| `cp[6]` | 空串占位 | 实现单源 |

**实践含义**：`$_ts` 不是「一堆随机变量」，而是**结构化的配置对象**。补环境时按字段取值，比按变量名硬编码稳定得多。

## 2. 变量名数组是可确定性重算的（最重要的升级）

文章口径是「变量名每次都变，只能正则动态匹配」。实现表明：**变量名由 `nsd` 唯一决定**，可确定性重算。

### 2.1 名称池生成

```js
const ALPHABET = '_$abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789'; // 64 字符
// 双重循环，生成 '_$' + a + b
// 前 5 个：_$__  _$_$  _$_a  _$_b  _$_c
// 全量 64 × 64 = 4096 个，无重复
```

### 2.2 池长度锚点（可执行，优于文章里的「固定数字定位」）

变量名池长度从 VM 代码里用一条稳定正则提取：

```js
/_\$[\$_A-Za-z0-9]{2}\s*=\s*_\$[\$_A-Za-z0-9]{2}\s*\(\s*0\s*,\s*([0-9]+)\s*,\s*_\$[\$_A-Za-z0-9]{2}\s*\(/
```

- 真实样本命中 `_$_6=_$$Q(0,851,_$_K(` → `keynameNum = 851`。
- 文章 1988393 独立称「`cp[1]` 是根据页面 `nsd` 生成的 **850** 个参数名」。
  → **850 / 851 双源互证**（差 1 属正常，锚点取的是池长度上限）。
- 这比文章 6 代用的「搜 `842,` 定位容器对象」更稳：842 是某一代的常量，锚点形态跨代复用。

### 2.3 置换算法

```js
// LCG：注意 & 会触发 ToInt32，序列有界且完全可复现
scd = 15679 * (scd & 65535) + 2531011;

// Fisher-Yates，取模用 LCG 序列
while (len-- > 1) { idx = next() % len; swap(knarr[len], knarr[idx]); }
```

- `nsd` 相同 → 变量名数组**逐元素相同**。
- `nsd` 不同 → 同一集合的另一排列。

### 2.4 工具与已验证结论

```bash
# 提取池长度锚点
node scripts/ruishu_keynames.js --extract-keyname-num <vm.js>

# 由 nsd + 池长度重算变量名数组
node scripts/ruishu_keynames.js --nsd 24296 --keyname-num 851

# 覆盖率校验（确认池长度/资源与这份 VM 代码匹配）
node scripts/ruishu_keynames.js --verify <vm.js> --nsd 24296 --keyname-num 851
```

在真实样本上的**实测结果**（`example/codes/main.js`，`nsd = 24296`）：

| 检查 | 结果 |
|---|---|
| 锚点提取 | `keynameNum = 851` |
| 反向覆盖率（代码内 `_$xx` 落在池中） | 68 / 69 = **98.6%** |
| 池使用量（信息性） | 68 / 851 = 8.0%（正常，VM 只用池中一小部分） |
| 负例：池长度取 100 | 反向覆盖率降到 23.2% → **正确报警** |
| 负例：池长度取 3000 | 100% → **测不出「过大」**（已知非对称） |

**两条硬约束（不要过度信任）**：

1. 覆盖率是**集合**判定，**不区分顺序** → **无法验证 `nsd` 是否正确**。`nsd` 正确性只能靠端到端 Cookie 对拍。
2. 该判据只能发现「池过小 / 实现族不符」，**发现不了「池过大」**。
3. 实测残留：真实样本中有 1 个标识符（`_$uf`）落在 851 池之外（68/69）。占比 1.4%，
   可能是另一命名空间或池边界问题。**处理口径**：不要为它强行扩大池（会把「池过大」的误报也一起放大）；
   记录在案，并以端到端 Cookie 对拍作为最终判据。若最终请求通过，说明它不影响结果；
   若失败且已排除其它原因，再回头查这一项。

## 3. `fixedValue20()`：6 代「4 位数组」的真实身份

实现里有一张 20 值常量表：

```js
values = [103, 0, 102, 203, 224,
          181, 108, 240, 101, 126,
          103, 11, 102, 203, 225,
          181, 208, 180, 100, 127];
```

文章 1846988（6 代）给出的 `valueMap` 值域为
`{103, 0, 102, 203, 224, 181, 108, 240, 101, 126, 11, 225, 208, 180, 100, 127}`
—— **与上表逐值一致**（表内 `103/102/203/181` 各出现两次）。

**双源互证的结论**：

- 这张 20 值表是**跨代/跨站点稳定的常量**，不是某站特有的魔法数。
- 「4 位数组」= 从这 20 个值里按 `$_ts.cp[1]` 决定的任务映射挑出 4 个，选取顺序由 `keys = [29, 30, 31, 32]` 对应的参数名决定。
- 所以文章里「方法内部数组值 → 方法返回值」的映射表，本质是**在查这张常量表**；实现里连「数组值」都不需要，直接按 `cp[1]` 索引取。

> 注意：文章给出的映射键（194 / 274 / 306 …）是实现里的**任务编号**，随版本变动；**值域是常量，键不是**。写代码时按值域 + `cp[1]` 索引处理，不要硬编码键。

## 4. `uuid()` 是 CRC-32（不是哈希库调用）

```js
val = 0 ^ -1;
for (i = 0; i < len; ) val = val >>> 8 ^ bignum[(val ^ byte[i++]) & 255];
return (val ^ -1) >>> 0;
```

- `bignum` 是 256 项查找表 → **标准 CRC-32**。
- 6 代文章里 `_$hM` 的那段 `_$jU = (_$jU >>> -1) ^ _$dk[(_$jU ^ _$k4[_$IM++]) & 255]` 与之同构（`>>> -1` 即 `>>> 31`），文章称「`_$yx._$4y` 是 256 位数组可直接固定」——**它就是 CRC-32 表，标准可复现**，不必从页面取值。

## 5. 基础数组（basearr）与分段结构

「128 位大数组」的真实结构是**带标签的分段数组**：

```js
numarrJoin(...)   // 拼接规则：首个元素原样；其后每遇数组插入 [长度, ...内容]；遇标量直接追加
numarrJoin(3, innerArr, 10, arr2, 7, arr3, 0, [0], 6, arr4, 2, fixedValue20(), 9, arr5, 13, [0], 15, arr6)
// → [3, <len>, ...innerArr, 10, <len>, ...arr2, 7, ...]
```

**双源互证**：文章 1988393 称「117 位数组前四位 `[1,0,33,128]`，前两个数字写死，第三个 33 是 `eval.toString().length`，第四个 128 是 `1<<7`」；实现里对应代码是

```js
numarrJoin(1, config['window.navigator.maxTouchPoints'],
              config['window.eval.toString().length'],
              128, ...)
```

→ 真实语义是：**`1` 是段号，`0` 是 `navigator.maxTouchPoints`，`33` 是 `eval.toString().length`，`128` 是 `1<<7`**。
「写死的两个数字」被升级为「段号 + 一个真实环境值」，可复现、可校验。

**段号是结构常量**（跨站点稳定），段内容是站点/版本相关。文章只能靠断点跟栈逐段观察，实现给出了段号到内容的完整对应，**应以段号组织理解，不要按「第 N 位」硬记**。

`numarrEncrypt()` 是基于频次 Huffman 树的变长编码，因此**分段数组长度会变**；站点适配里用 `lens`（基础数组长度）与 `encryptLens`（加密后长度）约束，生成后校验不通过就**重新生成**（最多 1000 次）。

## 6. 站点级适配与 Cookie 后缀

实现按 `adapts[simpleEncrypt(hostname 去掉 www 前缀)]` 做**站点级**适配，每个适配器含：

| 字段 | 含义 |
|---|---|
| `lastWord` | **Cookie 名后缀字母**（实测出现 `T` 与 `P`） |
| `flag` | 参与基础数组的站点常量（缺失会直接抛错） |
| `lens` / `encryptLens` | 基础数组长度 / 加密后长度约束 |
| `devUrl` | 站点标识（加密形态） |
| `hasDebug` | 该站是否为「额外 debugger」版本 |

**修正文章口径**（结论的权威出处为 `ruishu-botgate.md` §1.1，此处只给实现侧证据）：文章称「`T`=JS 生成 / `S`=服务端下发」「`O`=服务端 / `P`=JS 生成」。
实现表明**后缀字母是站点适配配置项 `lastWord`**，`T` 与 `P` 出现在不同站点。
→ 结论：**后缀字母只能用于识别「属于哪个适配族」，不能用于推断「谁生成的」**。

同理，文章「Cookie 值首位数字 = 代际」也不可靠：实现的 Cookie 组装是 `'0' + numarr2string(...)`，**首位是常量 `'0'`**，与 4 代样例的 `4a...` 冲突。
→ **禁用「值首位」判据**，改用 `ruishu-botgate.md` §1 的多条件交叉。

## 7. 环境字段的权威清单（来自运行配置）

> **唯一权威源**：`ruishu-botgate.md` §6 / §6.1 是环境字段的**权威清单**（含补法与坑位）。
> 本节只补充「实现侧实际读取的字段路径」这一视角，用于对照自查；字段有冲突时以 §6.1 为准，并回来更新本节。

实现把补环境需要提供的值集中成一份配置，字段名即**目标 JS 实际读取的路径**：

| 字段 | 说明 / 实测值 |
|---|---|
| `window.navigator.maxTouchPoints` | 0 |
| `window.eval.toString().length` | **33** —— 这就是文章里的魔法数字 33 |
| `window.navigator.userAgent` | 经 `uuid()`（CRC-32）参与运算 |
| `window.navigator.platform` | 如 `MacIntel` |
| `window.name` | `$_YWTU=...&$_YVTX=...&vdFm=_$hh` |
| `window.navigator.battery.{charging, chargingTime, dischargingTime, level}` | 文章只提 `getBattery().then`，实现需要 4 个字段 |
| `window.navigator.connection.{downlink, effectiveType, rtt, saveData}` | 另有 `connType`（映射自 `connection.type`）参与匹配 |
| `window.innerHeight` / `innerWidth` / `outerHeight` / `outerWidth` | 4 个都要 |
| `window.document.hidden` | **注意是 `hidden`，不是 `visibilityState`** |
| `codeUid` | 代码特征值，见 §8 |
| `currentTime` / `runTime`(秒) / `startTime`(秒，比 runTime 小 1~2) | 三个时间戳 |
| `random` | 替代 `Math.random` 的注入点（便于复现） |
| `execNumberByTime` | 固定时间内的循环运行次数（实测 1500~2000） |

**与文章环境清单的差异（务必按此修正）**：

1. 需要 `document.hidden`，不只是 `visibilityState`。
2. `navigator.battery` 需要 `charging` / `chargingTime` / `dischargingTime` / `level` 四个字段，不能只返回一个带 `then` 的空对象。
3. `navigator.connection` 需要 4 个标准字段，且 `type` 参与匹配（`bluetooth/cellular/ethernet/wifi/wimax`）。
4. `window.name` 承载 `$_YWTU` / `$_YVTX` / `vdFm`。**代际归属需分清**：6 代实测放 `window.name`（文章 2010081）；5 代是从 `window.localStorage.$_YWTU` 取（文章 1743411）。实现侧用的是 `window.name`。
5. `eval.toString().length` 必须为 33（Chrome 系）；`eval` 被替换后该值会变，属于环境不一致。

## 8. 代码内容参与校验（为什么不能重新格式化）

```js
codeUid = (uuid(主函数体) ^ uuid(主函数体.substr(len * keys[34], len))) & 65535;
// 其中 len = parseInt(主函数体.length / 100)
```

- `codeUid` 由**代码内容本身**派生 → 代码被格式化、重排、增删注释都会改变它。
- 与 `$_ts.jf`（格式校验标志）、文章 2042722「复制时记得恢复成原始单行格式，逻辑中会校验代码格式」、以及实现项目博客《瑞数vmp-代码格式化后无法正常运行原因分析》**三方互证**。
- **落地要求**：VM 代码与内联脚本一律以**原始字节**保存与加载，禁止 linter / 格式化器 / 编辑器自动改写。与本仓库 `AGENTS.md` 的 `.orig` 约定一致。
- 注意：真实样本的 VM 代码**并非严格单行**（实测 5 行，其中 2 行有内容；约 19.5 万字符 / 22 万字节）。
  → 判据是「**与浏览器取到的字节逐字节一致**」，不是「必须一行」。脚本里的 `singleLine` 只能当「疑似被重新格式化」的启发式提示。
