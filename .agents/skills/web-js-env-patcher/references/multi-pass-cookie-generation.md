# 多趟（自举）Cookie 生成：冷启动与热启动

当目标 Cookie 由前端 JS 生成，且**同一份 JS 连续运行两次会得到不同结果**时读取本文件。

典型现象：补环境跑完一遍，`document.cookie` 拿到一个值，但长度明显短于浏览器实际值（例如本地 ~219、浏览器 300+），或服务端返回 400 / 风控页；再跑一遍同一段代码，结果就变了。

配合阅读：`cookie-generation-analysis.md`（Cookie 分类与四层链路）、`ruishu-botgate.md`（实例）、`env-module-levels.md`（Storage 属 Level 2 状态层）、`high-strength-browser-detection.md`（失败排查顺序第 3 条）。

---

## 1. 机制

生成链路存在**自读依赖**：第一趟运行时读到的是空值，于是某些分支不执行或走默认分支，产出的是一份「不完整」的结果；这个结果被写进了 `document.cookie` / `localStorage` / `sessionStorage`；第二趟运行时同样的分支读到的是**第一趟写入的值**，于是追加了额外字段，产出最终被服务端认可的值。

一句话：**Cookie 的一部分内容，其输入是上一趟自己写下的状态。**

这也是为什么很多站「单个 HTML 页面用短 Cookie 就能过，接口却要求长 Cookie」——`load` 事件或接口前置逻辑触发了第二趟，把指纹派生字段追加进去。

## 2. 判据（出现任一即按多趟处理）

| 证据 | 说明 |
|---|---|
| 同一输入连跑两次，输出长度或值不同 | 最强信号 |
| 本地结果长度显著短于浏览器 baseline（且浏览器 baseline 已确认未截断） | 少跑了一趟 |
| 代码中存在「读 Storage / Cookie → 为空则跳过 → 非空则追加」的分支 | 直接证据，见 `ruishu-botgate.md` §4.3 的 `$_fb` / `$_f0` / `$_fh0` / `$_f1` 等 |
| 代码在生成过程中**写回** `document.cookie` / `localStorage` / `sessionStorage` | 自举的前提 |
| 服务端返回 400 / 风控页，但参数结构看起来正确 | 拿到的是第一趟的值 |
| 浏览器基线 Cookie 长度明显大于单趟产物 | 需要预热 |

## 3. 操作范式

### 3.1 两趟法（cold → warm）

```
第 1 趟（冷启动）：用原始空 Storage / 空 Cookie 运行，允许其写入 document.cookie 与 Storage
        ↓ 保留写入结果，不丢弃
第 2 趟（热启动）：复用上一趟的 Storage 与 Cookie 状态，再运行一次
        ↓ 读取这一趟的 document.cookie
交付：第 2 趟结果
```

实现要点：

- **同一进程内连续跑两次**最简单：`document.cookie` 与 Storage 的 stub 保持同一份可变状态即可。
- 若分两次进程运行，必须把第一趟的 Storage / Cookie **序列化持久化**再回灌第二趟，否则等价于冷启动。
- 第一趟的产物**只作为状态输入**，不要作为交付值；但**要留档**，因为它是对照组。

### 3.2 判定「要不要第二趟」而不是「一律跑两趟」

- 先跑一趟，与浏览器 baseline 比对长度与结构。
- 一致 → 单趟即可，不用预热。多跑一趟可能反而引入时间戳漂移，导致与 baseline 不一致。
- 不一致且差值来自 Storage 派生字段 → 上两趟法。
- 差值来自资源过期 / 版本变化 → 走 `dynamic-resource-freshness.md`，不是多趟问题。

### 3.3 趟数上限

瑞数 4 代的「假 Cookie → 真 Cookie」是同一次运行内的两段（不是两次运行），而 5/6 代的 Storage 依赖需要**跨运行**。两者容易混淆：

| 形态 | 特征 | 处理 |
|---|---|---|
| 同运行内两段 | 先写一个中间值到 `document.cookie` / Storage，同一趟稍后再读回 | 只要顺序正确，单趟即可；关键是**不要过早清理中间值** |
| 跨运行自举 | 第二趟读到自己上一趟写的值才能补齐 | 需要两趟法 |

跨运行自举一般**两趟收敛**。若两趟仍不一致，先怀疑是否每趟都在生成新的随机指纹（见 §5），而不是无限加趟。

## 4. 验证

1. **长度与结构**：第 2 趟结果与浏览器 baseline 分段对比（段数、每段长度、分隔方式），不是只看总长度。
2. **一致性**：对第 2 趟结果连跑多次，确认稳定部分一致、动态部分符合预期（时间戳 / 随机数在允许范围内）。
3. **服务端验收**：带该 Cookie 发一次授权范围内的真实请求，200 才算通过（`high-strength-browser-detection.md` 的排查顺序不因此豁免）。
4. **状态可复现**：记录第 1 趟写入的 Storage key 与值来源，确保最终入口能在运行时重新走一遍两趟，而不是把第 1 趟结果硬编码。

## 5. 陷阱

- **不要在最终入口硬编码第一趟的 Storage 值。** 那些值往往由 canvas / WebGL 等指纹派生，硬编码等于把某一次采样的指纹固化，换 baseline 或换设备就失效，且违反「指纹值必须有真实证据」。
- **不要把「指纹随机化」当多趟问题。** 如果每一趟都生成不同指纹，Cookie 永远不稳定；应先按 `fingerprint-value-replay.md` 固定同 baseline 的真实值。
- **不要在趟间清理 Storage / Cookie。** 中间件或 `clean_case` 之类的清理动作会破坏自举前提，调试期要显式排除。
- **不要忽略「为空则不加」的分支语义。** 这类分支决定了数组长度，长度又参与后续运算；把「空」补成任意非空值会得到看似正确但服务端不认的结果。
- **同运行内两段不要为了「更干净」提前删掉中间产物**，比如假 Cookie 或中间 Storage key。

## 6. 输出要求

阶段报告与最终总结至少记录：

- 是否判定为多趟生成，判据是哪一条证据。
- 第 1 趟与第 2 趟的输出长度、SHA-256 与结构差异。
- 第 1 趟写入的 Storage / Cookie key 清单及其来源（指纹 / 时间戳 / 常量）。
- 最终入口是单趟还是两趟，状态如何在运行时重建。
- 与浏览器 baseline 的分段对比结论，以及服务端验收结果。
