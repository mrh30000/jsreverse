# case · 「宣称端到端加密」的实际加密审计

> **抽象自** `52pojie-2089842`（默往聊天 App，宣称 E2EE，实测密钥硬编码 + 明文 JSON）。
> **适用**：目标是**IM / 聊天 / 协作类** App，需要回答"它到底有没有做端到端加密"，
> 而不是"把消息采下来"。同族场景：宣称"隐私保护"的云盘 / 笔记 / 健康类 App。
> **不适用**：目标是还原签名/参数 ⇒ 走 `../../../android-app-reverse/SKILL.md`。

---

## §1 ★★★ 三问定性法（30 秒给结论）

| 问 | 判据 | 本样本实测 |
| --- | --- | --- |
| ① **应用层有没有密钥协商？** | E2EE **必须**在应用层做双方客户端密钥协商（X3DH / MLS / 双棘轮…）。**只有 TLS 不算**（TLS 的握手对象是服务端，服务端本来就能解密） | ❌ 没有任何协商逻辑 |
| ② **应用层加密的密钥从哪来？** | **硬编码在包里** ⇒ 服务端（和任何人）都知道 ⇒ **不是 E2EE** | ❌ 全 App 只有**两个密钥，都写在源码里** |
| ③ **业务数据是明文还是密文？** | 取消息的类里看：是 `json` 明文直接 `send()`，还是先加密 | ❌ **业务数据以 JSON 明文**交给 `WebSocketManager.send()` |

```text
结论口径（源文原话式）：该应用**没有实现任何端到端加密功能**，
却宣传通过端到端加密保护聊天，且 App 内所有聊天顶部均提示"端到端加密"。
```

## §2 取证顺序（可复用）

```text
① 脱壳：拿到 dex（本样本是网易易盾加固；用在线/离线脱壳拿到源 dex 即可，**不必修复**）
② 找传输层：搜 `WebSocket` / `WebSocketManager` ⇒ 确认是 WS 而非自研 TCP
③ 找"应用层加密"的唯一入口：本样本是 `AESHelper`
   ⇒ ★★ 打开它，**只问一个问题：密钥是常量还是协商来的？**
④ 找"取消息"的类：本样本是 `...receive.MakeMsg`
   ⇒ ★★ 打开它，**只问一个问题：业务字段是明文 JSON 还是有加密调用？**
⑤ 找"有没有 E2EE 库"：在 dex / native 库里搜协商协议名
   （`X3DH` / `MLS` / `double ratchet` / `signal` / `libsignal` / `olmlib`）
   ⇒ ★★ **一个都没有 ⇒ 结论已经成立，不用再往下挖**
```

> ★★★ **判据（本 case 最值钱的一条）**：
> **"端到端加密"是可证伪的 —— 只要"密钥硬编码"或"业务数据明文"任一条成立，结论就定死。**
> ⇒ 不要花时间去"还原它的加密算法"，**先回答"密钥从哪来、数据是明是密"这两个是非题。**

## §3 消息发送链（把结论写成可核对的形式）

```text
1. 用户输入消息并点击发送
2. App 把 消息类型 / 发送者 / 接收者 / 内容 序列化为**明文 JSON**，交给 WebSocketManager.send()
3. WS 有 TLS（端到服务端加密）—— 但握手对象就是服务端，服务端能解密
4. AESHelper 是唯一的应用层加密手段 —— **密钥硬编码**，服务端与任何人可解密
5. 经这两层"保护"到达服务端
6. 服务端解掉这两层，看到完整聊天记录
```

> ★★ **写法纪律**：结论要写成**步骤 + 每一步的"谁能解密"**，
> 而不是写"该 App 不安全"（后者不可核对，也不可复现）。

## §4 报告口径与边界

| 该写 | 不该写 |
| --- | --- |
| "应用层无密钥协商；密钥硬编码在 `AESHelper`；业务数据明文 JSON" | "该 App 是骗人的"（情绪化，不可核对） |
| "E2EE 需要满足的三条判据，实测 0/3" | 把"TLS 用了"当成"加密做得好" |
| 结论附**脱壳产物哈希 / 类名 / 方法名**（脱敏后） | 贴出可被直接用于攻击的完整包与账号链 |

> ★ 同族判据：**"声称做了 X" 与 "实际做了 X" 是两件事** ——
> 与 `../../../android-app-reverse/SKILL.md` 铁律三同源（"看到字符串 ≠ 发现算法"）。
