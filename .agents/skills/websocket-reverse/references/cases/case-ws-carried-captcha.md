# 案例：WS 承载的验证码 / 风控挑战（帧分片 + 会话内 key 派生）

> **来源**：`docs/references/52pojie-2038972-v5滑块验证逆向.md`（v5 / verify5 滑块，单源样本）。
> **性质**：单一案例的观察，**不是定律**。可迁移的是"取证顺序"和"结构假设的验证方法"，
> 具体字段名与轮数**换站必须重测**。
> **协议语义归属**：厂商侧的提交参数配方与坑见
> `../../../web-verify-patcher/references/slider-vendor-matrix.md` §3.13；本文件只讲**WS 这一层的取证与拆帧**。

## 一、什么时候该怀疑"挑战走 WS"

任一命中就先按本案例走，**不要在 HTTP 侧反复找加密入口**：

1. 完成一次交互（拖动 / 点击）后，**没有任何 XHR/fetch 请求**，但页面状态确实变了；
2. `list_network_requests` 里有一条 `101 Switching Protocols`，之后长时间保持；
3. 反混淆后看到 `new WebSocket(...)`，且 `onopen` / `onmessage` 就在附近定义；
4. 交互结果（成功/失败、下一张图）通过 `onmessage` 才更新，DOM 上没有对应的响应数据。

> 与 `web-verify-patcher` 的分工：**是不是验证码、哪家厂商、怎么过** ⇒ 那边；
> **消息怎么切帧、连接怎么保活、key 在会话内怎么派生** ⇒ 本文件。

## 二、取证顺序（照做，别跳）

1. `browsercli call list_network_requests` 找到 WS 连接，记下 URL 与建连时刻
   （本技能工具**必须经 `browsercli call <tool>` 调用**，见 `SKILL.md` §browsercli 前置）。
2. `browsercli call create_hook --type websocket`（注入位置、方向、长度都记下来），**先只打方向 + 长度 + 前 64 字符**。
   先拿到"发 N 收 M"的**时序形状**，再动加密 —— 这一步能省掉一半试错。
3. 用 DevTools 的 `onopen` 断点回到源码：WS 相关调用栈通常很浅，**可以直接跳到 `new WebSocket` 那一行**，
   再往下找 `onopen` / `onmessage` 的定义位置（本案例即如此定位到加密函数）。
4. 把手动完成一次成功挑战的**完整消息序列**存成 fixture（方向 + 原始文本），后面所有复现都对它取样。

## 三、拆帧六件事（本案例实测形状）

| # | 观察 | 本案例取值 | 可迁移结论 |
| --- | --- | --- | --- |
| 1 | 消息数守恒 | 一次完整挑战 **发 6 条、收 3 条** | "发 2 收 1 × 3 轮"是一种常见形状；**用轮次边界切分，不要按消息序号硬编码** |
| 2 | 消息头 | 来源只给出**第二轮以 `1\|1\|` 开头**（第一轮的头形态未给） | 头里的字段含义**必须逐轮实测**；`1\|1\|` 只有单源，不要当常量 |
| 3 | 分片 | 待发串按 **1024 字节**切，每片再加头 | 拼回时要**先剥头、再按 1024 累加**；顺序错会得到"长度对但内容错"的密文 |
| 4 | 加密 | **AES-CTR + NoPadding**，输出 `btoa(IV + ciphertext)` | 解密 = `hex[:32]` 当 IV + 余下部分 base64 解码；**IV 是前置的，不在字段里** |
| 5 | key 派生 | `Y(d, h)`：取 token 末字符 `charCode % 2`，按奇/偶下标拆字符串得 key；**第二轮**用第一轮返回值**前 32 位** + token | key 是**会话内滚动的**：把每轮的 key 抄下来存档，别用第一轮的 key 解第二轮 |
| 6 | 新鲜度 | `requestId = "req" + 时间戳`；**过去时间戳必为 false** | 校验带时间窗；复现时时间戳必须当场生成 |

## 四、与 HTTP 挑战的关键差异（复现时要改的思维）

1. **不能重连**：重连会换 token / 换 key，之前算好的所有中间值作废。复现脚本必须在**同一条连接**上跑完三轮。
2. **不能用 HTTP 重放**：即便你把密文一模一样发过去，服务端也不会认（会话状态在 WS 侧）。
3. **收 > 发的分支要考虑**：本案例 6 发 3 收、按"发 2 收 1 × 3 轮"交替；若遇到服务端主动推（心跳、状态变更），
   需要先按 §二.2 的形状把"业务消息"和"保活消息"分开，否则会把心跳当成挑战轮次。
4. **明文里的指纹可以直接写死**（本案例除轨迹外都是浏览器指纹），
   但 `data.l` 之类的 token **必须取当轮返回的值**。

## 五、反例

- ❌ 一上来就逆加密算法（AES-CTR / key 派生），**跳过 §二.2 的时序记录** —— 没有轮次边界，算法对上也无法拼帧。
- ❌ 把 `1|1|` 当成固定消息头常量（单源样本，且来源只说了"第二轮"）。
- ❌ 重连后复用上一轮的 key / token。
- ❌ 只抓 `send` 不抓 `onmessage`：key 是**用返回值派生的**，缺一半就永远解不出下一轮。
- ❌ 把本案例的"6 发 3 收 / 1024 分片 / AES-CTR"当成所有 WS 挑战的通用形状 —— 换站第一步是重新数。
