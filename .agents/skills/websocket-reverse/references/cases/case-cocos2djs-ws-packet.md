# case · Cocos2d-JS 手游：WS 封包的「定长头 + 可选压缩」分层解码

> **抽象自** `52pojie-1784353`（coco2djs 手游封包协议分析 + jsc 文件解密）。
> **适用**：客户端是 **Cocos2d-JS**（`cocos2djs.so` + `*.jsc`）、业务数据走 **WebSocket** 的手游。
> **不适用**：Electron / 桌面打包产物里的 `.jsc` —— 那走 `../../../desktop-client-reverse/SKILL.md`
> （本 case 只借它的「jsc 是 xxtea 还是 V8 字节码」判据，**key 的定位法**在本文 §1）。

---

## §1 ★★ 判据：先判「游戏」这个载体，再判协议

| 现象 | 结论 |
| --- | --- |
| APK 目录里能看到 **`*.jsc`** 文件，`lib/` 下有 **`cocos2djs.so`** | 业务逻辑在 **`jsc`** 里，**不在 Java** |
| 游戏类 App（要频繁更新） | ★ **一般不加固加壳**（源文原话：「因为要频繁更新，所以一般不存在加固加壳的情况」） |
| `charles` 抓到「连接不上服务器」，但 `httpcanary` 能看到流量 | ★★ **换抓包工具**：这类流量是 **WebSocket / 纯 TCP**，Charles 的 HTTP 代理抓不到 |
| 发送包部分明文、接收包**有的明文有的是大段乱码** | ★★ **乱码且数据量大 ⇒ 判断做了压缩传输**（不是加密） |

### §1.1 jsc 解密 key 的定位法（取巧但有效）

```text
① 用 MT 管理器**以十六进制文本**打开 cocos2djs.so
② 搜 ASCII 字符串 "main.js"
③ 紧挨着的形如 0ed68e2d-8b2f-4a… 的串就是 jsc 的解密 key
④ 用 jsc 解密工具（v1.44 一类）：输入 key + 拖入 project.jsc ⇒ 解出 js
⑤ 格式化后按关键词大法搜：ws:// / send / sendmessage / encrypt / encode
```

> ★★ **源文自陈的边界（必须一起登记）**：「上文取巧通过搜索 `main.js` 来直接定位到了 key 的位置。
> **如果做适当的加密混淆可以避免这种情况**，那么就得像上贴大佬的方式去 `ida` 定位 `xxtea`，
> 然后 `frida` 来 hook 关键位置提取 key 值。」
> ⇒ **这条路径是「作者没混淆」的红利，不是通用保证**；拿不到 key 时回退到 `xxtea` + `frida`。

## §2 ★★★ 封包分层：`headerFlag` → 长度 → 模块 → 命令 → 状态

**解码（收包）顺序**（源文原样归纳）：

```text
① 读 4 字节   headerFlag     —— 判断数据是否被压缩；压缩则先 inflate
② 读 4 字节   data length    —— ★ 要做「字节集反转」= 大小端/网络字节序转换
③ 读 1 字节   moduleEnum     —— 模块枚举
④ 读 1 字节   cmdEnum        —— 命令枚举
⑤ 读 2 字节   statusCode     —— 状态码
⑥ 读剩余字节  readBytes      —— 从下个字节到尾部，长度应与 ② 相等 ⇒ 这才是最终数据
```

**编码（发包）**：按**相同逻辑**反向组包，★ **并且要带上 `HashCode`**。

> ★★ **源文判据**：`HashCode` 的用途是「服务器接收到客户端的数据后会根据这个 hashcode
> 来判断数据是否是合法提交」。
> ★★ **实测坑（源文自陈）**：「图上第一个包是发送的包，因为**没有做 hashcode 的判断**，
> 导致**前面多了两个字节、后面丢了两个字节**」⇒
> **判据：解出来的字段长度对不上时，先怀疑「头部的可选字段（hashcode）没有处理」。**

### §2.1 分层顺序为什么是这个顺序（可迁移）

```text
① 先判「是否压缩」   —— 因为压缩是**整体**的，必须先解压才能看内部结构
② 再读「长度」       —— 长度是**变长体的边界**，必须先拿到
③ 最后读「枚举字段」 —— 枚举/状态是**定长**的，放最后最安全
```

> ★ **可迁移判据**：**见到「定长头 + 可选压缩 + 变长体」，处理顺序永远是
> 「压缩标志 → 长度 → 定长字段 → 变长体」**；顺序错了会得到「长度对但内容乱」。
> ★ 同族参照（`../../../protocol-reverse/references/protocol-workflow.md`）：
> 「流缓冲区重组：不要依赖 TCP segment 边界」—— **WS 帧同理，一次 `onmessage` 未必是一个业务包。**

## §3 边界与不适用

| 事项 | 说明 |
| --- | --- |
| 源文样本**未加密、未做序列号** | 源文自陈：「这个游戏只是对数据做了压缩，且**短数据直接没有做处理**，没有做加密或者序列号的处理，不过考虑到游戏类对通讯的低延时要求，不做评价」 |
| **短数据不压缩** | ⇒ 解码器必须**同时支持「压缩」和「不压缩」两条分支**，不能只写一条 |
| 本 case 不覆盖 | 加密帧（AES/ChaCha）、protobuf 载荷、WS 承载验证码 —— 分别见 `case-websocket-protobuf.md`、`case-ws-carried-captcha.md` 与 `../../../protobuf-reverse/SKILL.md` |
