# 03 · 签名与封包：形态库与判据

> **定位**：参数已经定位到了（`sign` / `signature` / `sDjcSign` / `G-Auth-Sign` / `X-Ca-Signature` /
> `newSign` / `x-gorgon` / `ttEncrypt` / `requestTag` …），**接下来它长什么样**。
> 本文件按「**形态**」而不是「平台」组织 —— 同一个平台会换算法，同一套算法会跨平台复用。

## §1 签名串的二十三种拼装形态

**全部来自本批实测**，可直接当候选清单逐条比对：

| # | 形态 | 实测样本 | 关键点 |
| --- | --- | --- | --- |
| 1 | `value1|value2|…|SALT` → MD5 | `1137911`（某大学 App） | ★ **key 先 `Arrays.sort` 再按 key 取 value**；★「开发者自己写的 MD5」**其实就是标准 MD5 32 位**（别因为代码里有自写 `getHexString` 就以为魔改） |
| 2 | `key1=value1&key2=value2…` 按 key 排序 → MD5 | `1749556`（某星充电） | ★ body 侧 `Signature` 是 **H5 加载 js 生成**，不是 native |
| 3 | `SIGN_KEY + concat(所有参数值)` → MD5 | `1915954`（某练通） | ★ 参数值**按声明顺序**直接拼（无分隔符） |
| 4 | `参数名:值` 逐对拼接 → MD5 | `583158` / `676712` | ★ `676712` 的 key 排序用**自定义比较器**；`sign` 自身要排除 |
| 5 | `盐 + Base64(明文)` 后**逐字符排序** → MD5 | `1737837`（洞见者） | ★★ **「排序」这一步极不常见**，`('Xangah6iephe1Zsb' + base64(json)).split('').sort().join('')` |
| 6 | `MD5(deviceId:毫秒时间戳)` **再大写** | `2107752`（饰品交易） | ★ `requestTag` 是**请求头**里的名字，不叫 `sign` |
| 7 | 明文 = `hea + a1 + en + a2 + end` → `md5(明文)`；实际加密串 = `a1 + "-36cd479b6b5-" + a2 + "-36cd479b6b5-" + 该 md5` → **AES-ECB/PKCS7** → hex | `2014961`（zcool 登录） | ★★ **同一次加密里存在"两串"**：一串只喂哈希、另一串才是 AES 原文；两串的**分隔符写死**（`-36cd479b6b5-`） |
| 8 | 参数按 key 排序 → `k=v&…` → **删掉尾部的 `&`** → 拼盐（`v2020global`）→ MD5（**小写**） | `1139448`（mall 登录） | ★ `formatUrlMap(map, 参数2, 参数3)`：**参数 2 = 是否对值做 URL 编码**、**参数 3 = key 是否转小写** —— POST 场景两个都是 `false` |
| 9 | `MD5("ANDROID" + appKey + deviceIdentify)` 当**一次性 token** | `1396064`（抢茅台） | ★ 硬编码串 `"ANDROID"`；★ 落点字段叫 **`reservationToken`**，藏在 `orderAddInfo` 这个 **URL 编码的 JSON** 里（既不是 header、也不是裸 URL 参数）；★ **iOS 与 Android 共用同一套算法**（同文原话） |
| 10 | `固定串 + deviceId + 毫秒时间戳` → MD5 → **大写** | `1452996`（影视邀请） | ★ 那个"固定串"是**DES 解密**出来的产物（不是加密结果）⇒ 在算法助手里**搜不到**，只能靠注入打印；解密实现是 `DESede/CBC/PKCS5Padding`（key 与 `IvParameterSpec` 都来自 `getBytes()`） |
| 11 | `MD5( path + "?" + Uri.decode(排序后 rawQuery) + 盐 )` | `1644568`（听书 `sc`） | ★ 用 `TreeMap` 重排 query；★ 判据：**长度像 md5 就直接搜 `java.security.MessageDigest` / `md5`**，比逐层跟接口快 |
| 12 | `SHA1( 全大写("K=V&K=V&…&<常量>") )`，结果**按 76 字节分段、段间插 `\n`** | `1658810`（某拉雅 `signature`） | ★★ **"全大写"与"分段换行"是两个必须复现的细节**；★ 常量段是 `MOBILE-V1-PRODUCT-<64hex>` |
| 13 | `MD5( 包名 + <APK 签名 SHA256> + 固定串 + 时间戳 )` | `1555004`（加菲猫 `ns`） | ★★ 明文实为 `包名 + "1A06…AC7FA" + "&z4Y!s!2br" + 时间戳`；`<APK 签名 SHA256>` 与 `GetSignatureString()` 的 native 返回值**静态看不出来** ⇒ **动态断点读寄存器**；★ 另一参数 `old_key` 是**阿里 UTDID**（每设备不同，不是常量） |
| 14 | `APP_KEY + formatUrlMap(参数排序拼接)` | `1752032`（某头像 App） | ★ 与形态 8 同族（`formatUrlMap` + 排序 + 尾 `&` 要删）；★ **"盲猜几种方案都不对 ⇒ 去搜 `setParams`/`formatUrlMap` 这类"设置参数"的方法"**（源文的破局动作） |
| 15 | **HMAC-SHA256**（`sign` 为 64 位 hex，jadx 搜 `HmacSha256` 命中） | `1547120`（某生鲜超市） | ★ 同站另有 `eu` / `fv` 两个加密参数需一并还原；★★ 接口有 **5 分钟时效**（服务端检测 `t`）⇒ **时间戳必须同源** |
| 16 | `RSA(密码)`，公钥来自**本地 `SharedPreferences` XML 或响应里的 `rsa_public_key`** | `851229`（3733 平台） | ★ 判据：**抓包里只有密码字段在变** ⇒ 只还原它；★ **公钥既可能在安装目录 XML 里，也可能直接由接口返回**（两条都试） |
| 17 | `AES-CBC/PKCS5` → `toHexString`；或 `AES(data)` + `sign = MD5(排序后 k=v&… + signKey)` | `1163182`（某猫）/ `1915146`（手游 SDK） | ★ 某猫的加密封装在 **`AesEncryptionUtil`** 里（进去一眼看到 `AES/CBC/PKCS5Padding` + `toHexString`）；★ 判据：**字段名太大众（`data`/`sign`）⇒ 改搜"业务常量"**（`productCode` 这类不变量一次命中） |
| 18 | RN bundle（`index.android.bundle`）里的 `fenduan()`：**每80位长度,分割1次** → 逐段 RSA → 拼成 `token` | `1140214`（第 3 饭） | ★★ **"分段长度"是可复现的硬特征**，别当成"整体一次加密"；★ 代码里**同时留了公钥与私钥** ⇒ 本地可直接解密对拍（正常只需公钥，留私钥是作者的破绽） |
| 19 | `HMAC-SHA256(拼接后的请求参数)`，输出 **64 位 hex** | `1542726`（京东到家 `signKeyV1`） | ★★ **「64 位 hex ⇒ 先猜 HMAC-SHA256 / SHA-256」，别先猜魔改**（源文原话：看长度是 64 猜测 sha256）；★★ **so 侧 HMAC 的 hook 锚点**：`HMAC_Init_ex` 的 `args[1]` 是 **key**、`HMAC_Update` 的 `args[1]` 是 **消息**、`hmac_sha256` 是**一步式**封装（源文两套都 hook 了）；★ openssl 符号**未被 strip** ⇒ 可按导出名直接 `Module.findExportByName`（见 `02-native-dynamic-tracing.md` §4.1） |
| 20 | `MD5( 排序后 k=v&… + "&key=" + 固定 key )` → **大写** | `1735462`（什么值得买签到） | ★★★ **三处 hook 分工**（本批最省事的定位范式）：① 入口方法拿 **map + sign**（确认是这个接口）② KeyUtil 拿 **拼在末尾的 key** ③ MD5 类拿 **加密前明文 + 密文**；★ 判据：**搜 `sign` 命中一堆第三方 SDK ⇒ 改看「混淆类名（`e.e.b.a.n.a.a` 式）+ 方法体内出现目标接口参数名」的那一个** |
| 21 | `MD5( 哨兵串 + k1v1k2v2… + 哨兵串 )` → **大写** | `1796265`（汽车之家 iOS） | ★★★ **头尾同一个哨兵串包裹**（`@7U$aPOE@$` 出现在开头**和**结尾各一次）——只拼一遍必然算错；★ **`userpwd = MD5(密码)`、`_sign = MD5(312 字节待签串)`，两个都是裸大写 MD5、无魔改**（先分别对拍再下结论）；★ 定位见 `06-ios-app-reverse.md` §3b |
| 22 | `MD5( 按 key 排序后 "key\|value\|" 逐对拼接 + 固定盐 )` | `1979662`（一卡通） | ★★★ **「排序的是 key 名数组，取 value 用的是 key 在原数组里的下标」**——`strArr3`（key）被 `Arrays.sort`，再用排序后的 key 去 `strArr3`（原序）里找下标取 `strArr2[i]` ⇒ **复现时不能把 `(k,v)` 一起排序**，否则 value 与 key 错配；★ 固定盐硬编码在拼接末尾（`ok15we1****8x5afd@`） |
| 23b | `MD5(明文)` 后**逐字符 `toupper`** ⇒ 32 位**大写** hex | `1715751`（某 App `_sign`） | ★ 定位：**在 `Exports` 搜不到时进 `JNI_OnLoad`**（`VX+XXX` 假指针按 `Y` 修复 + `JNINativeMethod` 表按「参数个数」对齐）；★ 判据：**反汇编里 `toupper` 循环紧跟哈希调用 ⇒ 输出是大写**；★ 详见 `02-native-dynamic-tracing.md` §1.1b |
| 23 | 同一接口**两处 sig**，且两处**密钥相同** | `2114063`（人人网 RR） | ★★ 定位法：对签名函数做**交叉引用** ⇒ 四处调用点里「**实际序列化/传输入口**」那个才是真正发出去的 sig（另一处是本地校验、第四处是通用 `toString()`）；★ **资源混淆（AndResGuard 等）后 `res/values/strings.xml` 被物理删除、合并进 `resources.arsc`** ⇒ Jadx 加载时会**虚拟重建** `strings.xml`，在「资源管理器」里搜 key 名即可拿到明文（见 §1.1） |

> ★★ **判据**：**拼接串里必须显式带分隔符**（`|` / `&` / `:` / `#`）是常态；
> **完全不带的（形态 3）需要靠「长度 + 顺序」对拍**，不要一上来就假设有分隔符。

### §1.1 盐 / key 的三种来源

| 来源 | 现象 | 处置 | 来源 |
| --- | --- | --- | --- |
| **硬编码常量** | 点进去就是字面量 | 直接抄 | `1137911` / `1915954` / `2107752` |
| **native 侧固定串**（被简单变换） | 如 `f34988b = '#'`（分隔符） | 顺着常量找赋值点 | `2060153` |
| **派生表** | `key = table[(~byte) & 0xFF]`（**按位取反后查 256 字节固定表**） | 把表整张抄下来复现 | `2073893` |
| **配置/资源里带出来** | 先解一张加密资源（`.PIC`）→ JSON 里的 `k1..k6` 各管一段 | 走 `06-ios-app-reverse.md` §5「加密资源文件当"密钥字典"」 | `1537322` |
| **混淆资源表**（`resources.arsc`） | `res/values/strings.xml` 被 AndResGuard 之类**物理删除**、常量并入二进制 `resources.arsc` | ★★ **别在 APK 里搜 `strings.xml`**（会搜不到）——用 Jadx 打开 APK，它自动解析 `resources.arsc` 并**虚拟重建** `strings.xml`，在「资源管理器」里搜 key 名即可 | `2114063` |

### §1.2 ★★★ 「两串原文」与「同 key 复用」——两个省时间的判据

```text
判据 A（两串原文）：加密函数体内出现**两次字符串拼接**，且其中一串带 `md5(...)`：
  ⇒ 前者是"给哈希用的"，后者才是"给 AES 用的"。
  ⇒ 复现时**不要只拼一次**。（实测：`2014961`）
```

```text
判据 B（同 key 复用）：请求用某 key 加密；拿同一个 key 去解响应，
  解出来是**可读明文** ⇒ ★★ **直接复用，不要再逆向响应侧**
  （`2014961` 原话："后面解密第一步尝试用相同 key 解密看看，结果就是同一个 key 就直接不逆向了"）。
  ⇒ 这是**成本最低的一次实验**：比读反汇编快，且成功率高。
```

> ★ **反面对照**：`52pojie-1352135`（某东 `jwData`）虽然只是 `DESede/CBC/PKCS5Padding` + 全零 IV，
> 但明文是 `lng + "_" + lat + "_" + networkType + "_null"` —— **先定明文拼法，再定算法**，
> 顺序反了会一直觉得"算法不对"。

### §1.3 参数值的预处理（不是加密，但决定成败）

有些"算不出来"不是算法问题，而是**入参在进加密前被改造过**。实测两类：

| 预处理 | 做法 | 判据 / 陷阱 |
| --- | --- | --- |
| **中文取姓氏首字母** | `getBytes("GB2312")` 取两个字节 → `(b0 << 8 & 0xFF00) + (b1 & 0xFF)` → 与一张 **27 项的区间阈值表**比较 → 落在哪个区间取对应 `A..Z` | ★★ 这是**区间查表，不是 Unicode 映射**；★ 反编译出来的 `int[27]` 常量表**必须程序抽取**（手抄必错） |
| **手机号/身份证按位取子串再查表** | 如 `b[手机号[2]] + b[手机号[5]] + b[手机号[7]]`（从 11 项字母表取） | ★★ **下标是"字符位置的数字"，不是字符本身**；★ 两次取自**两张不同的表**（`a` / `b`） |

> 来源 `52pojie-1138081`（`keystr` 实名认证签名）：整条链是
> `姓首字母 + 手机号查表 + "_" + (pid+6) + 手机号查表2 + 身份证三段子串拼接 + 姓名首字母`
> → `MD5(该串)` → 再拼 `pjjsdsb` → **再 MD5 一次**（**两次 MD5，第二次的输入含第一次的结果**）。

### §1.4 ★ 常见「不是魔改，只是少见的标准算法」

| 算法 | 出现位置判据 | 处置 | 样本 |
| --- | --- | --- | --- |
| **XXTEA** | 代码里出现 `DELTA = -1640531527`（`0x9E3779B9` 的有符号形式）、`UByte.MAX_VALUE = -1`、`52 / (n+1) + 6` 轮数、`MX(...)` 函数 | `fixKey` 把 key **补/截到 16 字节**（`arraycopy`）；`encryptToBase64String` = `Base64(encrypt(...))`；★ **密文长度 = `4*(ceil(明文/4)+1)`** ⇒ 形状是「4 的倍数但**不是** 8 的倍数」（24→28、32→36、51→56），见 `scripts/app_cipher_shape.py shape` | `1530981`（某社区 `params`） |
| **DES-ECB-NoPadding（补齐到 8 倍数）** | `Cipher.getInstance("DES/ECB/NoPadding")`；key 由 `getKey()` **取前 8 字节补齐** | 主体在 native；**base64 后先 strip 空白再 MD5**（`replaceAll("[\\s*\\t\\n\\r]", "")`） | `1778152`（U3D 游戏 `code`） |
| **3DES-CBC + 全零 IV** | `DESede/CBC/PKCS5Padding` + `IV_BYTES = {0,0,0,0,0,0,0,0}` | 直接复现 | `1352135`（某东 `jwData`）；`589291`（合富 `pwd`，key `GDgLwwdK270Qj1w4`） |
| **RSA-NoPadding（明文右侧补 `\0` 到 key 长度）** | `Cipher.getInstance("RSA")` 默认 **NoPadding**，明文长度 = 密钥模长 | ★★ Python `PKCS1_v1_5` **不行**，必须手工：`bytes2int(右补0)` → `encrypt_int(m, e, n)` → `int2bytes(kLen)` → **hex 大写** | `1622354`（酷狗系 `pk`） |

> ★★★ **`RSA/NoPadding` 的复现骨架（Python，源文可跑）**：

```python
import rsa                                    # 需 pip install rsa
from Crypto.PublicKey import RSA
from base64 import b64decode

def zfill_to_keylen(s: str, n: int) -> bytes:  # 不是加密！只是把明文补到模长
    b = s.encode()
    return b + b"\0" * (n - len(b))            # n = rsa.common.byte_size(pubkey.n)

class RsaNoPadding:
    def __init__(self, key_b64): self.pub = RSA.importKey(b64decode(key_b64))
    def encrypt(self, message: str) -> str:
        n = self.pub.n; k = rsa.common.byte_size(n)
        m = rsa.transform.bytes2int(zfill_to_keylen(message, k))
        c = rsa.core.encrypt_int(m, self.pub.e, n)
        return rsa.transform.int2bytes(c, k).hex().upper()
```

> ★ 同文另一条：**`key` 参数不总是随机** —— 那里是
> `MD5(AppId + AppKey + APPVersion + str(clienttime_ms).lower())`，
> 属于 **"多个常量 + 一个时间戳" 型 key**；**先把 key 的生成式定下来，再算 t1/t2**。

## §2 ★★★ 多层嵌套：「会话密钥 + 公钥包裹」是主形态

### §2.1 四种实测嵌套（同一族）

| 形态 | 结构 | 样本 |
| --- | --- | --- |
| A | `b(RSA(AES(明文, key)))` | `1897636`（`sDjcSign`） |
| B | `3DES(sessionKey, payload)` + `RSA(pubKey, sessionKey)` ⇒ 组包 `data=&key=&timestamp=` | `2047651`（海外运营商） |
| C | `part1|part2|part3` = `RSA(key)` \| `AES-CBC(data)` \| `Base64(MD5(data))` | `2070898`（南银消金） |
| D | `sk = RSA(pub, 随机 AES key)` 放请求头；body = `AES(明文, 该 key)`；响应 = `AES(RSA⁻¹(sk))` | `2107752`（饰品交易） |

> ★★★ **共同骨架**：**每次请求随机生成一个对称密钥 → 用对称算法加密业务数据 → 用服务端公钥把
> 对称密钥加密后随包上传 → 服务端用私钥解出对称密钥再解数据。**
> ⇒ 见到「**同一个请求里既有超长 base64（RSA）又有 16 对齐的密文（AES）**」，
> 直接按这个骨架去对号入座。

### §2.2 ★★★ 「key/iv 是随机的 ⇒ 它必然要被上传」

**来源** `52pojie-2070898`。原文结论：

```text
part1：rsa(key)
part2：aes(data)
part3：base64(md5(data))
```

> ★★★ **判据链**：`iv = key 的前 16 字节`（**iv 是 key 的一半**）。
> 为什么 iv 不单独传？—— **因为 key 已经通过 `part1`（RSA）上传了，iv 就不需要随机**。
> ⇒ **「当你发现 key 或 iv 在随机，就要注意它的传递方式」**（原话）。
> ⇒ 反过来说：**若 key/iv 硬编码，通常就不需要上传**。

### §2.3 请求与响应可以不对称

`52pojie-2047651`：**请求体全加密，响应体是明文**（`arg[1]: [response={"errorCode":-304,...}]`）。
⇒ ★★ **判据**：**先分别判「请求要不要还原」和「响应要不要还原」**，别默认双向。
`52pojie-2070898`：响应体是 **Java 层**（先做简单的），请求体是 **native**（后做难的）。

### §2.4 `Cipher.init` 的模式数字

`cipher.init(1, key)` = **加密模式**；`cipher.init(2, key)` = **解密模式**（`2107752` 原话点明）。
★ 同文：`sg.a.h()` 返回 **RSA 公钥**（**`MIIBIj` 开头是 X.509 公钥格式的固定标识**），
`sg.a.g()` 返回**客户端硬编码的 RSA 私钥**（用于解响应）
⇒ ★★ **「加密用服务端公钥，解密用客户端私钥」**，两边不是同一个密钥。

## §3 魔改算法的识别

**判据统一是**：**先用标准实现跑一遍同一份输入，diff 一下；不一致再去找「改了哪一处」。**

| 魔改对象 | 判据 / 改了什么 | 样本 |
| --- | --- | --- |
| **RC4** | 标准 RC4 加解密对称，但这里**对输出字节再做一轮变换** ⇒ **标准 RC4 解不出来，必须先做字节反变换** | `2107248` |
| **「RC4」（S 盒长度 128）** | 初始化得到**128 长度的数组**再运算 ⇒ **非标准 RC4（标准 S 盒是 256）** | `2060153` |

| **MD5（声称自写）** | ★ 实测就是**标准 MD5 32 位** —— 别被「自写 `getHexString`」骗 | `1137911` |

> ★★ **顺序纪律**：**先证「它是标准的」，再证「它改了什么」。**
> 反例：`2073103` 先用标准 DES 加密，**结果完全不同**（但**位数一样**）⇒
> 才去逐张表比对，最终定位到「位序反转」这一处。
> ★ 配套判据（同文）：**判断 `ECB` vs `CBC` 的零成本实验** ——
> **修改明文入参，看相同明文块是否得到相同密文块**：一致 = ECB，不一致 = CBC。

### §3.1 ★★★ 魔改 MD5 的逐层识别法（一份可直接照抄的检查清单）

**来源** `52pojie-2073532`（明文 `1651480960074` → 密文 `76B5CEBECD2484F78CDF7A468C133EFB`）。
**它是本批唯一一篇「把标准算法改了什么」讲全的**，检查顺序可直接迁移到任何「标准算法魔改」题：

| # | 检查点 | 标准 | 实测 | 判据 |
| --- | --- | --- | --- | --- |
| 1 | **初始化常量** | `a,b,c,d = 0x67452301, 0xEFCDAB89, 0x98BADCFE, 0x10325476` | 四个数**一个没变**，但**赋值顺序被换**：`a=0x67452301, b=0x10325476, c=0x98BADCFE, d=0xEFCDAB89` | ★★★ **「常量没改、顺序改了」是最隐蔽的一类** —— 只比数值会得出「没魔改」的错误结论 |
| 2 | **F 函数** | `F(x,y,z) = (x & y) \| (~x & z)` | `(v9 & v14 \| v12 & ~v9)` | ★★ **按结构形状对位**：形状相同 ⇒ `v9=b, v14=c, v12=d`，剩下那个就是 `a`。**不靠变量名，靠形状** |
| 3 | **k 表** | `0xd76aa478` | `0x8A51407D` | 常量表逐项 diff |
| 4 | **`FF` 宏末尾加谁** | `a += b` | `md5_a = md5_d + v15` | ★★ **加数从 `b` 换成了 `d`** —— 这是第 2 个魔改点，也是**第一轮对不上的真因** |
| 5 | **移位方向** | `ROTATE_LEFT(a, 7)` | `__ROR4__(x, 25)` | ★★ **`ROR(x, 25)` ≡ `ROL(x, 7)`** —— C 里没有循环左移，编译后就是右移 `32-7`。**别因为看到 `ROR` 就以为移位被改了** |

**动作顺序（源文原样）**：

```text
① 用 unidbg 把流程跑起来（本样本**不需要补环境**，直接跑）
② 手边准备一份**标准源码**，逐轮对照
③ 每定位一个魔改点，就在本地同步改一处，然后与 unidbg 的 hook 值对拍
④ 对不上就继续找 —— 源文实测：改完 k 表后 unidbg 得 559a829a、本地得 75ff2b87
   ⇒ **不一致 ⇒ 还有魔改点**（最终定位到第 4 行的 `+d`）
```

> ★★ **读指针要按类型换算字节偏移**：`*(v10 - 3)` 中 `v10` 是 `int*` ⇒ **减 12 字节**；
> `*(v11 - 4)` ⇒ **减 16 字节**（源文 hook 时正是这么读的）。

### §3.2 非标 base64 的通用处置

> ★ 见到「解码报错 / 长度对不上 / 尾部字符怪」，**先把字符表打印出来**：
> 逐个字符的码点与标准表 `A-Za-z0-9+/=` 比对，差异通常只有 1~3 个字符。

### §5.1 ★★ 双段凭证：`密文 , 校验和`（二维码 / 支付码族）

**来源** `52pojie-1979662`（校园一卡通 APP 的付款二维码）。

```text
QRCODE = DES3(明文) + "," + eqLength(明文)
                     │
                     └─ 自定义 CRC-16：取一张 **256 项 int 常量表**，
                        逐字节 `crc = table[(crc >> 8) ^ b & 0xFF] ^ (crc << 8)`，最后 `& 0xFFFF`
                        （与标准 CRC-16/CCITT 同形但**表是站点私有的**，必须程序抽取）
```

> ★★ **可迁移判据**：
> ① **"一段 base64/hex + 一个十进制短数字"** 是凭证类字段的典型形态 ——
> **短数字通常是"校验和"**，用来让扫码方在解密前**先验完整性**（`eqLength` 名字即"相等长度"）；
> ② **24 字节的 DES 密钥是"拼"出来的**：本例 `bArr2[0:16] = bArr[0:16]`、`bArr2[16:24] = bArr[0:8]`
> —— **前 8 字节被复用**，别看长度 16/24 两头对不上就以为读错了；
> ③ 密钥材料的构造里出现 `& 0xFF / & 0xFFFF / >> 8 / ~` 的**逐位拼装**时，
> **整段抄进脚本跑一遍拿真实值**，不要"心算推导"（本例源文就因为 `AuthNum` 取值搞错而返工一次）。
> ★ 同文另一条：**"函数名会骗人"** —— 源文按 `GetQRCode` 找了半天，
> 结果抓到的是**扫码**函数（真实节点里写的是 `Scan`）⇒ **靠交叉引用找"另一处同名调用"才是生成侧**。

## §7 复现与验收纪律

| 纪律 | 说明 | 来源 |
| --- | --- | --- |
| **长度一致 ≠ 正确** | 必须**发包验证**（服务端返回成功才算） | `1897636` |
| **对拍要固定 key/iv/明文** | 与浏览器/App 密文**逐字节 diff** 是最终判据 | 台账 B1 已立 |
| **复现时不要照抄「假循环」** | 源文里 `for (s=0; s<e.length; s++) { t = encrypt(password); }` —— **循环变量没进实参** ⇒ 每轮算同一个输入、取最后一次 ⇒ ① 复现别抄这个循环 ② 对拍**不要拿「密文是否相等」当判据**（RSA PKCS#1 v1.5 填充带随机，8 次结果互不相同） | 台账 B37 已立 |
| **公钥能对拍 ≠ 这就是最终待提交值** | 断点位置不是生效路径时要**换关键词重搜** | 台账 B37 已立 |
