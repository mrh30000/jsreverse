## §1 ★★★ 同一连接里的「多 magic 分派」

**来源** `52pojie-1807699`（摄像头 P2P 协议）。命令通道与媒体通道**共用一条 UDP 连接**，
于是同一个连接里**并存四种 magic，各自一套结构**：

| magic（wire 字节） | 结构 | 用途 |
| --- | --- | --- |
| `3a cf 87 2a` | `magic[4] + data_size[4] + unknown[4] + **transmission_id[4]（=key）** + crc32[4] + payload[n]` | 控制/加解密数据 |
| `10 cf 87 2a` | `magic[4] + connection_id[4] + unknown[4] + packet_id[4] + payload_size[4] + payload[n]` | 分片封装 |
| `f0 de bc 0a` | `magic[4] + message_id[4] + message_length[4] + **encryption_offset[4]** + flag[2] + class[2] + payload[n]` | 业务消息 |
| `30 30 64 63` / `30 31 64 63` / `30 35 77 62` | I 帧 / P 帧 / AAC 各自的头 | 媒体帧（**不加密**） |

**动作顺序**：

```text
① 先按 magic 把抓到的包**分桶**（不要按"时间顺序"读，会来回跳）
② 每个 magic 单独切：长度字段位置、固定字段、是否有 key/offset 字段
③ 再把"同一连接里 magic 之间的封装关系"画出来（10cf 包着 f0de，f0de 里又是业务）
④ 最后才动算法
```

> ★★★ **判据**：**「同一个 key 换了 magic 就不管用」是常态，不是你的实现错了。**
> 源文实测：拿 `3acf872a` 的 `connection_id` 当 key 去解 `10cf872a` 的载荷 —— **失败**；
> `10cf872a` 的载荷是 `f0debc0a` 的**外层容器**，它自己那套是另一个 key 来源。
> ⇒ **遇到"换个 magic 就不对"，先停下来确认"这个 magic 是不是另一个 magic 的容器"。**

### §1.1 媒体 magic 与「不加密」判据

`I 帧 0x30 0x30 0x64 0x63` / `P 帧 0x30 0x31 0x64 0x63` / `AAC 0x30 0x35 0x77 0x62`
是**明文头 + 裸媒体数据**（H.264/H.265 的 NALU、AAC 帧）。

> ★★ **判据**：抓到"大段数据 + 头两字节是 `0x30 0x3X`"时，
> **先试 `ffmpeg` 能不能直接吃**（`copy` 进 `.h264` / `.aac`）——
> 能吃 ⇒ 媒体层没加密，**不要在这里耗**（把时间留给控制通道）。

## §2 ★★ SIMD（NEON）批量异或的翻译法

`52pojie-1807699` 的 `p2p_encrypt_and_decrypt` 伪码长这样：

```c
v3 = vdupq_n_s32(a3);                          // 把 key 复制成 4 个 int32
v9.n128_u64[0] = 0x5A6C7F8D1F2D3C4BLL;         // 128 位常量，拆成 2 个 u64
v9.n128_u64[1] = 0x8271635A38172E4BLL;
v4 = vaddq_s32(v9, v3);                        // 逐元素相加（key 参与"轮换"）
...
for (v6 = 0; v6 < v7; v6++)
    a1[4*v6] ^= v9.n128_u32[v6 & 7];           // 8 个 int32 循环异或
```

**翻译三步（照抄即可）**：

```text
① `vdupq_n_s32(x)` ⇒ `np.full(4, x, dtype=np.int32)`
② `.n128_u64[0]` / `[1]` 是**一个 128 位量的低 64 位 / 高 64 位**；
   **按小端拆成 4 个 int32**：
     0x5A6C7F8D1F2D3C4B ⇒ [0x1F2D3C4B, 0x5A6C7F8D]
     0x8271635A38172E4B ⇒ [0x38172E4B, 0x8271635A]
   ⇒ v9 = [0x1F2D3C4B, 0x5A6C7F8D, 0x38172E4B, 0x8271635A]
③ `vaddq_s32` ⇒ `[a+b for a,b in zip(...)]`；`^=` 逐 4 字节块异或，
   索引用 `v6 & 7` ⇒ **8 个 int32 循环**（不是 4 个，别只看 128 位就以为 4）
```

> ★★ **判据**：反汇编里出现 `vdupq_n_*` / `vaddq_s32` / `vld1q` / **`0x...LL` 大常量** ⇒ 就是 NEON。
> **不要试图读懂每一条 SIMD 指令**，直接按上面的表翻译成 numpy，再用**一组固定输入对拍**。
> ★ **长度补齐**：`(4 - (len % 4)) % 4` 补 0 到 4 的倍数再按 4 字节切（源文实现细节）。

## §3 ★★★ 连续流压缩（zstd-stream）—— 不能每帧重置

**来源** `52pojie-2119947`（Discord Gateway，`?compress=zstd-stream`）。
Server→Client 的**所有二进制帧拼起来是一个 zstd 流**，不是独立帧。

| 坑 | 表现 | 处置 |
| --- | --- | --- |
| **用单帧 API** | `ZSTD_decompressDCtx` 能解出**第一帧**（`OP10 HELLO`），**后续帧全是乱码** | 改用流式：`ZSTD_createDStream` → `ZSTD_initDStream` → `ZSTD_decompressStream`（循环喂） |
| **每帧都 reset** | 解完一帧就 `ZSTD_initDStream` 重置 ⇒ 后面的帧全乱 | **只在流创建时初始化一次**，帧之间**不 reset** |
| **Client→Server 也压缩** | 服务端回 `CLOSE code=4002`（`Error while decoding payload`）；换 `ZSTD_compressCCtx` / `compressStream2 + e_end` / 各种 level **全部 4002** | ★★ **改用 TEXT 帧（不压缩）发送** —— 服务端接受。**不要继续试压缩参数** |

> ★★★ **可迁移判据**：**"前几帧能解、后面全乱" + "每帧独立解压失败" ⇒ 99% 是连续流，不是加密。**
> 反过来：**"客户端发压缩包被拒" 时，第一选择是"客户端干脆不压缩"**
> （很多协议的压缩是**单方向协商**的）。
> ★ 同族记法：`permessage-deflate`（WS 扩展）也是同一个坑家族。

## §4 ★★ 双 TLS 栈 ⇒ MITM 抓不到一部分请求

**来源** `52pojie-2119947`（Discord Android）实测：

| 通道 | TLS 实现 | 是否走系统代理 / 信任用户 CA |
| --- | --- | --- |
| REST API（HTTPS） | **Rust `rustls`**（在 `liblibdiscore-rn-jsi-module.so`） | ❌ **不使用系统证书** ⇒ Charles/Fiddler **抓不到** |
| WebSocket（WSS） | **Java `OkHttp`** | ✅ 走系统代理 ⇒ 能抓到 |

> ★★★ **判据**：**同一个 App，一部分请求能抓、一部分抓不到** ⇒ 先怀疑**是不是两套 TLS 栈**
> （常见组合：Rust `rustls` / Go `crypto/tls` / BoringSSL 静态链接 / 自实现）。
> ★ **处置**：**别在 MITM 上继续折腾，改 hook 底层函数**
> （`SSL_write` / `SSL_read` / `BoringSSL` 的 `SSL_*`，或干脆 hook 应用层的
> `WebSocket.send` / `setHTTPBody:`）。等价判据见 `../../android-app-reverse/references/06-ios-app-reverse.md` §3。

## §5 TLV 结构的"固定字段表"读法

**来源** `52pojie-825868` / `52pojie-634074`（PC QQ 协议）。这类老协议的特征是
**大量 `00 XX 00 YY` 形态的 TLV**，且**字段长度写死在表里**。

```text
02                    ← 包头（TX 系列固定 0x02）
36 61 / 36 43         ← 版本（QQ8.6 / QQ8.1）
08 25 / 08 36         ← 命令（一次登录 / 二次登录）
7A 4D / 5C E1         ← 包序号（★ 随机即可，服务端不校验）
6A 4E AC D5           ← QQ 号（HEX，4 字节）
03 00 00 00 01 01 01 00 00 67 FD 00 00 00 00   ← 固定结构（dwClientType / dwPubNo_Ver / 0）
...
00 19 <25 字节 publickey>   ← 长度前缀 + 公钥
00 00 00 10 <16 字节 key>   ← 长度前缀 + 随机 key
<密文…>
03                    ← 包尾
```

> ★★ **读法纪律**：
> ① **先找出"长度前缀"的格式**（1 字节 / 2 字节、含不含自己）—— 这类协议里**同一包里可能混用**；
> ② **`03` 包尾 / `02` 包头**是廉价的**切片锚点**，用它把流切开再逐字段编号；
> ③ **把"固定内容"整段抄成常量表**，不要逐字段猜语义（`fix1`/`fix2`/`fix3` 这种命名是完全可接受的）。

### §5.1 ★★ 「字节集反转 = 大小端/网络序」

**来源** `52pojie-1784353`（Cocos2d-JS 手游封包，同族记法）。

```text
4 字节 headerFlag（判是否压缩 → zlib inflate）
4 字节长度        ← ★★ **字节集反转**才是真长度（大小端 / 网络序）
1 字节 moduleEnum
1 字节 cmdEnum
2 字节 statusCode
余下 readBytes
```

> ★★ **判据**：长度字段解出来**大得离谱或不自洽**时，**先试反转 4 字节**，再怀疑别的。
> ★ 同文另一条：**发送包必须带 `HashCode`**，否则服务端表现为
> 「**前面多两个字节、后面丢两个字节**」—— 这种"错位但长度对"的报错，往往就是**少了个校验字段**。

## §6 校验字段：CRC32 存的是"密文"还是"明文"

`52pojie-1807699`：`3acf872a` 结构里第 5 个字段是 **加密后数据的 CRC32**（源文由
`p2p_calc_crc` hook 确认）。`52pojie-634074`：`00 14 <16 字节随机> <4 字节 crc32>`。

> ★★ **判据**：**"CRC 不匹配"时不要立刻怀疑 CRC 算法**，先分别算**明文 CRC** 与 **密文 CRC** 各一次 ——
> 这类协议里两种都有实测样本。**先判"对谁算"，再判"用什么算"。**

## §7 定位手段：PC 端调试器（frida 对多线程失效时的替代）

**来源** `52pojie-1807699`。源文原话：「**Frida 大法暂时失效了，无法应对多线程**，
打印堆栈只有一些不痛不痒的东西」⇒ 转 PC 版：

```text
① 找同款 App 的 **PC 客户端**，`x64dbg` 附加
② 在 `recvfrom` 下**条件断点**：条件 = `buf` 开头等于目标 magic（如 `F0 DE BC 0A`）
③ 断下后看**调用堆栈** ⇒ 拿模块名 + 偏移
④ IDA 加载该 dll，**先把 IDA 基址改成 x64dbg 里的基址**，再跳同一个地址 F5
```

> ★★ **可迁移判据**：**移动端多线程 + hook 打不出堆栈时，"换 PC 端 + 系统调用条件断点"是低成本路线**
> （同一 App 的 PC 版通常**共用同一套协议与算法实现**）。
> ★ 配套坑：**x64dbg 里"快速找到相关线程"没有捷径**（源文自陈只能逐个地址去 IDA 里看）——
> **用条件断点把范围先收窄**，比找线程技巧更划算。

## §8 ★ 地址池 / 抗封禁结构（恶意 App 常见）

**来源** `52pojie-1916453`（诈骗 App 网络行为分析）。结构：

```text
① 把服务地址池存到**云存储**（此处是 `aliyuncs.com` 上的阿里云 OSS）—— 抗 DDoS、也**抗拦截**
② 从地址池取节点 → 再连真实业务接口
③ 地址池响应体**是加密的**（源文为 **AES-ECB**，无 IV）
④ 明文短、结构简单（就是一堆 URL）
```

> ★ **分派判据（源文原话）**：代码里对 **`aliyuncs.com`** 与 **非 `aliyuncs.com`** 走**两条不同分支**
> （`m1458f0` / `m1457g0`）—— 前者是 OSS 地址池、后者才是业务接口。
> 看到"按域名分派 + 其中一支是对象存储域名"，优先按本结构读。

> ★★ **判据**：**"同一个域名下请求返回一堆其它域名"** + **响应体是密文** ⇒ 按"地址池"读，
> **先解外层，再解业务**。
> ★★ 安全侧价值（源文原话）：**拦截要打在"节点"上，不是打在首页域名上**；
> 从恶意软件角度看，这种分发就是**为了躲避拦截**。

## §9 坑表

| 坑 | 表现 | 处置 |
| --- | --- | --- |
| 换 magic 就不对 | 拿 A 的 key 解 B 的载荷失败 | 先判"B 是不是 A 的容器"（§1） |
| 媒体数据当业务数据 | 在 I/P 帧上耗时间 | 先 `ffmpeg` 试吃（§1.1） |
| 前几帧能解、后面乱 | 以为加了密 | 连续流压缩（§3） |
| 每帧 init 一次 | 同上 | 只在创建时 init（§3） |
| 客户端压缩被服务端拒 | `4002` / 解压错误 | 客户端改不压缩（§3） |
| 一部分请求抓不到 | 以为 App 有反代理 | 双 TLS 栈（§4） |
| 长度字段不自洽 | 解出来过大 / 偏移全是错的 | 试 **4 字节反转**（§5.1） |
| 长度对但状态错 | "前多两字节后丢两字节" | 少一个校验字段（§5.1 `HashCode`） |
| CRC 对不上 | 以为 CRC 算法被改 | 分别算明文 / 密文 CRC（§6） |
| 参数块里的端口当成服务端口 | 构造出"长度对、状态错"的请求 | **端口是参数，不是连接目标**（`protocol-workflow.md` 已立） |
