# 私有二进制封包族：长度前缀 · 密钥变换 · 会话换钥 · 资源体加密

> **定位**：客户端（尤其**游戏/工具类 PC 与移动端**）自己写的 TCP 二进制协议。
> 前置：`protocol-workflow.md`（FourCC 小端立即数 / 流缓冲重组 / 单变量差分 / 端口混用）；
> `multi-magic-and-compression.md`（多 magic 分派 / NEON 异或 / 连续流压缩 / 双 TLS 栈）。
> 本文件补的是**前三本都没覆盖的那一层**：**封包头的"偏移/排序"语义**、**密钥的变换与会话中换钥**、
> **资源体（非流量）自身的加密**。
> 载荷是 protobuf ⇒ 转 `../../protobuf-reverse/SKILL.md`。

## §1 ★★★ 长度前缀是**唯一**允许明文的那一段

**来源** `52pojie-1468888`（赛尔号 Flash 客户端，源文原话）：

> 「因为封包长度的设定，本来就是为了从没有"分界线"的数据流中提取出封包来。
> **如果封包长度也加密了，那么两条加密封包之间没有明显的分界线**，我们无法提取这两条封包。」

⇒ **判据（可直接迁移到任何自研 TCP 协议）**：

```text
① 密文流里「长度字段明文、其余全密」是**设计上必然**的结果，不是作者偷懒；
② 因此"加密后长度 = 明文长度 + N"（赛尔号 N = 1）里，
   那个 N 的错位**永远作用在长度字段之后**；
③ 拿到第一段密文后，先猜「前 4 字节明文长度」去切，再谈解密。
```

> ★★ **反面对照**：`52pojie-1784353`（Cocos2d-JS）里长度字段**也被变换过**
> （字节集反转），但**仍然是明文的**（未加密）—— 所以"长度字段能不能用"与"它是不是明文"是两件事，
> 见 `multi-magic-and-compression.md` §5.1。

### §1.1 密文长度 ≠ 明文长度：错位量要先测出来

| 样本 | 关系 | 说明 |
| --- | --- | --- |
| `52pojie-1468888` 赛尔号 | 密文 = 明文 + **1** | 长度字段**不含**头，故偏移只影响头之后 |
| `52pojie-2057659` 修仙肉鸽 | **发送** `[len:2][cmd:2][body]`；**接收** `[len:4][cmd:2][body]` | ★★ **收发两侧长度字段宽度可以不同**（源码里 `PackSendHeaderLength` / `PackRecvHeaderLength` 是两个常量） |

> ★★★ **纪律**：**先分别量"发送"与"接收"两侧的头长度**，不要假设对称。
> 源文实测：`dataLength = totalLength - PackRecvHeaderLength`，把这两个常量当成两个独立参数处理。

## §2 ★★★ 密钥的三种变换形态

### §2.1 「传输密钥 + 偏移 再异或常量」——老国产客户端最经典的写法

**来源** `52pojie-292460` + `52pojie-522759`（飘零商业 4.0，2014 年的易语言程序，源文原话）：

> 「飘零的封包解密是跟他的传输密钥有关，**通过取传输密钥 +1 后与 4 异或**，
> 再用**分割出来的封包内容**异或，得到明文封包。」

```text
key_bytes   = 传输密钥（运行时从程序里读出，如 {1,9,9,3,0,5,1,6}）
derived[i]  = (key_bytes[i] + 1) ^ 4          # ← 关键变换，不是直接拿 key 用
plain[j]    = cipher[j] ^ derived[j % len]    # 逐字节循环异或
```

> ★★★ **判据**：**"密文与明文逐字节异或出来的键值，正好等于某个固定串的逐字节 +1 再 ^4"**
> ⇒ 你已经同时拿到了密钥与变换式。**别急着找"是不是 AES"**：这一代客户端的"加密"绝大多数是
> **逐字节异或 + 一层常量变换**。
> ★ **`+1` / `^4` 这类常量是**站点私有**的** —— 每个软件都不一样，**必须从汇编里读出来**（§4.1）。

### §2.2 ★★★ 会话中换钥：从「某个封包的最后 N 字节」派生

**来源** `52pojie-1468888`（赛尔号）。默认密钥是**硬编码在客户端 SWF 里**的
`!crAckmE4nOthIng:-)`（**命令号 < 1000 的封包甚至直接明文**，因为登录前 `RobotCoreDLL.swf` 还没加载）；
**收到 `LOGIN_IN` 封包后密钥被换掉**：

```text
seed   = LOGIN_IN 封包**明文的最后 4 字节**（按 uint 小端读）
mixed  = seed ^ 米米号                      # 与当前登录用户 ID 异或
newKey = MD5(str(mixed))[0:10]              # 取 md5 的**前 10 个字节**
# 源文另有一层"星号包裹"（setEncryptKeyStringArr 会把每字符前后加 '*'），
# 去掉所有 '*' 后剩下的才是密钥 —— 这是**防字符串搜索**的混淆，不是算法的一部分。
```

> ★★★ **两条可迁移判据**：
> ① **"默认密钥能解前几个包、之后全解不开" ⇒ 一定发生了换钥**，不是你的实现错了；
> ② **"种子是最后一次被读取的字段"** —— 源文用「如无必要，勿增实体」推：
> 该字段**之后再没被用到** ⇒ 极大概率就是**封包尾部的定长字段**。
> **先按"尾部 4 字节"试，命中率很高**，不必把整个 `readxxx()` 序列模拟一遍。

### §2.3 密钥来自**资源名**（非流量层）

**来源** `52pojie-2057659`（Unity + XLua 手游）。`assets/AssetBundles` 下的 `.assetpkg`
**头部没有 `UnityFS` 签名**（说明被整体加密），解密函数是：

```c
// 还原自 IDA：密钥竟然是 AssetBundle 的文件名
decrypted = AssetBundleManager.Decryption(encryptedData, webRequester.assetBundleName);
// 实现 = encrypted[i] ^ keyBytes[i % keyLen]，keyBytes = name.encode('utf-8')
```

> ★★ **判据**：**"文件头不是已知 magic + 数据分布看起来随机"** ⇒ 先试
> **"用文件名/路径名当循环异或密钥"**（Unity 系手游里反复出现）。
> **零成本验证**：解出来 `startswith(b'UnityFS')` 即命中。
> ★ 拿不到文件名时：先 hook `AssetBundleManager.LoadAssetAsync`（或等价物）
> **打印「逻辑资源路径 → 物理文件名」映射**（源文实测映射形如
> `luagame.assetpkg -> cced8de1b361f40750fbbfcd0e046241.assetpkg`）。

## §3 ★★ 封包头里的「偏移 / 排序」语义（不要当成流水账）

### §3.1 封包头存的是「本包自身各段的偏移」

**来源** `52pojie-413044`（石器时代 8.0，源文按 `封包头 → 封包加密段 → 封包正文` 三段拆）：

```text
封包头  ：**前 6 字节存「封包自身的偏移数据」**，且这 6 字节本身参与加密/解密
封包加密段：偏移 + **排序封包段**（不是顺序读，而是按偏移重排后再读）
封包正文：一级加密（另有 key0 加密方式把 001832b8 段搬到 001732c0）
```

> ★★ **判据**：**"同一逻辑字段在不同样本里的字节顺序会变" ⇒ 包内存在"排列/索引表"**，
> 不要按出现顺序直读 —— 先找那张表。

### §3.2 逐字段标注法：`长度前缀 + 数据` + 固定分隔

**来源** `52pojie-735209`（多玩歪歪登录协议，源文的读法值得照抄）：

```text
62 00 00 00   ← 数据长度（4 字节小端 = 0x62）
1E 73 00 00   ← 标识 / 序号
C8 00         ← 固定 200（应答码，非长度）
FF FF FF FF   ← 分割固定
FF FF FF FF   ← 分割固定
...
20 00         ← 接下来这段（StrMid）长度 = 0x20
64 37 35 39 64 33 64 36 32 30 65 62 38 32 63 35 37 30 37 62 66 34 30 30 31 65 61 36 39 34 35 35   ← 32 字节
00 00 50 82   ← "StrMid 后面四个就是 nVer"
08 00         ← StrVer 长度 = 8
38 2E 33 37 2E 30 2E 30
02 00         ← 长度 = 2
79 79         ← "yy"
```

> ★★ **纪律**：**"长度前缀 + 数据"要按"上一层长度 - 已读"自减**，
> 并把**每个定长块都标上"前面几个字节是它自己的长度"**；
> **固定串（`FF FF FF FF` / `C8 00`）是廉价的切片锚点**，先用它们把包切成段再逐段编号。
> ★ 响应里的**列表结构**要写成"**个数 + 每条 (长度前缀 + 数据 + 尾部定长)**"：
> 本例是 `IP 个数=6` → 每条 = `IP长度(=0x0F) + IP字符串 + 4 字节 + 端口数量(=2) + 端口(2 字节小端)`，
> 端口 `5B 00` = 91、`9B 1F` = 8091 ⇒ **同一服务的高低两端口**（注意 `9B 1F` 是 8091 的**小端**）。

## §4 定位手段

### §4.1 「倒着逆」：从结果倒推，别顺着读汇编

**来源** `52pojie-522759`（源文原话，**这是本批最值得抄的一句方法论**）：

> 「因为上面两段的循环搞得我头脑比较混乱，有一个循环之前我不知道他在干什么，
> **但是我从结果开始往上推算**，可以轻松的发现上面的循环，**只不过是得出一个相应的解密表罢了**！
> 所以很多时候，追算法的时候，如果没什么头绪的话，**可以倒着逆**，
> 将需要用到的变量一个一个向上逆出来。」

> ★★ **具体做法**：先拿到一组**已知明文/密文对**（或已知"解出来应该是 `123456`"），
> 在调试器里**从输出往上单步**，每一步记下"这个寄存器现在是多少、它来自哪"，
> 直到某一步的值能用**已有字段**解释为止 —— 那一步就是算法真正的入口。

### §4.2 定位"生成封包的代码段"

| 手段 | 做法 | 样本 |
| --- | --- | --- |
| **栈回溯 + 断点** | 在 `send`/封包缓冲区上找栈里的目标地址，再从**调用栈**回溯到生成点 | `52pojie-413044`（`001872b8` / `001632e4` / `001832b8` 三个栈） |
| **WPE 重放 + 改单字段** | 用 WPE 重放，**一次只改一个字节**，看服务端报什么错 | `52pojie-413044` |
| **明文/密文对拍** | 程序自己加密 vs 自己实现的加密，**逐字节 diff** | `52pojie-522759`（源文原话：「证明解密没有写错」） |

### §4.3 ★★★ 反编译出来的是「C 语言伪装的 AS/JS」怎么办

**来源** `52pojie-1468888`（赛尔号的 `MEncrypt.as` / `MDecrypt.as`）。

```text
判据：AS/JS 里出现
  · avm2.intrinsics.memory.li32 / li8 / si32 / si8   （按地址读写"内存"）
  · ESP = ESP & -16 ; CModule.mallocString(...)
  · 形如 F__Z15MEncrypt_x86_32PKhiS0_iPi 的 **Itanium 修饰名**
⇒ 这是 **CrossBridge（= FlasCC / Alchemy）**：把 C/C++ 交叉编译到 AVM2，
  逐个内存操作都是"翻译"出来的，**几乎无法直接读**。
```

> ★★★ **处置（源文的选择，也是本库推荐的）**：
> **① 不要读加密（`MEncrypt`）那一份 —— 读解密（`MDecrypt`）那一份。**
> 源文原话：「大多数情况下，客户端的加解密算法是互为逆向的……所以
> **我们只需要分析出客户端的解密算法（加密算法），然后对其算法求逆**」。
> **但注意反例**：也存在「客户端加密 ↔ 服务端解密」与「客户端解密 ↔ 服务端加密」**两套不同算法**的情况，
> **所以第一件事是验证"是不是同一套"**（用一组已知对拍）。
> **② 别硬读反汇编** —— 优先找**等价的高层产物**（本例是"解密后的 SWF 反编译成 AS 源码"）。
> 详见 `52pojie-1468888` 的另一半：**SWF 本身被"加密"时的两条路**
> （逆向解密逻辑 / **从内存 dump**）。

## §5 坑表

| 坑 | 表现 | 处置 |
| --- | --- | --- |
| 长度字段也去解密 | 密文流里切不出第二条包 | 长度字段**设计上必为明文**（§1） |
| 假设收发头长度对称 | `dataLength` 总是差几个字节 | 量出 `PackSendHeaderLength` / `PackRecvHeaderLength` 两个常量（§1.1） |
| 直接拿 key 异或 | 明文不可读 | 先算 `(key+1)^4` 之类的**密钥变换**（§2.1） |
| 前几包能解、后面乱 | 以为算法变了 | **会话中换钥**（§2.2），种子通常在**包尾定长字段** |
| 资源不是标准 magic | 以为要还原一整套算法 | 先试**"文件名当循环异或密钥"**（§2.3） |
| 按出现顺序直读包体 | 字段一直对不上 | 包头里有**偏移/排序表**（§3.1） |
| 解析列表时按固定长度读 | 第二条起全错 | 写成"个数 + 每条 `长度前缀+数据+尾部定长`"（§3.2） |
| 顺着汇编读不动 | 越读越乱 | **从结果往上倒着逆**（§4.1） |
| AS 里全是 `li32`/`ESP` | 完全读不懂 | CrossBridge 产物 ⇒ **读解密侧 + 求逆**（§4.3） |
