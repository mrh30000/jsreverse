## 3. 形态①：按日期算的自定义查询参数（`z` / `s1ig`）

### 3.1 现象与完整算式

**现象（`52pojie-1490196`，该案例实测）**：请求形如

```text
GET https://z1.m1907.cn/api/v/?z=<32位hex>&jx=<视频页url>&s1ig=<5位数>&g=vod.bun
Referer: https://z1.m1907.cn/?jx=<同一个视频页url>
```

`z` 是 32 位 hex，看着像签名，但它**只由「今天是几号」决定** —— 服务端与客户端用同一个算式各自算一遍。

**源文 JS 原样（只算 `z`；其余是标准 MD5 实现，此处只留算式与调度器）**：

```js
// 调度器：单参时 Et(e) == m(v(e)) == 小写 MD5 hex（Et = m∘v）
function Et(e, t, n) {
  return t ? (n ? y(t, e) : m(y(t, e))) : (n ? v(e) : m(v(e)));
}
function get_z() {
  var d = new Date().getTime();
  var m = new Date(d);
  var slig = m.getDate() + 9 + 9 ^ 10;
  var p = String(slig);
  p = Et(p).substring(0, 10);
  p = Et(p);
  return p;
}
```

> `v` = raw MD5、`m` = 转小写 hex、`y` = HMAC-MD5 ⇒ `Et(p)` **单参** = `hex(md5(p))`，即小写 MD5 hex 全串（32 字符）；两参 `Et(e,t)` = `hex(HMAC-MD5(key=t, msg=e))`（本文只用到单参）。

**源文 Python 原样（只算 `s1ig`；`z` 是 `node.call('get_z')` 拿的）**：

```python
import datetime
y = datetime.datetime.now()
p = int(y.day) + 9 + 9 ^ 10     # ← 源文算完这个 p 之后没有使用（见 §3.2 ③）
slig = y.weekday() + 11397      # ← 这才是另一个参数，URL 里叫 s1ig
# z = node.call('get_z')        # ← z 由 JS 侧算出
```

**纯 Python 等价实现（本流水线自算，用于对拍 / 半路排错）**：

```python
import hashlib
def get_z(day_of_month):
    slig = (day_of_month + 9 + 9) ^ 10                  # 显式加括号：+ 先于 ^
    h = hashlib.md5(str(slig).encode()).hexdigest()
    return hashlib.md5(h[:10].encode()).hexdigest()      # ★ 先切 hex 文本的前 10 个字符
```

> ★ 中间那步切的是「**hex 文本的字符**」，不是字节（`substring(0,10)`）。与 `references/hls-and-ts-structure.md` §4.3 的坑 1 同源：**切错单位仍得一个 32 位 hex、仍不报错**。

### 3.2 ★ 三个静默错与一个优先级判据

**（〇）运算符优先级**：`+` 优先于 `^`，且 `^` 是 **XOR 不是幂**（JS 与 Python 一致）。
⇒ `m.getDate() + 9 + 9 ^ 10` 等价于 `(day + 18) ^ 10`，**不是** `day + 9 + (9^10)`。
（Excel 学习惯把 `^` 当幂 ⇒ 这是本族最常见的第一处静默错。）

**（一）`getDate()` 与 `getDay()` 语义不同**：前者是**月内日（1–31）**，后者是**星期（0–6）**。
本样本 JS 用的是 `getDate()`。把 `getDate` 误读成 `getDay` 会让 `z` **全错但不报错**
（真机实测：同一天 `getDate=7` 而 `getDay=6`，两条路径产出不同的 `z`，见 §3.3 负对照锚点）。

**（二）两语言的「星期数」不能互相照抄**：**JS `getDay()` 是 0 = 周日**，
**Python `weekday()` 是 0 = 周一**（`isoweekday()` 才是 1–7）。本样本的 `s1ig` 是 Python 侧用 `weekday()` 算的，
若照抄 JS 的星期数会**整体差 1**。

**（三）源文两版口径不同、非矛盾（登记项）**：源文的 JS 片段**只算 `z`**；`s1ig` 是 **Python 侧**用
`weekday() + 11397` 算的。**不是**「同一参数两个算法」，而是「一个参数一段算式，各写在各语言里」
⇒ 复现时**不必**去找「`s1ig` 的 JS 实现」。
另登记：源文 Python 里算出来的 `p` **从未被使用**（`z` 走 node），属源文烂尾，**照抄时删掉即可**。

### 3.3 ★ 回归锚点（可复算、可对拍）

> ⚠️ 下表为**本流水线自算**并已逐字符复算命中；**源文没有给出任何示例值**，故无法与源文对拍，
> 只能作为「自己两条路径是否自洽」的回归锚点。

| 输入 | `slig` | `md5(str(slig))[:10]` | `z`（最终值） | 用途 |
| --- | --- | --- | --- | --- |
| `day=7`（`getDate` 路径） | `(7+18)^10 = 19` | `1f0e3dad99` | `15a40fd4c6c6019f8f3dba73ff9242f8` | **正锚点** |
| `day=1`（`getDate` 路径） | `(1+18)^10 = 25` | `8e296a067a` | `7468d5aae4ba551a0069655a67105999` | **正锚点** |
| `day=6`（**误走 `getDay` 路径**） | `(6+18)^10 = 18` | `6f4922f455` | `a037c5fdaf8efe76bea2b4964f7b3810` | **负对照**：与正锚点不同 ⇒ 能抓住「`getDate` 读成 `getDay`」 |

- `s1ig` 侧同样可对拍：`weekday()` 0–6 ⇒ `s1ig ∈ {11397, …, 11403}`（周一到周日）。

### 3.4 请求侧登记（该案例实测，仅登记不推广）

- 接口 `https://z1.m1907.cn/api/v/`；查询参数四项：`z` / `jx`（= 视频页 url）/ `s1ig` / `g=vod.bun`。
- `Referer` 带**同一个 `jx`**；Cookie 里出现过 `igh={"t":<毫秒>,"h":["vod.bun"]}`，**与 `g=vod.bun` 呼应**（登记，未判因）。
- ★ **易读错点**：源文**变量名**是 `slig`（`s`+`l`+`ig`），**URL 参数名**是 `s1ig`（`s`+**数字 1**+`ig`）；不要「顺手统一」。
- ★ **工程化**：`z` 与 `s1ig` 都只依赖当天日期 ⇒ **日级刷新**，抓到的东西当天有效，缓存到第二天必然失败。

## 4. 形态②：ts 分片 URL 本身就是 m3u8 的伪装形态

### 4.1 现象与处置（源文原话）

**现象（`52pojie-1843783`，该案例实测）**：F12 → Network → Fetch/XHR → 开始播放，
面板里点带 **`_0.ts?start=0&end=…`** 字样的请求，右侧 `Request URL` 复制出来；
交给下载器（猫爪）后提示「**密匙无法解析 / 密匙解析失败**」。

**处置（源文三步，原话照录）**：① 复制那条 `…_0.ts?start=0&end=…` 的 `Request URL`；
② **把 `_0.ts` 改成 `.m3u8`**；③ **把 `start=0&end=` 删掉** ⇒ 「就能正常下载啦」。

> 源文自述过程是「无意中删掉 `start=0&end=132927&` 这些字符后下载成功」；在删 Range 参数之前，
> 他先试过另一篇帖子「改 `_0.ts`」的方法，**同样下载失败** ⇒ 两个动作**必须一起做**：只改后缀、或只删参数，都不成立。
>
> ⚠️ **源文残留登记**：源文正文写作 `\_0.ts`，那两处 `\` 是 **Markdown 转义残留**，真实文件名是 `_0.ts`。

### 4.2 ★ 判据与原理（本文件的增量）

- `?start=0&end=132927` 这种成对的 `start` / `end` **是服务端按 Range 切片**的形态：
  同一条路径，服务端按字节区间切一段返回（这里是 `[0, 132927)`）。
- ⇒ **同一路径去掉 Range 参数，服务端就返回完整清单**（`#EXTM3U` 纯文本）。
- ★★ **通用判据（可迁移）**：**「下载器报 key / 密匙错误」不一定是 key 问题** ——
  先看手上拿到的是不是「**切片形态的 URL**」而不是「**清单 URL**」。
  **形态认错时，任何 key 处理都不会报错，只会一直失败。**
- **一分钟自查**：① 面板搜 `.ts`，找到带成对 `start=` / `end=` 的请求；② 复制 URL，
  `_0.ts → .m3u8` 并删掉 `start=…&end=…`（**连同后面那个 `&`**）；③ 浏览器打开：响应体以
  **`#EXTM3U`** 开头 ⇒ 对了；以 **`0x47`**（TS 同步字节）开头 ⇒ 那还是切片，不是清单。
  ⇒ **「清单 vs 切片」最快的判据是看响应体开头，不是看后缀。**

### 4.3 ⚠️ 边界与分工（必须连同「该案例实测」一起引用）

- **该案例实测，单样本**：本法只对「**ts 与 m3u8 同路径、靠查询参数区分**」的服务端成立。
  **不是所有站都能这么改** —— 很多站的清单与分片本就是**两个不同路径**，删参数只会 404。
- 改写后返回 **403 / 404 / HTML** ⇒ 立即回 `references/preview-gating-and-segment-enumeration.md`
  走**分片枚举补齐**，不要在这里反复试参数。
- **三分工各一句**：`references/playback-address-interfaces.md` 答「**怎么问接口要地址**」（线 A：签名 + 会话）；
  **本文 §4** 答「**已拿到一条 URL，它是切片还是清单**」（线 B：URL 形态判定）；
  `references/preview-gating-and-segment-enumeration.md` 答「清单**本身被截断**怎么补齐」（线 B 的下一站）。

### 4.4 第二个独立样本（同型复现，`52pojie-1757892`）

同一手法在小鹅通（`h5.xiaoeknow.com`）上**再次成立**，且**多了一条源文收尾动作**：

- 面板里拿到的是 `…/v.f421220_0.ts?start=0&end=76335&type=mpegts&exper=180&sign=<...>`；
- 处置与 §4.1 **完全一致**：`_0.ts → .m3u8`，删掉 `start=0&end=76335`；
- ★ **源文的两条补充判据**：
  1. **怎么挑那一条**：源文原话「**通常第一个为 `.m3u8` 的文件，往后的是 `.ts` 文件，选择紧跟 `.m3u8` 后面的文件即可**」
     ⇒ 即「清单请求 → 紧随其后的第一个分片请求」是最省事的定位法；
  2. **改写后连 `type` / `exper` / `sign` 一起保留**（源文替换后的 URL 只动了后缀与 `start/end`）
     ⇒ **不要顺手删干净所有查询参数**：这一族里 `sign` / `exper` 是**时效鉴权**，删了就失败。

> ★ **两个独立年份的样本（2023-10 / 2023-03）同型** ⇒ 这是**该族服务端的稳定形态**，不是偶发。
> 但仍**不等于所有站**：判据仍是 §4.2 那句「**看响应体开头是 `#EXTM3U` 还是 `0x47`**」。

**与 `preview-gating-and-segment-enumeration.md` 的关系（本批新增一条硬边界）**：
本形态只解决「**这一条 URL 是切片还是清单**」。若改写后**清单本身条目不全**（条目数远少于
总时长对应的分片数、或清单路径带 `_preview`），那才转

⚠️ **登记（源文未展开，不判因）**：`exper=180` 与 `sign=***` 这两个查询参数的语义源文**没给**，
只登记其存在与「**改写时不要删**」这一纪律；**不得**据此推断它是「有效期 180 秒」。

## 5. 形态③：页面直出（SSR）载体

### 5.1 现象（源文原话，`52pojie-1917707`）

- `2024-04-22` 起，西瓜视频播放页（`https://www.ixigua.com/<视频id>`）的**下载链接变化了**；
- 该视频的下载链接**在 `window._SSR_HYDRATED_DATA` 对象中**，它**位于该播放页的 HTML 文档中**；
- 变化表现：**在此之前**只需 `base64 decode` 一次即可拿到下载链接；**现在多了一层 `AES` 解密，再 `base64 decode`**；
- 源文自述：整个分析过程「**运气**占了 `90%`」。

### 5.2 算法（源文 Python 原样收录）

```python
from Crypto.Cipher import AES
from Crypto.Util.Padding import unpad
import base64

def aes_decrypt(data: str, key: str) -> str:
    data = base64.b64decode(data)
    key = key.encode()
    iv = key[:16]

    # mode 为 CBC、pad 为 PKcs7
    cipher = AES.new(key, AES.MODE_CBC, iv)
    res = cipher.decrypt(data)
    res = unpad(res, AES.block_size)
    res = base64.b64decode(res).decode()
    return res
```

- **解包顺序**：`b64decode(密文)` → **AES-CBC** → `unpad` → **再一次 `b64decode`** → `.decode()`
  ⇒ 一共 **两层 base64，中间夹一层 AES**。
- ★ **`iv = key[:16]`：IV 取 key 的前 16 字节**，不是另给的、也不是 `key` 本身。
  这是「**IV 从 key 派生**」的又一实例（对照 `references/hls-and-ts-structure.md` §4.4「Latin1 key + 前缀作 IV」）。
- 源文明确给出：`mode = CBC`、`pad = Pkcs7`。

### 5.3 ★ 判据：这是地址还原层的「零请求入口」

- **「页面直出数据载体」= 不需要任何接口调用**，直接从 HTML 里取 `window.*` 全局变量
  （SSR = Server-Side Rendering：服务端把首屏数据**直接写进 HTML**）。
- **识别信号**：HTML 里有一个**巨大的内联 JSON 赋值**（形如 `window._SSR_HYDRATED_DATA = {...}`）。
- ★ **与接口链路的分工（本文件的增量）**：**先看 HTML 有没有直出，再考虑抓接口。**
  直出数据是**服务端渲染那一刻**就定下来的，**不需要复现任何签名 / 会话**；接口链路则要先自举会话再算签名
  （`references/playback-address-interfaces.md` §2.2）。
- **交叉引用**：`references/playback-address-interfaces.md` §3.3 已登记「小红书 `__INITIAL_STATE__`：数据本来就在页面里」——
  那条是**明文直出**；本文形态③是**同一入口的加密版**（载体与入口相同，只多一层 AES）。
  两者合起来构成「页面直出」的两档：**明文** / **加密**。
- **取数动作**：① 打开播放页 → **查看网页源代码**（不是 Elements 面板：面板里是 DOM 展开后的对象）；
  ② 源码搜 `window._SSR_HYDRATED_DATA`（或 `__INITIAL_STATE__`），或直接在控制台读该全局；
  ③ **先试「只 base64」**，解出以 `http` 开头 ⇒ 旧的明文档，收工；否则按 §5.2 顺序解 AES。

### 5.4 ⚠️ 登记项（只登记不判因）

- **源文未展开**：源文自陈「**测试时发现有两种情况**」，给了**两张截图但未说明差异** ⇒ 如实登记「源文未说明第二种情况」。
- **源文未展开（key 来源）**：源文**只给了 `key` / `iv` 的截图、没有把 `key` 写成文本**
  ⇒ **不得编造 key / iv**，本文一律只写「**从截图取值**」。
- **单样本**：本条只有这一篇源文，且作者自称「运气占 90%」⇒ **引用必须带日期（2024-04-22 改版）**。

## 6. 排错速查

| 现象 | 判断 | 处置 |
| --- | --- | --- |
| 下载器报「**密匙解析失败 / key 无法解析**」 | 先怀疑**拿的是切片 URL 不是清单 URL**，而不是 key 有问题 | 形态②§4：改后缀 + 删 `start=&end=`；看响应体是否 `#EXTM3U` |
| 下载器报 key 错，但地址里**根本没有** `_0.ts` / Range 参数 | 这才可能是真的 key 包装层 | `references/key-wrapper-families.md`（先跑 §6 字母表守卫） |
| 地址里有短查询参数、**同一天内固定、隔天失效** | 按日期算的参数 | 形态①§3；先确认 `+` 与 `^` 的优先级 |
| `z` 算出来与服务端不一致，但**不报错** | 大概率 `getDate` 读成了 `getDay` / 跨语言照抄了星期数 | 用 §3.3 三个锚点对拍（含负对照）；差 1 看 §3.2（二） |
| HTML 里有一段巨长 base64，**解出来不是 `http` 开头** | 页面直出载体还差一层 AES | 形态③§5：`b64 → AES-CBC → unpad → b64 → utf-8` |
| 直出数据**解出来还是 base64** | **源文形态就是这样**（两层 base64 夹一层 AES），不是你解错了 | 再 `b64decode` 一次（§5.2）；`iv` 记得取 `key[:16]` |
| 页面能播，但面板里**只有 `.ts` 请求** | 清单可能在另一个请求里；或本身是切片形态 | 形态②§4.2 一分钟自查 |
| 改后缀 + 删参数后 **403 / 404 / 返回 HTML** | 该站不是「同路径靠查询参数区分」 | 转 `references/preview-gating-and-segment-enumeration.md` §3 |
| 清单拿到了，但解出来是乱码 / 花屏 | 已出本文范围 | 回 `SKILL.md` 分层判据表判 A–F 层 |
