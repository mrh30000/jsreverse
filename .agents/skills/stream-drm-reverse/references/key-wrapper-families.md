# key 二次构造 / 包装层（W 族）—— 唯一权威源

> **本文是「m3u8 key URI 拿到的不是真 key」这一族判据与还原法的唯一权威源。**
> 具体厂商的 ip 级配方仍归 `vendor-key-schemes.md`；本文只讲**结构族**与**机械判据**。
> 可执行实现：`scripts/key_wrapper.py`（自带 `--selftest`）。
> 结构化结论来源：B14 蒸馏（21 篇），其中 3 个族做到了**与文章原样 JS 逐字节对拍**。

## §1 为什么要有这一层（以及不做的代价）

`#EXT-X-KEY:METHOD=AES-128,URI="..."` 返回的 16 字节**经常不是真 key**。
站点在服务端先做一层「包装」，浏览器里由播放器 JS 还原。

现象与代价：

| 现象 | 误判 | 真实原因 |
| --- | --- | --- |
| 下载器报「填充错误 / key 长度不对」 | 「key 抓错了」 | 抓到的是**包装后**的 key（W 族） |
| 拿到 47 位 / 32 位 / 64 位「key」 | 「不是 AES-128」 | 是 base64 文本、hex 文本或拼接串，**长度本身就是判据** |
| 解出来是垃圾，但字节数正确 | 「算法不对」 | 包装还原方向或口径错（最常见：少做/多做一次 base64） |
| 换了个视频就解不开了 | 「站点改了」 | 包装是**会话相关**的（含 UID / 时间戳），必须每次重新派生 |

> **硬判据**：AES-128 的真 key 一定有且只有 **16 字节**。
> 拿到的值长度不是 16 ⇒ 100% 还有一层包装，**不要**先去怀疑算法或 IV。
>
> ⚠️ **这条判据单向成立，别反着用**：**长度是 16 ≠ 没有包装层**。
> W6（外部掩码异或）的产物就是**正好 16 字节**（见 §6.5），它只表现为"下载器报 key 错误"。
> 判据是：**长度不对 ⇒ 一定有包装；长度对 ⇒ 仍要试一遍"当 ASCII 读得出来吗"**。

## §2 八族总表（30 秒分流）

| 族 | 结构签名（看什么） | 典型长度 | 还原命令 |
| --- | --- | --- | --- |
| **W1** 重复密钥 XOR | 响应是 **base64 文本**，JS 里有 `charCodeAt(i) ^ token[i % d]` | 与明文等长 | `key_wrapper.py xor --mode b64-xor-b64` |

## §3 W1 重复密钥 XOR

实测形态（`52pojie-1624279`）：

```js
function strdecode(a, token) {          // token = md5(md5(格式化时间戳/1000 + key))
  a = Base64.decode(a);                 // ① 外 base64 解码
  for (var i = 0; i < a.length; i++)    // ② 与 token 循环异或
    e += String.fromCharCode(a.charCodeAt(i) ^ token.charCodeAt(i % d));
  return Base64.decode(e)               // ③ ★ 第二次 base64 解码
}
```

★ **三段链**：`b64( xor( b64(明文), token ) )`。
**少做或多做一次 base64 都会得到「看着像乱码的合法字节」而不报错** —— 本族最典型的静默错。
故 `key_wrapper.py` 同时提供 `w1_encode_b64_xor_b64` / `w1_decode_b64_xor_b64`，
并在自检里加了一条**反向断言**：少做一次解码必须**得不到**明文（防止把三段链误写成两段）。

判据：

- token 通常是 **32 位 hex 字符串**（md5 结果当字节用），长度恰好 32 ⇒ 与 16 字节 key 的异或只用到前 16 位。
- token 里常含**时间**（`new Date(...).getTime()/1000`）⇒ 有时效窗口，必须一次跑完「取 token → 解 key → 解分片」。
- 同一个 token 也可能同时用于**多个字段**（URL、body），别重复派生两次。

## §4 W2 字符表滚动变换（xiaoe 式）

实测全码见 `52pojie-1833748`。结构拆解：

```
密文 = [首字符 o][正文...][末 3 字符 t0 t1 t2]
  · o          → s = 表.indexOf(o)，同时决定滚动窗口的**起点** s % 8
  · t1         → 噪声间隔 n（`+t.substr(-3)[1]`，一个字符 ⇒ 只能 0..9）
  · 正文        → 表内字符与噪声字符**混排**，每个真字符后跟 n 个噪声字符
  滚动窗口 c = hexMD5( hexMD5(salt) + o ).substr(s % 8, s % 8 + 7) 的 ASCII 码
  正文第 h 位:  idx = 表.indexOf(正文[h]);  l = idx - f - c[f++];  while (l<0) l += 65
```

### §4.1 三个必须机械校验的结构常量

1. **`substr` 的第二参数是「长度」不是「终点」** ⇒ 窗口长度 **`(s % 8) + 7 ∈ [7,14]`，随首字符变化**。
   误按 `substring(start, end)` 语义实现时，`s % 8 != 0` 的样本会**整体错位**，
   而解出来的东西**仍然是一串合法 base64 字符**（不报错）。
   自检里有一条断言逐项核对 8 个 `s % 8` 的窗口长度。
2. **`e = hexMD5(salt)` 得到的 32 位 hex 是「字符串」再参与 `hexMD5(e + o)`** ——
   不是把 digest 当字节用。两层做错一层，`o` 与 `s` 的关系就全乱。
3. **加法是模 65 不是模 64**（表含填充符 `=`，共 65 字符）。
   写 `% 64` 会让 `=` 永远解不出来；写 `% 65` 但表只有 64 字符则最后一个字符永远取不到。

### §4.2 ★ 噪声字符的「三侧宽容度矩阵」（本族最隐蔽的不可移植行为）

原码这一句把噪声字符**也拼进了 base64 串**：

```js
u += t.slice(h + 1, h + 1 + n)   // ← 噪声不是"丢弃"，是"塞进 base64"
```

语义上它依赖 `atob` 忽略非法字符。但**三侧解码器的宽容度互不相同**（B14 实测）：

| 噪声字符 | Python `b64decode(validate=False)` | Node `atob` / `Buffer` | 浏览器 `atob`（forgiving-base64） |
| --- | --- | --- | --- |
| `!` `*` `.` `~` `%` | **忽略** | **忽略** | **抛 InvalidCharacterError** |
| `-` `_` | **忽略** | **静默吃进产物**（当 base64url） | **抛错** |
| `+` `/` `=` 与 `A-Za-z0-9` | **吃进产物** | **吃进产物** | **吃进产物** |
| `\t` `\n` `\r` ` `（ASCII 空白） | **忽略** | **忽略** | **忽略** |

⇒ **结论：三侧都忽略的字符只有 ASCII 空白。**

- `n == 0` 的样本**永远暴露不出这个问题**（噪声不存在 ⇒ 三侧行为一致）。
- 所以「原文代码能跑通」**不能**作为「噪声字符选得对」的证据。
- 实测反例：`atob('YQxx==') → "a\fq"`（不是 `"a"`）；`atob('YQ--==') → "a\u000f¾"`。
  两者**都不抛错**、产物长度还对。

判据写法：`key_wrapper.py noise-check --enforce` 会逐字符给出三侧判定
（`safe` / `silent-change` / `eaten` / `throws`），非 `safe` 一律以退出码 2 拒绝。

### §4.3 拒绝路径（必须报错，不能静默）

| 输入 | 原码行为 | 本脚本 |
| --- | --- | --- |
| 末 3 字符的中间位**不是数字** | `+t.substr(-3)[1]` = `NaN` ⇒ `n && (...)` 为假 ⇒ 噪声一个不跳 | 报错并说明原因 |
| 首字符 / 正文含**表外字符** | `indexOf` 返回 -1 ⇒ 产物变成 `undefined` 拼串 | 报错并给出下标 |
| 输入短于 `1 + 3` | 切片越界，解出空 | 报错 |

## §5 W3 字符表滚动变换（定长正文 + hex 标记串）

实测形态（`52pojie-2021915`，含评论区的完整复现）：

```
响应 = hex( <13 位随机数字> + "TG:@XMFLV" + urlencode([首字符][定长正文]) + <13 位随机数字> )
窗口 = MD5(secret + 首字符).substr(首字符下标 % 8, 7)     ← ★ 长度常量 7，与 W2 不同
正文第 i 位: out = 表[(首字符下标 + 表.indexOf(正文[i]) + 窗口[hi++].charCodeAt(0)) % 64]
```

与 W2 的**关键差异**（抄混了必然出错）：

| | W2（xiaoe 式） | W3（虾m 式） |
| --- | --- | --- |
| 窗口长度 | `(s % 8) + 7`，**随下标变化** | 常量 **7** |
| 取模基数 | **65**（表含 `=`） | **64** |
| 正文长度 | 跟随明文 | **硬编码 60** ⇒ 明文**恰好** 45 字节 |
| 偏移符号 | 解码**减**、`while(l<0) l+=65` | 解码减、`% 64` |
| 外层包装 | 首 1 + 末 3 字符 | hex + 前后各 13 位数字 + 9 字符标记串 |

### §5.1 两处「录入错」——必须自己算，不能照抄

1. **标记串与密钥字面量互相矛盾**：
   `signCoen` 用的标记是 `TG:@XMFLV`（9 字符），而 `secret_key = '54473a584d464c56'`
   解出来是 `TG:XMFLV`（**少了 `@`**）。**必有一处是录入错。**
   做法：两版各跑一次（盐只影响窗口，不影响结构），以能对上真实密文的那版为准。
   本脚本遇到标记串不匹配时会**直接把这条矛盾打印出来**，而不是丢一个「格式错误」。
2. **字符表缺 `/`、多了 `-`**：原文表是 `…789-=+`（65 元），而**编码侧用的是标准 `btoa`**
   ⇒ 只要明文 base64 里出现 `/`，`indexOf` 就返回 -1、`% 64` 落到一个**看似合法**的下标，
   **产物是错的不报错**。见 §6。

### §5.2 定长正文的两个静默边界

- **明文超长**：原码只跑 60 轮 ⇒ 多余明文**静默丢弃**（不报错）。
- **明文不足**：`input_string[i]` 是 `undefined` ⇒ `indexOf(undefined) == -1` ⇒ 产物全错不报错。

`xm_encode` 对两种情况都**报错**，`--allow-pad` 只留给「明知在造畸形夹具」的场景。

## §6 W5 字母表守卫（**先跑它**）

`key_wrapper.py alpha-check --table "<表>" --enforce`

四条判据（任一不满足即**不可用**，不要靠试）：

1. **长度必须是 65**（64 个字 + 1 个填充符）。用 `% 64` 与填充分不开。
2. **必须覆盖 `btoa` 输出空间** `A-Z a-z 0-9 + / =`。缺一个就必然出现 `indexOf == -1`。
3. **字符必须互不相同**（否则解码侧无法唯一还原）。
4. **下标 ≥ 64 的字符在 `% 64` 下会回绕到 0** —— 只要明文可能出现该字符，产物就不可逆。

### §6.1 实测案例

| 表 | 判定 | 说明 |
| --- | --- | --- |
| `…789+/=` | ✅ 同构 | 标准表 |
| `…789-=+`（文章原样） | ❌ `missing=['/']`、`extra=['-']` | 尾三字符被改写；与标准 `btoa` 不配套 |
| `…ABC**D**E**D**G…`（某 IR 的 base64 表） | ❌ `dup=['D']` | **单射性**被独立证伪（与 B13 同源教训） |

> 口诀：**「字母表 / 映射表 / 置换表」类常量，先跑一次单射性 + 覆盖性检查。**
> 两处独立来源一致也**不能**替代机械判据 —— 数学约束比「两篇文章都这么写」强。

## §6.5 W6 外部掩码异或（int32 大端）—— 掩码不在 JS 里

**结构签名**：`.key` 返回的 16 字节**长度完全正常**（这就是它躲过"不是 16 字节 ⇒ 有包装"这条判据的原因），
但下载器报「解码失败，请检查 key 是否正确」。JS 里的形态是：

```js
const $ = new DataView(y)              // y = E.data（拿到的 16 字节）
$.setInt32(0, $.getInt32(0) ^ b[0]),
$.setInt32(4, $.getInt32(4) ^ b[1]),
$.setInt32(8, $.getInt32(8) ^ b[2]),
$.setInt32(12, $.getInt32(12) ^ b[3])
E.data = $.buffer
```

而 `b`（掩码）**不在 JS 里** —— 它在 **DOM 属性**上：

```html
<div id="app-key" data-keys="3854078970,2917115795,3887476043,3350876132"></div>
```

```js
const e = document.querySelector("#app-key")
const E = JSON.parse(`[${e.dataset.keys}]`)   // → [3854078970, 2917115795, 3887476043, 3350876132]
```

还原：

```bash
python $S/key_wrapper.py dataview-xor \
  --input 80f5f48bd4a6d7ffd0e26a04f0d90e86 \
  --mask 3854078970,2917115795,3887476043,3350876132 --raw
# → 真实 key: eMgqyypl7TGO7cAb   (hex 654d67717979706c3754474f37634162)
```

### §6.5.1 两个必须点破的坑

1. **`DataView` 默认大端。** `getInt32(0)` 的 `littleEndian` 省略即 `false` ⇒ 按**大端**读。
   而 `Uint32Array` 视图是**平台端序**（x86 为小端）⇒ 同一个整数摊成字节串的**结果不同**。
   实测文章中"JS 用 DataView、Python 用 `n.to_bytes(..., 'big')`"两条路能对上，正是因为两边都是大端；
   **若把 JS 那份改写成 `Uint32Array` 再 `Uint8Array` 展平（文章里也给了这段"工具"），语义就变了，而且不报错。**
   本脚本用 `--endian big|little` 显式区分，自检里有「大端 ≠ 小端」的断言。
2. **掩码来源不止 DOM。** 也可能是**混淆常量数组**里的某几个元素，或由接口下发。
   找不到时：① 在 HTML 里搜 `data-keys` / `data-key` 一类属性；② 全局搜该 DOM 选择器；
   ③ 在常量数组上**爆破**（掩码是 4 个 int32，候选集很小，`uint32` 空间不需要全遍历——
   用「解出来必须是 16 字节的可见 ASCII 字符串」做判据即可，实测真实 key 是 16 个可打印字符）。

> **本族的判据特别"安静"**：长度对、字节数对、每个字节都变了但都不是明显垃圾。
> 唯一的判据是**解出的 16 字节能否当 ASCII 字符串读出来**（真实 key 常是 16 个可打印字符，
> 例如 `eMgqyypl7TGO7cAb`）。**"长度对了"在这一族里毫无信息量。**

## §6.6 W7 接口下发 + 前缀剥离 + 隔 2 异或 + popcount 修正（**3 样本全绿，B43 定稿**）

> 实测形态：`52pojie-1749758`（题目标题自称「某浪新版 key 解密」，**带 `1-` 前缀**）+
> `52pojie-1753800`（同站「某浪视频 key 解密」，**给出两对输入/输出**，无前缀）。
> ⚠️ **仍是厂商私有配方**：偏移 `+21`、两个「种子数字」`250 / 85` 都是源文实测出来的**常量**，
> **种子数字的来源源文没有解出**。落地前先用下面的「hex 字符 ASCII」判据验一次，**不要直接迁移**。

**B43 的三条增量（源文都没给，靠第 2、3 个样本反推）**：

| # | 增量 | 证据 |
| --- | --- | --- |
| 1 | **通用式是「掐掉输出数组的首 1 与末 1」，不是「取中间 16」** | 样本② `len(raw)=21 → key 16`、样本③ `len(raw)=37 → key **32**`；两样本都满足 `key = out[1:-1]` |
| 2 | **长度律：`len(key) = len(atob) − 5`**（= 掐头去尾 3 + 隔 2 少 2） | 21−5=16、37−5=32，两次都成立 |
| 3 | **oracle 可加锐**：真 key 是 **16 或 32 个「hex 字符」的 ASCII**（`[0-9a-f]`），不是「任意可打印 ASCII」 | 漏 `popcount` 的产物是 `0c24a4a562.c1411` —— **全可打印**但含 `.` ⇒ 用「可打印」当判据会**放行错 key** |

> **附带解开了 §6.6 原来登记的那处矛盾**：源文 18 位数组末位是 `27`、公式算 `49`。
> 既然通用式是 `out[1:-1]`，**末位本来就被丢弃** ⇒ 该矛盾对还原**无影响**，
> 原「只登记不判因」的处置保留，但风险等级从「未决」降为「已知无关」。

**结构签名**：需要的 16/32 字节**不来自 `.key` 请求**（源文实测 `key_url` 全程没被调用），
而来自一个**播放许可接口**（实测接口名 `play_licenses`），响应是**带 `1-` 前缀的 base64 文本**：

```
'1-yuYeqlPlHMU85XD+UOdM+QHmG8/P'      # 样本①（30 字符 = '1-' + 28）→ key 'abdef786c28046f5'（16 字节）
'muZOqFO3H6hTiHKVa9t3xGvYcZub'        # 样本②（28 字符，无前缀）      → key '1d45c6d6841e4752'（16 字节）
'ouZ2xWyJTcYA5R2rAIoclAHESuYE+RnYAJcetgmpFOBYsELAwA=='  # 样本③（52 字符）→ key '991b8fe94e58466fb9f6592f69076bff'（**32 字节**）
```

**还原链**（每一段的中间值本库都独立复算过；样本①②③ 全绿）：

```
接口明文（带/不带 '1-' 前缀的 base64 文本）
  └ 正则 test 判前缀 → 剥掉 '1-'（**没有前缀的样本要显式声明，否则 --enforce 会拒绝**）→ 28/28/52 字符
     └ atob（浏览器原生 base64 解码）             → 21 / 21 / 37 字节 raw
        └ 掐头去尾（去首 1 + 去尾 2）               → 18 / 18 / 34 字节 core
           └ ★在最前面补两个「种子数字」[250,85]     → 20 / 20 / 36 字节 q
              └ q 上「隔 2 异或 + 21 + popcount」   → 18 / 18 / 34 字节 out
                 └ ★再掐首 1 / 末 1（= out[1:-1]）  → 16 / 16 / **32** 字节 AES key（ASCII hex 文本）
```

**公式（本族最容易踩的一处）**：`q` = 上面那个（core 长 2 的）数组（种子数字在**最前**），
`j` = **输出数组里的下标（0 起）**：

```
out[j] = ( q[j] ^ q[j+2] ) + 21 + bin(j).count('1')   # ★ +21 与 popcount 缺一不可
key    = out[1:-1]                                    # ★ 掐首尾各 1（不是写死的 16 位切片）
```

**源文是怎么得到 `+ popcount` 的**（读旧文时对齐用）：源文先把 Python 结果与浏览器实际值**逐位求差**，
发现差值就是 `str(bin(index)).count('1')`。**三个坑**：

1. **源文的差值清单少写了一位**：源文列的是 15 项 `[1,2,1,2,2,3,1,2,2,3,2,3,3,4,1]`；
   本库独立复算是 **16** 项 `[1,1,2,1,2,2,3,1,2,2,3,2,3,3,4,1]`（= `popcount(1..16)`，正好对应「中间 16 位」）。
   源文那份等于 `popcount(2..16)`，**开头漏了一个 `1`** ⇒ 照抄源文的 15 项会对不齐。
2. **末元素与公式对不上（只登记矛盾，不判因；B43 已确认与还原无关）**：源文给的「浏览器 18 位数组」是
   `[49,97,98,100,101,102,55,56,54,99,50,56,48,52,54,102,53,27]`；
   本库按公式算出的 `out[0..16]` 与它**逐位一致**，但 `out[17]` 是 **49**、不是 27
   （`27` 恰等于 `q` 的末元素）。
   ⇒ **「末位原样透传」与「源文录入 / 截图误」这两种解释都没有独立证据**（本样本只有这一处矛盾），
   故**只登记该矛盾、不给结论**。
   ★ B43 补充：通用式是 `out[1:-1]` ⇒ **末位永远被丢弃**，该矛盾**对还原无影响**（原处置保留，风险降级）；
   但**不要**据此把末位当校验位、也不要据此实现"透传"逻辑。
3. **差值的「位置」必须钉死**：差值序列是 `popcount(输出下标 j)`，**不是** `popcount(q 侧索引)`。
   按 `popcount(j+2)` 算会**整体错 2 位**（`popcount(j+2) != popcount(j)`），
   而产物照旧是 16 个字节 ⇒ **又一个静默错**。凡「修正项 = popcount / 下标表」这类**基于位置**的项，
   落码前必须写清「位置是谁的位置」。

**可复算片段**（完整可跑；注释里的中间值 = 本库实跑结果，已与源文逐项复核）：

```python
import base64

s30 = "1-yuYeqlPlHMU85XD+UOdM+QHmG8/P"          # play_licenses 接口串（JS 自己加的 '1-' 前缀）
b21 = base64.b64decode(s30[2:])                 # 剥前缀 → atob
# b21 = [202,230,30,170,83,229,28,197,60,229,112,254,80,231,76,249,1,230,27,207,207]   （21 字节）
q = [250, 85] + list(b21[1:-2])                 # 掐头去尾（去首 1 / 去尾 2）→ 18 字节，再补两个种子数字
# q   = [250,85,230,30,170,83,229,28,197,60,229,112,254,80,231,76,249,1,230,27]        （20 字节）
out = [((q[j] ^ q[j + 2]) + 21 + bin(j).count('1')) for j in range(len(q) - 2)]
# out = [49,97,98,100,101,102,55,56,54,99,50,56,48,52,54,102,53,49]                   （18 字节）
key = bytes(out[1:-1]).decode("latin-1")        # ★ 掐首尾各 1（不是写死 out[1:17]）

```

> 直接用 `python $S/key_wrapper.py w7 --input "<接口串>" [--prefix ""] [--detail] [--enforce]`。

  （实测漏 popcount 是 `0c24a4a562.c1411`，含一个 `.`），用「可打印」当判据会**放行错 key**。
  工具里对应 `w7_looks_like_hex_key()` 与 `--enforce`。
- 源文自陈「经过多次测试这个算法能解密其他 `play_licenses`」⇒ **同一站内可复用**；换站**不可迁移**（见 §9）。

注意这与「反调试 / 反 hook 检测」是两回事：这里平台劫持 `console`，只是为了**不让你看见它自己打的日志**。

## §6.7 W8 双段剥离（字符级）：`slice(8)` → base64 → `[8:-8]`（B43 新增）

> 实测形态：`52pojie-1683783`（一次逆向四个影视站点，第四站 = dplayer 系播放器）。
> ⚠️ **这一族不是「key 包装」，而是「播放地址包装」** —— 但结构同源（都是「剥前缀 + 解 base64 + 剥首尾」），
> 故并入本表；拿到 `key` URI 也照样可能套这一层。
> **本库没有该站的真实密文样本** ⇒ 实现只做**往返自证 + 对齐律自证**，不做「与源文逐字节对拍」的声明。

**源文原码（还原后）**：

```js
string = urls['substring'](8, urls['length'])   // ① 先剥掉前 8 个【字符】
// 然后再拿去 base64 解码，解码完成后再把前面 8 个和最后 8 个【字符】删掉
```

源文 Python 等价式：`base64.decodebytes(url_3[8:].encode())` → `str(decoded, 'utf-8')[8:-8]`。

**★★★ 三条判据（都可在本地机械校验，不需要样本）**：

| # | 判据 | 为什么重要 |
| --- | --- | --- |
| 1 | 外层剥掉的字符数**必须 ≡ 0 (mod 4)** | base64 每 **4 字符 = 3 字节**；剥 8 恰是「6 字节前缀」的 base64 长度（6 是 3 的倍数 ⇒ 前缀的 base64 无填充，可直接拼接）。**剥 1~3 个字符会整体移位，解出来是乱码但不报错** —— 本族最阴的一处，工具用 `w8_strip_align_ok()` + `--enforce` 拦住 |
| 2 | 内层剥的是**字符**不是**字节** | 源文 `[8:-8]` 作用在**解码后的 UTF-8 文本**上。明文是 URL（纯 ASCII）时 8 字符 == 8 字节 ⇒ **恰好相同是巧合，不是等价**；明文一旦含 CJK 立刻分叉（自检里两组断言分别钉住「巧合」与「分叉」） |
| 3 | 两处剥的都是"校验/填充"，与真值同长 | 若剥错长度但仍是 4 的倍数，产物**不报错、只是另一串乱码** ⇒ 同 W7，**必须配 oracle**（这里 oracle = 「结果必须以 `http` 开头」/「长度与页面 `urls` 的可见位数对得上」） |

**可复跑**（往返自证；`--encode` 造的样本可当夹具）：

```bash
python $S/key_wrapper.py w8 --input "https://cdn.x.com/a/index.m3u8" --encode
#   → {"encoded": "PADBYTES" + b64("XXXXXXXX" + url + "XXXXXXXX")}
python $S/key_wrapper.py w8 --input "<上面的 encoded>"          # → 还原回原 URL
python $S/key_wrapper.py w8 --input "<密文>" --strip-chars 4     # 负面对照：对齐但值错 ⇒ 静默乱码
python $S/key_wrapper.py w8 --input "<密文>" --strip-chars 3 --enforce   # → 报「破坏对齐」
```

**★ 与 W7 的关系（读旧文时按这个分）**：两族共享「剥前缀」这一步，但**目的不同** ——
W7 剥完还要走「隔 2 异或 + popcount」才能得到 key；W8 剥完就是端到端结果（URL / 明文）。
两者可以**叠加**（先 W8 解出中间的 base64，再按 W7 解 key），落地时先判「这一步之后还需不需要再算」。

## §7 坑表（「不报错但结果错」专区）

| 坑 | 症状 | 判据 / 修法 |
| --- | --- | --- |
| 少做/多做一次 base64 | 解出的是合法字节的乱码，长度还对 | W1 必须成对提供 encode/decode；自检加反向断言 |
| `substr` 当成 `substring` | 只有部分样本错，错的样本解码结果仍是合法 base64 字符 | 逐项核对 8 个下标下的窗口长度 |
| `% 64` vs `% 65` | 填充符永远解不出来 / 最后一个字符取不到 | 表长即模数 |
| 噪声字符落在 base64 表内 | 静默改字节（`atob('YQxx==') → 'a\fq'`） | `noise-check`；只在**目标运行时**里实测 |
| 噪声字符是 `-` / `_` | Python 忽略、Node **吃进产物** —— 同一份代码两个结果 | 同上；跨语言对拍必须以**同一运行时**为准 |
| md5 的口径 | 非 ASCII 上算出另一把 key | `hexMD5`（`charCodeAt&0xff`）= **latin-1**；`CryptoJS.MD5(str)` = **utf-8**。同一份代码里两个库可能混用 |
| 空 XOR 密钥 | 静默原样返回 | 显式拒绝 |
| 明文长度与原码硬编码不符 | 超长静默丢弃 / 不足产物全错 | 两侧都报错 |
| 「看着像魔改、其实等价于标准」 | 白费时间读代码 | **先按标准算法跑一次**（B12 教训复用） |
| 基于**位置**的修正项（popcount / 下标表）取错了"谁的下标" | 长度对、不报错、后续 AES 解出乱码 | 把"位置语义"钉死：W7 是**输出数组下标**，按输入索引算会**整体错 2 位**（§6.6） |
| 许可/配置串**带固定前缀**却没剥 | 后续所有长度都差几字节 | W7 的 `1-` 前缀只用于**分流识别**，`atob` 前必须剥掉（§6.6） |
| 漏掉 `+ popcount` 修正（或照抄源文那串 **15** 项差值） | 解出的字节**仍是全可打印字符**（实测 `0c24a4a562.c1411`），只是另一把错 key | ★ **不要把判据设成「可打印 ASCII」**：用 `w7_looks_like_hex_key()`（16/32 个 **hex 字符**）或 `--enforce`；源文差值是 **16** 项，只列了 15 项 |
| 用「可打印 ASCII」当 W7 的 oracle | 错 key 被静默放行（本族最典型的假绿） | oracle 要**跟着族走**：W6 用「16 个可打印」、**W7 用「16/32 个 hex 字符」** |
| `out[1:17]` 写死成「中间 16 位」 | 遇到 32 字节 key（`len(raw)=37`）时**静默只拿一半** | 用 `out[1:-1]`：长度律 `len(key) = len(raw) − 5`（§6.6 增量 1/2） |
| 按字符剥 base64 时剥掉的字符数 ≠ 0 (mod 4) | 整体移位、解出乱码、**不报错** | W8 判据 1：`w8_strip_align_ok()` + `--enforce`（§6.7） |
| 把 W8 内层的「剥 8 个字符」当成「剥 8 个字节」 | 明文含 CJK 时立刻错位（纯 ASCII 样本上看不出来） | 源文口径 = **字符**（`[8:-8]` 作用在解码后的 str 上）；ASCII 下两者相同**只是巧合**（§6.7） |
