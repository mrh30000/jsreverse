# 静态索引替换的坑：字符串表「旋转未还原」会静默产出全错的字符串

> **来源**：`docs/references/52pojie-1746095`（作者 Broadm，2023-02，C# 正则替换解码 `_0x` 字符串表）。
> **定位**：本文**不是**再讲一遍 obfuscator.io 四步链（那见 `obfuscator-io-four-step-pipeline.md`），
> 也不重复字符串表怎么定位（那见 `string-array-and-minimal-eval.md`）。
> 本文只补这两篇**都没有显式覆盖**的一个失败模式：
> **「把 `_getName(0x1e7)` 这种字符串表访问直接用正则/文本替换成字面量」在漏做「数组旋转」时，会静默产出「语法完全合法、语义完全错误」的产物** ——
> 以及它在**运行之前**就能看出来的三个指纹。
>
> **一句话**：`_getName(0x1e7)` 里的 `0x1e7` **不是**数组下标，是「取值函数的入参」；
> 真正的下标 = `入参 - 偏移`，而数组在**运行时**还要先被 IIFE 旋转过 ——
> **源码里的「入参 → 字符串」静态对应关系，根本不是运行时的对应关系。**

---

## §0 结论：跳过旋转 = 静默全错

字符串表在生效前，会先被顶部那个自执行 IIFE **整体旋转**（`array.push(array.shift())`），
旋转到「自校验算式命中某个写死的 magic 值」为止才停。所以：

| 事实 | 后果 |
| --- | --- |
| 数组的**书写顺序 ≠ 运行顺序** | 源码里 `_getName(0x1e7)` 静态算出的第 19 项，**不是**运行时的第 19 项 |
| 旋转量写死在运行期、且每次样本都不同 | **不能**用「入参 - 偏移」直接查书写顺序的数组 |
| 旋转是纯数组操作，**不改任何语法** | 跳过它 ⇒ 产物的**语法完全合法、能 parse**；替换脚本自己**不报任何错**（源文脚本还打印「完成解码」） |
| 每个被替换的字符串都取了错位置的元素 | 产物**每个字符串都是错的** —— 静默、成片、且看不出 |

> 这正是它比 S3/S4 那些「漏做 ⇒ 能 parse 但结构坏」的坑更隐蔽的地方：
> 你连「坏了」都看不到 —— **产物长得就像一份正常的、已经反混淆好的 JS**。

## §1 三个可判定的静默失败指纹

用源文作者**自己的产物**当反例（他就是用「正则 + 未旋转的数组」做出来的）。三条**任一命中即说明旋转没还原**，
而且**都在打开产物时肉眼可判**，不用运行、不用对拍。

### 指纹 1 · 自检算式被替换成 `parseInt("非数字串")`

运行时，旋转的目标就是让这条自校验算式命中 magic 值（源文里是 `_break_val`）。
旋转**之后**，被 `parseInt` 的那几个位置恰好是「数字开头的字符串」；跳过旋转后，同一批位置落到了别处 ⇒ `parseInt` 收到的是普通单词：

```js
// 源文产物的自检算式（原式：parseInt(_getName(0x1e7))/0x1 + -parseInt(_getName(0x1d4))/0x2 + …）
var result =
    parseInt("active") / 0x1 +
    -parseInt("6101864rlJFPI") / 0x2 +
    -parseInt("textContent") / 0x3 +
    parseInt("hide") / 0x4 +
    (parseInt("/project-handling") / 0x5) *
    (parseInt("filter") / 0x6) +
    parseInt("35IfdNdC") / 0x7 +
    -parseInt("#projectcreation_error") / 0x8;
```

- `parseInt("active")` / `parseInt("textContent")` / `parseInt("hide")` / `parseInt("/project-handling")` /
  `parseInt("filter")` / `parseInt("#projectcreation_error")` 全是 **`NaN`** ⇒ 整式和恒为 `NaN`。
- 也就是说：`if (result === 0x920ef) break;` 这条**旋转自检的语义已经彻底不存在**（永远不成立）。
- **判据**：产物里只要出现「`parseInt("单词")` / `parseInt("选择器")`」这种**把明显不是数字的字符串送进 `parseInt`**，
  就说明这条算式里的下标**没有按运行顺序取** ⇒ 旋转没做。

### 指纹 2 · 语法合法的「语义荒谬调用」

原码是「属性名当字符串、函数名当属性」的正常代码；错位后，字符串还是合法字符串、语法还是合法语法，
于是**函数名和属性名互相串位**：

```js
// 源文产物：选择器丢了 '#'，于是 $("#projectcreation_error") 变成 $("projectcreation_error")
$("projectcreation_error")["filter"](function () { … });

// 源文产物：把「属性名」当「函数」调
active_project = document["innerText"]("response");
```

- `$("projectcreation_error")` —— 选择器变成了 `projectcreation_error`（丢了 `#`），选不中任何元素；正确形态应是 `$("#projectcreation_error")`（该串就在表里）；
- `document["innerText"]("response")` —— 把 `innerText`（属性）当函数调；正确形态应是 `document["getElementById"]("current_active_project")`（两者都在表里）；
- 同类还有 `$(document)["create"](…)`（jQuery 的文档就绪回调是 `["ready"]`，`"ready"` 就在表里）、
  `window["data"]["#projectcreation_success"]`（本该是 `window["location"][某属性]`，`"location"` 就在表里）。
- **判据**：看到「`obj["某个属性名"](…)`」「`$(选择器)` 少 `#` / 多尾巴」这类**语法合法但明显不是人的意图**的调用 ⇒ 停下来查旋转。

### 指纹 3 · 「本该是常量」的位置被替换成随机字符串

源文里 `type: _getName(0x1f1)` 本应解出 `'POST'`；错位后解出的是同表里另一项 —— 一个**看着像随机 token** 的字符串：

```js
// 源文产物（节选：注意 type / url 两个「结构位」的值都不是协议常量）
const broken = {
  type: "2774492jOaOCZ",    // 正确值应为 "POST"
  url: "435684KAJSHB",      // 正确值应为 "/switch-project"
};
```

- **判据**：`type:` / `method:` / `url:` / `dataType:` 这类**结构位**上出现了「一看就不是协议常量的乱码串」，
  或反过来 `'POST'` / `'success'` 这类常量出现在**本该是 URL/选择器**的位置 ⇒ 整表错位。

> 三个指纹的共同点：**它们全都在「源码级」可判**。不需要浏览器、不需要原码，
> 只要你知道「这张表本该先旋转」，看一眼产物就能否掉。

## §2 根因：那个替换脚本的三处缺陷

源文的实现是「C# 读原文件 → 正则 `_getName\((.+?)\)` 逐行替换 → 写新文件」。三处缺陷**每一处单独都足以致命**：

| # | 缺陷 | 为什么是错的 | 证据 |
| --- | --- | --- | --- |
| ① | **没有实现数组旋转** | 脚本直接拿数组的**书写顺序**当运行顺序查表；IIFE 的 `push(shift())` 一行都没跑 | 产物 `_getName(0x1e7)` → `"active"`（`0x1e7 - 0x1d4 = 0x13`，书写顺序第 19 项）；可它在运行期是**自检算式的一项**，必须解出**数字开头的字符串**，`"active"` 必错 |
| ② | **重建的取值函数逻辑本身就是错的**：`var _index = _index - 0x1d4;` | `_index` **未定义**（本该用的是形参），按变量提升先得 `undefined` ⇒ `undefined - 0x1d4` 是 `NaN` ⇒ `array[NaN]` 恒为 `undefined`。变量名遮蔽了形参，逻辑是坏的 | 源文那份「可读版」取值函数就是这么写的；**该写的是形参**（原文原始函数用的是 `_0x195fba = _0x195fba - 0x1d4`） |
| ③ | **纯文本正则无法区分「定义」与「调用」** | `_getName\((.+?)\)` 把函数体里的**定义** `_getName(index)`（形参名 `index`）也匹配进来，靠 `if (numberString == "index") return match.Value;` **侥幸跳过**才没把定义改烂 | 脚本里那条 `if (numberString == "index")` 特判；一旦形参改个名（如 `_i`），定义就被替换成字面量，产物必坏 |

**附注（同一根因的第四个表现 · 手工维护数组副本不可靠）**：源文的 C# 里**又抄了一遍**整张数组，
而抄错了 —— JS 里是 `"ul.nav a"`，C# 数组里成了 `"ul.nav 20a"`，于是产物输出 `$("ul.nav 20a")`（非法选择器）。
**手工复制数组 = 手工复制错误**，这也是「让工具去持有真值、你只维护配方」的理由。

> **这三处的共同教训**：字符串表是**运行时**才成立的对象，任何「用静态文本去等价模拟它」的做法，
> 都必须**先复现它的运行期变换（旋转）**；不做这一步，正则再对、脚本再无异常，产物也全是错的。

## §3 正确路线（按性价比排序）

| 优先级 | 路线 | 做法 | 为什么便宜 |
| --- | --- | --- | --- |
| **1（首选）** | **用现成 AST 解码器** | 直接走本技能已有的 obfuscator.io 流水线（`scripts/inline-literals.js` / `scripts/decode-obfuscator-pass.js` / `scripts/run-pipeline.js`，或一体化 `scripts/deobfuscate.js`） | **旋转由工具处理**，你不用碰「书写顺序 vs 运行顺序」这件事；顺序依赖与边界见 `obfuscator-io-four-step-pipeline.md` |
| **2** | **手写但先复现旋转** | ① 先求出**实际偏移量**（取值函数体里那条 `x = x - 常量` 的减数，源文是 `0x1d4`）；② 再求出**旋转量**（洗牌 IIFE 的第二个实参，或按 `string-array-and-minimal-eval.md` §「恒等式自校验」枚举 magic 值命中）；③ **先对数组做旋转**，再按**旋转后**的下标替换 | 只有必须手写、且要批量自动时才值得 |
| **3（最省事、零风险）** | **只做命名还原，绝不碰索引** | **保留原文件、让 `_getName` / 取值函数与数组原样不动**，只把 `_0x…` 变量 / 函数**重命名**成可读名字 | 不触碰字符串表 ⇒ **不存在「旋转漏做」这个失败模式**；读代码够用时优先选它 |

> **负面结论（源文作者的路线就是被否掉的那条）**：**不要**用「纯文本正则把 `_getName(0x…)` 直接替换成字面量」，
> 更不要**手工重建取值函数**或**手工复制数组** —— 前者必然漏掉旋转、后者必然引入抄写错误。
> 正则替换**只能**用于「结构位已知、且与运行期状态无关」的简单改写，**不适合**字符串表。

## §4 验收判据：能 parse ≠ 对

**唯一合格的验收**：

> **替换后必须能跑通一个已知输入，且输出与原文件在浏览器里跑出的同一个输出逐字一致。**

「能 parse」「能跑不报错」**都不是**验收 —— 因为：

- 源文作者那份产物**语法完全合法、能 parse**，替换脚本**全程无异常**、还打印了「完成解码」；
- 然而它的**每一个字符串都是错的**（§1 三条指纹全中）。

**反例即证**：一份「能 parse、脚本不报错」的产物，可以是** 100% 错误**的。
所以验收必须落在**行为对拍**上 —— 判据与 oracle 构造法见 `obfuscator-io-four-step-pipeline.md`
的 §0（自造样本 + 原码 diff）与文中那条**「最低验收线」**（每步漏做都不抛异常，所以「跑通了」不算验收）。

| 验收动作 | 能不能过 |
| --- | --- |
| `node --check 产物.js` / 产物能 parse | ❌ 不算（作者产物就能过） |
| 产物无 undefined 变量、加载不报错 | ❌ 不算（漏旋转不产生未定义标识符） |
| 已知输入 → 输出与原文件浏览器结果**逐字一致** | ✅ 唯一合格 |
| 全量字符串与「旋转后」数组逐项相等 | ✅ 等价合格（离线可核） |

## §5 边界

- **本文只讲「静态索引替换」的坑**：讲「下标 → 字符串」在旋转未还原时的三个静默失败指纹。
- 其它 pass（字典对象、`??` 分支、控制流平坦化等）的漏做症状**不在本文**，
  见 `obfuscator-io-four-step-pipeline.md`（四步顺序依赖表）与 `obfuscation-detector.md`（分流）。
- 字符串表**怎么定位**（偏移量 / 旋转量 / 大数组名三点）、**恒等式自校验旋转**的四个静默失败点，
  见 `string-array-and-minimal-eval.md`。
- **与语言无关**：源文作者选 C# 只是他的偏好，**Python / Node / 任何语言用同一思路都会踩同一个坑** ——
  决定成败的是「有没有复现旋转」，不是用哪门语言。
- **与站点无关**：只要目标是「字符串表 + 数组旋转」的 obfuscator.io 类产物，判据就成立；
  但旋转量、偏移量、magic 值**每个样本都不同**，必须现场求，**不能硬编码**。
