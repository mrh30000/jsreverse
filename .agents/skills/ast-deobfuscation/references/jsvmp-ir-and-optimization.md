# JSVMP 中间代码优化与回译（IR / 常量折叠 / CFG 回 JS）

> 本文件是 **JSVMP 还原的第三阶段**（`反汇编 → IR → 优化 → 回译`）的唯一权威源。
> 上游读 `jsvmp-bytecode-and-decompiler.md`（字节码 → IR / 符号执行反编译）；
> 本文件的落点是**手上已经有一份 IR，怎么把它优化干净、再变回可读 JS**。
> 可执行件：`scripts/jsvmp-ir-optimize.js`（零依赖，`--selftest` 项数以实跑输出为准）。

## 0. 判据：什么时候该走"IR 优化"这一步

| 现状 | 该做什么 | 为什么 |
| --- | --- | --- |
| 只有密文/字节码，还没有 IR | 先去 `jsvmp-bytecode-and-decompiler.md` | 本文件全程假定 IR 已存在 |
| 有 IR，但满屏 `M[i]`、短整型跳转、重复块 | **本文件**（`optimize` 全链） | 这些是"反汇编的伴生噪声"，不是业务逻辑 |
| 有 IR，但读不出业务语义 | 本文件 `emit-js --style structured` | 先把控制流展开成 JS，再按人眼读 |
| structured 版看着对但不敢用 | 本文件 `emit-js --style flat` 做保底对拍 | flat 与 structured 是**两条独立代码路径**，一致才算对 |
| 需要在浏览器里跑同一份逻辑 | 本文件 `emit-js` 产物可直接当模块 | 产物不依赖 VM 运行时 |

**关键认知**：这一步的产物**不是最终交付**，是"推理的脚手架"。
真正的纯算实现靠读它来写；但它本身已经能跑、能对拍，所以它能当 **oracle** 用。

## 1. IR schema（`jsvmp-ir-optimize.js` 的输入契约）

```json
{
  "entry": 0,
  "constTable": { "21": 8, "22": 0 },
  "deadCases":  [27, 34, 41],
  "instrs": [
    {"addr":0,"case":5,"op":"mov","dst":"r1","src":{"t":"imm","v":5}},
    {"addr":1,"case":5,"op":"mconst","dst":"r2","idx":21},
    {"addr":2,"case":5,"op":"binop","dst":"r3","kind":"add","a":{"t":"reg","v":"r1"},"b":{"t":"reg","v":"r2"}},
    {"addr":3,"case":5,"op":"condbr","cond":{"t":"reg","v":"r3"},"t":4,"f":6},
    {"addr":4,"case":5,"op":"call","dst":"r4","name":"sha1","args":[{"t":"reg","v":"r3"}]},
    {"addr":5,"case":5,"op":"br","target":6},
    {"addr":6,"case":5,"op":"ret","src":{"t":"reg","v":"r3"}}
  ]
}
```

⚠️ 上面这份是**可直接喂给脚本的最小可跑样例**（已实跑）：`addr` 必须 **0,1,2,3,4,5,6 连续**。
随手写成跳号会被**拒绝执行**（退出码 2，报 `addr 必须是从 0 开始的连续整数`）——
这是刻意的：稀疏地址会让后面每一步的下标计算都变歧义。
`deadCases` 只在 `prune-cases --from-ir` 时才会被读取（命令行给了 `--dead` 就以命令行为准）。

- `addr` **必须是 `0..n-1` 的连续整数**。反汇编阶段很容易满足（按顺序 push），
  而它让 CFG 的边计算无歧义 —— 不要为省字节做稀疏地址，后面每一步都要用它做下标。
- ⚠️ `condbr` 的 `t` / `f` 也是 `addr`（**不是**"相对偏移"）。
  若你的反汇编器产出的是相对跳转，**在进本工具前先算成绝对地址**，
  否则 `restore-logic` 的"同一对后继"判据会整体失效，而它**不会报错、只是不还原**。
- `constTable` 未列出的下标语义**是 `null`**（不是 0，也不是"不存在"）。
  这条来自 x96：`this.M` 只在少数 case 里被赋值，其余位置读出来是 `undefined`。
- 运算语义按 **32 位**：`add/sub/mul/xor/and/or/shl/shr` 走有符号 32 位，`ushr` 走无符号。
  写错这一点不会报错，只会在进位/符号位处**静默给出不同的数**。

## 2. 五个优化 pass（以及每个 pass 为什么是安全的）

`optimize` 全链的**实际执行顺序**（以下为实测，与脚本 `cmd === 'optimize'` 一致）：

```
prune-cases  →  fold-const  →  restore-logic  →  simplify-cfg  →  restore-logic  →  simplify-cfg
                               └────────── 这一对跑两趟（不动点）──────────┘
```

两条容易写错、也容易抄错的点：

- 🔴 **`prune-cases` 在最前，不是第二**。删死 case 会**改变地址与 CFG 形态**，
  先删再折叠，后面的每一步都少做无用功；反过来先折叠也"能跑"，但白算一遍。
- 🔴 **`restore-logic` + `simplify-cfg` 要跑两趟**（不动点迭代）：
  第一趟的块合并 / 不可达块删除会让**新的 `&&`/`||` 形态浮现**，
  只跑一趟会漏掉这部分短路还原。脚本把两趟的统计**累加**后一起报（`--stats` 里的 `and=` / `or=` 是两趟之和）。
- 单独调用某个 pass 时各自独立（`fold-const` / `prune-cases` … 各是一条命令），
  上面这个顺序只约束 `optimize` 全链。

### 2.1 `fold-const`：常量虚假指令表折叠

来源（x96 3.0 原文做法）：扫描 `this.M[<数字字面量>] = <数字字面量>`，
记进字典；再把所有 `this.M[k]` **整体替换成字面量**，未出现在字典里的替换成 `0`（原文口径）／`null`（本工具口径）。

- **判据**：`M` 表里的值在**初始化阶段一次性写死**（不依赖时间、随机数、DOM）
  ⇒ 它就是个常量表，不是运行时状态。原文对该表的原话是"前面的计算其实也不用管，
  因为也没有涉及到时间和随机数，也就是说计算前是定值，那么计算后，也一定是一个定值"。
- 🔴 **坑**：原文把缺席项替换成 `0`，本工具用 `null`。两者在"参与位运算"时结果不同。
  选哪个取决于 VM 的读表实现 —— 若读表代码是 `M[k] || 0`，两者等价；
  若是 `M[k] === undefined ? null : M[k]`，就必须用 `null`。**回原文确认，不要默认。**
  （`--stats` 会分别报 `folded=` 与 `nulled=`，一眼能看出是不是替换成了 `null`。）

### 2.2 `prune-cases`：死 case 消除（唯一需要动态证据的一步）

死 case 只能**实测**得到，推不出来。方法是原文给的：

1. 在**所有 case 前面都下断点**；
2. 调试运行，命中就取消该断点再继续；
3. 跑完之后**还有断点的 case**，就是从未执行过的。

原文实测样本：`[27, 34, 41, 48, 101, 117, 124, 147, 258, 283, 380, 400, 449, 459, 468, 469, 473, 479, 481, 485, 491, 496, 506]`
（23 个）。删掉后**结果不变** ⇒ 反证它们确实与加密逻辑无关。

- **删完必须重跑一遍确认结果一致**。这是本 pass 的准出条件。
- 断点探测法的前提是"输入的覆盖度够"。**换一组输入可能激活另一批 case** ⇒
  死 case 清单要随输入更新，不要当成永久事实写死在脚本里。
- 🔴 **删 case 不是"过滤一下"就完事 —— 必须重定位地址**。因为 IR 契约里
  `addr` 必须是 `0..n-1` 连续整数，删掉指令后所有后续 `addr` 都要前移，
  `br.target` / `condbr.t` / `condbr.f` / `entry` 全部跟着改。
  **落在被删指令上的跳转目标无法重定位** ⇒ 此时**拒绝执行并原样返回**（不是猜一个邻近地址）。
  同理，"删完会把全部指令删空"也拒绝。
  ⇒ `jsvmp-ir-optimize.js` 的退出码语义在这里派上用场：
  `2` = 输入不满足前置条件（拒绝执行），与 `1`（算错/校验失败）区分开。

### 2.3 `restore-logic`：`&&` / `||` 还原（本文件最容易漏的一步）

**为什么需要它**：编译器把 `a && b` 落成两个嵌套条件分支，于是两个分支的
true/false 后继**完全一样**：

```
5394: condbr a ? 5697 : 208
5697: condbr b ? 6491 : 4758     ← true 走 6491
 208: condbr b ? 6491 : 4758     ← true 也走 6491；false 都走 4758
```

判据：**两个块的条件分支指向同一对后继** ⇒ 它们是被拆开的短路表达式。
识别后应还原成 `if (a && b) { 6491 } else { 4758 }`，并把其中一个块作为
**重复的花指令丢弃**（否则产物里每处短路都翻倍）。

- 原文佐证：**在该 VM 的指令集里找不到 `&&` / `||` 运算 opcode** ——
  这是"所有短路都被展平成分支"的侧面证据。
- 🔴 **语义代价（原文作者自己承认的瑕疵）**：还原成 `a && b` 之后，
  若 `a` 为假则 `b` **不应被求值**；但展平后的 IR 已经先算了 `b`。
  当 `b` 是纯计算时无影响；**当 `b` 有副作用（自增、赋值、函数调用）时会改变语义**。
  ⇒ 还原短路的**准入条件**：被合并的第二个条件块**不得含副作用语句**。
  本工具的 `--selftest` 用"解释器 / flat / structured 三方结果逐字节一致"守住这一点。

### 2.4 `simplify-cfg`：常量折叠 + 块内传播 + 恒真恒假 + 不可达 + 单前驱单后继合并

六件事一次做完。原文给的两条可直接抄的判据：

- 恒真/恒假分支：`Jz` 的条件在折叠后变成字面量 ⇒ 只留一条边，另一条成不可达块。
- **单前驱单后继合并**：一个块的后继只有 1 个、且该后继的前驱也只有 1 个 ⇒ 合并。
  原文用 3 步把 `352 → 300 → 368` 串成一条，合并后**少一个节点**，
  且**再次运行结果不变** ⇒ 安全的证据是"改完实跑结果一致"，不是"看起来少了一层"。

### 2.5 `emit-js`：两种发射器（**保底与可读互为交叉验证**）

| 风格 | 形态 | 用途 |
| --- | --- | --- |
| `flat` | `while (true) switch (pc)` 原样循环 | **保底**：语义上几乎不可能写错 |
| `structured` | `if/while/for` 还原后的可读 JS | 给人读 / 当纯算模板 |

**两者必须结果一致才算通过**。这不是"自己跟自己比"：
flat 是把 CFG 逐块翻译，structured 走的是**块合并 + 结构识别**这条完全不同的路径，
所以一致是一个真正的交叉验证。

> 教训来源：B8 的 `dcm` 末块写错时 `encrypt → decrypt` 仍完美往返（错得对称）。
> **往返自检抓不到对称的错误** ⇒ 凡"两条独立路径产出的东西"，比对它们比比对往返更值。

## 3. 反汇编的两个真实编码（先认编码，再定 bit-field）

同一族的 VM 会用**不止一种**操作码编码。两个实测样本：

### 3.1 12 位家族 + 独立 opstr 表（某乎 x96）

- `opcode[]` 从 base64 解出：`n = t.charCodeAt(0) << 8 | t.charCodeAt(1)`
  是操作码条数，随后每 **2 字节**一条：`opcode.push(t.charCodeAt(i) << 8 | t.charCodeAt(i+1))`
  （**大端两字节**）。
- 紧接着是**字符串表**：每条 `c = charCodeAt(a) << 8 | charCodeAt(a+1)` 是长度，
  后续 `c` 字节是密文，经 `k(u)` 解密后 push 进 `opstr`。**与操作码分开存放**。
- 操作码内部字段布局（12 位家族）：`family = (opcode[pc] & 0xF000) >> 12`，然后
  - `family 9`（取值/常量）：`t = (opcode[pc] & 0x0FFF) >> 10`、`s = (opcode[pc] & 0x03FF) >> 8`、
    `i = opcode[pc] & 0x03FF`、`h = opcode[pc] & 0x3F`
    （`t=0` → 寄存器 `global_<s>`；`t=3` → 字符串字面量 `opstr[h]`）
  - `family 10`（运算/赋值）：`t = (opcode[pc] & 0x0FFF) >> 10`、`a = (opcode[pc] & 0x03FF) >> 8`、
    `c = (opcode[pc] & 0x00FF) >> 6`
  - `family 14`：`name = opcode[pc] & 0x0FFF` ⇒ 声明 `_0x<name>` 函数
- 🔴 **别照抄这里的位宽**：这些常量是**针对该样本实测出来**的。
  换一个 VM 必须从反汇编器源码里重新读 —— 照抄只会在新样本上静默错位。

### 3.2 3 字节家族 + 内联字符串表（某乎 x96 3.0）

- `w = charCodeAt(0) << 16 | charCodeAt(1) << 8 | charCodeAt(2)` 是操作码条数，
  随后每 **3 字节**一条（大端）：`D.charCodeAt(k) << 16 | ... << 8 | ...`。
- 字符串表**紧随其后**，条目 = `E = charCodeAt(V) << 8 | charCodeAt(V+1)` 长度的密文，
  **解码函数随版本变**。3.0 实测的形态是**链式异或**（前一字节参与后一字节）：

```js
function decrypt_text(item) {
  let U = 66;                                  // 初始种子
  let M = [];
  for (let b = 0; b < item.length; b++) {
    M.push(String.fromCharCode(24 ^ item.charCodeAt(b) ^ U));   // 24 = 0x18
    U = 24 ^ item.charCodeAt(b) ^ U;           // ← 结果回灌，逐字节链式
  }
  return M.join("");
}
```

- **判据**：这个解码**有状态**（`U` 在推进），所以**同一条密文解两次结果不同**。
  忘了回灌 `U` 会解出乱码但**长度完全正确** —— 这类错不会报错。
- 实用的定位法：解码函数一定在**操作码解析之后、字符串表 push 之前**那几行里，
  且必然出现一个 `charCodeAt` 与一个**异或常量**（实测 `24`／`0x18`／种子 `66`）。
  ⇒ 先搜"异或常量"，再确认它有没有把结果回灌到下一轮。

## 4. 三个厂商的 opcode 语义骨架（写解释器的起点）

### 4.1 某 Q 音乐：寄存器式 VM，82 个 handler

- 8 个入口寄存器：`regs = [world, initialData, params, this, arguments, vm_runtime, vm_code, 0]`
- `CreateVmFunction` 是重心：`createVM1 / createVM2` 递归建**子 VM 函数**，
  所以"这个 VM 是一层又一层虚拟函数组成的"，给定入口函数开始执行。
- `CreateVmFunction` 的参数序（原文给全了，直接照写）：

  | 字段 | 含义 |
  | --- | --- |
  | `count` | 该函数临时 params 的个数 |
  | `param_i` | 具体 params |
  | `target` | 寄存器操作数，保存创建后的虚拟函数 |
  | `offset` | 新虚拟函数的 pc 偏移（`pc = off + offset`） |
  | `length` | 新函数的 `length` 属性（形参个数） |

- 🔴 **`Object.defineProperty(fn, "length", …)` 是必做动作**：VM 用 `length`
  来指示形参个数，且 `writable:false / enumerable:false`。漏掉会让
  `Function.prototype.length` 相关的判断（如 `apply` 的参数个数校验）走偏。
- 指令类别（原文逐条列了语义，可直接当语义表模板）：
  基础 `Mov / MovCall / LoadImm / LoadConstant`；算术 `Add/Sub/Mul/Div/Mod/Neg/PreIncrementAssign/PostIncrementAssign`；
  逻辑 `LogicalAnd/LogicalOr/LogicalNot`；位 `BitwiseAnd/Or/Xor/Not/Sal/Shr/Sar`；
  比较 `Cmp`；控制流 `Jz/Ret/Call`；对象 `NewObj/PropSet/PropGet`；
  字符串 `StrConcat`；特殊 `ArrayCreate/ConvertToNumber/CreateVmFunction`。
- **IR 抽象**：定义 `IRInstruction` 基类（`ir_name` / `address` / `ins_len`），
  指令类继承它；操作数分两类 —— `寄存器` 与 `立即数`。这是把 switch-case 变成
  对象模型的关键一步，也是 CFG 能建起来的前提。

### 4.2 某音：8 参数入口 + 分支类型

`_0x20653b(字节码, 函数基址, 函数长度, 本地变量, 闭包变量, 函数调用者, 无意义, 分支类型)`

> 字节码 + 函数基址 + 函数长度 ⇒ 可以定位任意函数的指令区间，
> 于是"按需生成单个函数的伪代码"成为可能（原文先拿 `open` 方法试的：
> 基址 578、长度 71）。**这是"函数级按需反编译"的入口参数表**。

### 4.3 腾讯 chaos：**随机分段**（这是抗脱壳设计，不是 bug）

原文观察到的四个 opcode case：
① 两个 case 明显可以合并成一种 opcode，却分成两种；
② `case4` 的第一行与 `case9` 一模一样，却不把 `case4` 拆成两条 opcode。

⇒ **结论（原文推测，逻辑成立）**：开发者**有意把最原始的字节码随机分段**，
把多条 opcode 合并成 1 条新 opcode。于是"程序 A 的脱壳器脱不了程序 B 的壳"。

**对本技能的实操含义**：
- 不要把"case 数与语义 opcode 数不等"当成反汇编出错；
- `scripts/jsvmp-mnemonic-table.js` 的"按 token 归一化"正是为这类**每次重排**设计的
  （见 `jsvmp-bytecode-and-decompiler.md` §2）；
- `case_map = {opcode: case}` 必须**从 vmp 源码的 switch 里现解析**，
  不能沿用上一次的映射表。
- 腾讯系 VM 的三步形态固定：① 传入参数（密文 / 起始 index / `SysObj` 原生对象表 /
  `name_array` 关键词数组）→ ② 密文解密成字节码（`i` 调 `b/d/e/c` 一串）→ ③ `while(true)` + switch 执行。
  **`name = name_array[x]; target = SysObj[name];` 这个间接层的作用是"把五花八门的函数调用
  统一成一类字节码"** —— 所以反汇编时环境访问会全部长一个样，必须靠 `name_array` 反查名字。

## 5. 常量取证：先判断"这堆整数到底是什么"，再谈算法

**本批最容易踩的坑：一串"神秘整数"并不等于"哈希常量表"。**

实测形态（`52pojie-2076005` 的插桩日志，RSA 公钥对象被整个打印出来）：

```
dB-->--> [,…,"-----BEGIN PUBLIC KEY-----\nMIGf…",,true,,"1764209708_jsvmp_secret_key_2024",,1764209708,,,
          true,"MTc2…",{default_key_size:1024,default_public_exponent:"010001",log:false,
          key:{n:{0:192007799, 1:114825681, …, 36:34738, t:37, s:0}, e:65537, d:null, p:null, q:null}}]
```

第一直觉是"37 个常量的数组 ⇒ 魔改 MD5 的 T 表"，**方向完全错**。
它的真实语义是：

| 判据 | 实测 | 结论 |
| --- | --- | --- |
| 有 `t`（limb 个数）与 `s`（符号），且 `t == 下标最大值 + 1` | `t:37`，下标 0..36 | 是 **bignum 的 limb 表示** |
| 所有 limb `< 2^30` | 最大 266222446 < 2²⁸ | 基数只可能是 30 位 |
| `n = Σ limb[i] << (30*i)`（**低位在前**） | bit 长度 **1096** | 即 RSA 模数 n |
| 隔壁就有 `e` | `e:65537`、`default_public_exponent:"010001"` | 确认是 RSA 公钥 |

**可执行判据**：`scripts/crypto-signature-id.js --selftest` 里有 `analyzeBignum()`
的断言组 —— 包括**反向断言**：「真正的 MD5/SHA-256 标准 IV 不得被判成 limb 大整数」
（它们的 limb 都 ≥ 2³⁰，天然被排除）。这条反向断言是防"什么都能认"的关键。

**处置**：见到这种数组，**第一步是把它还原成整数**（或直接丢给目标库的
`fromString/toString`），不要逐值 diff。

**反过来**，真正的"该逐值 diff 的常数表"长什么样：
长度是**算法常量表的长度**（如 MD5 的 64 个 `K`、SM4 的 32 个 `CK`），
且逐个与标准表对得上/差一点。工具已经把 SM4 的 `CK`、AES 的 S 盒等收进常量库
（见 `jsvmp-dynamic-instrumentation.md` §6.5）。**先跑工具再读代码** ——
这一族里"看起来像魔改、其实是标准"的比例极高（B12 的百度 BCE DRM 同结论）。

## 7. 纯算落地：两个**已实测通过**的算法形态

### 7.1 知乎 x96：8 轮轮转查表（base64 变体）

`52pojie-1645300` 给的函数**在 Node 里实跑，输出与原文公布的密文逐字符相同**：

```
输入 "8b7997937c8e4f4a0ca46008f9285561\u0000"（33 字符）
输出 aXFqc4uykHtY6Rt0M_Y8FD98e8NpgU28G0Yyo09yoTNX   ✅ MATCH
```
（原文把密文写作 `M\_Y8F`，其中的 `\_` 是 Markdown **转义反斜杠**，真值是 `_`。
逐字符比对时会因此差一位 —— 这类转义要先还原再当数据用。）

结构要点（这是"倒着取明文 + 三条轮转表"的典型）：

- **倒着取**：循环从 `len-1` 往前，每次消费 3 个字符；`len % 3` 补 `\u0000` 到整除。
- **三条轮转表**全都**随加密轮数循环**，且回绕时下标归零：

  | 表 | 值 | 语义 |
  | --- | --- | --- |
  | `A` | `[42,0,0,0]` | 与字符码异或 |
  | `B` | `[8,16,8,16]` | 左移位数 |
  | `C` | `[63,6,12,18]` | 掩码 / 右移位数 |

- 每轮产出 4 个字符：`charAt(E & C)` 与 3 次 `charAt((E >>> C) & 63)`。
- **字母表** `RuPtXwxpThIZ0qyz_9fYLCOV8B1mMGKs7UnFHgN3iDaWAJE-Qrk2ecSo6bjd4vl5`
  （64 字符，含 `_` 与 `-`）—— 是"标准 base64 表被打乱"的形态，
  **不要当 base64 解**，它就是个 64 元查表。

> 判据：`A` 的三个 `0` 和 `B` 的 `8,16` 交替，是"3 字节拼 24 位"的拆装痕迹。
> 见到"4 个字符一组 + 掩码 63"就该怀疑这一族。

### 7.2 某音 X-Bogus：`p1` 19 元素 → 七组四字符

`52pojie-1744197` 把 28 字符拆成 7 组 × 4 字符，**每组流程完全相同**，
差异只在"乱码串的起始下标"（第 1 组 0/1/2，第 7 组 18/19/20）：

```
baseNum = c2 | c1 << 8 | c0 << 16          // c0/c1/c2 = 乱码串连续 3 个字符的 charCodeAt
str1 = short_str[(baseNum & 16515072) >> 18]   // 16515072 = 0xFC0000
str2 = short_str[(baseNum &   258048) >> 12]   //   258048 = 0x03F000
str3 = short_str[(baseNum &     4032) >>  6]   //     4032 = 0x000FC0
str4 = short_str[ baseNum &       63]          //       63 = 0x00003F
```

- 四个掩码/移位数（`16515072 / 258048 / 4032 / 63`）**可写死** —— 原文实测"每个步骤 q 里面的取值都是一样的"。
- 字母表 `Dkdpgh4ZKsQB80/Mfvw36XI1R25-WUAlEi7NLboqYTOPuzmFjJnryx9HVGcaStCe=` 同样是被打乱的 64 元表。
- **乱码串是怎么来的**（同文给出）：`md5 → hex 转 Uint8Array → 再 md5 → 再转 Uint8Array` 得到 `uint8Array`；
  再取时间戳与 canvas 指纹各拆 4 字节，拼成 19 元素 `p1`，**按奇偶位置交错**得到 `p2`：

```
p2 = [p1[0],p1[2],p1[4],…,p1[18], p1[1],p1[3],p1[5],…,p1[17]]   // 偶数位在前、奇数位在后
```

  再用一个 **RC4 变体**（`_0x46fa4c`：标准 KSA + PRGA）打乱，最后**前置两字节**：

```js
function _0x2b6720(a, c, e) { return _0x583250(a) + _0x583250(c) + e; }   // _0x583250 = String.fromCharCode
_0x2b6720.apply(null, [2, 255, 乱码串])     // ⇒ "\u0002" + "ÿ" + 乱码串
```
- 🔴 **`第 n 个位置先是 null → 下一步就出字符`就是这一族的定位法**：
  在日志里搜完整结果串，找"第一次出现"的位置；日志里结果串的下一个元素先是 `null`、
  再下一步就出了某个字符 ⇒ **这两步之间就是那个字符的生成逻辑**。
  据此把上一步（`位置 2 索引I 16 索引A 738`）作为条件断点；
  因为 `位置/索引I/索引A` 的组合通常有 40+ 处，**必须再加一个 `S[7] == 21` 之类的限制条件**才能收敛。

## 8. 插桩日志的"读法"（IR 视角）

> **本节只保留与"IR / 回译"相关的部分**。日志采集、三层插桩、减量、预算递进、
> 干扰项处置、以及"整个库对象"那条富矿的完整口径，**唯一权威源是
> `jsvmp-dynamic-instrumentation.md` §4/§5/§8**（不要在两处重复维护）。

从 IR 视角看，日志分析只需记住三件事：

1. **先定"结果由几段拼成"，再逐段追。** 这一族几乎都是 `固定串 + 若干段派生串` 的拼接
   （实测：某 Q 音 sign = `zzc` + 3 段；`X-Bogus` = 7 组 × 4 字符；
   腾讯滑块 = 4 段各 `btoa` 后拼接再 `replace(/\+|\/|=/g,"")`）。
   **先量段数**能砍掉一大半搜索空间。
2. **索引取值点是必经之路。** 字母表 / 常量表 / 映射表都靠下标取，
   所以"日志衔接不上"多半是索引点没插桩（见 `references/jsvmp-dynamic-instrumentation.md` §4.4）。
3. **结果串的下一个元素先是 `null` ⇒ 下一步就是它的生成点。**
   这是逐字符反查的通用锚点：把"上一行的 位置/索引I/索引A"作为条件断点，
   再加一个额外限制条件（三元组常有 40+ 处重复）收敛到唯一位置。

### 8.1 腾讯系滑块的拼接形态（`collect` 参数）

实测形态（`52pojie-2084662` / `2086034`）：

- 结果 = **4 段**乱码串各自 `btoa` 后拼接，再 `replace(/\+|\/|=/g, "")`。**顺序是打乱的**。
- 每段乱码串 = 明文字符串**每 4 位一组**，`charCodeAt` 后与固定值/下标乘法做左移、
  再与上一次结果做或运算，最后 `String.fromCharCode` 拼回。
- **每段下面都直接打印了对应的明文字符串** ⇒
  **"研究透一段，其余三段只换明文再拼即可"**，工作量直接砍到 1/4。
- 🔴 关键辨识：`btoa` 是**标准的**（没有魔改），产物就是合法 base64 字符集；
  **被打乱的 64 元查表见 §7.1/§7.2 —— 两者不要用同一套解法**。

### 8.2 一条被忽略的富矿：**插桩日志会把整个"加密库对象"打出来**

用"打印整个对象"的日志断点（例如把 `apply` 的参数 `JSON.stringify` 出来、
并滤掉 `window` / 空值 / 超长字段），会**连带打印出加密库的内部状态**。
实测一例（`52pojie-2076005`）：

```
dB-->--> [,…,"-----BEGIN PUBLIC KEY-----…",,true,,
          "1764209708_jsvmp_secret_key_2024",,1764209708,,,true,
          "MTc2…",{default_key_size:1024, default_public_exponent:"010001", log:false,
                   key:{n:{0:192007799, …}, e:65537, d:null, p:null, q:null}},
          [Function:nI],,{},"jsvmp_secret_key_2024"]
```

一眼可读出四件事，**都不需要再逆算法**：

1. **算法族**：`default_key_size:1024` + `e:65537` + `BEGIN PUBLIC KEY` ⇒ RSA-1024，指数 65537；
2. **密钥材料**：`n` 就是公钥模数（limb 形式，判法见 §5）；
3. **明文构造**：`aT-->--> [8,"1764209708_jsvmp_secret_key_2024",[Function:concat],19,…]`
   ⇒ 时间戳 + 固定后缀 → `concat` → 再 `btoa` → 再 RSA，salt 直接读出来；
4. **混淆噪声**：`key:{d:null,p:null,q:null,dmp1:null,…}` 全是 null ——
   **这是 jsbn 对象的默认字段，不是"被擦除的私钥"**，不要在这上面找 `d`。

⇒ **实操口径**：插桩时优先选"能一次打出整个参数对象"的点，
往往比逐层打运算日志更快得出配方。
**判据：对象里出现库的内部字段名（`default_key_size` / `default_public_exponent` / `log`）
⇒ 你抓到了一整个库对象，先把它读干净再决定要不要继续插桩。**

| 靠"往返能还原"证明 `dcm`/分段类算法写对了 | 对称的错误往返照样通（B8 教训）；必须**逐字节对照独立推导的期望值** |
| 只打 `call`/`apply` 就下结论 | 日志必然衔接不上；要补运算与**索引取值**（§8 第 4 条） |
| 把日志里的所有数值都当真 | 原文明确存在**干扰日志**（§8 第 7 条）；只采信结果的数据流回溯链 |
| 把 token 里的"时间戳段"当签名的一部分去逆 | 先按 `-` 切段：`<32hex>-<10位秒>` 是"签名+时效"，时间戳要单独对拍（B12 同款） |
