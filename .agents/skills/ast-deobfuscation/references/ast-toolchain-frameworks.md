# 反混淆工具链框架形态（ast_tools 一族）

> 定位：本文件给的是「**拿来即用的第三方反混淆框架**」的**形态契约 + 选型判据 + 使用前提**，
> **不含任何一个 pass 的实现**。具体 pass 怎么写，指向
> `decode-obfuscator.md`、`obfuscator-io-four-step-pipeline.md`、`string-array-and-minimal-eval.md`。
> 本仓自己的分层管线见 `pattern-layering.md`。
> 样本来源：`docs/references/52pojie-1601414-ast框架一键还原某里140初体验.md`（2022-03，作者 漁滒）。

一句话：**框架的价值不在"它有几个 pass"，而在"每个 pass 各自独立 + 顺序由主函数集中声明"** ——
这才是「换一个站点只改其中一环」的前提。

## 一、框架形态：`sml2h3/ast_tools` 的契约

源文逐字描述的框架契约（**只有形态，没有实现**）：

| 位置 | 是什么 | 源文原话 |
| --- | --- | --- |
| `main.js` | **入口文件** | 「以 main.js 作为入口文件」 |
| `common_fix.fix` | **关键函数**：「把源代码得到输出代码」 | 「其中的【common_fix.fix】是关键函数，把源代码得到输出代码」 |
| `common_fix` 的来源 | 从 `pro/demo1_fix.js` 导入 | 「其中的【common_fix】是由【./pro/demo1_fix】中导入」 |
| `pro/demo1_fix.js` | **15 个各自独立的功能函数** + **一个主函数声明执行顺序** | 「这里一共有15个函数，每个函数都是各自专属的功能，最后是反混淆的主函数，表明了每个api的执行顺序」 |
| 「官方函数」区 | 文件开头统一 `import` Babel API | 「一开始是官方函数，基本所有使用babel库的都是这样导入api」 |

⇒ 于是这个框架的形状是：

```
main.js
  └── common_fix.fix(code) ── 一个函数，输入源码 → 输出源码
        └── ./pro/demo1_fix.js
              ├── [Babel 官方 API 的 import 区]
              ├── pass1() … pass15()      ← 15 个，各自独立、各干一件事
              └── main()（或等价的主函数） ← 集中声明 pass 的调用顺序
```

**判据：一个反混淆框架"能不能改"，看一眼它的 pass 是不是各自独立、顺序是不是集中声明就够了。**
顺序散落在各个 pass 内部互相调用的框架，改一个动作会连带改掉执行次序 —— 这是最难排查的一类 bug。

## 二、判据：为什么「函数独立 + 顺序显式」值得学

这两点各自的收益是分开的：

| 设计 | 收益 | 没有它的症状 |
| --- | --- | --- |
| **每个 pass 只干一件事** | 换站点时只替换其中一环，其余不动 | 一个 pass 里塞了 3 件事 ⇒ 只想改第 2 件，第 1、3 件的结果也跟着变 |
| **顺序由主函数集中声明** | 顺序即文档；调顺序不用翻实现 | 顺序藏在函数调用链里 ⇒ 「为什么 S2 必须在 S3 之前」只能靠读代码反推 |
| 文件头集中 import Babel API | pass 内只关心 AST 变换 | 每个 pass 各自 import，版本与命名不统一 |

**与"人工按文档一步步来"的对比**：手工路线的顺序知识写在文档里、靠人执行；
框架路线的顺序知识写在代码里、由机器执行。**两者要表达的是同一条顺序依赖**
（例如 obfuscator.io 的四步链，见 `obfuscator-io-four-step-pipeline.md`），
差别是**顺序错了会不会被静默吞掉**。

## 三、与本仓分层管线（`pattern-layering.md`）的关系

两者是**同一种设计**的两个尺度，不要二选一：

| 维度 | `ast_tools` 式（源文） | 本仓 `pattern-layering.md` |
| --- | --- | --- |
| 分层单位 | 15 个**函数**（进程内） | **通用变换层 / 检测与流水线选择层 / 站点适配层**（跨文件、跨脚本） |
| 顺序声明 | 一个**主函数**里显式列 | `scripts/pipeline-config.js` + `run-pipeline.js` |
| 站点差异 | 换一个 `pro/demoN_fix.js` | 新增 `references/patterns/` 下的站点文件 + `scripts/patterns/` 下的 pass 脚本 + 配置命中项 |
| 可回退性 | 靠 pass 独立、顺序可调 | **显式要求**：每阶段能独立运行与排查 |
| 可验证性 | 源文只说"执行速度快" | `detect-patterns.js` 命中 → `run-pipeline.js` 报告 → `collect-residue-metrics.js` 统计残留 |

**判据：**
**「函数独立 + 顺序显式」是内层（单文件、单样本）的纪律；本仓的"分层 + 可回退 + 可检测"
是外层（跨样本、跨站点）的纪律。** 要在本仓新增一个站点适配时，
先读 `pattern-layering.md`（四件事要一起补）；要在一个文件里手工推进一条 pass 链时，
照 `ast_tools` 的形状组织（15 个独立函数 + 主函数列顺序）。

⚠️ **不要把 `ast_tools` 的 15 个 pass 当成"本仓该有的 15 个脚本"**：本仓已经用
`deobfuscate.js` / `decode-obfuscator-pass.js` / `prune-opaque-predicates.js` / `fold-wrappers.js` /
`unpack-webcrack.js` / `deobfuscate-sojson.js` 等**职责更窄、边界更明确**的脚本覆盖了同类能力
（见 `../SKILL.md`「入口脚本」一节）。**回灌判据**见 `pattern-layering.md` 末条：
「除非某条规则已经在多个无关样本中重复出现，而且安全边界依然清晰，否则不要把站点规则回灌进通用脚本」。

## 四、使用前提与落地要点

```bash
npm install iconv-lite      # 源文两条分开装
npm install @babel/core

node main.js                # 入口；运行中会打印控制流反混淆的过程信息
# 默认输出到 demos/demo1/output.js        （源文原话【./demos/demo1/output.js】）
```

- **耗时量级**：源文在自述「（对比我的要好几分钟）」的语境下称
  「**大概10秒钟左右执行完成**」⇒ 这是**单样本、单机、2022 年**的数量级，不是 SLA。
- **入口只有一个**：`main.js`；改反混淆逻辑改的是 `pro/demo1_fix.js`，
  **不需要动 `main.js`** —— 这正是「顺序集中声明」带来的好处。
- **输入来自本地文件**（源文用 WebStorm 从 GitHub 拉项目、运行 `main.js`），
  不是从页面直接取；取页面源码见 `browsercli-tools.md`。

**★ 验收标准（最重要的落地判据）**：

> **「控制流被还原 + 字符串被解出，可读性显著上升」就算成功，不是「100% 去混淆」。**

源文的验收描述是「可以看到控制流已经被还原，字符串也已经反混淆好了，简单的一步操作，
将代码的可读性大幅增加」—— **这是"可读性提升"的验收，不是"算法已还原"的验收**。
⇒ 用它做**第一遍降层**，之后按残留类型走本技能对应的专项（见 `../SKILL.md` 的工作流第 5 步）。

## 五、边界（源文未声称通用）

- **源文是初体验**（2022-03，标题即「…初体验」），并且**明确说没有时间研究那 15 个函数**
  （「这里的15个自写的api反混淆函数还没有时间详细研究」）⇒
  **这一句同时是"框架契约可信"和"pass 内容不可信"的分界线**：
  契约（入口、15 个函数、主函数列顺序、输出路径）是**作者读了文件的结论**；
  pass 的实现细节作者**没读**。
- 源文的样本是「某里 140」（阿里系某个 140 字节/140 版本的混淆产物），
  **没有第二个站点验证** ⇒ 迁移性未知。
- 「执行速度快」是**作者的本地观察**（对比自己的实现"要好几分钟"），不是基准测试。
