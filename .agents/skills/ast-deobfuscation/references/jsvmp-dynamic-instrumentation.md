# JSVMP 动态插桩（三层插桩 / AST 自动插桩 / 日志取证）

> **本文是「插桩路线」的唯一权威源。** 反编译器（符号执行 / 助记符表）路线以
> `jsvmp-bytecode-and-decompiler.md` 为准；CFG 构建、异常表、PC 状态机、旁路 AST 以
> `jsvmp-cfg-and-symbolic-paths.md` 为准。三篇不重复维护同一份清单。
>
> 先读 `jsvmp-deobfuscation.md` 建立 VM 结构认知（栈式 / 寄存器式、字节码、解释调度循环），再读这里。

## 0. 判据：什么时候走插桩

| 目标 | 路线 | 成本 |
| --- | --- | --- |
| 只要**跑出结果**，不需要读懂 | 补环境（`web-js-env-patcher`） | 最低 |
| 要拿**一个常量 / 一个公式**（key、派生、编码表） | **插桩**（本文） | 低 |
| 要理解**完整控制流 / 数据结构**（判定链、编码器全貌） | 反编译器（`jsvmp-bytecode-and-decompiler.md`） | 高，一次性 |
| 只需要**知道该往哪插**（插桩点找不到） | 先做 CFG（`jsvmp-cfg-and-symbolic-paths.md` §1），再回来插桩 | 中 |

**判据：插桩解决「值是什么」，反编译器解决「结构是什么」。**
两者不是替代关系——多篇实战的共同结论是「**CFG 帮你定位插桩点，插桩帮你验证 CFG**」
（`52pojie-2023103` 原话：「通过这种方法可以辅助插桩，因为插桩最重要的是不知道插在哪里」）。

**什么时候**不要**插桩**：

- 目标有强环境检测且你只需要结果 → 补环境。
- VM 的指令数组每次彻底重排且助记符不稳定 → 反编译器也救不了，退回补环境。
- 目标 90% 是 `Math.random` / 时间戳噪声（见 §8）→ 插桩日志会被噪声淹没，
  先做「输出是否稳定」判定，再决定是否值得分析。

## 1. 三层插桩（顺序不可乱）

插桩不是一次插完，而是**由粗到细三轮**，每轮看一轮日志：

| 轮次 | 插什么 | 目的 | 典型产出 |
| --- | --- | --- | --- |
| **1.0 函数调用层** | `fn.call(...)` / `fn.apply(...)` | 看**大致流程**：输入怎么被处理、出现了哪些标准算法、结果怎么拼 | 「某段输出 40 位 ⇒ 疑似 SHA-1」 |
| **2.0 运算符层** | `+ - * / % ^ & \| << >>` 等 | 深析**内部结构**：某个数组/字符串是怎么算出来的 | `res = index*2 + a*16 ^ b` |
| **3.0 赋值层** | `x = y` | 定位**常量来源**：字典表、固定数组从哪来 | `{0..9,A..F}` 字典 + 20 元素定值数组 |

**为什么必须这个顺序**：1.0 的日志量最小、信息密度最高，先建立「哪里是加密、哪里是拼接」的地图；
2.0 会把日志量放大一到两个数量级（每个运算一条），所以必须在 1.0 缩小范围之后再插。
反过来先插 2.0 会直接淹死。

**实测口径**（`52pojie-2096887`）：三轮之后 sign 的全部参数都能还原；
`52pojie-2034891` 第一轮 apply 插桩的日志「大概一万多行」——这就是为什么第二轮必须先有范围。

### 1.1 只插**真正走到的**分支

VM 里同一个语义常有 `i` 和 `a` 两个重复解释器（`2116112` 的 `i()` / `a()`），
**先打断点确认走的是哪一个**，只插那一个。两个都插 = 日志量翻倍 + 两个都看不懂。

判据：源码里搜 `.apply(` / `.call(`，在浏览器里只给**实际命中的那一处**打断点。

## 2. 四种插桩实现方式（选型表）

| 方式 | 做法 | 优点 | 代价 / 风险 |
| --- | --- | --- | --- |
| **手动** | 直接在源码里改，加 `console.log` | 零依赖、立刻可用 | 超过 3 处就不可维护；改错难回滚 |
| **AST 自动**（本文 §3） | 用 Babel 定位节点、构造 `console.log`/`push` 节点 | 可复用、可批量、可回滚 | 需要**语义等价性验证**（§3.4） |
| **运行时改解释器** | 在 DevTools 里直接改 `fn.apply` 等原生方法 | 不动源码 | 只适合一次性观察，不可复现 |
| **旁路 AST SDK** | 把 `@babel/types` 打进页面，在 opcode handler 里**同时**建 AST | 边执行边出 AST，不破坏原流程 | 见 `jsvmp-cfg-and-symbolic-paths.md` §0 与 §4 |

**默认选择**：≥3 个插桩点 ⇒ AST 自动；只有 1 处 ⇒ 手动。
`52pojie-2096887` / `2034891` / `2073645` 系都是手动起步、发现要插十几处之后转 AST 的。

**AI 辅助插桩**（`52pojie-2027657` / `2106666` 的实践）：把「目标 + 要观察的变量 + 期望日志格式」
给模型，让它产出插桩代码，再**人工核对插桩点是否覆盖了关键路径**。
适用信号：`if/else` 分支极多、`switch` 极长、手写定位特征成本高。
**注意**：AI 产出的插桩代码同样要过 §3.4 的语义等价性验证，不能因为「能跑」就信。

## 3. AST 自动插桩

### 3.1 定位特征（按可靠性排序）

1. **解释器主循环内的赋值**（最可靠）：`ExpressionStatement` → `AssignmentExpression`，
   且父节点是 `SwitchCase`、后兄弟节点是 `BreakStatement`（`52pojie-2079058` 的做法）。
   这个特征直接圈定「指令 handler」，不会误伤业务代码。
2. **`.call` / `.apply` 出现在赋值右侧**：`AssignmentExpression.operator === '='
   && right.type === 'CallExpression' && right.callee.property.name === 'call'`（`2123850` 的做法）。
3. **裸的 `fn.apply(...)`**：定位最宽，会误伤函数绑定类 `apply`（如 `fn.bind` 相关），
   需要人工排除——`52pojie-2034891` 明确写了「排除用于函数绑定的 apply，需要插桩的就这一处」。

**优先用 1，其次 2，3 只作为兜底。**

### 3.2 节点构造

`console.log` 在 AST 里不是一个节点，而是
`CallExpression(callee = MemberExpression(Identifier('console'), Identifier('log')), arguments=[...])`。
所以要分两步构造，并**封装成函数**复用：

```js
function insertLog(args) {           // args: 数组，元素是已构造好的节点
  const member = t.memberExpression(t.identifier('console'), t.identifier('log'));
  return t.callExpression(member, args);
}
```

**生产环境不要用 `console.log`**：VM 一轮执行几十万条指令，`console.log` 直接卡死浏览器。
改成 `__vmpLog.push([...])`（见 §4）。

### 3.3 两个必须处理的坑

#### (1) 「动态 k 值」——先改后还原

有些 VM 把操作数编号写成 `k++`（每次 handler 命中就自增），直接插桩会读到错的 k。
`52pojie-2079058` 的做法是**两趟**：

1. 先把 `k++` 改写成可计算形式（把 `UpdateExpression` 节点替换成 `k - index`，
   **注意 index 要按出现顺序倒排**：`updateExpressions.reverse().forEach((p, i) => p.parentPath.node.property = k - i)`）；
2. 插桩；
3. 再把 `k - index` 还原成 `k++`。

**为什么必须还原**：不还原会让「插桩后的代码」与「原代码」语义不同，
你拿它跑出来的日志对应不上真实执行路径。

#### (2) 二次调用导致走错分支

插桩代码本身如果**再调用一次被插桩的函数**（例如把 `f(x)` 的结果同时喂给日志和业务），
会触发第二次执行，`k++` 之类的有状态变量被多推进一次 ⇒ **后续分支整体错位**。
这是 `52pojie-2079058` 作者被大佬提醒后才发现的坑。

**规则：插桩只读不调用。** 要记录返回值，就把返回值先赋给一个临时变量，
日志读这个临时变量，不要再调一次函数。

### 3.4 语义等价性验证（**必做**）

> 来源：本技能 B3 批次的真实事故——某个 AST pass 静默删掉了约 9,096 个节点的代码，
> 产物**仍能被 parser 解析、`errors = 0`**，只有节点数对比才抓得到。

插桩 pass 写完后，必须跑完这三条，缺一不可：

1. **实跑对拍**：同一份夹具，`node <原文件> > a.txt` 与 `node <插桩文件> > b.txt`，
   除日志输出外**结果必须逐字节一致**。
2. **节点数对比**：`nodesAfter > nodesBefore`（插桩只会**增加**节点）。
   如果 `nodesAfter <= nodesBefore`，说明有代码被静默删除，立刻停手。
   本仓库现成工具：`node artifacts/skill-evolution/tools/count-nodes.js`。
3. **幂等/重复插桩守卫**：插桩产物里打一个哨兵（如 `globalThis.__VMP_INSTRUMENTED__ = true`），
   再次插桩时检测到哨兵就**报错退出**，而不是插第二遍。

本技能提供 `scripts/jsvmp-instrument.js` 一键完成上述三条（`--selftest` 自带合成 VM 夹具）。

## 4. 日志采集

### 4.1 采集方式

| 方式 | 适用 | 说明 |
| --- | --- | --- |
| `console.log` 直打 | 一次性、日志 < 500 行 | 超过就卡；且 DevTools 会截断历史 |
| **push 到数组，最后一次性 dump** | 默认选择 | 不受 DevTools 缓冲限制 |
| 分阶段断点 + 条件过滤 | 日志上万行 | 见 §4.3 |

**dump 时不要直接 `JSON.stringify` 整个数组**：环境值里有循环引用和特殊对象，会抛错。
需要一份「不会抛错的 stringify」（处理循环引用 + `Symbol` + 函数 + 长度截断）。

> **本技能不提供这个 safe-stringify 的实现**（已知缺口）：`2104849` 的导出器里带了完整的
> `maxDepth` / `maxArrayLength` / `maxObjectKeys` / `maxStringLength` 截断配置，
> `2073641` 则建议「直接找 AI 要一份 JSON 避免报错的代码」。
> 你要么照这两篇自己写，要么**改用 `push` 到数组后分批 dump**，
> 但**不要**假定本技能有现成工具而直接 `JSON.stringify`（会抛 `Converting circular structure to JSON`）。

### 4.2 导出到本地

浏览器控制台导出脚本（`2104849` / `2106666` 都提供了同类脚本）要满足：

- 拦截 `console.log/warn/error/info/debug`，**保留原方法**（不能无条件置空，见
  `../../web-reverse-algorithm/references/09-antidebug-and-automation-fingerprint.md`）；
- 分批导出（`exportBatchSize`）、可关的自动导出定时器；
- 支持 `txt` / `json` / `jsonl`；
- 保留调用栈（可选）。

**分析工具**：上万行日志用编辑器打开会卡，`2106666` 推荐 **klogg**（轻量日志查看器，支持大文件与正则过滤）。

### 4.3 日志减量

- **固定密文**：把明文固定成 `'1'`（`52pojie-1983577` 的习惯），日志会明显变短、更容易看出「哪一段是常量」。
- **hook 随机源**：`Math.random`、`Date.now`、`crypto.getRandomValues` 全部固定，
  保证同一套日志可复现。
- **条件断点**：先统计某个判定值出现多少次，再在第 N 次打断点（`2073641` 里 `t=30` 出现 9,520 次，
  在第 9,520 次断住）。
- **阶段性断点**：不要只打一个断点，按阶段多打几个，防止 DevTools 崩溃。

## 5. 日志分析工作流

**核心方法：从结果倒着往上推。**

```
最终结果 → 它由哪几段拼成 → 每段由哪个函数返回 → 该函数的入参从哪来 → … → 直到入参是明文/常量
```

实操要点：

1. **先认长度**：结果长度是识别算法的第一线索（40 hex ⇒ SHA-1 / 32 hex ⇒ MD5）。
2. **找拼接点**：最终串常常是 `固定前缀 + 段1 + 段2 + 段3`（`52pojie-1983577` 的 `zzc` + 三段）。
   把每一段的来源分别定位，任务就被拆成 3 个独立小问题。
3. **识别「定值」**：多传几组不同输入，**重复出现的就是常量表**（`52pojie-2096887`：
   `[23,14,6,36,16,40,7,19]` 与 `[16,1,32,12,19,27,8,5]` 是固定的索引数组）。
4. **索引数组的语义**：`'SHA1结果'.charAt(索引)` 逐字符拼接是最常见的形态。
5. **往上找第一个「长度合理」的数组**：`52pojie-2096887` 找 1280 长度数组时，
   往上是 `1252`（`charCodeAt` 逐字节）、再往上是明文表单数据——**长度跳变处就是算法边界**。
6. **`return` 是最有价值的断点**：`52pojie-2023103` 的经验是「重点关注指令集很长的 case，
   尤其是 `case 1 --> return`，通过它可以直接在对应位置打上断点输出结果」。

**日志折叠**：把 `[BIN_n] 左值/右值/结果` 三行折叠成一个表达式，日志会缩短一个数量级。
落地方式是把「运算符层」的插桩输出**改成一条**（即 `__vmpLog.push(['BIN', op, left, right, left op right])`），
而不是打三行——**在插桩阶段就合并，比事后写脚本折叠更省事**（日志格式由你自己的插桩器决定）。

**⚠️ 已知缺口**：本技能目前**没有**「通用日志折叠器」脚本。
`2106666` / `2104849` 的分析都是靠 **klogg + 手工过滤**完成的。
原因是各家日志格式差异过大，通用折叠器的投入产出比不成立。
如果后续遇到同一格式的日志重复出现 ≥3 次，再考虑补一个日志折叠脚本（命名待定）。

## 6. 标准算法识别（长度 → 寄存器特征值 → 轮函数）

只靠长度不够（40 hex 可能是 SHA-1，也可能是魔改后的 MD5 变体）。
**三层证据同时成立**才下结论：

### 6.1 第一层：输出长度 / 字符集

| 输出 | 候选 |
| --- | --- |
| 32 hex | MD5 / HMAC-MD5 / 魔改 MD5 |
| 40 hex | SHA-1 |
| 64 hex | SHA-256 |
| 32 hex 且有大写 | 可能是 `btoa` 后的 24 字符，不是 hex |
| base64 且含 `+ / =` | `btoa` 家族 |

### 6.2 第二层：**初始寄存器特征值**（最硬的证据）

把日志里出现的「一组定值数组」转成 16 进制，对照标准 IV：

| 算法 | IV（hex） | 十进制 |
| --- | --- | --- |
| MD5 | `0x67452301, 0xEFCDAB89, 0x98BADCFE, 0x10325476` | 1732584193, 4023233417, 2562383102, 271733878 |
| SHA-1 | `0x67452301, 0xEFCDAB89, 0x98BADCFE, 0x10325476, 0xC3D2E1F0` | 1732584193, 4023233417, 2562383102, 271733878, 3285377520 |
| SHA-256 | `0x6A09E667, 0xBB67AE85, 0x3C6EF372, 0xA54FF53A, …`（8 个） | — |
| SM3 | `0x7380166F, 0x4914B2B9, 0x172442D7, 0xDA8A0600, …`（8 个） | — |

**MD5 与 SHA-1 的前 4 个 IV 完全相同**——所以「看到 1732584193 就说是 MD5」是错的。
**判别点在第 5 个值**：MD5 只有 4 个寄存器，出现第 5 个 `3285377520` 才是 SHA-1。

**这就是本批新增 `scripts/crypto-signature-id.js` 要解决的问题**：
给它一组数字，它同时报出所有可能命中的算法，并**逐值列出差异**。

### 6.3 第三层：轮函数结构

- **每 80 轮后更新 h0..h4** ⇒ SHA-1（`2116112` 的判据：`h0` 的新值 = 上一轮 `h0` + 临时变量）。
- **每 64 轮、4 个轮函数轮换** ⇒ MD5。
- **每 20 轮换一个处理函数** ⇒ SHA-1 的 `f1/f2/f3/f4`。
- **单块处理前读 64 字节（512 位）** ⇒ 分组长度 512 位。

### 6.4 第四层：padding 反推（**算完必须拿日志核对**）

标准 MD5/SHA-1 的 padding 是 `1 个 0x80 + n 个 0x00 + 8 字节大端长度`。用**字节视角**
（VM 里操作的就是字节）算：

```
r = L % 64                                  # 最后一个残块的字节数
若 r < 56:  补 1 字节 0x80 + (55 - r) 个 0x00 + 8 字节长度
若 r >= 56: 本块补满到 64，再新开一块 56 字节的 0 + 8 字节长度
校验：补完总长必须是 64 的整数倍
```

**工具**（本技能 `crypto-signature-id.js --padding`，自带断言）：

```bash
node .claude/skills/ast-deobfuscation/scripts/crypto-signature-id.js --padding 971
#  r=11 → 0x80×1 + 0x00×44 + 长度 8 字节 → 总长 1024（可被 64 整除）
```

**`52pojie-2116112` 的实测（971 字节请求体）**：

- `971 % 64 = 11` ⇒ 最后一块只剩 11 个有效字节；
- 按标准公式补：`0x80` 1 个 + `0x00` **44** 个 + 长度 8 字节 ⇒ 总长 `971 + 53 = 1024`（= 16 × 64）✓
- 原文的预期观察是：日志里应当出现 `0x7D7D7D00 | 0x80`（= `2105376000 | 128`），
  因为明文末尾三个字节是 `}}}` = `0x7D7D7D`，`0x80` 应紧跟在同一个 32 位字里。

**⚠️ 原文的重点不是公式，而是它对不上**：实际日志里**根本没有**这个值。
作者由此判定**这个 VM 的实现是非标准填充**，转而用日志的实际值反推它自己的方案。

> **顺便：原文这段的中间算术是错的**——它写「`64 − 11 − 1 = 42`」，但 `64 − 11 − 1 = **52**`；
> 并且把「一个 block」说成 32 位（SHA-1 的一个分组是 512 bit = 64 字节）。
> 与 §7 的 hex 换算错误是同一类问题：**文章里的数字一律自己算一遍**。
> 本节的 `44` / `1024` 是本仓库用 `--padding` 重算并断言过的值，与原文的 `42` 不同，**以本节为准**。

**结论（本节真正的可用结论）**：padding 公式只用来**生成预期值**；
必须拿**日志实际值**核对，**对不上就说明这个 VM 的 padding 是非标准的，此时一律以日志为准**。
另外，若填充位置/长度整体错位，**先验证分组长度是不是 512 bit**，再谈 padding。

## 7. 魔改常量取证：**标准 vs 实测逐值 diff**

> 这一节是本批最可复用的方法。判据：**不要看代码，看数字。**

拿到日志里的常量数组后，**逐值**与标准实现对照，差异就是「改了什么」：

**实例 A（`52pojie-2034891`，某程 token）**

日志给出 `[1732584201, 4023233415, 2562383102, 271733878, 942946097, 7, 3614090360]`，转 16 进制：

```
0x67452309  0xEFCDAB87  0x98BADCFE  0x10325476  0x38343731  0x7  0xD76AA478
```

- 前 4 个 = **标准 MD5 IV + 微小偏移**（`0x67452309` 差 `+8`、`0xEFCDAB87` 差 `−2`，C/D 未改）；
- 第 5 个 `0x38343731` = 非标准（MD5 只有 4 个寄存器，这是额外的状态寄存器）；
- `0x7` = 计数器 / 轮数；
- `0xD76AA478` = **标准 MD5 的 T[0]** ⇒ 确认是 MD5 家族，T 表没改。

> **⚠️ 踩坑留痕**：`52pojie-2034891` 原文把这第 5 个值写成 `0x38514731`，
> 但它自己给的十进制 `942946097` 实际是 **`0x38343731`**（`0x38514731 = 944850737`）。
> **文章里的十六进制换算不可信，一律自己转一遍**——
> `node .claude/skills/ast-deobfuscation/scripts/crypto-signature-id.js --input "..."` 会直接打印实测 hex。

**实例 B（`2106666`，某程 phantom-token）**

日志中 `A = 0x67452309`（标准 `0x67452301`，**+8**）、`B = 0xEFCDAB87`（标准 `0xEFCDAB89`，**−2**）、
`C`/`D` 未改、**多了一个非标准 `H4` 寄存器**。⇒ 结论：**只改 IV**，T/S 表未动。

> 两个实例的 diff 完全一致（`+8 / −2 / 0 / 0`）——**同一家公司的两个产品用了同一套魔改**。
> 这类「同族复用」是魔改常量取证的高价值副产品：找到一个就等于找到一族。

**工具输出的实际形态**（复现 `52pojie-2034891` 的结论，逐值 diff 由机器算出）：

```
[7 个元素]
  ⚠️ 疑似魔改 MD5（容忍前缀 4/4，其中精确相等 2 个）
     逐值 diff（实测 - 标准）:
       [0] 实测 0x67452309 (1732584201) / 标准 0x67452301 → diff +8  ≠
       [1] 实测 0xEFCDAB87 (4023233415) / 标准 0xEFCDAB89 → diff -2  ≠
       [2] 实测 0x98BADCFE (2562383102) / 标准 0x98BADCFE → diff 0  =
       [3] 实测 0x10325476 (271733878) / 标准 0x10325476 → diff 0  =
     佐证：输入里命中 MD5 的 T/K 表常量 1 处
  单值常量命中:
     [6] 0xD76AA478 = MD5 T[0]
```

**判族为什么要「佐证」**：MD5 与 SHA-1 共享前 4 个 IV，
单看「4 个值像 MD5」无法排除 SHA-1。`crypto-signature-id.js` 用
**容忍前缀占比 + T/K 表常量命中数**一起打分定族——
上面这个例子里 MD5 得 `4/4 + 0.2×1`，SHA-1 只有 `4/5 + 0`，所以判 MD5（并保留同分候选）。

**操作步骤**：

1. 从日志里把「初始化那一组定值」抄出来；
2. 跑 `crypto-signature-id.js` 得到「命中的标准算法 + 逐值 diff」；
3. 按 diff 改本地实现（**只改被改的常量**，T 表/S 表没改就不要动）；
4. **用真实密文对拍**：改完后用同一输入跑本地实现，与浏览器结果逐字节一致才算完。

**为什么这一步能省大量时间**：`2034891` 的作者原话是「照着日志检查一下特征数，然后改一改，
最后发现魔改的不多，改一下这个就行了」——**没有读一行 VM 字节码**。

## 8. 噪声 / 防重放与字段边界（指纹类 VMP 必读）

`2106666` 的 phantom-token 是一个「**指纹长串 + 噪声包裹**」的典型。三条机制：

### 8.1 噪声字符

```
charCode = ceil(random() * 94) + 36        # 范围 37 ~ 130
```

**注意 128–130 是不可见的 Unicode 控制字符**：

- 在日志文本里**不显示**；
- 复制粘贴时会**静默丢失**；
- 于是「从日志里复制指纹串到本地跑」的结果必然对不上。

**处置：日志必须落成文件（含不可见字符的转义形式），不要手工复制。**

### 8.2 无分隔符拼接 ⇒ 字段边界不可从字符特征判断

22 个字段的噪声与数据**直接拼接，没有分隔符**，且噪声的字符范围与真实数据**完全重叠**
（字母/数字/符号都在 37–130 内）。例如 `Xp@cb74974f828eab54011bb68d4ee0d5a8/Pr` 中
`Xp@` 与 `/Pr` 是噪声，中间 32 位才是 MD5。

**结论：不要试图用「找到 32 位 hex」来切字段。** 必须还原 VM 里每个字段的噪声长度配置。

### 8.3 噪声的目的（决定了你的处置策略）

| 目的 | 机制 | 对逆向的影响 |
| --- | --- | --- |
| **防重放** | 噪声由 `Math.random()` 驱动 ⇒ 同浏览器同请求两次 token 也不同 | 服务端无法用「token 重复」判重放 |
| **防字段提取** | 无分隔符 + 字符范围重叠 | 静态切字段必失败 |
| **不可见字符陷阱** | 产出范围含 128–130 | 文本复制会丢字符 |

**派生效应**：噪声 → 指纹串不同 → 种子不同 → 字母表演化链（洗牌）完全发散 → 最终 token 不同。
所以**「同一输入两次结果不同」不代表你分析错了**，先确认噪声源再判断。

### 8.4 洗牌类字母表演化（同类结构速查）

`2106666` 的 shuffle：

```python
def shuffle_alphabet(alphabet, salt):
    chars = list(alphabet); v = 0; acc = 0
    for i in range(len(chars) - 1, 0, -1):
        v %= len(salt)
        integer = ord(salt[v]); acc += integer
        j = (integer + v + acc) % i
        chars[j], chars[i] = chars[i], chars[j]
        v += 1
    return "".join(chars)
```

配套的**基数拆位拼接**（43 进制 = 字母表长度）：

```
两个字符 = 长串[num / len(长串)] + 长串[num % len(长串)]
```

**判据**：只要日志里出现「一个整数被拆成两个索引」，就先试「整除 + 取余」，
`num / L` 与 `num % L` 必须都落在 `[0, L)` 内——不满足就换 L（很可能是字母表长度而不是 36/64）。

## 9. 反例黑名单

- **不要一次插完三层。** 2.0 的日志量会把 1.0 的结论淹没；顺序是 1.0 → 2.0 → 3.0。
- **不要用 `console.log` 插生产级 VM。** 一轮几十万条直接卡死；用 `push` 到数组最后 dump。
- **不要深拷贝插桩用的节点后**只改副本**而忘了替换原节点**——日志会打印「改之前」的值。
- **不要在插桩代码里再调用一次被插桩函数。** 有状态变量（`k++`、`pc`）会被多推进，后续分支整体错位。
- **不要因为「`--selftest` 全绿」就认为插桩正确。** 必须做**实跑对拍 + 节点数对比**（§3.4）。
- **不要从日志文本里手工复制含噪声的字符串。** 128–130 的不可见字符会静默丢失（§8.1）。
- **不要看到 1732584193 就断言 MD5。** SHA-1 的前 4 个 IV 与之相同，判别点在第 5 个值（§6.2）。
- **不要跳过「只插真正走到的分支」这一步。** 重复解释器（`i()` / `a()`）两个都插 = 日志翻倍且互相干扰。
- **不要假设 padding 一定存在。** 先按 §6.4 用长度算，再回日志核对。

**关于 `-r` 预加载的两条硬约束**（都踩过）：

1. `-r` 后必须写 `./` 或**绝对路径**：`node -r artifacts/... ` 会直接
   `Cannot find module`（Node 把它当裸包名解析）。正确写法是 `-r ./artifacts/...`。
2. 预加载要**同时覆盖 CJS 与 ESM 两条解析链**：
   `jsvmp-instrument.js` / `jsvmp-mnemonic-table.js` 走 `require`（CJS），
   而 `analyze-jsvmp-vm.js` / `../../web-reverse-algorithm/scripts/detect-crypto.js` 是**原生 ESM**
   （顶层 `import`），CJS 的 `Module._resolveFilename` 补丁**拦不住**它们。
   本仓 `tools/node-resolve-preload.js` 已同时注册 CJS 补丁与 ESM resolve hook
   （`tools/esm-resolve-hook.mjs`），一条 `-r` 即可跑通两类脚本。
   若换成别的 Node 版本导致 ESM 侧失效，症状是 `ERR_MODULE_NOT_FOUND`——
   检查 `node -v`（`module.register()` 需要 ≥ 20.6）。
