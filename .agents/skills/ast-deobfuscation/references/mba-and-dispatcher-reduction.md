## 1. 什么时候该用这份文档

满足以下任一条件时读本文，而不是继续调 `references/opaque-predicates.md`：

- 控制流平坦化的 dispatcher 变量不是「单一状态值」，而是**由状态值按位切片**算出来的多个变量（典型形态：`Ci = 31 & li; fi = li >> 5; mi = 31 & fi; ...`）。
- 表达式里出现大量 `~` / `&` / `|` / `^` 与 `+` / `-` / `*` 的混合，且看起来在隐藏一个很简单的运算（`x ^ y`、`x + y`、`x - y`）。
- 目标是 VMP 的「万用门」混淆：`not_not_and` / `not_not_or` 模拟出其它逻辑与算术指令。

## 2. 多层 switch dispatcher 归约

### 2.1 识别形态

```js
for (var li = 16996; void 0 !== li;) {
    var Ci = 31 & li,  fi = li >> 5,
        mi = 31 & fi,  bi = fi >> 5,
        Ai = 31 & bi;
    switch (Ci) { case 0:
        switch (mi) { case 0:
            switch (Ai) { case 0: Dn.push(0), li = 11522; break;
                          case 1: L = mo,     li = 24641; break; ...
```

三个变量都是 `li` 的**位切片**，宽度 5 位（`& 31`）。这是「把一个大 switch 拆成三层嵌套 switch」的混淆，目的是让静态阅读时必须同时跟踪三个变量。

### 2.2 归约配方

位切片是**可逆的线性映射**：已知 `Ci/mi/Ai` 就能反算出唯一的 `li`。

```
li = Ci | (mi << 5) | (Ai << 10)
```

对上例：`Ci=0, mi=0, Ai=1` → `li = 1024`，正好对应原文归约后的 `case 1024:`。校验一下原值：`li=16996 → Ci=4, mi=19, Ai=16 → 4 | (19<<5) | (16<<10) = 16996` ✓

**自动化做法**（不要手算）：写一个 AST pass，对每个最内层 `case`，从外到内收集各层 `case` 的字面量，按「外层 shift 为 0、下一层 shift 为切片宽度、再下一层 2×宽度」的规则拼装成单个数值，然后把三层 switch 替换成一层 `switch (li)`。切片宽度从 `31 &`（→5 位）、`255 &`（→8 位）、`0xFFFF &`（→16 位）这些掩码直接读出来，不要硬编码 5。

### 2.3 归约后再做两件事

1. **拆逗号表达式**：`Dn.push(0), li = 11522;` 一次执行两条语句，无法逐条下断点。按 `references/sequence-normalization.md` 拆成独立 `ExpressionStatement`。
2. **串接 case 尾跳转**：每个 `case` 的最后一句总是指向下一个 `case`（`li = 11522` / `li = z ? 8833 : 15362`）。把「被指向的 case」拼到当前 case 尾部，反复迭代直到每个 switch 只剩一个 case；单 case 的 switch 等价于没有 switch，直接内联函数体。

完成后控制流变成自上而下，字符串仍是混淆态——那是下一阶段的事，不要混在一起做。

## 3. 控制流平坦化的顺序依赖（静默失败）

`while + switch` 的还原**依赖「字符串数组先还原」这个前置步骤**，而且顺序错了不会报错。

失败链条（已在真实样本上复现）：`handlerWhileSwitch` 靠 `node.value.includes("|")` 找执行顺序串。若字符串尚未还原，兄弟节点里先命中的是 `_0x315530(0x3b)['split']('|')` 里的字面量 `'|'`，于是取到 seq = `"|"`，`caseMap` 一个都匹配不上，`replaceWithMultiple([])` **把整个循环删掉**——函数体被清空，产物仍能正常 parse。

**硬守卫**（放进任何 CFF handler，缺一不可）：

```js
const seq = sequenceArray;                    // 如 ["3","1","2","0","4","5"]
if (!caseMap || Object.keys(caseMap).length === 0) return;      // 没有可映射的 case
if (!seq.every(k => caseMap[k] !== undefined)) return;          // 顺序串有孤儿项
if (seq.length !== Object.keys(caseMap).length) return;         // 数量不匹配
// 通过后再 replaceWithMultiple(...)
```

配套断言：还原前后对函数体做**语句数快照**，若语句数骤降（如从 40 条变 0 条）直接 fail，不要静默写文件。

## 4. MBA：混合布尔算术的构造与反构造

MBA（Mixed Boolean-Arithmetic）把算术运算与位运算混合，把一个简单表达式等价转换成难以阅读的复杂表达式，用于隐藏常量与运算，也是 VMP 万用门的理论基础。

### 4.1 核心引理（构造与化简都靠它）

> **同一个 MBA 表达式，n 位变量与 1 位变量同样成立。**

所以只要在 1 位真值表上枚举出恒等式，就能直接用到 32/64 位整数上。这是「真值表法」合法性的全部依据（论文：*Information Hiding in Software with Mixed Boolean-Arithmetic Transforms*、*MBA-Blast*）。

### 4.2 线性 MBA 的构造

1. 取一个恒等于 0 的表达式 `E`（如 `x + y - (x ^ y) - 2*(x & y) == 0`）。
2. 用 `E` 的右边替换 `x + y`，得到混淆式。
3. 用 z3 验证等价性：`solver.add(混淆式 != x + y); check()` 返回 **unsat** 即成立。

多项式 MBA 同理，用多项式恒等式构造；注意 `E` 里要保留一个常数项，否则展开时会泄露原式。

### 4.3 化简的线性基

以两个变量为例，取一个行列式非 0 的真值表作基，则任意布尔表达式的真值向量都可由这组基线性表出：

| 真值 (x,y) = (0,0),(0,1),(1,0),(1,1) | 布尔表达式 | MBA 形式 |
| --- | --- | --- |
| `0,0,0,1` | `x ∧ y` | `x & y` |
| `0,1,0,1` | `x` | `x` |
| `0,0,1,1` | `y` | `y` |
| `1,1,1,1` | `true` | `-1`（全 1） |

化简流程：把 MBA 式里每一项的布尔部分替换成上表第三列，合并同类项。若合并后结果是布尔运算，就与常见布尔表达式的真值比对，真值相同即等价。

**实战例子**（VMP 反编译产物）：

```
E = ~(~(M - 0x34C612) & 0x6963) & ~((M - 0x34C612) & 0xFFFF969C)
令 x = (M - 0x34C612), 则 E = ~(~x & ~y) & ~(x & y)
真值表与 x ^ y 完全相同  ⇒  E = x ^ y
⇒ M = (M - 0x34C612) ^ 0xFFFF969C
```

VMP 的万用门用 `not_not_and` / `not_not_or` 模拟其它逻辑与算术指令，MBA-Blast 论文给出了一批化简对照，可直接照抄。

### 4.4 什么时候**不要**用 MBA 化简

- 表达式本身只有 2~3 个运算（如 `(a - 0x34C612) ^ 0xFFFF969C`）——它本来就不是 MBA 混淆，只是普通混合运算。
- 变量不是整数（浮点/字符串）——MBA 的位运算前提不成立。
- 目标只是「让代码能跑」而不是「读懂算法」——直接跑原函数更省事。

## 5. MBA 化简的执行流程

1. **先做约束求解，不要先化简**：用 z3 直接求解目标表达式。求解器能解出来的，不需要 MBA 化简。
2. 求解失败（unsat 或超时）时再走化简：按 §4.3 把表达式规范化成布尔项 + 系数。
3. 化简后用 z3 **验证化简前后等价**（`化简前 != 化简后` 应为 unsat）。这一步不能省——手工合并同类项极易错系数。
4. 验证通过再回灌到代码里，并保留原始表达式在注释中，方便日后 diff。

## 6. 反例黑名单

- **不要在没做字符串还原的情况下跑 CFF handler**。会静默清空函数体（§3）。
- **不要硬编码位切片宽度为 5**。`& 31` 才是信号，`& 255` 的站点存在。
- **不要手工合并 MBA 同类项后不复验**。系数错一位，产物看起来仍然「像」合法代码。
- **不要把 MBA 化简套到浮点表达式上**。位运算语义不成立。
- **不要在一次 pass 里同时做 CFF 归约、逗号拆分、MBA 化简**。任何一步出错都无法归因；`references/pattern-layering.md` 的分层原则同样适用。
- **不要相信「产物能 parse」等于「产物正确」**。上述所有失败模式产物都能正常 parse。
