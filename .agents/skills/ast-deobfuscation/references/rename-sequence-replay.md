## §1 题型判据：先判「是不是仅 minify」

**三条都满足 ⇒ 走本路线**（源文判据，原话：原版混淆**仅为 minify——只改了名，没有控制流扁平化**）：

| 判据 | 满足时的样子 |
| --- | --- |
| 没有控制流扁平化 | 无 `while + switch` 状态机、无 dispatcher、无 opcode 分发链 |
| 没有字符串数组 | 无大数组 + 取值函数、无数组旋转（`push/shift`） |
| 没有不透明谓词 | 无恒真/恒假分支、无数学恒等式混淆 |

三条都满足、**只剩短标识符**（`_0x…` 或打包器生成的短名）⇒ 题型就是"仅 minify"。

**代价警告**：若只看到短名就去跑**控制流还原管线**，是**白费功夫且引入风险** ——
控制流还原必然改写结构，而结构一旦被改，「行为零变化」这条唯一可靠的验收手段（§3）就失效了。

## §2 「改名变换序列回放」范式

源文做法：从**历史已验证状态**推导出「改名变换序列」，现场对**自备样本**的 AST 回放。

- **序列元素是三元组 `[遍历序号, 旧名, 新名]`**。
- **序号是锚点**：用来在结构可能漂移时定位 —— 按**遍历序号**对齐，而不是按文本位置/字符偏移对齐。
- 回放 = 对样本 AST **按序号锚定**逐项应用改名，用 **Babel 作用域安全重命名**（§4）落地。

**为什么它比「现场重新发明命名」更强**：

1. **命名是一次性的、跨版本可复用** —— 源文的序列来自"历史已验证状态"，
   做完一次之后，同一套「旧名 → 新名」可以拿去回放别的样本，不必每次重新推断语义。
2. **重命名本身是可验证的** —— 一条自洽的序列要求：**同一个旧名必须映射到同一个新名**。
   若同一个旧名在不同作用域被要求映射成不同新名，说明序列不自洽，可在**回放前**就发现。
3. **零结构改动 ⇒ 可与源样本对拍验收**（§3）。

## §3 「零结构改动」的纪律与验收

**纪律**：只改标识符、**零结构改动** ⇒ 产物与源样本**行为零变化**。
正因为行为零变化，验收才可以退化成"**改动后仍然可运行 / 可与源样本对拍**"，而不必逐函数理解语义。

把它写成**会失败的断言**（任一条不成立即判违规）：

```text
断言 A（节点数守恒）：回放后 AST 节点总数 == 源样本 AST 节点总数
                      —— 纯 Identifier 改名不增删任何节点
断言 B（结构指纹守恒）：除 Identifier.name 外，其余所有节点的类型与字段逐一对齐
断言 C（违规即失败）：出现任何「标识符重命名之外」的改写
                      （新增/删除节点、重排语句、常量折叠、分支简化、字符串内联…）
                      ⇒ 直接判违规，不得放行
```

一句话：**任何超过「标识符重命名」范畴的改写都应视为违规。**

## §4 作用域安全重命名（为什么必须用 Babel scope API）

必须用 Babel 的 **scope API / binding 级重命名**，**不能**用纯文本或正则替换：

- **同名标识符在不同作用域是不同绑定** —— 函数 A 里的 `a` 与函数 B 里的 `a` 互不相干。
- 纯文本/正则替换会**静默地**把"只该改一处"的改名扩散到**同名它处** ⇒ 语义改变，而且**不报任何错**。
- 因此「同一个旧名 → 同一个新名」这条不变式必须在**绑定（binding）级别**成立，
  而不是在**文本级别**成立 —— 后者只是"看起来对了"。
- 这与 `static-index-replacement-pitfalls.md` 是**同一类静默失败**（"能 parse ≠ 对"），
  只是触发原因不同：那里是字符串表旋转未还原，这里是同名不同绑定的作用域混淆。

## §5 跨版本迁移判据

序列来自"历史已验证状态"，换版本时会有两类失效：

- **序号锚点漂移**：新版本的结构 / AST 遍历顺序变了 ⇒ 按序号定位可能错位，需重新对齐。
- **新增模块没有历史名**：新版本新增的文件、导出、局部绑定在旧序列里**没有对应项** ⇒
  必然还原不到语义名（只能保留短名，或另行命名）。

> ★ **单样本纪律**：源文只给了一个版本（2.1.252）的一组数字，
> 「换版本是否失效 / 是否仍可用」**未复核** —— 不要把它写成"换版本必失效"或"换版本必可用"的结论。

## §7 可迁移性

- **判据可迁移**：**只改名、不改结构的 minify 是打包器的默认行为，不是这个产品的特例**。
  因此凡是"standalone 打包产物里 JS 只被 minify"的目标，都可走本路线。
- ★ **保真边界**：源文只验证了 **Bun standalone** 一个样本；
  「Deno / Node 的 standalone 产物同样适用」是**按判据推广的未复核推断**，
  使用前请先自行核对目标"是不是只改名不改结构"（§1 三条判据）。
- **与字节码路线的分工**：若 exe 里的 JS 不是被 minify 的**明文**，而是**字节码**，
  本路线不适用，改走 `../../desktop-client-reverse/references/jsc-and-v8-bytecode.md`。
