## 1. 先分流：五种「源码 ≠ 显示」的族

> **本文第 1 节是全技能「族划分与分流判据」的唯一权威源。**
> `SKILL.md` 里的分流表只是它的摘要（为了能 30 秒内定位），两处不一致时以本文为准。
> 新增族、改判据、去掉某族 —— 只改这里，再同步 SKILL.md 那 8 行摘要。

**最重要的一条判据：B/C/D/E 四族都没有字体文件请求。**

| 族 | 现象 | 网络特征 | 锚点 | 走哪里 |
| --- | --- | --- | --- | --- |
| **A** 字体 cMap | 页面正常，源码里是 `&#x9fa4;` / 生僻字 / 私有区 | **有** `.woff/.ttf` 或内嵌 base64 | `cmap` + `glyphName` | `font_cmap_dump.py` |
| **B** 雪碧图 | 数字位置上是 `<i class="iconfont">` 空标签 / 背景图 | 有 1~3 个 `.svg`，**无字体文件** | 背景图 base64 串本身不变 | `css_obfuscation_reverse.py offsets` |
| **C** CSS 位移换序 | 源码字符顺序对、渲染顺序错 | 无新资源，纯 CSS `left` 偏移 | 偏移像素值 | `css_obfuscation_reverse.py order` |
| **D** 伪元素 | 文字**缺失**（少几个字），源码里是空 `<span class="context_kwN">` | 无新资源，规则内联在 CSS/JS 里 | `content` 字面量 | `css_obfuscation_reverse.py pseudo` |
| **E** 打包编码串 | 接口返回一长串 `0-9A-Z` 定长分组 | 无新资源 | 自定义码表 + 分组长度 | `css_obfuscation_reverse.py pack` |
| **F** 同源字体换表 | 页面正常、源码「也是正常汉字」但**字义不对** | **有**字体文件，`cmap` 看起来完全正常 | `glyf` 轮廓 | `font_template_diff.py` |

> **判据陷阱**：A 与 F 都有字体请求，区别在于「源码里的字是不是乱码」。
> A 族源码是乱码/私有区（一眼可疑）；**F 族源码是能读的正常汉字**（`搈`、`江`、`政`），
> 所以 F 族**最容易误判为「没有反爬」**——注意「看/复制不一致」这个症状本身就是证据。

## 2. B 族 雪碧图 + CSS 偏移

### 两种子形态

**B1 · 图标字体式**（大众点评旧版、汽车之家）：
HTML 里是 `<i class="iconfont">` 或空白字符，数字由字体渲染。这种其实落在 A 族，只是码位是空的。
**B2 · CSS 背景图式**（大众点评新版全部评论、实习僧）：

1. HTML 里是 `<svg><textPath xlink:href="#69">君助圣榜彼敏展嫁喝率…</textPath></svg>`
   或 `<img>` + 一长串 `background-position`；
2. CSS 规则长这样：`.ruefbo{background:-112.0px -2752.0px;}`；
3. 背景图是 `.svg`，里面是若干 `<path id="NN" d="M0 <row_px> H<宽>"/>` + 对应 id 的 `textPath` 字符集。

### 还原算法（大众点评公式）

```
col   = |x| / 图片宽 + 1           # 1-based
row   = |y| - 1 + 图片高            # 结果要与 path 的 d 起点逐字符相等
```

**两个必须注意的口径**：

1. **`x`/`y` 代入绝对值**。CSS 写 `-112.0px -2752.0px`，但 `d` 侧是 `2775`（正数）。
   教程原文两处都写成正数，照抄 CSS 的负数会得到 `-2729`，查不到任何 path。
2. **必须先取整再计算**。`-2752.0` 直接参与运算没问题，但 `.0px` 与 `.5px` 混用时，
   必须先 `int()`，否则 `y - 1 + 24` 会算成小数，与 `d` 的整数字符串永远不相等。

```bash
python .../css_obfuscation_reverse.py sprite --x -112.0 --y -2752.0 --cell 14x24
# {"col": 9, "row_px": 2775, ...}  → 到 d="M0 2775 H600" 的 path 拿 id=69
#                                  → 到 textPath#69 取第 9 个字 → "喝"
```

**坐标单位是「图片宽/高」，不是「点数」**。大众点评的格子是 14×24，
所以 `col` 的步长是 14px、`row` 的步长是 24px。站点换版会换这套尺寸 → **必须每次实测**。

### 陷阱

| 坑 | 症状 | 处理 |
| --- | --- | --- |
| 把 CSS 的负号代进公式 | `row_px` 是负数，匹配不到任何 path | 代入绝对值 |
| 按渲染后的 DOM 取字符 | 拿到的是显示后的字，绕了一圈 | 从**接口返回或源码**取未渲染文本 |
| 一个页面有 3 个 `.svg`（1 个数字 + 2 个汉字） | 用错表 → 静默取到别的字 | 先 dump 每个 svg 的字符集判断哪个是数字表 |
| `background-position` 值带 `.0` | 字符串比较失败 | 统一 `float()` 后 `int()` |

## 3. C 族 CSS 位移换序

### 形态（猿人学第 4 题）

接口返回的不只是数据，还有 `key`/`value`；页面拿到后：

```js
var j_key = '.' + hex_md5(btoa(data.key + data.value).replace(/=/g, ''));
$(j_key).css('display', 'none');     // 用它隐藏干扰图
$('.img_number').removeClass().addClass('img_number')  // 抹掉类名里的密文
```

每个 `<td>` 里放了**多于 4 张**图，其中若干张被 `display:none` 掉；
正常显示的 4 张靠 `left` 偏移错位排列，读出来的顺序与源码顺序不同。

### 还原算法

```
位置 = 源码下标 + round(left偏移 / step)
```

原文实例：源码序 `2,9,4,1`，第 3 位 `left:+11.5px`、第 4 位 `left:-11.5px`
→ 4 左移一格、1 右移一格 → 显示 `2914`（而不是源码的 `2941`）。

```bash
python .../css_obfuscation_reverse.py order --pairs "2,0;9,0;4,11.5;1,-11.5" --step 11.5
# {"result": "2914", "slots": ["2","9","1","4"], ...}
```

> **`--step` 的口径**：原文代码里硬编码的除数是 **11**（`int(float(i) / 11)`，即字符像素宽），
> 而 CSS 里下发的偏移量是 **11.5**。本脚本把除数参数化为 `--step` 并默认取 11.5，
> 对 ±11.5 这组样例与 `/11` 得到同一个结果；换成别的站点时**以实测的偏移量步长为准**，
> 不要照抄 11 或 11.5。

### 三个必须做的自洽检查

脚本对以下三种情况**直接报错退出**，不产出「看着像」的结果：

1. 偏移不是 `step` 的整数倍 → 网格口径不对（可能站点换了单元格宽度）；
2. 换算出的位置越界；
3. 两个字符落到同一格（撞位）。

> 为什么必须硬失败：这一族的错误产物**仍然是一个四位数**。
> 静默产出一个错的四位数，比抛异常危险得多 —— 后者会被立刻发现，前者会一路汇进最终结果。

### 干扰项的处置

被 `display:none` 的图**必须在求和前剔除**，剔除条件由 `key`/`value` 现算：

```python
def get_j_key(key, value):
    s = base64.b64encode((key + value).encode('ascii')).decode().replace('=', '')
    return hashlib.md5(s.encode()).hexdigest()      # 与 j_key 对应的 class 名的 hash 段
```

图片 base64 串 → 数字的字典是**固定**的（10 张图的 base64 在所有页都一样），
所以这一族可以离线建字典；变的只有 `key`/`value` 与偏移。

## 4. D 族 伪元素 `::before`

### 形态（某小说站点）

```html
<p><span class="context_kw6"></span>叫顾凡<span class="context_kw0"></span>顾<span class="context_kw7"></span>得</p>
```

```css
.context_kw0::before { content: "，"; }
```

**症状是「文字缺失」而不是「乱码」**——直接 `.text()` 会少字，且不报错。

### 还原算法

```bash
python .../css_obfuscation_reverse.py pseudo --css rules.css --html page.html -o fixed.html
# {"rule_count": N, "by_index": {"0":"，","7":"的"}, "replaced": 2, "output": "fixed.html"}
```

`replaced` 与 `rule_count` 都应非零；`replaced == 0` 通常意味着选择器口径不匹配。

### 关键点

- **锚点用 class 名尾部的数字**，不要用完整 class 名：
  同一站点可能出现 `context_kw0` / `context_kw0x` / `context_kw12` 混用，
  用尾部数字才能对上 HTML 侧的 `class="...context_kwN..."`。
- 规则可能由 JS 动态写入（`document.styleSheets[0].addRule(...)` / `insertRule(...)`），
  此时 CSS 文件里搜不到 → **必须先在 JS 里搜索 `content:` 或 `::before` 的字面量**。
- 这一族常与 OB 混淆一起出现：JS 里 `'.context_kw'`、`'::before'`、`'content: "'`
  这些片段会**成串进了字符串数组**。检索命不中时先解混淆（见 `ast-deobfuscation`），
  不要直接断言「没有反爬」。

## 5. E 族 打包编码串

### 形态（优某愿）

接口返回 `"0031001L001D0030001I003B001G0035001J…"`，是**定长 4 字符一组的自定义进制**：

```js
var k = "0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZ", l = k.length;   // l = 36
// 每组 4 字符
s[i] = ((b1 + b0 * l) * l + b2) * l + b3;      // 组合成一个码点
b = String.fromCharCode(...s);                  // 码点 → 字符
// 之后按 '|' 切成条带，t>0 的条带里取 【...】 内容，否则整段保留
```

```bash
python .../css_obfuscation_reverse.py pack --input "001H0039001H0032"
# {"codes": [53,117,53,110], "text": "5u5n", ...}
```

### 两条口径

1. **字符编码与厂商映射是两层，不要混**：
   本步骤只做「定长串 → 字符」（得到 `5u5n`、`【` 这类）；
   得到的字符**还要再过一遍厂商映射**才能变成数字。
   > 实测交叉验证：`0x3010`/`0x3011`（`【`/`】`）按 base36 编出来正是文章样本里的 `09HS`/`09HT` ——
   > 这一条能同时确认「字典 = `0-9A-Z`」与「分组 = 4」，比看代码更可靠。
2. **首段（`t == 0`）按文章口径丢弃**。它是前缀（如 `쿮`），不是数据。

### 陷阱

| 坑 | 症状 | 处理 |
| --- | --- | --- |
| 分组长度猜错 | 解出一堆无关字符 | 用 `【`/`】` 等**已知码位**反查分组长度与字典 |
| 字典含小写 | 大小写混淆 | 先按 `0-9A-Z` 试；不行再按实际字典（注意有的字典是 `0-9A-Za-z`） |
| 拿到字符后不做第二层映射 | 数字全是 `5u5n` 这类怪串 | 字符 → 真值 需另建表（`cmap` / 偏移 / 字典） |

## 6. F 族 同源字体换表（cmap 完全正常，字体图元被换）

### 形态（超星学习通）

站点拿一份**正版字体**（如 `SourceHanSansCN-Normal`），把 A 字码位挂到 B 字的**图元数据**上：

```xml
<!-- 站点下发的 ttf -->
<TTGlyph name="uni6408" xMin="47" ...>
  <contour><pt x="757" y="339"/><pt x="528" y="339"/>…</contour>   <!-- 其实是 争 的轮廓 -->
</TTGlyph>
```

```xml
<!-- 百度下载的官方 SourceHanSansCN -->
<TTGlyph name="uni4E89" xMin="47" ...>
  <contour><pt x="757" y="339"/><pt x="528" y="339"/>…</contour>   <!-- 同样的轮廓 -->
</TTGlyph>
```

**`cmap` 映射一个字都没改**（原文明言「映射结果是一致的，说明不是修改映射关系」）：
`cmap[0x6408] = uni6408`，一切"正常"。但屏幕上画的是 `争`，复制出来是 `搈`。

> 口径：原文只核验了 `cmap` 未改，**没有提 `post` 表**。本族下 `post` 一般也未动，
> 但判定请以「`cmap` 自报的名字与 `glyf` 图元对不上」为准，不要依赖 `post` 是否变化的推断。

> 这是本族最危险的地方：**任何只 dump cmap 的做法都会 100% 失效且不报错**。

### 还原算法

```bash
# 1. 用官方字体建轮廓指纹模板库
python .../font_template_diff.py template SourceHanSansCN-Normal.ttf -o tmpl.json
# 2. 用目标字体 × 模板 → {码位: 真值}
python .../font_template_diff.py apply enc.ttf --template tmpl.json -o map.json
```

指纹算法与 `font_glyph_fingerprint.py` 完全同构（同一份 `_parse_simple_glyph`）：
取 `numberOfContours` + `endPtsOfContours` + **绝对坐标点序列（含 on-curve 标志）** 拼规范串取 md5。

### 为什么必须「歧义不猜」

同一份轮廓可能对应多个名字（`空格` / `.notdef` / 部分汉字在特定字库里同形）。
脚本遇到一个指纹对应多个不同真值时，输出到 `detail.ambiguous` 并**从结果里剔除**，不猜。

> 猜错的话，产出的仍然是「看着像字的字」—— 这是最危险的一类静默错误。
> 宁可让调用方去看 `ambiguous` 列表，也不要让错误数字流下去。

### `unknown_fingerprint` 非零时的自救顺序

不要一上来就换字体重来，按这个顺序定位（每一步都能排除一整类原因）：

1. **先看比例**。`unknown_fingerprint / cmap 项数` ≈ 0 说明只是个别字形；
   ≈ 100% 说明模板字体整体不对（换模板），不要逐个排查。
2. **抽 3 个 unknown 的字面自行渲染比对**：把站点字体的该字形画出来（或用字体预览站），
   与源码里的字义对照。**这一眼就能分开**三种情况：
   - 渲染出来就是源码那个字 → 站点没改图元，走模板 A 校准（本族不成立）；
   - 渲染出来是另一个字，且那个字在你的模板里有 → 模板字体的**版本差**，换同版本；
   - 渲染出来是另一个字，但模板里也没有 → 站点做了**轮廓扰动**，见第 3 步。
3. **轮廓扰动**（微调点位、加噪、合并非相邻轮廓）会让点序列指纹整体失配。
   退路是把「点序列指纹」换成**低分辨率位图指纹**：把字形光栅化成固定尺寸灰度图再取 dHash，
   对亚像素扰动不敏感。本技能目前没有内置这一步，需自行实现（判据：肉眼几乎看不出差别，
   但 `pts:` 指纹全不同）。
4. **复合字形**（引用其它 gid 拼形状）在真实字库里很常见。本脚本按「组件指纹 + 参数」递归归一，
   已在 `--selftest` 里覆盖；若你的站点字体是自定义打包格式，这一步会整体失效，
   表现为 `unmapped` 偏高而不是 `unknown_fingerprint` 偏高 —— 注意区分这两个字段。

### 找官方字体的路子

1. 字体工具里直接看**字体名与版本**（`TTFont()['name']` 或在线字体预览站）；
2. 按 `字体名 + Version` 搜官方发布页；
3. **不要求"完全同一个版本"**：轮廓指纹只关心字形点序列，
   同字体不同版本的常规字形通常一致；差异会体现为 `unknown_fingerprint` 不为零。

### 输出字段怎么读

| 字段 | 含义 | 处置 |
| --- | --- | --- |
| `resolved` | 成功还原的码位数 | 应当 ≈ cmap 项数 |
| `ambiguous` | 轮廓在模板里对应多个不同真值 | 人工裁决，**不要猜** |
| `unknown_fingerprint` | 目标字体的轮廓在模板里找不到 | 模板字体不对，或站点做了轮廓扰动 |
| `unmapped` | 码位没能在目标字体里定位到 gid | 字体结构不标准（多为复合字形） |

## 7. 交叉验证与 oracle 清单

这一族反爬的产物**长得都像正常数字/汉字**，所以「看着对」不能作为验收。
至少要有一个机械 oracle：

| 族 | oracle | 通过标准 |
| --- | --- | --- |
| B | `row_px` 与 HTML 里 `path d` 的起点**逐字符相等** | 相等（不是"接近"） |
| C | 还原后的位置数组是 `0..n-1` 的**一个排列**，无空位无撞位 | 严格排列 |
| D | `replaced == rule_count` 且抽样 3 处与渲染页面肉眼一致 | 数量相等 + 肉眼抽查 |
| E | 把解码结果**重新编码**回去，与原始串逐字符相等 | 逐字符 |
| F | 对**未改造的官方字体**跑一遍，结果必须等于 cmap 自报的字 | 反向断言 |

> **反向断言特别重要**：F 族的脚本如果"什么都能认"，那它一定在瞎认。
> 必须有一个「输入未加密字体 → 输出必须等于 cmap 自报值」的用例把住下限。

## 8. 排错速查

| 症状 | 最可能的原因 |
| --- | --- |
| 有字体请求，但 `cmap` dump 出来一切正常、原文也不是乱码 | F 族，走 `font_template_diff.py`；注意「看/复制不一致」这个症状 |
| 没有任何字体请求，数字位置是空标签/背景图 | B 族；先 dump `.svg` 里的字符集定位 |
| 数字"看着对"但总和不对 | C 族干扰项没剔除；检查 `key`/`value` → `j_key` 的现算逻辑 |
| 文本比页面少几个字、不报错 | D 族；`::before` 的 `content` 可能是 JS 动态注入的 |
| 接口返回一长串 `0-9A-Z` | E 族；注意有第二层「字符 → 真值」映射 |
| 换了 `--face` 还是缺表 | TTC 的表偏移相对**整个文件**，不是相对字面头 |
| 两份字体 `code→glyphName` 每次刷新都变 | A 族模板 C/D；改用轮廓指纹对齐（`font_glyph_fingerprint.py`） |
| `unknown_fingerprint` 占多数 | 用错了模板字体；先确认站点用的字体名与版本 |
