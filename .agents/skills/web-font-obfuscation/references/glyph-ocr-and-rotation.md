## 1. 一句话定位与在族谱里的位置

**一句话**：当「cmap 查表」这条路走不通（映射每次都变、且真假码位之间没有稳定对应）时，
改走「字形识别」——**把每个字形当图认**，而不是继续去猜码位。

本文件是 `web-font-obfuscation` 的 **A 族（字体 cMap）在「查表失败」时的分支**：

- 它把 `references/font-cmap-decode.md` §7 那条「渲染 + 识别」的**兜底**，
  展开成一个带**实测选型取舍**与**替换顺序陷阱**的完整工作流。
- **不替代** `references/font-cmap-decode.md`：映射模型 / 稳定性判定 / 轮廓指纹一律以它为准；
  本文件只补「OCR 这一段怎么选、怎么落地、替换时怎么不把自己污染」。
- 族划分（A–F）的唯一权威源仍是 `references/css-and-sprite-obfuscation.md` §1。

## 2. 路线判据：30 秒分流（cmap 查表 vs 字形 OCR）

| 情况 | 走哪条 | 入口 |
| --- | --- | --- |
| 刷新后 `code→glyph` 不变，或 `glyphName` 稳定可当锚点 | **cmap 查表** | `references/font-cmap-decode.md` 模板 A/C |
| 只有码位重排，但**轮廓能跨版本对齐** | **轮廓指纹**（比 OCR 便宜、可回归） | `scripts/font_glyph_fingerprint.py` |
| 每次刷新整体重排，且 glyphName / 轮廓都当不了锚点 | **字形 OCR（本文件）** | 下面五步 |

★ **源文实测的判定步骤（三步，按顺序做）**：

1. **新开标签页 → 先 `F12` → 在设置里禁用 JS → 再粘贴网址。**
   （源文实测：「打开网址，F12，**发现网页直接跳转了**」——不禁用 JS 拿不到未渲染源码。）
2. **对比「网页显示的文字」与「HTML 源码里的文字」** ⇒ 两者不等 = 命中反爬。
3. **刷新两次、对比两次源码的文字**——源文原话：
   「发现是两次源代码的文字是不一样的，**确认是动态加载**！」⇒ **这就是「映射每次变」的判据**。
   随后从源码/CSS 里提取**内嵌 base64 字体**（`data:application/font-ttf;...;base64,`），解码落成 `.ttf`。

★ **与 `font-cmap-decode.md` 的分工**：
**码位 ↔ 真值的对应表稳定 ⇒ 查表；不稳定 ⇒ OCR**。判「稳定」用 `scripts/font_cmap_dump.py diff`。

> ⚠️ **口径**：源文的「两次源码文字不同」只是**两个时间点的样本**，
> 只能推出「**该样本**在两次加载之间映射不同」，**不要**外推成「所有知乎页面都这样」。

## 3. 完整流程骨架（源文五步）

源文给出的主流程（原话）：

> `读取网页源代码 -> 提取 base64 编码的字体文件 -> 取出来字体文件中的字符图片以及真实的 Unicode 字符 -> 识别图片中的文字 -> 按照规则进行文章的文字替换`

逐步展开：

1. **读源码**：按第 2 节的「禁用 JS」方式拿到未渲染 HTML。
2. **提取 base64 字体**：定位内嵌 `base64` 串，解码另存为 `.ttf`。
3. **导出「字形图片 + 真 Unicode」**：对每个字形，取出它的**位图**与它在字体里的**真码位**
   （源文例：`uni8981`）。
4. **识别字形图片**：对每个字形位图跑 OCR，得到「这个形状看起来是什么字」。
5. **按规则替换正文**：把「码位 → 识别出的字」当映射表，替换正文文字（**替换陷阱见第 5、6 节**）。

★ **这一步的分水岭（源文点破）**：源文说
「现在软件可以通过 `uni8981` 查询到这个字是"要"，但是软件是**不知道这个字代表的是"发"**」。
即：**码位/字形名给出的字（要），不是正文要的答案（发）**——所以必须走图像识别，
不能靠 `chr(int(name[3:], 16))` 这类「名字即真值」的捷径。

> 对照 `references/font-cmap-decode.md` §7：那里的 `uniXXXX` 只在 **`XXXX == 真值码位`** 时才能直接 `chr()`；
> 本例恰恰是「名字/码位与真值**无稳定对应**」的情形，于是整条链路落到 OCR。

## 4. OCR 选型的实测取舍（源文三段弯路）

源文按「Tesseract → easyocr → CnOCR」试了三轮，取舍如下（**这是本文件相对既有文档的增量**）：

| 库 | 源文实测 | 结论 |
| --- | --- | --- |
| **Tesseract** | 谷歌出品；Win 需另装 exe。装好后「**可能是设置问题，一直没有识别出来**……一个都没识别出来」 | 放弃 |
| **easyocr** | pip 包很大；「**某些可以识别，某些不能识别**」；文档是英文 | 放弃 |
| **CnOCR** | **有中文文档** + **有在线测试网站**（可先上传图片验证再落地） | **采用** |

⚠️ **如实标注**：源文这两次放弃是**源文环境/配置问题，不代表库不行**——
Tesseract 要正确装中文 `chi_sim` 语言包与页面分割参数；easyocr 对**渲染留白/通道数**敏感
（同一形状渲染得太挤就会「某些能、某些不能」）。**不要把这里的放弃读成「这些库不可用」。**

★ **可迁移判据（本文件的核心经验）**：
**选 OCR 之前，先用它的在线 demo 跑你自己的字形图。**
能不能识别、识别率多少，十分钟就能有结论，比读英文文档 + 装环境快得多。

★ **落地坑：先备齐模型文件（源头是网络问题，但这一步是硬前置）**：
CnOCR **需要单独下载「检测模型」和「识别模型」**；源文因网络原因无法自动下载，
只能**手动下载后放入本地指定目录**。
⇒ 写成**前置步骤**：**先确认模型文件已就位，再跑识别**，否则会卡在下载上白折腾。

> 提示：单字形识别其实只需要**识别模型**；CnOCR 的默认流水线还会加载**检测模型**，
> 把已经切好的单字图喂进去时，检测阶段可能把字丢掉。
> 已有可用配方见 `references/font-cmap-decode.md` §7：渲染居中留白 + `cnocr` 的
> `ocr_for_single_line(np.array(img))`（带 `score`，汉字更准），或 `ddddocr`（单字符数字/字母准）。

## 5. 核心坑：按映射表逐条 `replace` 会「自我污染」

源文的替换跑完后「**不出意外的话，还是出意外了**」，原因是**字符重复替换**。源文的解释（原样收录）：

> 如果原文本是：`一二一二一二一二一二一二一二一二`
> 你识别出来的字符是数组是 `[("一","二"),("二","一")]`
> 那么替换两次，
> 第一次把「一」替换为「二」，这个时候源文本就全是「二」了
> 第二次把「二」替换为「一」，文本就全是「一」了。原理差不多就是这么个原理

**断点里看到的实证**（原文）：

> 从断点中也可以看的出来，数组是从 `00` 开始替换；
> 到 `02` 的时候把文章的"不"替换为了"用"
> 到 `31` 的时候又把文章的"用"替换了"可"
> 到 `04` 的时候把个替换为了生
> 到 `30` 的时候又把"生"替换为了"和"

⇒ **同一个字被第二次替换吃掉**：`用`（`不` 的结果）又被 `用→可` 再吃一层。

源文的修法（**原样收录代码**，用一个 `set()` 记录已替换的位置）：

```python
replaced_positions = set()
    for old, new in result:
        for i, char in enumerate(conent):
            if i not in replaced_positions and char == old:
                conent = conent[:i] + new + conent[i+1:]
                replaced_positions.add(i)
            elif i in replaced_positions:
                continue
    with open('正文.txt','w',encoding='utf-8') as f:
        f.write(conent)
```

## 6. 通用解：单趟逐位置映射（源文没做的那一步推演）

★ **源文只给了 `set()` 这个具体补丁，没回答「为什么会这样」。根因是两条**：

1. **顺序**：外层是对**每一对 `(old, new)` 各跑一趟**全文替换；
2. **就地改写同一个串**：第 2 趟处理的**不是原文**，而是第 1 趟**已经改过**的串。

**正确的通用解是「单趟逐位置映射」**——先算出**每个位置**的替换结果，再一次性拼装：

```python
table = dict(result)                      # {混淆字: 真值}，前提是 old 键唯一（见下方「剩余风险」）
fixed = ''.join(table.get(ch, ch) for ch in conent)
```

即：`text` 里每个字符**只查一次表、只改一次**，与「趟数」和「执行顺序」彻底解耦。

### Node 实跑对比（同一 fixture，源文例子 + 源文断点）

```
原文         : 一二一二一二
趟式replace  : 一一一一一一     ← 错（正是源文说的「全是一」）
set() 修法   : 二一二一二一     ← 与单趟一致
单趟位置映射 : 二一二一二一     ← 正解

原文         : 用不             （源文断点场景：不→用，用→可）
趟式replace  : 可可             ← 错
set() 修法   : 可用             ← 与单趟一致
单趟位置映射 : 可用             ← 正解

表里 old 重复（非函数）：原文 甲，表 [甲→乙, 甲→丙]
set() 修法   : 乙（首个命中）
单趟(dict)   : 丙（末个命中）     ← 二者在此才分歧
```

对应代码（可逐字复核）：

```js
// 趟式 replace（源文最初的写法，会自我污染）
let s1 = text;
for (const [o, n] of table) s1 = s1.split(o).join(n);

// 单趟逐位置映射（正解）
const m = new Map(table);
let s2 = ''; for (const ch of text) s2 += (m.get(ch) ?? ch);
```

### 两者差别与「剩余风险」（**本技能相对源文的增量，务必看清**）

- **`set()` 方案与单趟在「函数表」下等价**：只要 `result` 里 **`old` 键互不重复**
  （每个混淆字只对应一个真值——字形混淆里这是常态，因为混淆码位彼此不同），
  上面两组 fixture 里 `set()` 与单趟**输出完全一致**。
  ⇒ 所以「`set()` 仍依赖遍历顺序」这个担心，**在函数表下并不成立**：
  位置 i 只会被「old == 该位置原文」的那**唯一一对**命中，顺序无关。
- **真正会「依赖顺序」的是「非函数表」**：当表里出现**同一个 `old` 映到多个真值**时，
  `set()` 是**首个命中生效**（按 `result` 列表顺序），而 `dict`/单趟是**末个生效**（后写覆盖）。
  上表第三个 fixture 复现了这个分歧。
  ⇒ **代价是：问题的根不在替换循环，而在「表本身得是函数」**。先保证映射是「一个混淆字 → 一个真值」，
  再谈循环怎么写。
- **`set()` 方案的限制**：它用 `conent[:i] + new + conent[i+1:]`，**只对「单字符 old → 单字符 new」成立**；
  混淆字若跨多字符即失效。单趟用 `get(ch, ch)` 也只吃单字符——但它是**显式**的单字符口径，不会假装通用。
- **两者共同无法解决（真正的剩余风险）**：替换只认**字符本身**，无法区分
  「这个字是**被混淆的字**」还是「它**本来就是真值**、只是恰好等于某个 old 键」。
  当站点把混淆文本和正常文本**混排**时，两种写法都会误伤正常文本。
  ⇒ 靠**限定作用域**（只替换目标 DOM 区域 / 只替换已定位的混淆区间）解决，**不是**靠改替换循环。

> 一句话收尾：**源文用 `set()` 治好了「病」（单字符映射下的自污染），
> 但没点出「病因」（多趟 + 就地改写），也没给出「通用解」（单趟逐位置映射）。**

## 7. 交叉验证：猿人学第 7 题（每次请求下发不同字体文件）

**第二个同族独立样本**：猿人学 `api/match/7?page=N`。

- **形态**：接口响应里数据是空格分隔的 `&#NNN` 串，**同时带一个 base64 的 `woff` 字段**。
  源文脚本**每翻一页都重新下载该 woff 并重建映射**（`namedict` + `numberdict`），**不跨请求复用**
  ⇒ 写法上把它当作**字体文件本身是每次请求下发的动态资源**。
- **与既有形态的区别**：
  - `references/font-cmap-decode.md` 里的抖音案例是「**静态字体 + 版本漂移**」（URL 带 hash，内容偶尔变）；
  - 本例与第 2 节的知乎样本（**页面每次加载内嵌一份新 base64 字体**）都属于「**字体即动态资源**」
    ——每次加载 / 每次请求都可能是一份新字体。
  ⇒ 再次印证 SKILL.md 反例黑名单那条：**不要把「URL 不变」或「同一份 base64」当作映射不变**。
- **解析口径**：`code → name`（cmap）→ `name → 数字`（**glyf 轮廓的前几个点**）。
  源文的数字表按**首点 x 坐标**硬编码分支（`300 / 297 / 310 / 307 / 384 / 105 / 66 / 292`），
  这正是 `references/font-cmap-decode.md` §4 轮廓指纹的**手写退化版**。
  ⇒ 通用做法是换成 `scripts/font_glyph_fingerprint.py`（跨版本对齐），不要硬编码单站坐标。
  > 配套的第 7 题完整走读见 `../../web-reverse-algorithm/references/17-yuanrenxue-match-playbook.md`。
- **交叉验证的价值**：两个**互相独立**的样本（知乎 = base64 内嵌；猿人学 = 接口按请求下发）
  都落进「字体文件动态」这一形态，说明这不是单站特例；
  而**两个样本的解法锚点都是「字形」**——一个用 **OCR**，一个用 **轮廓首点**。
  **锚在字形、不锚在码位**，是本族的共同结论。

## 8. 低成本前置：先人工看一眼 cmap

源文推荐在线查字体站 `https://www.bejson.com/ui/font/`——上传 `.ttf` 直接**看 cmap 与字形预览**。

定位：**「先人工看一眼，再决定走哪条路」的低成本前置**。
30 秒看清「`code ↔ glyph ↔ 形状`」三者关系，再决定 查表 / 轮廓指纹 / OCR。
`scripts/font_cmap_dump.py` 只 dump **数字化的 cmap**，**看形状**仍需这种渲染/预览工具。
