# 点选类识别与顺序还原（文字 / 图标 / 语序 / 图文 / 空间语义）

本文件解决一件事：**拿到题面和底图后，怎么把「点哪几个位置、按什么顺序点」确定出来**。
训练细节（标注、参数、自举、收敛判据）在 `references/captcha-model-training.md`；
视觉坐标 → 提交坐标的换算是另一层，见 `references/tile-scramble-and-coordinate-mapping.md` §四。
三者**必须分开推进**：识别对了但顺序错、顺序对了但坐标没换算，都会静默失败。

## 零、先判是哪一类点选（做错这一步后面全白干）

| 子类 | 题面长什么样 | 识别路线 | 顺序从哪来 |
| --- | --- | --- | --- |
| 文字点选 | 题面给 3~4 个汉字 | 检测 + 分类/相似度 | **题面顺序 = 提交顺序** |
| 图标点选 | 题面是一组图标小图 | 检测 + 相似度 | 题面顺序 = 提交顺序 |
| 语序点选 | 「请按正确语序依次点击」 | 检测 + 分类 + **语序还原** | **题面顺序 ≠ 提交顺序**，需额外一步 |
| 图文点选（无题面文字） | 只在图上给参考小图 | 检测 + 特征相似度 | 参考图在底图上的位置 |
| 空间语义 / 几何体 | 「点击最大的/最小的 X」 | 检测 + 按题面规则筛选 | 按题面形容词筛出唯一目标 |
| 参考位置固定型 | 题面图标坐标固定 | **直接裁剪**，不做匹配 | 站点固定槽位 |

**判据（按顺序问自己）**：
1. 题面文字是「点击 A、B、C」还是「按正确语序点击」？后者 ⇒ 走 §四，多一步还原。
2. 题面出现「最大 / 最小 / 最左 / 相邻」这类关系词 ⇒ 目标是 `semantic-reasoning`，
   识别路线是「检测出全部候选 + 按规则筛」，**不是**做相似度匹配。
3. 候选内容每轮都换、且"问题图和底图里某几个格子相同" ⇒ 相似度路线（`captcha-model-training.md` §八），
   **不要**去训分类模型。
4. 参考图标每次都出现在同一坐标 ⇒ 直接裁剪固定区域，别浪费一轮匹配（极小概率会多出一组，做个数兜底）。

## 一、数据集与标注：点选类有三条捷径

### 1.1 图标点选：不要去 labelimg 一张张手标

**先建图标库再打标**：把采集到的验证码图里的图标**种类去重**，去重后的图标与自建数据集合并，
标注时直接记录「位置 + 种类」并转 YOLO 格式。数据集规模完全自己控制，几十张底图就能扩出上千个框。

**判据**：图标集合**可枚举**（去重后是有限图库）⇒ 这条路成立；每轮都出新图标 ⇒ 回到相似度路线。

### 1.2 文字点选：两级模型 + 类别过采样

- 一级：YOLO 检测（只标"文字"一类，不做识别），50~60 张手标就够。
- 二级：把检测框抠出来的小图当分类数据集，训 YOLO-cls / CNN / ddddocr 自定义模型。
- **类别不均衡必须处理**：常用字几百张、生僻字一两张，直接训会把生僻字全判成常用字。
  做法是**过采样**（把每类训练样本补到 `min_samples`，例如 20 张）+ 打散重组。
- 分类模型的增强只保留"现实中会变"的：`degrees=15`（字体有 ±30° 倾斜）、`translate`/`scale`/`shear`、
  `hsv_s`/`hsv_v`；**`fliplr=0.0`、`flipud=0.0` 必须关**（左右翻转会让字形语义变化，标签被污染）。

### 1.3 自举标注：用模型/多模态 OCR 帮你分类，人工只做审查

```text
少量手标(50~60) → 训小模型 → 导出 ONNX → 自动标注 → 人工修正 → 重训
文字类替代法：检测框抠图 → 多模态 OCR（如 qwen-vl-ocr，提示词写明"单个汉字、可能有 ±30° 旋转"）
            → 按识别结果分桶到 <汉字>/ 目录 → 人工审查错分桶 → 生成 class_map.json + dataset.csv
```

- 分桶后类别数常到 **1000+**，**人工审查是必需环节**，不能省。
- 文件名清洗要剔掉文件系统非法字符（`\ / : * ? " < > |`）；识别为空或长度 > 1 的一律丢进 `unknown`。
- 分桶结果先落 `class_map.json`（`{汉字: idx}`，"目录名排序"保证索引稳定）再切 train/val，
  否则两次运行的标签对不上。

## 二、检测路线选择：先用零训练的那个

| 路线 | 何时用 | 代价 |
| --- | --- | --- |
| `ddddocr` 内置检测 `detection()` | 1.3.0+ 起自带目标检测，常规印刷体/干扰少的底图直接可用 | **先试这个**，省掉整套标注 |
| 自训 YOLO 检测 | 字体特殊、干扰强、`detection()` 框不稳 | 需标注 + 训练 |
| 纯 OpenCV 轮廓/投影 | 单行、粘连少、背景干净 | 泛化差，只作兜底 |

`ddddocr` 的**正确用法是"先切后拼再认"**，不要单字直接认：

```python
boxes = det.detection(bg_bytes)          # [[x1,y1,x2,y2], ...] 所有文字框
canvas = 把每个框抠成灰度 → autocontrast → 二值化 → 横向拼成一行
text = ocr.classification(canvas)        # 一次认出整串
assert len(text) == len(boxes) or 重试   # ★ 长度不等说明认漏/认多，整轮丢弃
pos  = [boxes[text.index(t)] for t in targets]
```

> **为什么必须拼接**：单字小图直接识别效果差（这是最容易踩的坑）；拼成一行后上下文能显著提分。
> **为什么必须断言长度**：字符数对不上，后面用下标回查坐标就是**错位**，而且不会抛异常。

#### 路线 0：**不识别文字**，只做"渲染图 × 目标图"相似度（`52pojie-1606710` 实测）

当题目是**生僻字 / 繁体字 / 带偏旁部首**的汉字九宫格时，OCR 的成本极高
（原文口径：准确识别需要大量样本训练，"多试几次"的 API 路线识别率也不高）。
但点选**不需要认出所有字**，只需要知道"哪个格子的字与题面要点的字最像"：

1. 用**同款字体把题面文字渲染成图片**（原文用**微软雅黑粗体** `YaheiCu.ttf`，字号 88，
   单字图 **85×85**）；
2. 把九宫格按**估算的分割坐标**切成 9 块（原文初始坐标表：
   `[[10,20],[10,121],[10,220],[108,20],[108,121],[108,220],[206,20],[206,121],[206,220]]`，
   九宫典型位置 `block_list = [159,169,179,459,469,479,759,769,779]`）；
3. 逐块与渲染图比相似度：**像素相同数量**或**余弦距离**二选一（原文实测两者准确率都很高，
   "连试 10 次基本没一次错误"）；
4. 提交最相似的格子坐标。

**三个必须调对的细节**：
* **降噪**：先去随机黑点噪声，再去**跨宫干扰线** —— 判定一条线算不算干扰的条件是
  "**同色像素数 > 10**"（原文的 `noiseline()`），阈值放宽是为了避免把"同色系的文字像素"一起抹掉；
* **分割坐标要估**：图片文字**整体右偏**，最右侧要**补全让汉字居中**
  （原文用 `np.zeros(85*5*3)` 造了最右侧的补全矩阵）；
* **字体要接近目标**：字体不像，相似度直接失真（这是本路线的唯一"前置假设"）。

> 与 §一「点选类有三条捷径」的关系：**这条路线在"数不出类别"的汉字题上比分类路线更省**，
> 代价是必须知道字体与分割几何 —— 换站要重新标定。

## 三、匹配与指派：题目 → 坐标

### 3.1 两级匹配（精确优先，相似度兜底）

```python
available = detections.copy()               # 可用池
for i, target in enumerate(targets):
    for j, item in enumerate(available):
        if item['char'] == target:          # 一级：绝对精确
            matched[i] = item['center']; available.pop(j); break
for i, target in enumerate(targets):
    if matched[i] is None and available:    # 二级：字形相似度兜底
        j = argmax(available, key=字形相似度(target, item['char']))
        matched[i] = available[j]['center']; available.pop(j)
```

两条铁律：
- **匹配成功必须从可用池 pop 掉**。有重复字时（题面 `['金','针','菇']`、候选里两个「金」），
  不 pop 就会把同一个坐标返回两遍。
- 字形相似度要用**只算字形**的模式（有的库默认还会混拼音和语义），否则「针/十」这类同音或形近会互相污染。

### 3.2 相似度矩阵 + 指派

先算 `matrix[i][j] = 题目第 i 个 与 第 j 个候选框 的相似度`，再解指派：

- **贪心**（`argmax` → 把该行该列置 0 → 循环到矩阵全 0）：N ≤ 6 时够用，实现最短。
- **匈牙利**（最优指派）：N 更大、或贪心出现"两个题目抢同一个框"时换它。
  直接用 `scripts/assign_by_similarity.py`（零依赖，含贪心/匈牙利两种实现与自检）。

**置信度门槛**：top1 与 top2 的分差小于阈值时，**由调用方丢弃该轮重取**，不要硬提交。
（`scripts/assign_by_similarity.py` 只把该轮标成 `overall_confidence: "low"` 并以退出码 1 结束，
**它不会替你丢弃** —— "重取"这个决定在调用方，别指望脚本自己拦住。）
相似度路线在"多格内容相近"或"图标低对比"时必然误判 top1，硬提会被记一次失败并可能触发风控升级。

### 3.3 颜色必须一致，必要时反色

同一个题面里黑/白图标混排时（例如某盾图标点选会给黑白两套参考图）：
先用检测类别或像素均值判出目标颜色 → **只用同色参考图**去比 → 否则匹配必错。
参考图与目标图底色相反时先反色（`cv2.addWeighted(img, -1, zeros, 0, 255)`）再算相似度。

### 3.4 特征匹配（SIFT/SURF）作为"相似度模型"的替代

| | 相似度模型（Siamese） | 特征匹配（SIFT/SURF） |
| --- | --- | --- |
| 速度 | ~35 ms/对（CPU），5×3 就 ~500 ms | **5~10 ms/对** |
| 需要数据集 | 需要（且要分类训练） | **不需要** |
| 抗干扰 | 强（取决于数据集） | 弱：对颜色、形变、噪声敏感 |
| 适用 | 图标有变形/换色/带干扰 | 参考图与目标**同色同形**、图库稳定 |

- 做法：`SIFT_create().detectAndCompute` → `BFMatcher().knnMatch(k=2)` →
  用 `m.distance <= 0.88 * n.distance` 过滤 → **good 数量即匹配度** → 组成矩阵后走 §3.2 指派。
- 两张图**先 resize 到同一尺寸**再提取特征（尺寸不同会直接掉精度）；
  速度要求更高时用 SURF（特征点更少，准确率略降）。SIFT/SURF 有专利，仅限研究用途。

## 四、顺序还原（语序点选专用）

流程固定三步：**目标检测 → 文字识别 → 语序还原**。前两步见上，第三步是这类题唯一的新东西。

| 路线 | 做法 | 代价 / 判据 |
| --- | --- | --- |
| 离线词典 + n-gram 打分 | 对候选字的**所有排列**打分取最高：`Σ len(sub)² × log(freq + 1)` | 零网络、可离线；需一份词频表（百万级词库先按识别字表"瘦身"） |
| 统计语言模型 | KenLM（`pycorrector` 提供了小/中/大三种模型，大模型 3 GB），取 `perplexity` 最小 / `score` 最大 | 效果最好；模型体积大 |
| 大模型直接排序 | 把候选字丢给 LLM 让它给语序 | 快；需要外网 + 稳定性差 |
| jieba 分词 | —— | **效果差，不推荐** |

- **长度平方是关键词**：`('物理系')` 长度 3 权重 9，`('物理') + ('系')` 加起来才 4+1，
  长词才会"分数爆炸"式胜出。缺少这一项时语序会稳定判错。
- `freq` 为 0 的词必须**强制取 1**，否则 `log(1) = 0` 让整条候选白算（词频表里 `0` 很常见）。
- 直接用 `scripts/order_restore.py`（零依赖、支持外部词频表、内置小词典自检）。
- **顺序错了不会报异常，只会静默失败** ⇒ 建议一次会话内用两种顺序各提交一次做 A/B，
  失败计数按"整轮"记，不要靠单次结果反推是识别错还是顺序错。

## 五、坐标生成与边界

- **九宫格固定切分时逐格 OCR，不要整图 OCR**：题面均匀分布时整图识别率极低，按 `3×3` 切开逐格识别
  明显更稳；目标位置直接得到 `(行, 列)`。
- 点击点 = 格中心 + **小幅随机抖动**（`±cell/3`），并 clamp 到图内；
  抖动是为了避免"每次都点正中心"这种过于机械的样本。
- 输出坐标的**语义不要自己改**：站点要 `[行, 列]`（1 起）就给 1 起，要图片像素就给像素；
  要提交距离再走 `tile-scramble-and-coordinate-mapping.md` §四 的换算。
- **重试策略**：目标数不足（例如应点 4 个只识别到 3 个）时**重新取题**，不要用残缺结果提交。

## 六、反例清单（这些不要做）

| ❌ 不要 | 后果 |
| --- | --- |
| 把语序点选当文字点选（照题面顺序点） | 静默失败，且会被记一次失败 |
| 对"每轮内容都换"的九宫格/图标题硬训分类模型 | 训不出来，方向就错了（应走相似度） |
| 分类路线不关 `fliplr`/`flipud` | 标签污染，loss 下不去 |
| 用整图 OCR 识别九宫格题面 | 识别率极低 |
| 用单字小图直接 OCR（不拼接） | 识别率显著下降 |
| 匹配命中后不从可用池移除 | 重复字拿到同一个坐标 |
| top1/top2 分差很小时直接提交 | 必错一次，还可能升级风控 |
| 忽略参考图标与目标图底色相反 | 相似度直接反向，匹配到错误槽位 |
| 拿残缺的识别结果硬提交 | 浪费一轮挑战，且 `token` 被消费 |
| 把训练产物（权重/数据集）写进技能目录 | 应在 `artifacts/` |

## 七、排错速查

| 现象 | 先查 |
| --- | --- |
| 识别出的字都对，但验证失败 | ① 顺序是否按题面而非提交要求 ② 坐标要不要换算（CSS 缩放/固定偏移）③ token 是否已被上一轮消费 |
| 某个字总是识别错，且集中在生僻字 | 类别不均衡未做过采样；或该字样本 < 10 张 |
| 相似度匹配结果偶尔整体错位 | 可用池未 pop；或参考图颜色与目标不一致 |
| 语序结果稳定判错 | 打分公式漏了 `len²`；或 `freq=0` 未兜底成 1 |
| 检测框数量对不上识别字数 | 断言过松，必须 `len(text) == len(boxes)` 否则整轮丢弃 |
| 本机跑 `det.detection()` 报依赖缺失 | 本仓库 Python 无 numpy/cv2 时改用平台或人工复核，不要静默降级到 OpenCV 硬匹配 |
