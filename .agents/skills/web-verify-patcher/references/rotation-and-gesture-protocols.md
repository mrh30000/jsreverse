## 1. 分流：先判是「旋转」还是「手势」

| 信号 | 判为 | `captcha_variant` |
| --- | --- | --- |
| 题面「拖动使图片正向」、角度提示、单一水平滑轨 + 图片绕中心转 | `rotate` | — |
| 题面/交互是**在图上沿某形状描画一笔**，提交的是**轨迹点列** | `trace-draw` | `gesture-draw` |
| 内外双环各转一次 | `rotate` | `dual-ring`（罕见，见 §2.1） |
| 拖动过程中图片**自身也在转**（弧线移动） | `slider` | 见 `motion-and-coordinate.md`「旋转 / 弧线滑块」 |

**手势 ≠ 滑块**：手势的提交量是**整条绘制轨迹**，不是距离；把 `gesture-draw` 当 `slider` 处理会一直
缺一个必填的轨迹字段，现象是「参数看起来都齐了但一直 `Fail`」。

## 2. 旋转系

### 2.1 通用：角度从哪来、守方怎么加防

> **强度**：整节出自 `52pojie-1754224`（**单源**，一篇综述 + 作者自研项目的经验总结）。
> 其中"某一具体开源仓库的 star 数/更新时间"这类随时间失效的信息没有收录；
> 收录的都是**方法论与判据**（哪条会翻车、为什么）。

- **最容易做、也最容易翻车的一条**：轴对齐角度（90/180/270）不引入插值伪影，
  非 90 倍数的角度**必然引入插值伪影**，而伪影本身会被网络学成特征
  ⇒ 换分辨率/换来源后准确率断崖。**判据**：同一模型在「高分辨率先旋转再裁切缩放」与
  「先裁切缩放再旋转」两种数据管线下准确率差一个档位——**取前者**，代价是更贵。
- **分类定式的三个已知失真**（都能靠改网络结构缓解，来源明确列为待改进项）：
  ① one-hot + 交叉熵把「1° 与 2° 的距离」和「1° 与 180° 的距离」算成一样（圆形平滑标签可解）；
  ② 分类数不是越多越好（来源实测 360 类降到 128 类更好，但**该数字与数据分布强相关，不要当常量**）；
  ③ 全连接层展平会破坏上下左右的空间关系。
- **守方两招**：
  - **鬼影**：在旋转图上随机涂抹大块脏污（明度/色相/饱和度都变）。效果是
    **基于感知哈希的攻法全挂**，CNN 还有一战之力。
  - **双旋转**：内外环各转一次。攻方只需解决**咬合**这一步，咬合后按单旋处理；
    咬合做法是取「内环外侧」与「外环内侧」沿圆环展开成灰度序列，用**互相关**求平移量。
    半径较大时互相关比逐像素色差高效。
- **自测角度的小技巧**：把图丢进任意画图软件自由旋转，很多软件会实时显示角度——
  比对着浏览器刻度目测准得多。

### 2.2 百度 `baidu-captcha`（旋转 / 滑块 / 点选同源）

> **强度**：本节的**代际判据、两套接口名、`rzData` 两代结构、`ac_c` 两代口径、AES IV、三个报错码**
> 全部来自 `52pojie-1806246`（**单源**）；`52pojie-1792807` 只互证了一件事
> ——**「百度旋转的提交值是 `fs = AES(rzData)`，可直接导库复刻」**，以及"该家存在两代形态"。
> ⇒ 本节的 `★双源` **只覆盖那一条**，别把整节当双源。

**一票判据**：脚本是 `wappass.baidu.com/static/captcha/` 下的 **`mkd.js`（v1）或 `mkd_v2.js`（v2）**。
代际**只按核心 JS 文件名判**，不要按接口名判（v2 换了接口名，但结构与 v1 一致）。

| | v1（`mkd.js`） | v2（`mkd_v2.js`） |
| --- | --- | --- |
| 取参 / 取图 | `viewlog` → `getstyle`（带 `tk`，返回 `backstr` / `img`） | 同名结构、接口名不同 |
| 提交 | `viewlog`（二次）→ 返回 `op == 1` 即通过，并给 `ds` / `tk` | 同上（返回 `op`） |
| 收尾 | `viewlog/c`（带上一步的 `tk` / `ds`）→ `code == 0` 才算过 | `cap/c` |
| 加密明文 | `rzData` 平铺 | `rzData = { common, captchalist: [spin-0, puzzle-0, click-0] }` |
| AES IV | `as + "appsapi0"` | `as + "appsapi2"` |
| 旋转换算 | `ac_c = parseFloat(angle / 360).toFixed(2)`（滑轨 212） | `ac_c = Number((angle / 360).toFixed(2))`（可滑动长度 = `290 − 52 = 238`） |
| 滑块换算 | —（v1 主打旋转） | `ac_c = Number((distance / 290).toFixed(2))` |
| 点选换算 | — | `ac_c` = 各点击点的 `x / y / 时间戳` |

> **★双源点只有一处**：`fs = AES(rzData)` 这一整体结构（"可直接导库复刻"）由 1806246 与 1792807 互证。
> 上表里 **IV 串、接口名、`ac_c` 四个口径、`rzData` 结构全部是 1806246 单源** ——
> 不要把"这一节有双源点"读成"这一节的参数都被互证过"。

- **v1 的 `ac_c` 有两种写法且等价**：`parseFloat(o / 212).toFixed(2)`，其中 `o = angle × 212 / 360`
  ⇒ 化简后就是 `angle / 360`。**滑轨长度（212）抵消掉了**，所以别去页面上量滑轨。
- **v2 的换算不是 360 平移**：`distance = angle × 238 / 360`，再 `Number((distance / 238).toFixed(2))`
  ⇒ 同样化简为 `angle / 360`，但**滑块那条分支用的是 `distance / 290` 而不是 `238`**，
  两个除法分母不同（`290` 是滑动框整体长度），**照抄旋转的口径去算滑块会整体偏大**。
- **`rzData` 里到底哪些要真算**：`ac_c`（角度）、`backstr`（`getstyle` 返回值）、
  `p`（由 `ext` 经 **Worker** 的 `powMap` 算 —— 出处是**既往已登记来源** `52pojie-2057521`，
  不在本批 13 篇里）、`mv`（轨迹；`52pojie-2057521` 明确写「`common.mv` 这组轨迹**不校验**、可有可无」）。
  同理 `loc.cl`、`cr`（屏幕信息）等环境项可写死。
  ⚠️「不校验」是**实测口径**、且各字段分别只有一篇来源支持，换站/换版本要重测一次——别把它当协议保证。
- **`fs` 是否二次加密：本批两篇独立来源都只描述了一次 AES 且实测通过**，
  而另一来源给出的口径是二次（`fs₁` → 包一层 `{common_en: fs₁, backstr}`）。
  ⇒ **先按一次实现**；出现「参数结构看着没问题但一直不过」时，再补第二层。
  这类「同一站两种口径」的根因通常是**站点接入版本不同**，不是谁抄错了。
- **AES key 派生带算法开关**：`getNewKey(as)` 取 `as` **最后一个字符**查表选哈希
  （`FB→MD5` / `eR→SHA1` / `JQ→SHA256` / `o→SHA512` / `DZ→SHA3-256` / `NZ→SHA3-512`），
  输入是 `as + 'appsapi2'`，取 hex 串的**前 16 个字符**当 key
  （16 字符按 UTF-8 存进 `CryptoJS.enc.Utf8.parse` 恰好 16 字节 = AES-128；**不是"16 字节 hex"**，
  别把 hex 串先转字节再用）。
  **遇到"同一加密函数换站表现不同"先怀疑这种查表选算法。**
- **填充不要统一**：`fs` 用 **AES-ECB + ZeroPadding**，`fuid`（`window.passFingerPrint()`，含 canvas 指纹）
  用 **AES-ECB + PKCS7**。

**该家专属坑（按踩到概率排序）**：

1. **收尾接口要"等一会儿"**：第一步校验通过后立刻调 `viewlog/c` / `cap/c` 会返回
   `{'code': 1, 'isRectified': False, 'msg': 'Verification Failed'}`。
   **处置：随机 `sleep` 1~3 秒**再调收尾接口。
2. **`Referer` 必须带且必须对**，否则：v1 无 Referer → `Unregistered Host`；
   v1 Referer 错 → `Invalid Request`；v2 任一情况 → `code 100600 Unauthorized Host`。
   **这三个报错都不指向参数算法**，别去翻加密代码。
3. **`存在安全风险，请再次验证`（`code == 0`）不是失败**：手动在浏览器滑也一样会出。
   本地加一层「再次验证」重试逻辑即可，一般第二次过。
4. **断点打不上的两种原因**：脚本 URL 带动态后缀（`?cdnversion=<时间戳>`）⇒ 全局搜 `cdnversion`
   删掉后缀或 DevTools Overrides 重写文件；页面是 SPA ⇒ 在 `<script>` 上打断点抓加载时机。

### 2.3 小红书 `xiaohongshu`（旋转，★单源）

- **接口**：`POST /api/redcaptcha/v2/captcha/register`（取图）→ `POST /api/redcaptcha/v2/captcha/check`（校验）。
- **`register` 入参**：`biz` / `captchaVersion` / `secretId` / `sourceSite`（当前页 URL）/ `verifyBiz` / `verifyType` / `verifyUuid`（UUID）。
- **`register` 出参**：`rid`（给 check 用）+ **`captchaInfo`（加密串，里面就是验证码图片）**。
- **`check` 入参**：`rid` + 上面那组原样字段 + `checkCount` +
  `captchaInfo = <加密的 JSON 字符串>`，明文四件套是 `mouseEnd`（距离）/ `time`（耗时 ms）/
  `track`（点列）/ `width`。
- **加解密同一个函数** ★单源：`captchaInfo` 的解密与提交值的加密在**同一处实现**，
  定位到解密就能顺手加密。**该来源用截图展示算法，未落到文字** ⇒
  带 `redcaptcha` / `captchaInfo` 的样本要现场扣函数，不要期待本文件给出现成算法。
- **参考量级**（仅作"像不像"的旁证，**不是通过条件**）：某次通过样本
  `mouseEnd = 249`、`time = 3884`、`x` 约 0→250 再回 249 的多段轨迹、`width = 286`。
- **角度怎么来的**：来源用的是「叠图 + 人工找正后模板比对」，属于**可离线**路线；
  批量场景换成 §2.1 的角度模型。识别失败**重试即可**（来源口径：识别 95%、协议 100%，
  因为失败就循环再取一次图）。

## 3. 手势系：VAPTCHA（`vaptcha`）

> **强度总览**：`get`/`config`/`validate` 三段链与 `en` 的**机制**= ★双源；
> 四段链（含 `{vid}` → `api`）、`en` 的 11 项明细、图片顺序减法公式、轨迹两条坑
> **各自只有一篇** ⇒ 逐节标了强度，**不要把 §3 当整节双源**。

### 3.1 一票判据与链路

**判据**：域名 `vaptcha.com`；页面初始化 `vaptcha({vid: ...})`；`localStorage` 里出现
`vaptchanu` / `vaptchaut`；脚本里出现 `SelectFrom` / `GenerateFP` / `hashComponents` / `secretC`。

**四段链（前两段是"取服务端"和"取配置"，很多人以为没用而跳过）**：

> **强度**：**只有 1888845 完整给出四段**（含第 1 段 `{vid}` → `api`）；
> 2051922 从 `config` 开始，细节（`t` 的三种取值、`z` 的时区算式、`rm` 写死）也出自它。
> ⇒ 「四段链」标**单源**，三段（config/get/validate）才是双源。

| # | 请求 | 关键入参 | 关键出参 |
| --- | --- | --- | --- |
| 1 | `GET {vid}`（vid 即业务唯一标识） | — | `api`（**下面三段请求的域名**） |
| 2 | `config` | `vi`=vid、`t`（`embed`/`popup`/`invisible`）、`s`/`v`（写死）、`z`=`0 - new Date().getTimezoneOffset()/60`、`u`=`localStorage.vaptchanu`（**首次为空**）、`callback` | **`knock`**（下一段要用）、版本信息 |
| 3 | `get`（取验证码） | `vi`、`k`=上一步 `knock`、`origin_url`、`rm`（写死）、`en` | 图片 URL、`r` / `ha` / `hb`、`img_order` |
| 4 | `validate` | 与 `get` 同构，**`en` 换成含轨迹的版本** | **`token`**（最终目标） |

`u` 的来源是 `localStorage['vaptchanu']` ⇒ **清缓存后为空的路径必须能跑**（这是最容易被本地环境坑到的一步）。

### 3.2 `en` 的构成（字段级强度）

`en = encryFunc(SelectFrom(3, 15), <加和值>)`，其中 `SelectFrom(3, 15)` 是 **3~15 的随机整数**。

> ⚠️ **两个参数的先后顺序，来源表述为「A 和 B 经过 encryFunc 生成」，未明确谁是第一个入参** ⇒
> **单源未定**，落地前用固定入参在浏览器里对一次。

加和值由 11 项拼成（`_0x` 名随版本变，**按下标/函数识别，不要按名字匹配**）：

| # | 项 | 构造 | 强度 |
| --- | --- | --- | --- |
| 1 | canvas 指纹 | `GenerateFP()`：canvas 画特定字符 → base64 → 取 **CRC32** | ★双源 |
| 2 | 环境哈希 | 异步 `GenerateFP([], true)`：把一份**浏览器环境对象**做哈希，`true` 返回全长、`false` 截前 8 位。**该哈希是 murmurhash3_x64_128** | 机制★双源 / **算法识别单源** |
| 3 | `knock` 尾 5 位指纹 | `GenerateFP(knock.substr(-5, 5))` | 单源 |
| 4 | 同上（异步版） | 异步 `GenerateFP(knock.substr(-5, 5))` | 单源 |
| 5 | 盐化 md5 | `md5(项3 + 项4 + "adszzSECRETB").slice(0, 5)` | 单源 |
| 6 | `ha` | `ha === "" ? "0123456789qwe" : ha + GenerateFP(ha)` | 单源 |
| 7 | 常量 | `"0123456789qwe"` | 单源 |
| 8 | `vaptchanu` | `localStorage.vaptchanu.split(",")[0]`，空则 `"0123456789qwertyuiopasdf"` | ★双源（默认串单源） |
| 9 | `vaptchaut` | `localStorage.vaptchaut`，空则 `"0123456789qwertyuiopasdf87654321"` | 单源 |
| 10 | UA/host md5 | `md5(uaDelExtra(navigator.userAgent) + location.host + secretC.substr(0, 10)).slice(0, 5)` | 单源 |
| 11 | `globalMd5` | `md5(splicingObj(config 响应))` 取前 5 位 | 机制★双源 / `slice(0,5)` 与细则单源 |

- **`splicingObj` 的拼接口径：机制 ★双源 / 具体规则 单源 + 待复核**。
  两篇都独立描述"`globalMd5 = md5(排序拼接 config 响应)` 取前 5 位"（机制双源）；
  但**「按 key 排序、字符串/数字原样、布尔转 `"true"/"false"`、数组 `join(",")`、其它对象转 `"[object Object]"`」
  这套细则只出现在 1888845**，而且**是作者用 Python 复刻（`sort_dict_by_key` + `splicing_obj`）来对齐的**，
  不是逐行读站点 JS 得到的 ⇒ 标 `单源 + 待复核`。
  2051922 侧的 JS 函数名是 `splicingObj`（1888845 侧只有 Python 复刻名 `splicing_obj`）。
  **顺序错了 md5 就全错**，所以这条落地前必须用浏览器原函数对一次。
- **`secretC` 是一个 10 位数字常量 ★双源**（一份口径给全值 `8549731620`，另一份只用到 `substr(0,10)`）。
  **它不是密钥**：一份用于图片顺序的整数运算，一份进 UA 的 md5 盐。
- **`validate` 阶段与 `get` 阶段的差异**：**新增 `dt`/`ch`/`cw`/`v` 四个量是 1888845 单源**；
  **「`globalMd5` 的拼接结尾要多拼一个固定值」是 2051922 单源**。两条合起来才是完整差异表，
  ⇒ 逐条标注、不要合并成"双源"。
  `dt`（耗时，不足 4 位补 0）/ `ch`（canvas 高）/ `cw`（canvas 宽）/ `v`（加密后轨迹）。
- **`hashComponents` 不认识的哈希就是 murmurhash3_x64_128**：一份来源（2024-02）明确写「我没见过这种加密」，
  另一份（2025-08）给出完整 Python 实现并点名 murmurhash。
  ⇒ **"这里有一个环境哈希"是双源；"它是 murmurhash3_x64_128"只有 2051922 一篇支持（算法识别单源）**。
  这类"一家认不出、另一家认得出"的搭配是双源里价值最高的一种：**单篇永远拿不到算法识别**。
  需要复刻时用 `scripts/rotation_and_gesture_calc.py murmur3`。

### 3.3 图片还原（**几何** ★双源 / 公式与顺序语义逐条标注）

> **逐字段强度**（这一节是"整节贴 `★双源` 会骗人"的典型）：
> 源图几何 **`400×230`、5 列×2 行、每片 `80×115` = ★双源**；
> **`order = Decrypt(img_order, N)` 的减法+补零公式 = 单源（2051922）**；
> **顺序值语义（`< 5` 上排 / `≥ 5` 下排）= 双源**；
> **`N` 的四项归属 = 两篇口径不完全一致（见下）**；
> **画布尺寸 = 各自单源且数值不同**。

- **源图 400 × 230**，切成 **5 列 × 2 行 = 10 片**，每片 **80 × 115**。
- **还原顺序来自一个整数减法**：`order = Decrypt(img_order, N)`，其中
  `Decrypt` 不是密码学解密，而是 **`str(int(img_order) - N)`，不足 10 位左侧补 `'0'`**
  （1888845 只把它当"某个 `Decrypt` 方法"调用、没给公式；公式出自 2051922）。
- `N = hex2int(canvas指纹(ha)) + hex2int(环境哈希(hb)) + secretC + Worker 计算值`
  —— 四项里 **`ha`/`hb` 的归属两篇口径不完全一致**（一篇分别用 `ha` 与 `hb`；
  另一篇说两项都与 `ha` 有关、`hb` 未出现）⇒ **按 `ha`/`hb` 各占一项实现，实际以抓包对齐**；
  **缺失项直接记 0**。
- **顺序值的语义 ★双源**：`order[i]` 是"第 `i` 个源片该贴到哪个槽位"，
  **`< 5` 贴到上排、`≥ 5` 贴到下排（槽位 = 值 − 5）**。
  ⚠️ 这与 `restore_slices.py` 的 `source-to-target` 同型；**不要**用顶象的 `target-to-source`。
- **画布尺寸是渲染值，不是协议常量**：一份来源按 **400×230** 原尺寸还原，
  另一份按 **290×167** 且对每片做缩放（源片 80×115 → 画布片 58×83）——**两个数值各自只有一篇支持**。
  ⇒ **顺序与源几何是协议；画布尺寸现场量**。批量还原建议按**源尺寸**做（不引入缩放误差），
  需要比对时再统一缩放到渲染尺寸。

### 3.4 轨迹（★逐字段强度：这一节**基本是单源**）

> **逐字段强度**（本批自查时改掉的一处整节误标）：
> **`+30 px` 补偿、`< 5` 抽稀阈值、"轨迹 = 鼠标位置 − 绘制起点" = 单源（1888845）**；
> **"轨迹加密前还要过一套清洗算法"、点列来源（打码平台/自训模型）= 单源（2051922）**。
> 两篇**没有**在同一字段上互证 ⇒ 本节整体标 `单源`，两篇各自贡献的条目已分开写。

- **坐标补偿**：canvas 逻辑高 **230**，但事件区比它**多出 30 px**（实际 260）
  ⇒ 取到的鼠标点要 **+30**，否则整条轨迹整体上移，现象是"画得挺像但一直不过"。
- **抽稀阈值**：**轨迹点 `x` 或 `y` 的间隔小于 5 时不会入列**。
  自己造轨迹时必须按同样阈值抽稀，否则点数比真实多、节奏也不对。
- **轨迹 = "鼠标位置 − 绘制起点"**（1888845）；**加密前还要过一套清洗算法**（2051922，
  清洗细节来源未展开 —— **落地前必须在加密函数入口把清洗前后的点列都抓下来对比**）。
- 起手式：`dt` 用 4 位补零；`ch`/`cw` 是 canvas 高/宽；`v` 是加密后的轨迹。

### 3.5 `validate` 返回码（★单源，但可直接当排错表用）

| 码 | 含义 | 码 | 含义 |
| --- | --- | --- | --- |
| `0101` | `AccessDenied` | `0106` | `RefreshTanto` |
| `0102` | `RefreshAgain` | `0107` | `DrawTanto` |
| `0103` | **`Success`** | `0108` | `Attack` |
| `0104` | `Fail` | `0109` | `ChannellError` / `challengeExpire` |

"域名挂了"与"challenge 过期"——后者重新走 `config` 即可。

## 4. 两族共性（可直接迁移）

1. **非滑块题型的"距离"通常不是距离**：旋转是**角度占比**，手势是**轨迹点列**。
   换算一律先写成 `angle / 360` 这种**无量纲比**，再乘平台自己给的量程，
   避免把某一家的滑轨像素当全局常量。
2. **canvas 常常比事件区小**（VAPTCHA 差 30 px）。凡"事件坐标 ≈ 图片坐标"的假设都要先验证。
3. **"取配置"接口不是可选项**：百度要给 `tk`/`backstr`，VAPTCHA 要给 `knock`。
   想跳过它就得把它的返回值写死——**一次性短时效**，写死只能用于单次调试。
4. **收尾接口是独立的一次校验**，自带时效与行为判断（百度要 sleep、VAPTCHA 有 `RefreshTooFast`）
   ⇒ **"第一次校验通过"不等于"验证通过"**。
5. **环境指纹可以离线伪造，但同一次会话内的盐必须一致**
   （VAPTCHA 的 `hashComponents`：只要同一请求内相同参数算出相同值，就不用真跑 canvas）。

## 5. 反例黑名单（不要做的事）

- ❌ **不要把 VAPTCHA 当滑块**：它没有"距离"这个提交量，轨迹才是主字段。
- ❌ **不要用完整 base62 造 VAPTCHA 的 `vaptchanu`**：默认值是一串**数了才写对**的固定串
  （`0123456789qwertyuiopasdf87654321` 这类），抄错一位整条 `en` 全错。
- ❌ **不要按"源码顺序"展开旋转/手势的提交字段**：VAPTCHA 的 `en` 是**加和**，
  项的顺序不影响值；但 `splicingObj` 的**排序**影响 md5 ⇒ 两种"顺序"别搞混。
- ❌ **不要在百度 v2 上套用 v1 的 `ac_c` 口径**：v2 滑块分支的分母是 `290`，旋转分支是 `238`。
- ❌ **不要把"识别失败"当协议失败**：小红书来源的做法是**失败就重新取图重试**，
  成功率 100% 靠的是循环，不是单次识别率。
- ❌ **不要把鬼影/双旋转当成"图片加载坏了"**：那是守方设计，先确认题型再谈还原。
