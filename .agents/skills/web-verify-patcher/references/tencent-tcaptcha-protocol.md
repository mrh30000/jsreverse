| 形态 | 判据 | JS 文件 | 参数形态 |

## 2. 形态 A 的接口链

```
① cap_union_prehandle            → 返回 sess（服务器给，客户端无法自造）
② （取图 / 用户交互）
③ cap_union_new_verify           → 提交 5 个参数，返回 ticket/randstr
④ （站点自己的业务接口，带 ticket 登录）
```

**参数来源表**（两篇独立文章对同一目标给出的结论逐项一致 → 已互证）：

| 参数 | 来源 | 可不可以自造 |
| --- | --- | --- |
| `ua` | `base64(User-Agent)` —— **就是请求头的 UA，base64 解出来逐字节相同** | ✅ 直接算 |
| `sess` | ① 的响应字段 | ❌ 必须取自 ① |
| `collect` | `window.TDC.getData()`（`tdc.js`，JSVMP） | ⚠️ 需还原 VM 或补环境 |
| `eks` | `window.TDC.getInfo().info` —— **本质是 `window` 上的一个随机字符串**（源码里直接写死返回） | ⚠️ 每次变，但要拿到它必须走 VM |
| `vData` | **`XMLHttpRequest.prototype.send` 被重写**（`vm-slide.js`），提交时才注入 | ⚠️ 同 `collect`，另一个 VM |

**`vData` 的定位技巧（重要）**：在 `send` 处下断点时**还没有 `vData`**，实际发出去却有了
⇒ 说明 `XMLHttpRequest.prototype` 被改写过。判据：检查 `XMLHttpRequest.prototype.send` 是否还带原生
`[native code]`。同类的"提交前才注入"参数都该用这一招找。

## 3. `collect` 的结构与加密

### 3.1 明文结构

```json
{"cd":[24,"about:blank?rand=...","0-0-0-24-*-*-|-*",[],176688296,[],0,0,"",[],0,0,0,1,9,
       [],0,0,1634221284,0,"Mozilla/5.0 ...","top",259121870,1634221284,0,"?rand=...",0,"",
       "other",1634221284,"UTF-8",[1024,768], ...]}
```

- 数组里混了 **window/document 的面宽高、UA、随机数、时间戳、`"top"`、`"UTF-8"`、`[1024,768]`** 等。
- **⚠️ 数组内的数据顺序不固定：一个滑块对应一种顺序。**
  ⇒ **不要假设固定下标**；想伪造明文必须先解出"本次的顺序"（这也正是"扣代码"容易失效的原因）。

### 3.2 生成链路（38 步拼接）

1. VM 的 `mInit()` 先跑一遍**环境检测模块数组**（每个模块一个检测点，导出了 `on` 就在初始化时执行）；
   其中包含 `setErrorStack` 之类的**堆栈环境检测**。
2. `mGetData()` 依次调用 **37 个 `get()` 函数**，把返回值**按顺序拼接**。
   每个 `get()` 返回一个环境相关值：可能是经过一番运算的数字（环境检测的"得分"），
   也可能是**纯固定值**（没有任何运算）。
3. 拼接结果用填充函数补齐，再进加密函数（`>> 5` 被改为 `>>> 5` 的**魔改 TEA**）。
4. **分段加密**：会对同一明文调多次；**以 `"],"` 结尾的那一段才是最后一段**
   （判据：观察待加密明文尾部，别按"调用次数"判断）。

### 3.3 TEA 细节

| 项 | 值 |
| --- | --- |
| 算法 | TEA，**`>>` 被魔改为 `>>>`**（无符号右移） |
| 密钥长度 | 16 字节（4 个 int32） |
| 密钥有效期 | **几天到十几天**（作者发文时 key 为 `QiPXNgNXhnjVfFhT`） |
| 密钥获取 | 可 AST 动态还原，也可手工取一次用一段时间 |

**TEA 是对称的**：拿到 key 就能**解密网页生成的 `collect`**。
⇒ **第一步不要急着伪造，先拿 key 解密一条真实的 `collect`**，把明文结构看清楚。
这一步的性价比远高于直接扣代码。

### 3.4 环境检测项的处理原则

模块返回的"检测得分"（例：第一个 `get()` 返回 `10`）**不需要理解中间怎么算的**。
原则：**只要知道"检测通过时的正确返回值是多少"，然后固定这个值即可。**
逐项逆运算环境检测函数是纯粹的浪费——除非该项的返回值随本次请求变化。

## 4. `vData` 的结构与加密

`vm-slide.js` 生成，代码结构与 `collect` 的 VM 一致（同为 `__TENCENT_CHAOS_*` 系）。

### 4.1 明文：8 个键

- 8 个键里**除 `key` 外全部是固定值**。
- `key` 的算法：把 `tlg` 里的**每一个值当作下标**，去 `sess` 上取值。
  `collect` 常上千位 ⇒ `tlg` 是四位数 ⇒ **`key` 是 4 位**。

### 4.2 加密三步

| 步骤 | 说明 |
| --- | --- |
| ① 填充 | 补到 **16 的倍数** |
| ② 打乱 | **打乱字符串顺序** |
| ③ TEA | 魔改 TEA，**密钥固定**（作者实测：`34e2c8f07b5169ad`） |
| ④ 编码 | **base64，但编码表被改过**，其余一致 |

**⚠️ ④ 是最容易被忽略的一步**：直接用标准 base64 解码会得到"看起来像但不对"的结果。
判据：标准 base64 解出来的字节数对、但 TEA 解密后是乱码 ⇒ 优先怀疑**自定义 base64 码表**。

### 4.3 跨文章互证：`vData` 三段式一致

`1729065`（反汇编系列第三章）与 `1521480`（某鹅滑块笔记）对 `vData` 的描述**一致**：
填充到 16 的倍数 → 打乱 → 魔改 TEA。两条独立来源同结论 ⇒ 可作稳定判据使用。

## 5. 纯算（不补环境）路线的实操顺序

补环境更快更省事（结论：腾讯滑块"有什么补什么，不算难"），纯算只在需要**长期稳定**时才值得做。

纯算的实操顺序（插桩优先，不要先读 VM 源码）：

1. **找值**：在出值前发现 `encodeURIComponent()` 调用（特殊符号被替换）
   ⇒ **分析 `encodeURIComponent` 之前的字符串**，不要分析最终值。
2. **拼结构**：搜到多处"某个字符串 `btoa()` 之后拼到一起"⇒ 这些值是**同一套算法**，
   只挑一处分析即可。
3. **打运算符插桩**：把运算符也打上日志（7 万行级别，**建议 push 到数组最后一次性 dump**，
   直接 `console.log` 会让控制台卡到不可用）。
4. **切片粒度**：字符串**每 4 个字符切一次**，`charCodeAt(0/1/2/3)` 得到 4 个数，
   再经 4 次数值运算得到一个中间值。这是这类编码器的通用骨架。
5. **落点**：最终由 `[235, 7, 11, 255]` 这类数组经 `fromCharCode()` 拼出目标字符串。

**判据**：`charCodeAt(<0..3>)` + `fromCharCode()` + `btoa()` 三者同时出现，
说明这是一段"自定义二进制→文本"的编码器，与加密无关，可以独立还原。

## 6. 五请求链形态（站点适配层）

有的站点不是"三请求"而是**五请求**：`collectData` 载荷生成正确也仍可能失败，
因为登录还依赖另外两个接口。

| 请求 | 产出 | 易错点 |
| --- | --- | --- |
| ①取 challenge / verifyId | `challenge`、`verifyId` | **请求头要带 `csrf-token`**，该值取自响应 Cookie；不带则请求失败 |
| ②取静态资源 | `bgUrl`、`sliceUrl`、`staticServer` 域名、**`shuffle`（切割列表）**、**`publicKey`（加密轨迹用）** | `shuffle` 是底图还原的顺序来源；`publicKey` 是轨迹加密的 key |
| ③`collectData` | `result`（= 后续登录要的 `secure_key`） | 载荷由 `publicKey` 加密轨迹后生成；**轨迹是模拟的，不保证 100% 过** |
| ④`secret-key` | `iv`、`secret_key`、`secret_key_id` | **同样要更新 `csrf-token`** |
| ⑤`login` | 登录结果 | 需要 ③ 的 `result`（作 `secure_key`）+ ④ 的 `secret_key_id`；`username`/`password` 走 AES（用 ④ 的 `iv`/`key`） |

两个通用结论：

- **`csrf-token` 型请求头要"发一次 → 从响应 Cookie 取值 → 再发"**。凡是"不带某头就失败、
  但该头又要从响应拿"的情况都走这个两步法。
- **底图有两个缺口时用中心点计算**（不是边缘），并加一条"红线校验"防误切。
  详见 `tile-scramble-and-coordinate-mapping.md`。

## 7. 排错速查

| 现象 | 优先怀疑 | 处理 |
| --- | --- | --- |
| `collect` 解密后结构对但提交失败 | **数组顺序本次不同** | 不要固定下标；顺序要从本次数据里解 |
| `vData` TEA 解密后是乱码 | **自定义 base64 码表**（§4.2 ④） | 按站点码表改解码表 |
| `collect` 解密失败 | TEA key 已轮换 | 重新取 key（有效期几天到十几天） |
| `send` 断点处没有目标参数 | 原型被重写 | 检查 `XMLHttpRequest.prototype.send` 是否原生 |
| `ua` 对不上 | 忘了 base64 | `ua = base64(请求头 UA)`，逐字节比 |
| 载荷都对、登录仍失败 | 缺第 4/5 个请求 | 走 §6 五请求链核对 |
| 视觉偏移对但验证失败 | 轨迹/环境评分 | 图像线与参数线分开排查（见 `verification-workflow.md`） |
| 缺口坐标差一个固定值 | 滑块初始位置偏移 | 例：实测某站点 `距离 = 识别缺口 x - 60`；**偏移量按站点实测，不要跨站套用** |

## 8. 反例黑名单

- **不要把"解出乱码"当成算法错。** 先确认是不是自定义 base64 码表（§4.2 ④）。
- **不要按固定下标伪造 `collect` 明文。** 数组顺序一个滑块一个样。
- **不要逐项逆运算环境检测函数。** 只取"通过时的正确返回值"并固定（§3.4）。
- **不要分析 `encodeURIComponent` 之后的值。** 要分析它之前（§5.1）。
- **不要把 `eks` 当成"随机数所以随便造"。** 它每次变，但必须经 VM 拿到（§2 表）。
- **不要把 `ua` 当成某种加密结果。** 它就是 UA 的 base64。
- **不要在一个 VM 里同时做"读懂"和"跑通"。** 跑通走补环境，读懂走反编译器（见
  `../../ast-deobfuscation/references/jsvmp-bytecode-and-decompiler.md` §0 判据）。
- **不要跨站点套用密钥与偏移。** TEA key、`ac_c` 偏移、切片几何都是站点专属且会轮换。
