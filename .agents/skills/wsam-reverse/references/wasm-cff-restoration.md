## 1. 判据：什么时候该走反 CFF

**先判「是不是 CFF」，不要凭代码长就上**。实测判据（任一条命中即基本确定）：

| 判据 | 现场表现 |
| --- | --- |
| **F5 伪代码里一个函数上千行，且全是嵌套 `while` + `if` + 一个可疑状态变量** | `func54_vodplay` 实测 **约 1925 行**伪代码 |
| **状态变量被反复赋成互不相同的「魔法常量」** | 伪代码里成片出现 `i32_store(instance->w2c_env_memory, state_var_addr_v77, 0xE9102B37)` |
| **调度块（dispatcher）有自环** | CFG 上存在「回到自身」的块 ⇒ 平坦化的分发器 |
| **大量 `call i32_store` / `call i32_load` 出现在块尾** | 状态变量在 **wasm 平坦内存里**（不是寄存器） |

**CFF 常与 BCF 同时出现**。判对「是 CFF」只是第一步，**最终目标是恢复出可读的控制流**，
不是「把混淆完全剥掉」。

> **层判错很贵（沿用本库既有教训）**：wasm 里出现大量 `i32.const` / `local.get` / `i32.xor` 循环
> **不等于 CFF**——那可能只是 **VMP（自建字节码解释器）**。VMP 的反 CFF 路线完全不同
> （见 §11）。**先分清 CFF（控制流被打散）还是 VMP（指令集被替换）**，再选路线。

## 2. 为什么必须绕道 `wasm2c → .o`

**这是本文最重要的一条「为什么有效」的解释，也是整条路线的立论点。**

反 CFF 的标准打法是「**建块映射 → 改控制流**」，而这两件事分别需要：

- **建块映射** → 一个能跑**符号执行**（angr）的 IR；
- **改控制流** → 一个能**打补丁**（keystone / IDA 微码）的目标文件格式。

**wasm 栈机本身两个都不满足**：没有成熟的符号执行引擎（原文：「据说 Angr 可直接模拟执行 wasm，
但不如模拟执行 ELF 成熟，未求证，未实践」），也没有成熟的二进制补丁工具链。

**wasm2c 恰好把这两个前提一次补齐**：

```
wasm（栈机）  --wasm2c-->  C（寄存器机语义，可控变量/函数）  --gcc -c-->  .o（宿主目标文件）
                                                                        ├─ angr：符号执行 ✓
                                                                        ├─ IDA：CFG / 交叉引用 ✓
                                                                        └─ keystone：打补丁 ✓
```

**代价**：从 `.c` 到 `.o` 再反编译**不产生新信息，可能损失信息**。绕这一圈唯一目的就是**换工具能力**
（IDA 的符号改名 / 交叉引用 / Findcrypt / Signsrch）。实测：正是靠这些插件，作者注意到函数里是 **TEA**。

> **可平移的判断**：任何「在 A 平台做不了符号执行 / 打补丁」的问题，先问一句
> **「有没有一个把它翻译到 B 平台、且 B 平台工具齐全」的转换器**。

## 3. 四步法总纲

原文给出的通用流程（**顺序不要换**）：

```
a. 找出有效块（真实块 real_block）
b. 找出状态变量 state_var
c. 建立「有效块 → 有效块」的映射关系
d. 修改控制流（把有效块串成真正的控制流）
```

四步里 **a 是唯一的“地基”**：`c` 依赖 `a`，`d` 依赖 `c`。
原文明确警告：**「若反 CFF 结果不佳，优先检查 `get_real_block`」**——
漏报有效块（丢真实代码）或误报有效块（引入假节点），都会一路传导到 `d` 的产物上。

## 4. 找有效块（真实块）

原文的 PoC **只针对单个函数**（`func54_vodplay`），是「针对性经验算法」，
**换函数必须改 `get_real_block`**——不要期待它是一个通用工具。

### 4.1 先划出 dispatcher（分发器）并排除

```python
def get_dispatchers(addr):
    # BFS；若某个块在「当前路径」里再次出现 ⇒ 该块有自环 ⇒ 判定为 dispatcher
    # 返回排序后的 dispatcher 起始地址列表
```

得到 dispatcher 后，**先把它们从候选里排除**，再在剩下的块里挑有效块。

### 4.2 两类有效块模板（块尾模式匹配）

| 模板 | 块尾形状 | 语义 |
| --- | --- | --- |
| **`is_block_0`** | `call i32_store` + `jmp` | 有效块干完活，**设置新的状态常量**，然后跳回 dispatcher |
| **`is_block_1`** | `call i32_load` / `i64_load` … `cmp` … `jz` | 对应 **`cmov` / `csel`** 情形 |

实现要点（IDAPython）：

- `is_block_0`：块尾最后一条是 `NN_jmp`；倒数第二条是 `call`，且**解引用到的函数名**（去 `_.` 前缀、
  去 `@` 后缀后）**等于 `i32_store`**。再加块大小过滤（实测：**`0x52` 排除、`< 0x31` 排除**）滤掉假有效块。
- `is_block_1`：块尾字节是 `\x74\x05`（`je`），前一指令是 `NN_cmp` 且 `op1` 是立即数 `0`、
  `op0` 是 `[rbp-0x3c]` 一类偏移；再往前找**最近的 `call`**，函数名 `startswith(("i32_load","i64_load"))`。
- 原文实测：`h5_worker_pub.o` 里**没有** `cmov`/`csel` 指令——它们被拆成了 `is_block_1` 的形式。
  **所以模板是「编译器产物形状」，不是「源码形状」**，换编译器/换优化级别要重新校准。

### 4.3 「有效块」的取舍原则：宁滥勿缺

原文的取向**明确偏保守**：

> 「我将**绝大多数不对应 while、if 的块**算作有效块，其中一些可能只设置了状态变量就跳转，
> 并未真正干活，但仍视之为有效块。」

理由：**漏报有效块会丢有效代码**（不可逆），而**误报只是多留几块**（可读性略差）。
这一点与 JS 侧 CFF 还原的「先宽松后收敛」是同一取向。

### 4.4 别忘了返回块

`ret_block`（含 `retn` 的块）也要手工加进 `real_block_list`——它不是由模板匹配出来的。

## 5. 找状态变量 `state_var`

**本例的状态变量不是寄存器，而是 wasm 平坦内存里的一个地址**（这是 wasm CFF 与 x86 CFF 的关键差异）。

- 定位方式：F5 伪代码里 `grep` 形如
  `i32_store(instance->w2c_env_memory, state_var_addr_v77, 0xE9102B37)` 的成片代码，
  `state_var_addr_v77` 就是它。
- **它的用途不是帮你建映射**（原文 PoC 没用到它），而是**反 CFF 之后做清理**：
  这些「设置状态变量」的赋值在还原后**完全没有意义**，可以批量删除：

  ```bash
  grep -v "instance->w2c_env_memory, state_var_addr_v77" restored.c > cleaned.c
  ```

> 换句话说：**第 2 步是「为第 8 步的清理做准备」**。不看这一步，反 CFF 的产物会残留一大片噪音。

## 6. 建立「有效块 → 有效块」映射（angr 符号执行）

对每个有效块，用 angr 从它的入口符号执行，**跑到「下一个有效块」为止**，把那条边记进 `flow`。

### 6.1 关键设计：ihelp 函数 vs 非 ihelp 函数

原文把 `call` 分成两类，**两类处置完全不同**：

| 类别 | 函数名 | 作用 | 处置 |
| --- | --- | --- | --- |
| **ihelp** | `i32_load`、`i32_load8_s`、`i32_load8_u`、`i32_store`、`i32_store8`、`i64_load`、`i64_store` | 访问 **wasm 平坦内存**（**状态变量就在这儿**） | **必须用 `angr.SimProcedure` 重载**，自己模拟它对 memory 的读写 |
| **非 ihelp** | 其它全部（真正的功能函数，如「TS PES NALU 解密」） | 真正业务逻辑 | **全部 hook 成空函数 `retn_procedure`**，抑制路径爆炸 |

### 6.2 🔴 最反直觉的一条：**不要设 `angr.options.CALLLESS`**

`CALLLESS` 会把**所有** call 变成 NOP——**包括 ihelp**。
而 ihelp 一旦被 NOP，状态变量就不再被写进内存，**符号执行根本追不到下一次分发**，
`flow`（有效块映射）直接失效。

**原文原话**：「因为我精细化 hook，所以创建 `init_state` 时，未指定 `angr.options.CALLLESS`。
否则 ihelp 函数也被 NOP 化，将导致模拟执行时无法跟踪 CFF 状态变量。」

> 这是一条**「省事的开关恰好关掉了唯一有用的那一层」**的典型案例。
> 通用的检查动作：**任何「一键 NOP 掉全部 X」的选项，先问「X 里有没有我必须保留的子集」**。

### 6.3 分支（`jz` / `je`）的处置

遇到 `jz`/`je` 时，原文用 `block.vex.constant_jump_targets` 拆出 true/false 两个目标，
各自 `find_jz_succ()` 跑到下一个有效块，得到 `(succ_true, succ_false)`；
两个方向都必须能落到有效块，否则 `assert` 失败（说明有效块集不全，回到 §4）。

### 6.4 循环体（内部小循环）的剥离

块内可能含有**不属于 CFF 的正常小循环**。原文用 `find_cycle_ex(seq, min_occurrences=8)`
在内部路径序列上找**重复出现 ≥ 8 次**的最短循环，命中即认定为正常循环，用 `remove_cycle_ex()` 剪掉后再判后继。

**判据来源**：CFF 的 dispatcher 也会形成重复，但**重复次数与「连续相同片段」的形状不同**；
用「出现次数下界」把「普通循环」和「分发回跳」区分开。

## 7. 汇编级修改控制流

把 `real_block` 按 `flow` 串起来，原文演示的是**汇编级 patch**（keystone 改指令字节）。

### 7.1 三个已知代价（都要接受，或换方案）

| 代价 | 现象 | 原文实测 |
| --- | --- | --- |
| **没有足够的「安全空间」放补丁** | 想把一条 `mov` 改成 `jmp`，但 `jmp` 比 `mov` 长/短，塞不下 | 实测在 `0xbe129` 处踩到：`mov` 被改成 `jmp` 后，**原来这个 `mov` 在给某地址变量赋值，后续还要用** ⇒ 该变量丢失。尽管如此「整体反 CFF 结果还可以，有助于理解函数逻辑」 |
| **x64 上只改指令字节流不够** | `IDA` 数据库里改完字节，F5 结果**可能完全不符合预期** | 必须再让脚本**完成对应的「c 操作」**（清理/重建指令），否则反编译视图不同步 |
| **微码级 patch 是另一条路** | 微码级 patch **天然解决「空间不够」**（不写机器码，改 IDA 的中间表示） | 但微码级 patch 有自己的劣势。原文结论：**「没有完美的 Patch 方案」** |

### 7.2 选型建议（从原文实测反推）

- **只想「读懂逻辑」** → 汇编级 patch 够用，即使丢了个别变量，整体控制流仍然可读。
- **要「能编译回去跑」** → 汇编级 patch 不够，得走微码级或「反 CFF 后手工重写」。

## 8. 收尾清理

反 CFF 后**必须清理**，否则产物仍然是「可读但脏」：

1. 删掉全部「设置 `state_var`」的赋值（§5 的 `grep -v`）。
2. 删掉只为设置状态变量而存在的空转块（§4.3 的误报块）。
3. 重新跑一遍 F5，确认控制流已是 `if/while` 形状。

原文给出的还原结果示例（`func54_vodplay` 清理后）已经可以看出完整业务语义：
**计数器 + 限流（`counter >= limit_val * 5120`）→ 上下文完整性校验与备份区恢复 → `malloc(p1+4000)` + `memset`
→ 调 `TEA` 族解密 → 成功后 `func58_TEA` + `memcpy` 回写、返回实际长度**。

## 9. AI 反 CFF 的定位

原文把「让 AI 静态反混淆」当作**补充手段**，并明确其定位：

- 把 `func54_vodplay` 丢给 AI，AI 能给出**结构合理**的还原结果（含 CFF + BCF，并识别出
  「防刷/限流」「防篡改与完整性校验」「核心解密」「结果回写」四段）；
- **但原文的态度是「未细究 AI 的反混淆结果，只是尝试一种可能」**——即
  **AI 的产出是「待验证的草稿」，不是结论**。

**正确用法**：AI 给结构 → 用 §3–§7 的机械流程（或至少用已知输入输出对拍）验证；
**不要**把 AI 的还原结果直接当算法定义写进交付件。

## 10. 排错：结果不对先查哪里

严格按这个顺序（**不要跳**）：

1. **`get_real_block` 是否正确** —— 有效块集漏了/多了（原文唯一的点名项）。
2. **`flow` 是否覆盖全部有效块** —— 每个块都应该有明确后继；`assert` 失败即说明 ① 没做全。
3. **`CALLLESS` 是否被误开** —— 开了就必然追不到状态变量（§6.2）。
4. **ihelp / 非 ihelp 分类是否搞反** —— 把业务函数当 ihelp 去模拟 ⇒ 路径爆炸；
   把 ihelp 当业务函数 hook 掉 ⇒ 状态变量不更新，`flow` 全空。
5. **patch 空间告警是否被忽略** —— 丢变量的补丁会**静默**产出错的伪代码（能反编译、不报错）。
6. **是否忘了 `ret_block`** —— 函数出口没进 `real_block_list`。
7. **状态变量取值是否被当成有效块了** —— 只设置状态就跳转的块属于「误报」，可留但会加噪。

> **第 5 条是本族最像本库既有教训的一条**：「补丁丢了变量 ⇒ 产物仍能反编译、不报错、但语义错」，
> 与 B3 的「AST pass 静默删掉 9000 个节点」、B8 的「`dcm` 末块走错分支」同属
> **「不报错但结果错」**。**必须有一条会失败的断言兜住它**（例如：patch 前后指令字节数/变量引用计数对比）。

## 11. 边界与替代路线

### 11.1 明确不做的事

| 不做 | 原因 |
| --- | --- |
| 提供通用 `get_real_block` | 原文 PoC 本身只针对单函数；模板随编译器/优化级别变，写成通用反而会**静默误判** |
| 在本技能内实现 angr / keystone 流程 | 依赖重、本机不可离线验证（见文首声明） |
| 用本技能脚本「自动反 CFF」 | 会给出**看起来完整的错结果**，比不提供更危险 |

### 11.2 **先分清 CFF vs VMP**（最容易选错的一步）

| 特征 | CFF | VMP |
| --- | --- | --- |
| 代码形状 | 大量 `while` + 状态变量常量；**指令集不变** | 一个**超长字节码数组** + 一个**分发器**（dispatcher）；指令集被替换 |
| 有效块识别 | 本题模板（块尾 `call i32_store` + `jmp`） | 模板不适用；**大多数函数都走进同一个分发器** |
| 反制路线 | 本文（符号执行建映射 + patch） | 提取解释器 → 反推 opcode 语义 → 生成 IR（JS 侧同类经验见 `../../ast-deobfuscation/references/jsvmp-ir-and-optimization.md`） |
| 判据来源 | `2107193` | `2103854` 实测：**「大部分函数都走到 f50 函数里面去了，f50 就是一个分发器」** ⇒ 作者直接放弃在 C/JS 转换产物上补环境 |

### 11.3 **VMP 场景下的正确退路（实测有效）**

`2103854` 的三次尝试给出了**量化的路线代价**：

| 尝试 | 做法 | 结果 | 结论 |
| --- | --- | --- | --- |
| ① `wasm2c` + 逐个补导入函数 | 转到 C，用 AI 补导入 | 能跑，但**缺浏览器环境 ⇒ 解密结果不对（花屏）**；因为是 VMP，**看不出环境从哪个函数进去** | ❌ 放弃 |
| ② `wasm2js` + 在 JS 里补环境 | 转成 JS 后补 | 同样花屏 | ❌ 放弃 |
| ③ **不动 wasm，直接扣原 JS + 补环境** | 用 CDP 把播放逻辑扣成 Node，环境（`location`、一个 xhr 拉 json）按浏览器逐项对齐 | **2 分钟视频只剩 2 个 NAL 解密失败**；长视频仍会花屏 | ✅ 部分成功，是 VMP 场景的**首选退路** |

**可执行的两条**：
1. **判据**：如果「大部分函数都汇进同一个函数」，**不要再在 C/JS 转换产物上补环境**，
   直接回原 JS 扣取 + 补环境。
2. **验收 oracle**：解密结果用 **`ffmpeg -v error -i out.mp4 -f null -`** 判是否成片；
   「NAL 解密失败数」比「画面能看」更可靠（B12 已确立「回写」是独立一层）。
